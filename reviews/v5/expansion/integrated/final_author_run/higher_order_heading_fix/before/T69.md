# T69: Dispatch, closures and type erasure

## Purpose and outcomes

Build interface evidence, closure environments, erased ownership and dynamic code lifetime from C17 data and functions. An application binary interface (ABI) joins separately built modules; it is distinct from the C type system and a security boundary. Small-buffer optimization (SBO) reuses T70 byte storage, while ordinary operations retain typed receivers.

## Entry check and remediation

Reconstruct operation-table and callback contracts from T19, checked arithmetic and ownership from T18/T21, and the exact dod.small_buffer invalidation/allocator contract. Diagnose a mismatched callback type, a stale borrowed environment and failed construction. Revisit X-T03-003, X-T03-005 and X-T70-002 when the argument relies only on successful execution.

## Study sequence and teaching

### T69.01 — Named interfaces, structural probes and semantic conformance

The receiver/table association binds a concrete object to operations that interpret its actual representation. A nominal interface registration records this association through a named constructor; it does not prove the implementation's semantic laws. An operation table can validate the presence of a function pointer but cannot infer that the pointer uses the same concrete representation as its object or satisfies the promised law.

Implement DSView/DSOps and ds_measure for a borrowed int implementation and a second concrete counted-byte implementation that measures logical length. Every successful callback publishes one int; the wrapper calls exactly once and preserves caller output on failure. Build a nominal typed constructor for each implementation and a C17 _Generic structural probe that accepts only explicitly listed receiver types. Supply three rejected translations: wrong callback signature, an unlisted receiver, and incompatible named wrapper types. A second implementation with the correct signature but an incorrect length result must compile and fail semantic tests.

A borrowed int7 measures7. A callback returning DS_FAILED after writing123 into its private output leaves caller output99 unchanged. A missing table rejects before invocation. The wrong-return-type callback fixture must fail strict C17 compilation.

Observable evidence: {ref}`X-T69-001` requires Enumerate int values-8..8 and counted spans0..16; instrument callback count and outputs. Compile every diagnostic fixture separately under GCC/Clang -std=c17 -Wpedantic -Werror and retain the intended diagnostic. Wrong semantic callbacks must compile and be rejected by behavior/invariant checks, not by a cast or a runtime type-name string. Never execute a deliberately incompatible function-pointer call.

### T69.02 — Fat views, embedded tables and unsafe qualifier substitution

An erased interface view stores a receiver pointer and compatible operations without exposing the concrete receiver type. An embedded operation table pointer instead places the dispatch metadata inside the owner object, so each external view need not carry a separate table pointer. Neither representation owns the receiver or extends its lifetime. A pair of pointers is an implementation choice, not a universal language ABI. Indirection changes where metadata lives, and apparently harmless qualifier widening can make a const object writable.

Implement ds_embedded for DSBox and compare its in-object table with DSView external table storage under the same measure contract. Construct arrays of1000 synthetic objects and1000 borrowed views, account for owner bytes versus view bytes and measure direct/embedded/fat calls with an equal workload. Compile the qualifier_reject.c fixture, then derive the counterfactual write that would become possible if T** could implicitly convert to const T**; analyze that write without executing it.

DSBox containing int17 measures17 through its embedded table. If its table returns DS_FAILED, output99 remains99. Assigning char** to const char** produces the intended diagnostic. A successful cast compilation is not permission to perform the counterfactual const write.

Observable evidence: {ref}`X-T69-002` requires Compare outputs and failure side effects for every int-16..16 and both valid/failing tables. Measure sizeof/_Alignof/offsetof rather than assuming sizes. Analyze all three pointer levels in the qualifier fixture and keep diagnostics apart from runtime evidence. Rebuild both representations under GCC/Clang with and without link-time optimization; a compiler eliminating the indirect call is an observation for that build.

### T69.03 — Dictionary passing, specialization and effect-sensitive folds

### T69.04 — Capture ownership and shared, mutable, consuming invocation

The capture environment stores the state needed by a closure, including any borrowed references whose referents must remain live. Closure invocation capability determines whether a call observes that state, mutates it or consumes the callable; copying a captured pointer does not copy its referent. Capture form and call capability answer different questions. A local runtime flag cannot make all aliases obey linear consumption, and error paths need a defined consumption policy.

Implement DSClosure init/call with shared, mutable and once modes. The concrete body performs checked int addition of capture and argument. Shared keeps capture, mutable stores a successful result, and once consumes on the first admitted attempt even if arithmetic fails. Add a typed closure holding a borrowed array slice and a once closure owning a synthetic resource with a no-fail release callback. Define capture lifetime, allowed invocation and failure cleanup explicitly for each.

Capture3 shared calls with2 return5 repeatedly without capture mutation. Mutable calls return5 then7. Once capture1 with2 returns3 and later DS_EMPTY. Once INT_MAX with1 returns DS_RANGE with unchanged output and becomes inactive.

Observable evidence: {ref}`X-T69-004` requires Enumerate captures/arguments-4..4 for all modes, retain mode/state/output after every call, then test int extrema. In the resource variant inject rejection before and after invocation admission and count release exactly once. Do not dereference ended borrowed storage; use an instrumented lifetime token to demonstrate rejection and separately analyze the raw-pointer counterexample.

### T69.05 — Owning erased calls over the byte-only small buffer

An invocation thunk has the actual public callback signature and decodes the agreed capture representation before calling the concrete operation. Casting an incompatible function pointer cannot perform that adaptation. The erased callable owner holds the capture bytes and its cleanup obligation; it may still contain references borrowed from another owner. The owning wrapper adds obligations beyond a function/context pair: capture representation, external cleanup, movement and borrowed result lifetime. Reusing T70 preserves a single storage contract.

Implement DSErased assign/call/move/drop by importing DSmall, not copying its algorithm. Captures are explicitly encoded counted bytes; the supplied thunk accepts one byte and argument[-100,100]. Add an int32 capture codec with a portable admitted signed conversion and a capture larger than16 bytes to exercise spill. Resource ownership transfers only after assign succeeds. A separate borrowing callable view must document owner/table lifetime and immediate versus retained use.

Capture byte7 called with3 produces10. Move leaves the source inactive/empty and destination active. Dropping source then destination twice invokes the resource destructor exactly once. Allocation failure during a large capture assignment leaves the destination empty and ownership with the caller.

Observable evidence: {ref}`X-T69-005` requires Drive assign/call/move/drop traces through a logical ownership model and an allocator request/release log. Compile with sanitizers, but diagnose ownership-state errors before invoking an inactive or mismatched thunk. Count bytes copied, allocations, owner size, dispatch and destructors under the13-dimension contract.

### T69.06 — Ordered multiple dispatch and cache invalidation epochs

An ordered dispatch key preserves both operand positions: a method for `(A, B)` need not be the method for `(B, A)`. The dispatch cache epoch binds a cached selection or cached absence to a particular method-table version. Caching a method is caching a semantic decision. Ignoring registration generation or sorting an ordered pair changes behavior even when the called functions are individually correct.

Implement a3x3 ordered binary-method table and one-entry cache. A cache is bound to one DSMethods object; its key includes ordered type pair and non-wrapping table epoch. Epoch1 is empty; each admitted registration/removal increments it and epoch3 forbids further changes. Add a two-entry cache and compare direct table lookup. Specify a separate subtype fallback graph and reject ambiguous equally specific matches instead of silently choosing registration order.

Register subtraction for(0,1): arguments10,2 produce8; reversed types(1,0) are unsupported. Replace the same entry with addition: the old cached result must be invalidated and produce12. A third registration rejects at the finite epoch limit.

Observable evidence: {ref}`X-T69-006` requires Use an uncached dictionary keyed by ordered pair and version as the independent oracle. Replay every sequence of up to4 registrations/calls over types0–2 and methods add/subtract/missing, respecting finite epochs. Record cache hits/misses separately from correctness. Add a new table identity while retaining cache storage to demonstrate why ownership binding matters.

### T69.09 — Authority attenuation, revocation and the limits of C tokens

The attacker perspective reveals whether a token is actually authoritative or simply trusted data. A subset check is meaningful only under a threat model that prevents the caller from changing the checked authority metadata.

Implement the original DSAuthority/DSCapability model over a synthetic int counter. Rights bits1(read) and2(add), owner identity and finite epochs enforce checked API requests. Issue and attenuation must never add rights; add requires both root and capability permission; revoke invalidates old epochs and retires after3. Attack only this cooperative local model by requesting a stronger mask, reusing a revoked capability and crossing owners. Then analyze a C client that directly forges exposed fields: explain why this violates the model and refutes a broader security claim. Design an opaque broker/process boundary that can enforce the stronger threat model.

A full-rights capability can add5. Its attenuated read-only capability cannot change the counter. Attempting to attenuate read-only rights to full rights rejects with output unchanged. After revocation, the former full capability returns stale and the counter remains5.

Observable evidence: {ref}`X-T69-009` requires Enumerate rights0–3 and all subset/non-subset requests. Retain capabilities through each revoke and retirement, comparing the counter and status to an independent set/epoch model. Mutation1 permits amplification; mutation2 accepts a stale epoch. Success is an observable synthetic counter change contrary to the declared policy, not abnormal termination or privilege escalation. Repairs require both rejection and preserved state.

### T69.10 — Versioned plugin objects and borrowed code lifetime

A loaded-code borrow keeps the module owner live while a client may call its functions or access exported data. Its release ends that permission, even if the loader leaves pages mapped. A symbol address supplies neither semantic compatibility nor lifetime. A successful dlclose need not remove mappings, and a surviving address is not permission to keep using a logically unloaded API.

Implement DSLoaded open/acquire/release/close using only original test DSOs. Analyze constructor execution before validation and why version checks cannot sandbox malicious same-process code.

The ABI9 original fixture rejects and leaves the module empty. ABI1 opens; acquire then close returns busy. Its apply(17,3) returns20. Clear the borrowed pointer, release, and close empties handle/API. Never call a pointer after release/close to infer whether the loader really unmapped it.

Observable evidence: {ref}`X-T69-010` requires Build DSOs and host separately with recorded flags. Use dlerror around symbol resolution and inspect dynamic symbols/dependencies. Retain handles after failed close and classify initialization side effects. All executable targets are original local DSOs; no external plugin/service load is authorized. No destructor, stale callback or invalid ABI is invoked after rejection.

### T69.11 — Quiescent hot reload with staged state handoff and retirement

Reload quiescence excludes active calls and retained callback or data borrows before replacing the current module. After publication, a retired module owner keeps the previous module's cleanup responsibility until collection succeeds; this differs from candidate migration failure before publication, which leaves the old current module unchanged. Hot reload is a lifetime and state-compatibility transaction. Swapping a function pointer is insufficient when old callbacks, data schemas or cleanup failures remain live.

Implement DSHost reload/collect with current and one retired DSLoaded owner, integer state and non-wrapping generation0–3. Stage candidate migration from old schema/state, then atomically transfer ownership and publish state only on success. The previous module remains owned in retired until explicit collection. Reject reload while current/candidate borrows exist, retired remains occupied or generation is exhausted. Plugin1 preserves state; plugin2 doubles admitted state0–500. Add a failure-injecting loader backend model for collection failure without passing invalid real loader handles.

Starting state7, load schema1 then schema2: state becomes14, generation2, candidate becomes empty and the former module is retired. Collect releases retired. With old state600, migration rejects and retains state600, generation2, current and candidate ownership unchanged.

Observable evidence: {ref}`X-T69-011` requires Use both actual original DSOs for the admitted synchronous protocol and a deterministic backend model for failure stages that cannot safely be induced through real invalid handles. Inject candidate load/migration/collection failure; enumerate all borrow counts0–4 and finite generations. Record exactly which steps commit and which require recovery. Never unload a running callback as an experiment.

The **semantic carrier** matters because a concrete representation in which an interpreter computes the meaning of an expression. A syntax node records the form of a term; a semantic carrier holds its interpretation, which may itself be text or a callable.

The **final interpretation** matters because representation of a term by applying interpretation operations to the meanings of its components. An initial syntax representation stores constructors for later traversal; final interpretation makes the chosen operations produce meanings directly.

The **typed carrier boundary** matters because a C function signature that distinguishes admitted representation types for integer expressions and function expressions. A typed carrier boundary diagnoses incompatible C argument types; it cannot prove that correctly typed callbacks implement the promised laws.
