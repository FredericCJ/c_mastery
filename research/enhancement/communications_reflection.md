# Communications research reflection after broad discovery

This is a research/design note, not teaching authorship. Broad discovery on October 9, 2026 searched both the SWE work/concept indexes and the explicit current Knowledge catalog, then public manufacturer and standards-organization leads. Catalog identities and search snippets are leads; only subsequent actual passages will become assignable locators. The current library has a held CAN standard and networking textbooks, so normative access must be tested rather than presumed unavailable.

The main gap is a boundary gap. I2C, SPI and UART names describe different combinations of signaling, timing and transaction conventions; USART is an MCU peripheral capability, while RS-232/422/485 describe electrical interfaces that can carry an application-selected byte protocol. CAN adds arbitration, framing and error confinement; its identifiers are not automatically destination addresses. Ethernet combines particular physical entities and a MAC/link service. An HTTP exchange over an existing socket cannot establish that the learner implemented the lower layers. The proposed domains should make these distinctions observable through waveform, frame, ownership and fault evidence instead of a table of acronym definitions.

T38 should collect serial/bus foundations and their MCU bindings. Candidate mechanisms are open-drain rise-time/loading and I2C transactions; SPI sampling/selection and device-specific framing; asynchronous UART bit timing versus synchronous USART capability; electrical levels, differential signaling, termination, biasing and half-duplex direction; classic CAN arbitration, timing, filters and error state; and the FD frame/data-rate distinction. These are too broad for one firmware task. Coherent small projects should reuse prior bounded ring/driver mechanisms, use declared synthetic fixtures for reasoning, and have separate physical-observation gates. A simulator may exercise parser/state logic but cannot prove voltage, cable reflection, edge timing or a real transceiver's behavior.

T39 should begin with service/protocol/interface and encapsulation reasoning, then Ethernet PHY/MAC/management, frame layout, address/type/FCS policy, receive/transmit descriptor ownership, and packet-path diagnostics. The OSI model is a reference decomposition, not an instruction to invent seven distinct libraries or claim a TCP/IP stack implements every OSI service. The L1-to-HTTP capstone needs a named finite interoperability subset and rejected cases: direct-link Ethernet, bounded ARP and IPv4, UDP or a small TCP state machine, then HTTP. Routing, fragmentation, TCP options/windowing, retransmission, checksums and close/reset behavior cannot disappear behind a successful nominal GET. Root's capstone design should declare what is implemented and what is supplied by hardware or tools.

The initial source plan has four layers of authority. NXP's I2C specification and ST's actual MCU manual can establish a transaction and peripheral binding. TI electrical interface notes and transceiver datasheets can establish a measured device boundary without being mislabeled as TIA normative standards. Bosch implementation/compatibility documents can explain FD, while the held ISO 11898-1 edition may supply normative clauses if it is an ordinary readable PDF; the older Bosch 2012 FD protocol must not silently substitute for ISO FD. IEEE Ethernet and ITU X.200 access need actual inspection. Held textbooks should support the mechanisms through short selected passages rather than whole-book assignments.

Platform questions need focused resolution before authoring. F439's product lead identifies classic CAN and an Ethernet MAC with DMA; it does not establish CAN FD capability or a complete Ethernet PHY on the chip. An external FD controller or separately selected optional MCU is therefore a distinct configuration. The exact physical board and its PHY, clocks, pin routing and solder bridges need their own documented identity. MCU interrupt/controller, peripheral/DMA, external transceiver, PHY and network software duties should not be collapsed into a generic Cortex-M description. A broad rule about cleaning CPU caches must be checked against the actual Cortex-M4/F439 architecture rather than copied from a different MCU.

Focused inspection will test: (1) exact I2C START/STOP, ACK, repeated START, arbitration/stretching, rise-time and recovery scope; (2) ST SPI/UART/USART/CAN/Ethernet sections and memory/clock limits; (3) TI RS-232 polarity versus logic voltage, RS-422/485 topology, termination/failsafe and transmit-complete direction; (4) classic/ISO FD framing, CRC/stuffing changes, bit timing and explicit access limits; (5) OSI service boundaries and Ethernet framing/PHY management; (6) actual board and external-controller evidence; and (7) edition-matched held textbook explanations. Any unsupported essential claim will remain a gap rather than an invented assigned reading.
