# T44 research reflection

The existing curriculum already teaches error contracts, program testing, minimization, dynamic/static tools, concurrency and embedded diagnosis. T44 must add an evidence-driven practice route and repeated causal reasoning, not another collection of disconnected debugger commands or duplicate system implementations.

The investigation began with a bounded canonical audit of T21, T24, T25, T29, T31, T32, T33 and T35 and relevant briefs, then read library rules/current pointers and the SWE/data-structure corpus and relation seeds before catalog discovery. Graph verification and catalog metadata were treated as leads. Ordinary held textbook pages and exact official/paper passages supplied authority. The Knowledge holdings were read only. Library/_old and opaque documentation contents remained outside the source scope. An initial broad filename search emitted opaque package filenames before the full rules were read; no opaque content was opened, the traversal stopped, and subsequent discovery used the pinned catalog and exact ordinary payloads. This procedural error is recorded privately and is not evidence of inspection of those packages.

The core uncertainty was whether a novice route could teach useful debugging without making all advanced modules prerequisites. The answer is a staged route: T03/T05 and selected T21/T32 foundations support the first three milestones; hosted I/O/concurrency and firmware dossiers are later selected preludes. T45 is optional deeper memory practice, not a T44 prerequisite. Existing C implementations are reused, while each dossier introduces a new intentional defect, a finite replay, competing hypotheses and a repair justified by its invariant. Only incremental new work is charged.

The ARM textbook is useful for concrete source/disassembly and layered crash triage, but its board, proprietary tools and broad compiler claims do not establish our platform behavior. Official GCC/GDB/Arm/ST contracts delimit the example. In particular, a C divide-by-zero or other UB example has no guaranteed crash symptom; an explicit architectural trap needs target configuration and actual evidence. GDB's current manual is a development snapshot, not an installed release. Watchpoints have width, slot, scope and thread limits. These limits belong in learner decisions and fallback tasks.

Input reduction must preserve the same failure predicate. The actually inspected ISSTA2000 paper supplies a tri-state reducer and 1-minimal certificate. The later expanded2002 paper and cause-effect-chain paper could not be obtained from the attempted primary endpoints, so neither is assigned. A smaller trigger is evidence for localization, not proof of the causal code transition. The final diagnosis must identify the earliest violated invariant and reject a symptom-only patch.

Static fixture calculations will validate finite histories, classifications and certificates. They cannot establish a learner C execution, a sanitizer report, a core file, a race schedule or a physical HardFault. Actual observations need a separate image/input/environment dossier, and unavailable capabilities keep their claim open. The research gate accepts source support only; teaching and publication require the later independent content review and artifact checks.
