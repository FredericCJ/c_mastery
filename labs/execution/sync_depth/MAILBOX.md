## State, dependencies and assumptions

Use C17 with exact-width integer types, the original sixteen-task CMX kernel and caller-owned stationary storage. Clients are the fixed live logical task slots0 and1; the server is task2. A client has at most one operation, but both clients may be outstanding together. CMX slots are not safe identities across reap/reuse: no participating task may exit, be reaped or have its control replaced while this protocol retains it. All calls and state accesses share one external exclusion domain. Hosted schedules are serialized logical tasks, not evidence that raw CMX supports unsynchronized native threads.

`CDMailbox` owns a capacity0 or capacity1 CMX queue, two client controls, two progress semaphores of maximum2, and two actual four-entry `CLAck` receipt stores. It borrows its kernel. Every request and reply is exactly four bytes; the payload has no implicit native-endian interpretation. Delivery outputs own a copied byte array and identity. Controls, required outputs and live inputs must be valid, nonnull and disjoint, except the explicitly owned in-place state. Inputs cannot alias control storage. No allocation, networking, RPC framework or operating-system message library implements the mechanism. Host orchestration is separate from the target dependency closure.

Capacity1 owns a copy of input at begin, including while a full mailbox holds the operation pending; the caller can then reuse its original bytes. Capacity0 borrows the four input bytes until the wrapper's receive-copy boundary or a definite pre-transfer terminal cancellation/timeout. The caller cannot change, free or reuse them earlier. `cdmb_delivery` is the authoritative release check. A raw CMX identity-word match can occur before the server wrapper copies those bytes, so the underlying send result alone is insufficient for that borrowed-storage guarantee. No control or live borrowed region may be moved, destroyed or concurrently accessed contrary to this contract.

## Begin, transfer and application reply

`cdmb_begin` checks a free client slot and live task, allocates its next checked generation, publishes the identity, then submits the encoded slot/generation through actual `cmx_queue_send`. It returns that transport operation's status. Even a transport admission timeout consumes the newly issued identity and leaves a terminal operation to collect. Precondition/capacity-of-identity refusal leaves output unchanged and creates no operation. A successful mailbox send means buffering or direct delivery, not server processing. A rendezvous has no buffered queue cell. For receiver-first rendezvous, begin can report the raw match while `cdmb_delivery` still reports BLOCKED until copying completes.

`cdmb_receive` drives the actual server receive, retaining a pending receive state when CMX blocks. It may be called again only to observe completion of that operation, then to start another. A capacity less than four returns FULL before starting or consuming a receive. On success it validates the current client/generation, copies the four bytes, marks delivered/received and signals progress. A stale queued identity is consumed and returns STALE with output unchanged. A cancelled server wait returns CLOSED; cancellation after the raw kernel match does not retract that result. The wrapper's copied-byte boundary is the selected application transport commit.

`cdmb_reply` accepts only the exact current session/slot/generation for an active operation actually received by the server. It copies one reply and signals progress. Duplicate or late replies reject without satisfying a new operation. The server owns its received copy and can dispose of a rejected late reply. `cdmb_poll` drives completion, including actual semaphore waits, consumes stale progress notifications and returns BLOCKED until a reply or terminal outcome exists. A short reply buffer returns FULL with output and operation unchanged; retry with four bytes retrieves the same reply. Successful retrieval copies the reply and retires the operation. Terminal errors retire it without writing output. A second poll rejects.

Each operation has at most one delivery notification and one reply notification. The semaphore capacity two therefore bounds pending progress without treating a wake count as a reply. The predicates are `delivered`, `received` and `has_reply`, checked under the common exclusion boundary. A ready task need not mean the application has finished. No notification or signal authenticates a request.

## Identity and finite boundaries

Identity is `(session:uint32, generation:1..65535, client:0..1)`. The queue word encodes generation and client; the queue instance is bound to one session. Generation exhaustion returns FULL rather than wrapping. The client cannot begin g2 until g1's terminal result is collected, but the server may still hold a copied g1 request. Timing out g1 therefore does not authorize its late reply to complete g2. An old queue word can remain after a mailbox outcome becomes ambiguous; its generation check prevents it from reading a new operation's input.

`cdmb_restart` is a serialized supervisor transition, not an emulation of an OS crash or durable reboot. It refuses at session UINT32_MAX before mutation. Otherwise it cancels active operations under their transfer rule, aborts the old queue, releases its waiting server, creates the next session and resets volatile receipt metadata while preserving the synthetic effect counters. Already copied successful replies remain retrievable; an unresolved transferred call reports UNKNOWN. Old-session replies and effect requests reject. Client generations continue increasing and are not reset by restart. Quiescence/exclusion is a premise; the function does not stop arbitrary concurrent callbacks. A session generation is a finite freshness fence, not authentication or cryptographic uniqueness.

## Cancellation, timeout and retry

Before a rendezvous wrapper transfer, cancellation prevents copying and reports CLOSED. A timeout before that boundary reports TIMEOUT. After buffering or transfer, cancellation/timeout can no longer assert that no effect occurred: the result is `CDMB_UNKNOWN`, unless a copied reply already won. Cancellation does not undo a received request or an effect. The caller may reuse its borrowed input after definite cancellation because the server validates operation state before dereferencing a stale identity. A copied received request remains server-owned independently of client timeout.

The terminal boundary is the actual CMX wait completion, not the next client poll. If a tick has already selected timeout, a late reply must reject before changing `has_reply`, and a delayed receiver must not copy an expired rendezvous borrow. Conversely, a reply that wakes the progress wait first wins even if the deadline passes before polling. Merely advancing the clock without an active wait does not retroactively select timeout: an already available reply can still satisfy the predicate. Report this policy explicitly instead of claiming a strict wall-clock acceptance cutoff.

Never silently retry an UNKNOWN outcome with a fresh logical identity. The original synthetic-counter demonstration applies delta1, loses the reply through cancellation, then compares replaying the stable identity with issuing a fresh one. Stable-ID replay returns effect1; a fresh-ID retry applies again and yields effect2. This is an observable local protocol violation when an application mistakes a fresh operation for a retry. It is not a demonstration of external compromise or distributed exactly-once execution.

## Actual bounded receipt composition

`cdmb_effect` routes each client to its own actual `CLAck` store, using session as epoch and generation as request ID. New effects are admitted/applied through `cl_request`/`cl_apply`; duplicate IDs return the stored result without reapplying. Binding includes delta: same ID with a different delta rejects. There are four receipts per client and no implicit eviction when full. A fifth unacknowledged request returns FULL unchanged. The sum is checked by the imported producer before applying an overflowing delta.

`cdmb_acknowledge` explicitly retires a terminal receipt. The retained high-water mark then refuses replay of an evicted old ID with STALE, while freeing storage for a newer ID. The successful-result replay window is the set of retained unacknowledged receipts, not an arbitrary number of seconds. After eviction the server promises refusal, not reconstruction of the old result. The comparison control erases high-water on acknowledgement and demonstrates a repeated old effect. Session restart invalidates the old epoch and retains only the counter, so a caller cannot recover an unresolved old result from this volatile store. Deliberately issuing a fresh session/ID after UNKNOWN can still duplicate an application effect. Crash durability, adversarial authentication, unbounded deduplication and inter-server replication require additional mechanisms and are not inferred.
