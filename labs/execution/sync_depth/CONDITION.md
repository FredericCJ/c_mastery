## Representation, environment and lifetime

Use ISO C17 and the actual sixteen-task CMX core. `struct cd_queue` owns one registered nonrecursive mutex, one condition, two fixed storage cells and sixteen request records. Capacity is one or two. A request copies its send value or retains a claimed received value, never a pointer into caller storage. The queue and kernel are initialized, stationary, live and externally serialized for every operation. Initialization is for fresh storage only. Raw task numbers are borrowed CMX slots and may not survive reap/reuse; do not exit or reuse a task with an active request. No direct access to mutable fields is permitted outside the declared fixture setup and wrapper/owner operations. Native concurrent C calls require a separate port exclusion mechanism; this is not an ISO C lock-free queue.

The hosted driver executes logical task schedules. A separate owned Cortex-M4 emulator executes selected freestanding state transitions. No library implements the queue, condition or mutex mechanism; no dynamic allocation is used. Host orchestration and independent trace calculations are not target dependencies. Record the compiler, flags, sources, image, generated assembly, linker map and actual implicit/explicit helpers. These observations do not establish native task context switches, SMP correctness, physical timing or a certified latency bound.

## Operations and state machine

`cdq_begin(q,task,PUT|GET,value,deadline)` requires a ready/running task, no outstanding request and no current ownership of the queue mutex. Admission errors leave no request; self-owned entry returns DEADLOCK. Once admitted, the request exists even if its first lock attempt times out. It moves through LOCK, CONDITION and DONE, with IDLE indicating no request. `CMX_BLOCKED` means inspect actual task completion and call `cdq_resume`; calling begin again is invalid. Resume while the kernel task remains waiting returns BLOCKED. Repeating resume after DONE reports the existing result without consuming it.

Once ownership is acquired, a PUT waits while full, and a GET waits while empty. Both predicates use the same mutex and condition. Waiting calls actual `cmx_cond_wait`, which enrolls before releasing under the common external protection domain. A successful signal only makes a waiter eligible to reacquire. Resume rechecks the predicate every time. A deadline due at a recheck does not invalidate an already available item; a false predicate at that deadline selects TIMEOUT. This is the explicitly inherited CMX policy, not a portable promise about every timed-wait API.

`cdq_begin_locked` starts the same request with ownership already held and transfers that ownership into the operation: success, terminal failure or blocking wait releases it as specified. Admission rejection leaves the caller owning. This permits an atomic owner-side observation followed by another predicate wait without an unlock/relock gap. It does not permit recursive locking. The caller must not separately unlock after an admitted locked-begin operation.

`cdq_result` is the exactly-once result-consumption operation. Before DONE it returns BLOCKED with both outputs unchanged. For DONE it writes the terminal status; only a successful GET writes the value. It then retires the request to IDLE. A second result call rejects. Outputs are live distinct storage, disjoint from each other and from the controls. They are never retained beyond the call.

Owner-only `cdq_put_locked` and `cdq_get_locked` perform immediate queue operations without creating requests. A full PUT or empty open GET returns TIMEOUT as a nonblocking refusal. `cdq_pulse` additionally requires the exact matching mutex pointer, valid owner and broadcast flag; another owned mutex is insufficient. An extra pulse changes notification eligibility but never invents an item. A signal with no waiters is not remembered.

## Ledger and failure semantics

`accepted = queued + claimed + consumed`. PUT increments accepted only with a committed copied value. GET removes one queued value; an asynchronous request holds it as claimed until result consumption, whereas the owner-only GET consumes immediately. The FIFO order of accepted values survives either route. Rejected operations do not change this ledger. Accepted never wraps: at UINT64_MAX every further PUT returns FULL unchanged even if space exists. Under the invariant, claimed/consumed increments cannot overflow independently. Application-level receipt persistence or crash recovery is not part of this volatile ledger.

The boolean closed state is a second predicate. `cdq_shutdown` requires ownership, refuses new PUTs and closes the actual condition, selecting CLOSED for blocked predicate waiters. They still must reacquire before finishing. Already queued accepted values remain available to later GETs; empty closed GET returns CLOSED. A request already DONE retains its outcome. A request blocked on initial mutex acquisition evaluates closed/drain state after acquiring. Shutdown does not destroy controls or discard claimed/queued values.

`cdq_destroy` refuses while any request remains active, any queued/claimed value remains, or the actual mutex is owned/referenced. Destroying a mutex cannot be used to bypass a pending condition reacquisition. The chosen changed-condition policy is refusal, not a return without ownership or an invented successful destruction. After successful destroy there are no future users or retained task/control references. No forced task death, robust recovery or asynchronous cancellation of arbitrary code is supplied.

## Concrete ordinary and changed-condition schedules

1. Pulse an empty condition with no waiters. A subsequent GET still waits. Let consumer0 wait; coordinator3 acquires, copies value42 and signals, then consumes42 while still owning. After release, consumer0 reacquires but finds empty and waits again. Cancel it, reacquire, report CLOSED and check accepted1=consumed1. This exposes the distinction between predicate state and a wake notification without a native data race.

Also pulse after coordinator3 acquires but before it changes the predicate. Consumer0 enters mutex reacquisition and cannot run the protected recheck until ownership is released. This ordering by itself is not a defect: both the signal and state change remain under the matching mutex. The harmful change is exposing a false publication/enrollment boundary, not merely moving the signal statement earlier. The test then deliberately consumes42 before releasing, so the final false predicate still requires a loop.

2. Enroll consumers0,1,2 on empty capacity1, publish value44 and broadcast. All three become mutex-reacquisition candidates. Consumer0 claims the item; consumers1 and2 each reacquire, find empty and re-enroll. Before result consumption, accepted1=claimed1; afterwards accepted1=consumed1. An extra broadcast with no item causes only rechecks, not extra claims. Shutdown then releases both remaining consumers through their ownership-restoration paths.

3. At time0 enroll consumer0 with deadline5, then let task1 hold the mutex. Independently repeat timeout, cancellation and condition close. Each selects a pending terminal status while consumer0 remains in the mutex wait phase. Advance to99: neither resume nor result may return the terminal result early. Destroy must refuse. Only task1's unlock restores consumer0's ownership, after which the wrapper releases cleanly and publishes TIMEOUT or CLOSED. Repeat the association check with another mutex that task1 really owns; it must reject despite valid ownership of that other object.

4. Use one condition for two predicates. Fill capacity1, then enroll two PUTs for values2 and3. Coordinator3 consumes the first item and, while still owning, enters a locked GET on the now-empty queue. Releasing for that wait admits producer0. With single-signal policy, producer0 inserts2 and signals producer1, whose space predicate is false. Producer1 re-enrolls; consumer3 remains asleep even though an item exists. This is an explicit liveness counterexample under an admitted comparison policy. A coordinator broadcast repairs the stalled schedule. With broadcast-on-change policy the same inputs progress without that repair. In both cases the final ledger is accepted3=consumed3. The example does not claim that every single-signal schedule deadlocks.

5. Fill capacity2 with7,8 and block a producer of9. Shutdown under ownership wakes that producer with CLOSED after reacquisition;9 was never accepted. Destroy refuses until7,8 are drained and their results consumed. The next GET returns CLOSED and quiescent destruction succeeds. Test finite accepted-counter refusal on a directly constructed valid near-limit ledger separately from claims about executing UINT64_MAX operations.

Graduated hints: enumerate who owns the mutex before reading count; a wake can be stale without a lost memory write; timeout and reacquisition are separate phases; the two predicates need different eligible waiters. Assessor implementation and worked analysis remain private. Measure O(capacity) fixed storage plus sixteen request records, and the base CMX bounded scans/priority recomputation. ISO C enforces neither matching-condition ownership nor one-shot request consumption; checks and disciplined API use enforce this contract. A language-level condition API likewise does not turn a signal into an item reservation.

Security scope is the original local kernel state and synthetic integers only. An adversary chooses admitted operation order, pulses, cancellation and shutdown timing. The demonstrated property failures are a fabricated claim, premature terminal completion, missing wake or lifetime refusal violation, with explicit prerequisites in each trace. Repairs restore loops, ownership restoration, broadcast selection, shutdown wake and association checks. No external service, real credentials, production firmware, host security change or deployed target is involved.
