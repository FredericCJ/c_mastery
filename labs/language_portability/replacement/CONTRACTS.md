## Representation, ownership and callback contract

LeOwner is either entirely zero/nonowning or owns exactly one allocated byte span, size, synthetic identity1/2 and matching LeOps release context. It is live, exclusively owned, serialized and not copied except for the specified transfer followed by clearing the source. The output must initially be entirely empty and disjoint from callback state and local resource storage. Ops and context must outlive all callbacks, including final release of a transferred owner.

`le_run` validates transfer0/1/2 and both callbacks, then acquires resource1 of8 bytes and resource2 of16 bytes. An acquisition returns fresh disjoint live storage or NULL without creating ownership. Failure of either acquisition returns LE_NOMEM, leaves output unchanged and cleans every earlier acquired resource exactly once. On success resource1 contains bytes1..8 and resource2 bytes17..32. Transfer0 publishes no owner; transfer1/2 moves that owner to output before returning. Other initialized local owners release in reverse acquisition order. Explicit cleanup labels and GNU scope cleanup must implement the same public contract.

`le_drop` snapshots the callback/owner, empties the public owner first and then releases once; repeated drop does nothing. Callbacks return normally, do not reenter, mutate or destroy controls/context, and retain no borrowed control pointers. Release is nonfailing. A release callback may read the already-emptied owner only while that owner remains live. Invalid admission performs no callback and preserves output. No asynchronous cancellation, longjmp, process termination, exception unwinding or fallible close is part of this contract; the GCC passage's exception behavior is not silently generalized to them.

Two live resources occupy24 payload bytes; at most two acquisitions and two releases occur. Core control work/storage are constant. Allocation cost is a separate provider cost. ISO C does not enforce unique ownership; typed interfaces, diagnostics, runtime tests and programmer discipline have distinct roles.
