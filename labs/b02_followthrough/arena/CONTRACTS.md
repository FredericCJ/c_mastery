## Representations and operations

B2Arena stores offsets into a conceptual64-byte region, four saved cursors and nonreused mark IDs1..15. A mark consists of its live owner address, exact depth and ID. Only the current top can roll back. Out-of-order, repeated, foreign and same-depth replaced tokens are STALE. Depth exhaustion and permanent ID exhaustion are FULL; failure preserves cursor, depth, next ID and outputs. Reserving n bytes at alignment1/2/4/8 uses checked remaining capacity. Invalid alignment is INVALID; insufficient space, including SIZE_MAX length, is FULL. Zero length may consume alignment padding and may return offset64, without authorizing dereference.

BfArena adds an actually aligned64-byte unsigned-character array, sixteen active allocation records, eight cleanup records and four saved record counts. Allocation IDs1..31 are never reused during the owner's lifetime. A BfBorrow is a live owner address plus allocation ID; no raw byte pointer is returned. Reserve first rejects null required arguments, then BUSY for active/pending cleanup, then FULL for metadata/ID exhaustion, then applies actual B2 admission. On failure control, backing and output are unchanged. On success it appends one record, zeroes the admitted bytes and publishes the borrow. Even an empty allocation owns a record/ID; it has no admissible byte index.

Get validates the live owner/ID and index before publishing one byte; stale or foreign is STALE, out-of-range is RANGE, null required control/output is INVALID. Set uses the same lookup, but BUSY takes precedence while cleanup is active/pending. Get is allowed during cleanup so callbacks can inspect retained bytes. This API cannot make an already-dangling owner pointer safe to evaluate, revoke a separately escaped raw pointer, or protect a copied control. These are caller lifetime premises, not runtime guarantees. The declared unsigned-character backing remains byte storage: numerical alignment does not create arbitrary typed objects or a destructor model.

Mark saves the actual B2 cursor identity plus allocation/cleanup counts. Register requires an active mark, a nonnull close callback and free cleanup capacity. A successful registration transfers cleanup responsibility; failure transfers none and the caller must unwind the unregistered resource. A zero callback result means resource release succeeded; nonzero means that resource remains owned and its context remains valid for retry. Callbacks may use checked Get, but all wrapper mutation returns BUSY. They must not directly mutate the arena, alter other cleanup records/contexts, end the owner lifetime, retain a byte borrow beyond reclamation, or exit nonlocally. Callback duration and eventual success are not bounded by the API.

Rollback attempts all not-yet-successful callbacks in reverse registration order. Successful records are marked done and never invoked again. If any callback fails, return CLEANUP and retain the entire top scope: cursor, allocation records, marks and all byte authority remain. New allocation, mark, registration, set and commit return BUSY. Only retry of the same exact top mark can resume cleanup; other rollback tokens return BUSY while pending. Get remains available. On successful retry of all remaining callbacks, invoke actual B2 rollback, restore saved record counts and invalidate reclaimed borrows. Thus external cleanup effects can occur on failure: this is retained retry, not atomic rollback of external effects. A successful callback may destroy its own context because retry skips that record without dereferencing the context.

Commit requires an exact top mark and a parent mark. Root commit is INVALID; stale/foreign is STALE; active/pending cleanup is BUSY. Successful inner commit only pops depth. Cursor, bytes, allocations and cleanup ownership remain; the parent rollback inherits all of them. The committed mark becomes stale. A later sibling gets a fresh ID even at the same depth. Commit never calls cleanup and never recycles IDs. Cleanup and rollback remain available after allocation or mark ID exhaustion.

## Reasoning and costs

Prove cursor<=64, depth<=4, count<=16 and cleanup_count<=8. Every admitted allocation interval is contained in backing; rounding uses remaining extents, never unchecked offset+length. Active allocation IDs are unique, increasing and never reissued. A rollback removes a suffix of records; inner commit changes no allocation membership, so parent reclamation still removes the correct suffix. Mark IDs prevent same-depth reuse, while allocation IDs prevent old borrows naming newly allocated bytes at the same offset. The live-owner/noncopy premise is essential: address identity alone cannot distinguish a newly initialized object at the same address.

Separate three properties: numerical byte reclamation, checked-borrow validity, and resource cleanup. The retained allocation_depth ALArena pop policy removes allocation authority before a fallible callback and reports failure; it does not implement this retained retry policy. Preserve that provider rather than treating two different failure contracts as equivalent. The new done bit ensures a successful destructor is not repeated; the pending state prevents allocation reuse while any cleanup is unfinished. Retaining all bytes is deliberately conservative even when only one resource failed.

Mark/commit take constant work, reserve takes O(n) zeroing, and Get/Set scan at most16 records. Rollback takes O(k) record checks and invokes at most k<=8 callbacks per attempt; callback cost and number of retries may be unbounded. The implementation uses fixed control/backing storage and constant call depth; no heap allocation or recursion is required. Record actual sizeof(BfArena), object symbols, code size and compiler stack usage. Fixed finite IDs trade availability for stale-authority rejection; increasing widths postpones exhaustion but cannot justify silent wrap. No timing or physical cache guarantee follows from these bounds.
