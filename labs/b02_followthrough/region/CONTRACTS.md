## Actual MBRegion and typed batches

Request3/align1 followed by5/align4 yields offsets0,4, cursor9, payload8 and lifetime high9. Checked reads require initialized current spans. ## Child cohorts and nonzero slices

BfRegionTree owns three distinct actual MBRegion controls: parent and two children. Their owner identities are distinct. Reset child0 only invalidates its handles; initialized parent and child1 spans remain readable. Whole-tree reset processes child1, child0, then parent. Each generation retires independently. The tree/control is not copied or moved while any span exists. No callback in this tree may call a tree operation or mutate another region; with that premise reset has no fallible callback boundary. This models sibling lifetime groups, not arbitrary graph reachability or inferred ownership of raw pointers.

BfSlice is a separate byte-only variant over an admitted caller array of at most64 bytes whose actual base is aligned8. Init requires a positive slice capacity, begin<=array_length and capacity<=array_length-begin; failure preserves the old control. Begin may be nonzero. Allocation uses actual absolute offset begin+cursor to derive padding, never cursor alone. For base begin3, length5 and alignment8, result offset8 consumes padding5 and raises cursor10/payload5/high10. A returned offset indexes the original backing; it is not a relative pointer to a new object. Positive sizes and alignments1/2/4/8 are accepted; invalid inputs are INVALID, insufficient capacity or retired generation is FULL. Failure preserves state/output. Reset clears cursor/payload, retains high and advances generations1..3 to permanent4. Get validates live owner/generation and absolute extent before copying an initialized byte. The aligned-root premise is caller discipline; numerical offsets do not establish it for an arbitrary pointer.

## Fixed versus growing chunks

BfGrowth begins with one caller-owned, actual typed BfChunk containing32 bytes and a cursor. It can own at most three additional chunks returned by explicit acquire/release callbacks. Each acquired chunk is a distinct live exclusive typed object with alignment8, disjoint from all controls and previously owned chunks. Acquire returns NULL on failure; its external attempt counters may change, but allocator state/output remain unchanged. Release is nonfailing and returns normally; it releases exactly that chunk once. The first chunk remains caller-owned. Callbacks cannot mutate/reenter the allocator except checked reads of still-live bytes; allocate/reset during callbacks returns BUSY. A callback must finish any read before freeing its own chunk.

Requests are positive and no larger than32, alignment1/2/4/8. Use the current chunk if the whole request fits; otherwise acquire a new chunk without altering old cursors or metadata first. On acquisition success append it and allocate at offset0. On exhaustion/failure, preserve output, payload, occupancy, chunk count and peak records. A large request is never split; there is no compaction or relocation. The handle includes live owner, generation, chunk index, offset and length. It grants byte access only while current and initialized. Reset releases extra chunks in reverse acquisition order, retains the first, clears current payload/occupancy, preserves peaks and advances to permanent retirement after generation3.

Payload sums requested bytes; occupied sums per-chunk consumed prefix including alignment padding; reserved byte backing is32*chunk_count. Tail slack remains retained and does not count as occupied. High tracks peak occupied; capacity_high tracks peak reserved bytes. Four20-byte requests consume80 bytes but reserve128. Under the same sequential request/refusal contract, the fixed32-byte MB arena accepts one20-byte request then refuses the second; the growth model may accept four, at the extra provider/retention cost. Growth refusal preserves the already accepted prefix in both policies; neither promises transactionally accepting the entire batch. The host test uses actual malloc/free only for raw BfChunk objects, injects every needed growth failure for the three-request workload and checks reverse release. Target uses separate static typed cells; it is not evidence of target malloc or physical memory behavior.

## Fallible cleanup composition

BfRetryRegion composes the actual preceding BfArena retained-cleanup mechanism rather than pretending MB's void callbacks can fail. It owns one root mark. Allocation/registration delegate to that core; reset retries its reverse failed-cleanup list, retaining all bytes and the root while any callback fails and skipping successful callbacks. On successful reclamation, establish the next fresh root mark. If mark identities are exhausted, remain inactive permanently; later reset is harmless and new reserve/register returns FULL. No ID is recycled. The changed representation uses64 backing bytes, sixteen allocation records, eight callbacks, fifteen root IDs and31 allocation IDs; these costs differ from the32-byte MB baseline. Checked Get through the imported core remains available during pending cleanup. Same-offset replacement never restores old borrow authority. This is a bounded cooperative retry protocol, not automatic destruction, cancellation safety or recovery from owner death.

## Language comparison and enforcement

The inspected C++ draft [monotonic resource members](https://eel.is/c++draft/mem.res.monotonic.buffer.mem) specifies upstream growth, bulk release and no effect for individual deallocation. Its allocation can fail through the upstream resource. This C comparison separates fixed refusal from explicit growth and does not infer object destruction from byte release.

The inspected [bumpalo lifecycle documentation](https://github.com/fitzgen/bumpalo#deallocation-en-masse-but-no-drop) distinguishes bulk reclamation from Drop; its boxed wrapper can run a value's destructor without individually freeing arena bytes. Collections carry Rust lifetime restrictions, while C owner/borrow discipline needs explicit contracts and checks. A cleanup callback is not Rust borrow checking, and a no-op deallocate is not a C resource-release protocol. These are bounded source comparisons, not executions or full conformance assessments of those libraries.

ISO C supplies the actual declared object types and access rules. The selected implementation supports alignment32 and the audited ABI. Runtime checks enforce admitted extents, finite generations, wrapper state and output publication. Python models provide bounded independent expectations. Caller discipline still supplies valid live pointers, no-copy controls, exclusive backing, initialized bytes and callback compliance. Counterexamples include casting aligned MB bytes to an unrelated declared type, resetting a live control to resurrect a handle, retaining a parent pointer after its owner dies, or closing a resource twice after a failed cleanup pass. Analyze invalid C accesses without executing undefined behavior as a golden result.
