## Representations and operations

Bottom-up sorting moves scalar `B2Item` values. It merges adjacent runs of width1,2,4 and so on into caller scratch, then copies the complete pass back. Equality chooses the left input. It never compares by subtraction. The final partial run has length bounded by the remaining extent. `bf_sort_width(n,width,out)` admits n>=2 and0<width<n, and returns min(n,2*width) without overflowing the intermediate: compare width against n-width first. Refused width queries preserve output. This scalar helper supports the complete size_t domain independently of the algorithm's64-record bound.

Indirect sorting returns a permutation of indices into immutable `BfRecord` owners. Each record may contain a self-pointer and owned byte resource; sorting reads only its key. It initializes the index sequence in original order and merges indices, choosing left on equal keys. Records, owned bytes and self-pointers never move or change. The output is a borrowed ordering view: its indices remain in range after destruction, but using them to access destroyed or relocated owners is invalid. There is no ownership transfer, clone or hidden destruction. The caller retains exactly one responsibility for releasing each actual resource after all consumers finish. Const access does not revoke a separate mutable alias; the immutable-owner premise is caller discipline.

## Reasoning and costs

Prove sorted merge prefixes, permutation and stable equal-key order separately. An index appearing twice may still produce sorted keys while violating the permutation. A right-on-equality merge may preserve sortedness and permutation while violating stability. Prove start<=middle<=end<=n before forming accesses; advance to end, never compute an unchecked start+2*width. Width saturates at n and therefore terminates even near SIZE_MAX.

For n>=2, let L=ceil(log2(n)). The supplied bottom-up policy writes n scalar records to scratch and n back on every pass: exactly2*n*L record writes. It makes at most n*L key comparisons. Indirect initialization adds n index writes; subsequent passes write exactly2*n*L indices and zero payload bytes. Its comparison sequence matches the bottom-up ordering for the same keys. Scratch is n B2Item versus n size_t, plus indirect output n size_t; both algorithms have constant auxiliary call depth. The retained recursive sort has logarithmic call depth and caller scratch n B2Item. Compare byte traffic using the actual sizeof types and include later indirection/key reads; zero payload writes alone is not a universal speedup. No physical cache measurement is claimed by logical write counters.

The inspected [Open Data Structures11.1.1 merge code and recursion-tree discussion](https://opendatastructures.org/ods-cpp/11_1_Comparison_Based_Sorti.html) supports the recursive decomposition and work argument. Its strict comparison selects the right run on equality, so its sorting contract is weaker than this exercise's required stability. The C exercise also replaces the source's allocating array representation with explicitly admitted caller scratch.
