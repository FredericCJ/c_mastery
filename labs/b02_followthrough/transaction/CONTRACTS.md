# Acquisition styles and retained compensation

Complete PR-T21-01 and actual B02 transaction first; bring the acquired-prefix proof, callback trace and error taxonomy. C17 is the implementation baseline. Original profile C component uses ordinary control flow, caller storage and explicit synchronous callbacks, with actual retained B02 as a comparison provider. Host tests may allocate real memory; strict M4 uses a separately named static provider. No library implements cleanup or transactions for the learner.

Controls, backend state and output objects are distinct, live, correctly typed, stable-address and externally serialized. No live owner is shallow-copied, moved, reinitialized or destroyed. Init applies only to fresh or terminal fully reclaimed storage after all uses finish. Failures cannot be used to test invalid lifetimes. No asynchronous activity is hidden behind a callback result.

## Three control-flow forms and original provider

`bf_construct(style,backend,published)` compares style0 actual `b2_transaction`, style1 early return, style2 nested blocks and style3 cleanup labels. Invalid style/output/missing callback is INVALID before any event. Acquire resources0,1,2 in order; zero transfers that resource, nonzero transfers none for the failed call. Original release cannot fail. First acquisition failure releases the successful prefix in reverse and returns FAILED unchanged output. Full success publishes3 and transfers all three to the caller, which releases2,1,0. All four implementations must produce identical exact event traces for failures0,1,2 and none. Repeating a failed constructor after complete cleanup repeats observable acquisitions; unchanged output is not idempotency.

The proof is acquired-prefix length plus reverse cleanup. Early returns repeat short cleanup sequences; nesting expresses dependency directly but grows indentation; labels centralize shared suffixes but require precise target ordering. For this fixed three-resource contract each uses O(1) state/time; the actual generalization to n resources is O(n). Choose by reviewability and invariant locality, not a blanket prohibition or preference for `goto`. Supply the four disassemblies/stack observations as measured compiler outputs, not a claim that any source style is universally faster.

## Fallible cleanup state machine

`struct bf_tx` keeps backend, state IDLE/LIVE/PENDING/DONE, owned mask, original failure stage/cause, accumulated failed-cleanup mask and latest cleanup cause. Fresh init has stage4 (no primary failure), mask0. `bf_tx_begin` validates all callbacks/output/state before events, then acquires0,1,2. Each success adds its bit; first failure records its exact nonzero backend code and stage0..2. After all acquisitions, a final commit callback either succeeds or records its exact cause and stage3. Success alone writes caller output3 and enters LIVE. A failed begin preserves output even if external actions occurred.

After a failed begin, cleanup runs from the highest owned ID downward. Release0/1/2 may now fail: zero irrevocably relinquishes exactly that resource; nonzero retains it and any dependencies. Every resource i may depend on all lower IDs, so cleanup stops on the first failure. It records the failed bit and latest code, preserves the original cause, retains the failed resource and lower prefix, enters PENDING and returns BF_TX_RECOVERY. It must not free a lower resource underneath a retained registration. A successful release is never repeated.

`bf_tx_close` on LIVE begins caller-requested reverse cleanup with primary0. On PENDING it retries the highest retained obligation. Repeated cleanup failure may remain PENDING indefinitely: liveness requires the external operation eventually succeeds. On mask0 enter DONE and return FAILED if a primary construction/commit cause remains, otherwise OK. Repeated close on DONE returns that same terminal classification without callbacks; historical cleanup diagnostics remain available. Close on IDLE and begin on anything but IDLE are INVALID. Thus cleanup availability is separate from success publication; retrying construction while an obligation remains is forbidden.

The model explicitly requires a failed release to retain ownership and a successful release to remove it. It does not cover ambiguous remote removal, lost acknowledgements or asynchronous cancellation. Those changed assumptions require an operation identity plus query/reconciliation or quarantined ownership; blindly retrying an unkeyed external operation is not equivalent. No durable commit, process-restart recovery or physical hardware quiescence is promised.

## Delayed external registration

Use two actual malloc-backed synthetic resources: memory0 and channel1. Registration2 is a local registry entry borrowing both. Successful registration is externally visible before the final commit callback. Inject commit error41 and compensation error22 on removing registration. On failure output stays sentinel99, the registry remains active, both allocations remain live, primary41 remains distinct from cleanup22, and state is PENDING. A later successful removal permits channel1 then memory0 release, reaches DONE/FAILED and preserves both diagnostic causes. Exactly eight callback events occur in this supplied one-failed-compensation history. Repeated terminal close emits none.

The registry is original, in-process and synthetic. No service, credential, deployed firmware or external data is contacted. Harmless success for the flawed control is an assertion that a lower resource was released while a registration still borrowed it, before any invalid memory use. Repair stops cleanup on that failure; regression tests cover every failure site and repeated retry. Residual limitation: a real external operation may have different failure/acknowledgement semantics, which cannot be inferred from this local model.
