`struct sr_hub` owns two real original `store` objects, one four-page two-way `struct sc_cache`, one mutex, and two `struct sr_slot` objects. Each slot contains a complete fixed-capacity `struct sl_snapshot`, a nonwrapping serial and a live flag. A `struct sr_lease` names the stable hub, slot and exact serial. It is an ownership token: do not forge, edit or duplicate ownership, and do not destroy/move its hub while a token or caller can refer to it. Ordinary temporary copies used to present the same still-owned token to an operation are borrows; release consumes the owner. Reading and release are serialized, so a read admitted after release returns stale. Callers must separately join before hub destruction.

No second process, raw store call or external backend mutation may bypass it. Backend callbacks are synchronous, nonreentrant, do not retain buffers and satisfy the parent full-page read/write/flush contract. Constructor recovery may write the image. A failed constructor leaves no live mutex/owned hub and may have performed the documented recovery effects.

## Publication and shared cache authority

Implement `sr_publish` as one locked begin/put/commit/checkpoint/reader-refresh sequence. Both store handles use the same IO wrapper, whose page reads invoke the actual `sc_read`; metadata and commit pages bypass that cache. Clean data pages are tagged by image identity, publication revision and physical home/redo page. The hub revision is a trusted monotonic cache authority, distinct from the persistent engine generation and snapshot slot serial.

Preflight revision exhaustion before any write. After a successful commit, advance revision before checkpoint reads/writes can expose reused physical pages. Then checkpoint the writer and reopen the reader under the same lock. This deliberately serializes publication with all live reads and snapshot capture; it does not add concurrent writers or silently make two independently opened engines coherent. Reopening the reader is necessary because its root, bitmap, generation and private cache may otherwise remain stale even when the shared cache has correct tags. Updating only the shared cache is insufficient.

The two actual handles' private clean caches remain present. The test invalidates only those private entries in a quiescent fixture, then calls both actual `store_page_read` paths and observes shared-cache hits and identical bytes. Do not relabel a standalone cache simulation as this composition. New revision may issue `UINT64_MAX` once; the next publication refuses before begin or IO. Existing reads/lease release/close remain available. Exhausted imported cache counters can be reported through the original boolean backend error path; no wrapping counter is permitted.

Admission/input errors preserve the prior committed map. A failed precommit operation aborts according to the original engine; it may be retried only if the engine remains usable. Commit or checkpoint/reader-refresh failure poisons the hub, because persistence or current authority may be uncertain. No further live get/publish/capture is admitted through a poisoned hub; copied snapshots and cleanup remain available. `STORE_INDETERMINATE` is not relabeled a rollback. This API does not implement reopening a poisoned hub in place.

## Snapshot versions, retention and reclamation

`sr_capture` holds the hub mutex while the actual `sl_snapshot_capture` validates and copies the committed reader map. An output must own no previous lease. Capacity is checked first: two live versions or permanently retired slots return `STORE_FULL` without backend work or output publication. Capture failure leaves the destination token and slot ownership unchanged. On success, increment the chosen slot serial, publish the copied version, then return the token. The snapshot records persistent source generation, but its lease authority is owner/slot/serial; a generation number alone is not a safe C pointer.

Publication never mutates a live copied version. Readers use `sr_snapshot_get` to validate authority and copy one record under the lock, with unchanged outputs on missing/stale/small-buffer refusal. They receive no interior pointer. `sr_release` validates the exact live serial, clears the copied records and makes the slot reusable. A serial reaching `UINT64_MAX` retires that slot after release; cleanup is still possible. Duplicate/stale releases reject and cannot consume a later version in the reused slot.

This is full-copy snapshot retention, not page-level multiversion concurrency. It pays O(number of records) capture/copy storage; the two fixed slots bound retained versions independently of later page reuse. There are no old physical pages to pin. A zero-copy variant would additionally need page-version identity, a reader registration/admission protocol, retained roots/pages until all readers leave, recovery rules for version metadata, and a safe reclamation mechanism. Explain which protections copying replaces and which C object-lifetime obligations remain.

`sr_close` always stops new live work/captures and returns `SR_BUSY` while either copied version is owned. Existing snapshot reads/releases continue. Once drained, close returns OK; only after joining all callers may `sr_destroy` destroy the mutex. BUSY does not authorize freeing the hub. No callback, thread cancellation handler or failed join is assumed to establish quiescence.
