## Reasoning and failure semantics

Derive the five transitions: installation, attempted trial, authentication acknowledgment, application-health/park, persistent commit. Explain why the boot authentication acknowledgment cannot set FW_HEALTHY. Explain why stale SRAM acknowledgments must be cleared before peer release and why a terminal peer failure cannot be repaired by pretending the core is quiescent. `fw_peer_step` must refuse health during outstanding operations and confirm only both healthy/no outstanding/no failures. A privileged application can lie or corrupt its service; this design trusts the signed teaching applications and does not provide application isolation.

The recycler writes the other journal before erasing the old. At every program/erase reset point, cold `bs_select` must produce exactly an authenticated old or fully committed new pair. A reset after all new bytes are durable but before return may select new: completion observed by the caller is not the commit point. After `FH_DONE`, issue the keyed SYSRESETREQ system reset and never return; RM0399 section9.4.2 identifies either core's request as a device system-reset source. If a polling budget expires while pending, retain ownership and stop; do not reset/reuse the software object as if hardware were canceled. Error cases fail stopped for explicit supervised recovery. Physical reset behavior and retained backup-state qualifications remain separate.
