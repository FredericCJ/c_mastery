# Assessor analysis: PR-T59-06

Display version and security epoch need not advance together. A monotonic floor prevents reintroducing an older vulnerable generation; moving it too early can make the fallback unbootable before the new image is confirmed.

Derive the invariant floor never decreases and analyze the confirmation/floor ordering under reset. State the threat model for storage tampering and what a RAM model cannot enforce.

The reference implementation is in `core.c`; inspect it together with the public test. The named fault is: The faulty update accepts a smaller floor from an otherwise valid image. A signed image is not permission to weaken anti-rollback policy.

Require the learner to derive 0 from the fixture inputs independently. A trusted monotonic store is a separate dependency, not a property of unsigned arithmetic.

Transfer answer obligations: Introduce a finite monotonic counter that reaches exhaustion; design a fail-closed recovery/key-rotation protocol without silently wrapping its security epoch.

Real erase/program granularity, torn writes, cache maintenance, boot ROM interaction, watchdog reset and physical power-interruption evidence remain required on dedicated boards. Model success is not secure-boot certification.
