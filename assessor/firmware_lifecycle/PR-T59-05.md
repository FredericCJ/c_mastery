# Assessor analysis: PR-T59-05

A persistent record becomes authoritative only after all its fields are valid and its commit marker is complete. Redundancy helps only if the selection algorithm excludes torn or inconsistent candidates.

Enumerate crashes after each field write and before/after marker programming. State why the XOR check is a synthetic torn-write control, not an authentication mechanism or robust error code.

The reference implementation is in `core.c`; inspect it together with the public test. The named fault is: Repair selection of an uncommitted newer record and ambiguous equal-generation records. Numerical sequence comparison is invalid after uncontrolled wrap.

Require the learner to derive 1515870801 from the fixture inputs independently. Reject ambiguity instead of guessing which equal generation is newer.

Transfer answer obligations: Replace the atomic marker with a multi-byte program unit that can tear; derive a coding/validation rule and prove at least one old or new valid record survives each allowed fault.

Real erase/program granularity, torn writes, cache maintenance, boot ROM interaction, watchdog reset and physical power-interruption evidence remain required on dedicated boards. Model success is not secure-boot certification.
