# Assessor: copied snapshots and shared cache

The central distinction is among the persistent engine generation, hub cache revision and slot serial. They serve durability ordering, current clean-byte authority and ownership identity respectively. A correct cache hit does not refresh a reader handle's root/bitmap/private cache. Therefore publish commits, changes the trusted revision, checkpoints, and reconstructs the reader while all users are excluded. The original engine is not modified or made independently thread-safe.

Every original page read through either handle reaches the same wrapper. Super/commit pages bypass caching. Data-page physical addresses determine home versus redo in the view, so the shared cache compares physical location as well as revision and identity. Advancing revision before checkpoint prevents an old cached redo image from satisfying the next use of that physical slot. A failure after commit poisons the hub; old copied snapshots remain valid because they own records, not backend references. An input or usable precommit refusal is distinct from an uncertain commit/checkpoint outcome.

Capture admission precedes any source read; no slot means no IO and no output. The actual snapshot producer stages its copy and validates the full tree before publishing. The hub does not expose the slot until this succeeds. Reuse increments the serial and stale release is harmless to the new owner. MAX may issue once and is then retired. Closing prevents admission but retains every live snapshot and the mutex until owners release and all callers are joined. This separates cancellation/admission from quiescence.

The copied-version cost is two fixed SlSnapshot arrays, in addition to the two actual store objects and shared cache. Capture performs a full structural check plus full record copy under the mutex; get searches copied records under that mutex. Publication includes full-image redo/checkpoint and reader reconstruction. These costs rule out an unqualified scalable MVCC claim. A page-version implementation would need retained roots, generation-tagged references, registered readers/epochs or equivalent ownership, delayed page reclamation, and durable metadata recovery; it cannot simply omit copies and retain raw pointers.

Controls1/2 separate shared-cache revision failure from stale reader-handle metadata. Control3 accepts an old serial after slot reuse and is rejected by exact stale read/release checks. Control4 overwrites a still-owned snapshot during publication and is rejected even though the live map is correct. The finite model predicts all216 histories from state/ownership rules rather than executing the C implementation as its oracle. The native thread test separately exercises mutex serialization and retained snapshot independence; sanitizer silence establishes neither all schedules nor the C/OS contract itself.

Require a learner to explain the capacity-before-effect check, distinct identities, failure poison, actual two-handle import and close/drain order before awarding understanding.
