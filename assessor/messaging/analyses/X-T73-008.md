# X-T73-008 assessor technical analysis

Under the mutex, each active pin selects one immutable logical version; collection marks those plus current. Four pins therefore require at most five distinct retained entries, leaving room in eight slots. Generation validates the pin lifetime separately from the version timestamp. A forgotten pin can retain old data indefinitely, but the finite reader bound still bounds this representation’s version count.

## Delayed case X-T73-008-DELAYED

Give each version separately owned payload storage whose clone can fail; publish only after full construction and preserve old readers on failure. Delayed assessment adds independent keys and predicate queries: construct write skew under snapshot isolation and explain what validation or locking would establish the stronger requested property.

Require the revised contract, minimal counterexample, implementation/trace and cost evidence before feedback. Assess the invariant under the new assumptions, not just output similarity. Two transactions each observe that the other on-call worker is available and independently mark their own worker off-call. Per-key snapshots can admit both, violating the joint invariant. The correction must validate the predicate/read dependency or serialize the conflicting decisions, not merely add more version slots.

## Executable owned-version and predicate successor

`followthrough/versions.c` is the separate assessor implementation for
`VERSIONS.md`; the learner only receives its header, contract, stub and tests.
The outer mutex serializes the core's visibility operations and the payload map,
with outer-before-core lock order. Construction happens before the publication
lock. The core's collect may reclaim a slot and immediately reuse it; therefore
release the previous payload for the selected slot even if its live bit is now
true. Control61 omits exactly this release and fails allocation accounting. Read
retention is acquired while protected; control62 skips it and fails a destructor
counter assertion before the test could evaluate a reclaimed pointer. Reader
pins protect version selection; shared tokens protect independently allocated
payload lifetimes. Neither mechanism subsumes the other.

The clone test has three distinct cuts: payload record allocation, byte allocation,
and shared-control allocation. The clone itself undoes its first allocation if
its second fails; the wrapper drops the completed clone if the third fails. An
initial-control failure cannot consume the supplied owner. Clock exhaustion must
also destroy a completed candidate without replacing an old version. Retained
leases explicitly survive pin release and store destruction. The store admission
gate, callback normal-return rule and allocator-context lifetime are preconditions,
not properties enforced by ISO C or inferred from sanitizer silence.

The two-key adapter snapshots actual atomic cell values under an outer mutex,
then admits concurrent transaction bodies. Its commit still calls the original
core after installing the exact validation mask. Always include written keys;
otherwise a blind stale write can silently replace a newer committed write
(control64). In predicate mode include observed keys as well (control63 ignores
them). With both bodies having observed[1,1], write-only validation accepts the
disjoint writes0 and1, producing[0,0]. Full observation validation accepts the
first and rejects the second. Zero-valued keys remain in the predicate universe;
recording only matching rows would miss their later change. This finite mask is
not a dynamic range predicate lock. Read-only transactions can conflict in the
strict mode; an unrelated unobserved key change need not do so. Timestamp gaps
from failed core commits are allowed and are not evidence of partial publication.

Assess X-T73-008-R4 and X-T73-008-DELAYED separately from public anchor success.
The independent Python value-history model checks3,910 version words; its
set-based conflict model checks1,296 paired transactions. Real threads force both
body snapshots before either commit, but these observations prove neither arbitrary
client serializability nor scheduling fairness. Require a written serial-order
counterexample, ownership accounting and an unseen variant, not just matching the
reference implementation. Resource costs, a read-copy-update comparison and the
thirteen shared dimensions still require their explicit submitted evidence.

## Required read-copy-update comparison

This snapshot store protects acquisition and release with mutexes and represents
up to four independently chosen historical views. A read-copy-update design
needs a distinct read-side lifetime protocol and a grace-period condition before
reclaiming an object that a pre-existing reader could still use. Publishing an
atomic pointer alone supplies neither condition. A reader that may retain an
arbitrary old snapshot after leaving a read-side section needs an additional pin
or owner; merely waiting for that section cannot free its retained payload.
Conversely, the snapshot store's bounded pin table can refuse a fifth reader;
that admission rule must not be hidden in a comparison with a design promising
unbounded readers. Stalled readers, payload copying, retired storage and writer
synchronization must be included in the cost model. The supplied pin-versus-copy
measurements are actual equal-value workloads; they are not measurements of an
unimplemented read-copy-update library or evidence of lock-free progress.
