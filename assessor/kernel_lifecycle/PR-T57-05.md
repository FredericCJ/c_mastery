# Assessor analysis: PR-T57-05

Cancellation is a request to prevent or stop future work, not permission to free storage while a worker can still access it. Teardown closes admission first, then drains or cancels work and only then releases its owner.

Prove release implies quiescence and closed admission. Compare cancellation return values with work ownership; do not hold a lock required by the worker while synchronously draining it.

The reference implementation is in `core.c`; inspect it together with the public test. The named fault is: A faulty release ignores running work after close; the sentinel release flag demonstrates premature destruction. A deadlock also occurs if teardown waits while holding the worker lock.

Require the learner to derive 0 from the fixture inputs independently. Do not free until the final possible callback is quiescent; synchronous cancellation has its own lock constraints.

Transfer answer obligations: Allow a worker to requeue itself; introduce a closure generation and prove no requeue survives the close linearization point.

Actual guest module build/load/unload, concurrent open/remove traces, allocation-fault injection and lockdep/KASAN observations remain mandatory target evidence; host model tests do not satisfy them.
