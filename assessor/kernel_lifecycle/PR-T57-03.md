# Assessor analysis: PR-T57-03

A count protects an object only if the operation accessing the count already has a lifetime guarantee. Starting work and incrementing afterward permits the worker to consume the last reference first. Protected lookup needs both table serialization and successful reference acquisition.

Associate every reference with a named owner; count conservation is initial plus successful acquires minus releases. Explain why a nonzero count cannot validate a pointer that may already be freed.

The reference implementation is in `core.c`; inspect it together with the public test. The named fault is: Reject resurrection after the terminal release and a get-after-handoff schedule. Delaying free alone masks the race without creating valid ownership.

Require the learner to derive 0 from the fixture inputs independently. Acquire before publication; synchronize lookup with removal and keep the count storage live.

Transfer answer obligations: Add a lookup table and compare mutex-protected get-unless-zero with RCU-protected storage lifetime; show why refcount and grace period solve different obligations.

Actual guest module build/load/unload, concurrent open/remove traces, allocation-fault injection and lockdep/KASAN observations remain mandatory target evidence; host model tests do not satisfy them.
