# Segmented ownership analysis

Two pages reuse actual DSparse rather than reimplementing its generation
mechanism. The composed handle binds segment, page and inner page-owner token;
checking only page number would admit a handle from another owner. Add transfers
the resource only after page admission succeeds. Remove first invalidates the
handle, then clears the resource pointer and invokes exactly one destructor.
The callbacks remain nonreentrant and nonfailing; changing that assumption
requires a retained cleanup state like X-T66-011.

The test fills both pages, removes/reuses slot0 through generations1..3, and
shows generation retirement even while the other seven slots remain full.
Rejected add retains the caller's resource. Ten admitted owners produce exactly
ten destructor calls. One control omits destruction; another preserves the old
generation and admits a stale token after reuse.

The borrowed int address remains a valid C pointer to the still-live slot member
even after logical deletion. Observing77 through it after reuse safely disproves
the claim that generation checks revoke pointers. This does not access the
destroyed external resource. With actual object deallocation the analogous
dereference could instead be undefined behavior and is not needed for this
demonstration. Concurrent reclamation remains a different contract.

## Insertion order solution

The owning adapter uses DSparse for stable payload slots and generations, and a
separate index-linked order for traversal. Dense swap-removal cannot preserve
insertion order. Reusing the deleted slot appends a new link at the tail rather
than restoring its former position. Four link writes per successful add/remove
are observed at actual writes; the bound96 follows from four slots, three
generations and at most one add plus removal per issued generation. Dense-pool
stores are not part of that counter. Linked iteration takes one step per live
entity instead of scanning tombstones, at the cost of next/previous metadata
and pointer-chasing locality. Handle lookup remains the original O(1) check.

Mutation invalidates iterator versions even when a surviving payload address
is unchanged. The stale iterator control omits removal's version update; the
wrong-order control prepends. Both fail without accessing expired C storage.
Separate address stability, logical entity lifetime, generation validation and
borrow permission in the learner explanation. The diagnostic iteration counter
saturates; version exhaustion rejects writes. The adapter's exclusive mutation
precondition is necessary because external writes to the embedded pool would
bypass its links/version. This is ordinary C discipline, not a hidden static
ownership guarantee or a concurrent container.
