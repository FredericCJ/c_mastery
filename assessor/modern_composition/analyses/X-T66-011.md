# Five-resource recovery analysis

The original nonfailing owner cleanup cannot represent external release
failure. `McRecovery` has two ownership slots, never two copies of one owner:
current is externally published; pending is inaccessible to the consumer but
must remain reachable until recovery completes. On precommit open failure,
pending is the staged owner. After commit, pending is the old owner. This
distinction explains why cleanup-pending and committed are independent bits.

The resource mask changes only after a close outcome proves release. Retained
failure preserves its bit and makes retry legal; released-with-error clears
the bit while incrementing diagnostics. Retrying a Linux descriptor after a
reported close error can close an unrelated reused descriptor. A portable
adapter needs platform-specific outcome semantics, especially EINTR; do not
infer them from ISO C or from this Linux port.

Three cells remain held until the final external release. This is conservative
but gives a simple invariant: any pending resource is described by a complete
live owner record. Peak6 cells/4 resources fits the real eight-block allocator.
The fixture's12 rows independently distinguish an allocation prefix from a
resource-open prefix. With second-open failure and retained cleanup, current
sum stays5, pending owns3 cells/1 resource, and total live counts are6/3.
On successful replacement plus retained retirement, current sum is16 and live
counts are6/4. Neither state is a storage leak while the recovery record remains
reachable. Discarding that record is a leak and violates the API precondition.

Generation rejection reserves one final retirement token. A version that
allows commit at UINT32_MAX can create a live owner that can never be retired.
The test at MAX-1 detects this without billions of operations. Repeated or stale
tokens must preserve the caller's diagnostic output and make no close call.

The two compiled controls erase retained ownership or retry an already released
identity. The harness fails explicit accounting assertions; it does not need
to close an unrelated real descriptor to show the defect. `/dev/null` open/close
are real host operations, but fault outcomes are injected around them. No
filesystem error, durable commit, hardware reset or independent learner result
is claimed. For delayed assessment, withhold a different ordered close-outcome
trace until the learner seals the commit/recovery state graph.
