# Assessor analysis: PR-T61-01

A checked operation needs both a successful arithmetic result and a failure contract. Proving only the success branch can hide output corruption on rejection. Solver bitvectors and mathematical integers must be related explicitly.

Derive the pre-add inequality without executing overflowing signed arithmetic. Prove unchanged output on failure as a separate postcondition and identify pointer validity assumptions.

The reference implementation is in `core.c`; inspect it together with the public test. The named fault is: Repair wrapping arithmetic that reports success and a harness that assumes away every overflow input. Demonstrate a witness satisfying the assumptions and violating the mutant.

Require the learner to derive 0 from the fixture inputs independently. The arithmetic bound is b<=MAX-a when both operands are unsigned and valid.

Transfer answer obligations: Generalize to checked multiplication and mixed-width conversion, deriving a new precondition rather than mechanically substituting the addition predicate.

Actual solver version/commands/results, reachable assumption witnesses, complete-unwinding evidence and bounded fuzz campaign logs remain distinct requirements; missing tools do not become successful proof.
