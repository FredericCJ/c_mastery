# Assessor analysis: PR-T60-04

An IR makes ownership, stack effects and failure behavior inspectable between parsing and machine code. It is not just an opcode list: a consumer needs bounded storage, valid operands and a terminal result convention.

Associate every opcode with input/output type and stack effect; prove validated execution cannot underflow/overflow its bounded stack and returns the expression denotation.

The reference implementation is in `core.c`; inspect it together with the public test. The named fault is: A nominal interpreter reports success without publishing the computed result, while another executes malformed IR before checking its stack effects.

Require the learner to derive 11 from the fixture inputs independently. Use one arithmetic semantic function and separately compare it with a mathematical oracle.

Transfer answer obligations: Add basic blocks and conditional branches; derive join-state type/stack compatibility and bound or explicitly budget loops before extending execution.

Execute emitted x86-64 code against an independently compiled C oracle, execute Thumb output in a dedicated emulator, and complete changed-condition extensions. Public IR anchors do not certify a general C compiler.
