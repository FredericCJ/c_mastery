# PR-T21-04: Correlatable fault record and recovery boundary

## Contract

Implement a bounded fault-record encoder/decoder with format version, build identity, operation/state fields and a simple declared checksum. Reject corruption and incompatible format/build identity before using diagnostic fields. Define collection storage assumptions separately from a recovery procedure, which must reinitialize and validate state under the selected fault model.

The declared profile **C** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 6 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

The fixture record bytes [1,4,9,2] use additive modulo-256 checksum 16. The supplied checksum 16 is accepted; 17 is rejected. Expected build identity is 4, so a record identity 5 is stale. The checksum detects these specified corruptions, not every possible corruption.

## Steps

Specify byte layout and reset/persistence assumptions. Implement explicit serialization, decoder validation and matching-build symbol correlation in the dossier. Inject partial/corrupt/stale records. Design a recovery action that starts from a known initialized state and verify its required invariants independently from successful decoding.

Retain corruption/build-correlation tests and recovery evidence explicitly separated from collection. ## Failure cases

Never treat a checksum as cryptographic integrity or a complete corruption detector. Do not symbolize with mismatched debug artifacts. Persistent-storage atomicity needs actual platform evidence at the later hardware integration, while the current byte model remains synthetic.

## Acceptance and evidence

Submit exact codec vectors, corruption/version/build rejection and a recovery test plan/result for the declared environment. Explain what the record can diagnose and what it cannot prove about safe continuation.

Record contract, build/dependency evidence, independent cases, minimized failures and the specific evidence file for every linked objective. A passing synthetic oracle does not establish a passing implementation. Use {ref}`guide-assessment` for the review gate.

## Hints and recovery

Keep collection minimal and bounded; use a separate richer decoder in the hosted harness. Mark invalid records without trusting their length fields.

If stuck, separate the violated contract from the observed symptom and reduce the input before changing the implementation. Revisit the linked teaching section and retain the minimized case after repair.
