# PR-T47-10: Crash schedules and adversarial oracles

## Contract

Implement or audit the simulated medium and preserve reproducible schedule identifiers. Run 800 deterministic mixed C operations against an independent 80-key map. For each commit cut record return code, persisted pattern, recovered generation and all application values. Add compound interruption during recovery and distinguish corruption rejection from successful old/new recovery.

Budget 7 implementation and 5 verification hours. Reuse the same engine throughout; previous milestones are not charged again. The public API and original disk format are in the storage laboratory.

## Inputs and expected results

Use [the contract fixture](../../fixtures/storage/PR-T47-10.json) and the actual C tests `storage.crash, storage.checkpoint, storage.recovery, storage.differential`. The image has 67 pages of 4096 bytes; the tree owns 32 logical data pages. The reference transaction changes the complete map from {1:10,2:20} to {1:11,3:30}. Compare whole maps. No fixture asserts physical power-cut durability.

## Progressive execution

The immediate learner gate is `storage.crash`, `storage.checkpoint`, `storage.recovery`, `storage.differential`. The separately named assessor mutation controls require explicit assessor source and are not learner checkpoint prerequisites. Passes cover their finite mechanism only; retain the separate invariant, failure and transfer evidence.

## Steps

1. Predict the state transitions on paper, naming capacities, ownership and the earliest invalid state.
2. Implement this milestone in your external learner workspace; reveal only the next relevant stage of the hint table when blocked.
3. Run the named positive and negative C cases and preserve exact commands, source identity, seed/cut and return codes.
4. Explain one rejected result using the invariant, then repair and rerun the same trigger.
5. Revisit an unfamiliar variation without hints and record separate evidence for T47.10.a, .b and .c.

## Failure cases

Make the oracle accept either individual value independently; show how that weak oracle misses a mixed transaction. Restore a whole-state comparison and kill the deliberately wrong variants.

An unavailable compiler, sanitizer runtime, syscall or device produces unavailable evidence; it never counts as a clean run. A wrong implementation must fail a semantic assertion after successful setup.

## Acceptance and evidence

Deliver the invariant/cost argument for .a, actual C/build/test transcript for .b, and minimized failure plus repaired and delayed transfer results for .c. Include the exact source-reading locator and fault assumptions. A CTest family pass supports its executed cases, not automatic completion of every objective. Use `tools/verify_storage_fixtures.py` for contract-index consistency; it neither compiles your C nor awards runtime mastery.

## Hints and recovery

A crash test needs a semantic oracle and a persistence model. The model maintains stable and pending pages, permits reordering unsynchronized writes and can return an error after partial or complete persistence. The suite walks every write/flush boundary of selected transactions and applies five representative patterns. Its independent key/value oracle checks old/new state, not merely whether opening succeeds. These finite schedules do not enumerate every possible tear offset or pending subset; the ordering proof and measured test coverage have different roles.

The staged laboratory hints separate invariant, observation and repair direction. Keep the original failing image or key sequence and compare it with a clean control.

## Transfer challenge

Add one new partial-persistence subset or tear offset and explain what coverage it adds without claiming exhaustive hardware fault coverage.
