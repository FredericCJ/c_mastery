# PR-T05-02: C99 and C11 capability migration

## Contract

Create isolated migration probes for designated initialization, compound literals, restrict, variadic macros, integer formatting, alignment, generic selection and static assertions. Inventory VLA, inline, atomic and thread support separately. Keep the C17 component baseline; historical modes are comparisons rather than a global restriction.

The declared profile **A** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 8 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

The fixture provides a synthetic feature matrix with required layers language, header, link and runtime. A feature is usable only when all its declared required layers succeed. ## Steps

Write one probe per claim and a shared behavior test for migrated code. Compile strict edition configurations where supported. Inspect any atomic helper dependency and distinguish thread header availability from an executed thread. Record the chosen compiler, target and C library for every matrix row.

- **T05.04:** Port a tiny C90-style record initializer and formatter to C99, adding cases for lifetime, integer formatting and macro invocation. Retain separate compile/link/run evidence for each feature and regressions that preserve the old intended behavior. - **T05.05:** Probe alignment, _Generic and _Static_assert; inventory thread/atomic support and any runtime dependency without claiming a race proof. Retain a capability matrix with language acceptance, headers, linking, runtime and declared limits. For its three original objectives, record separate evidence references: T05.05.a (Study atomics, thread facilities, alignment, generic selection, and assertions.); T05.05.b (Identify optional facilities and implementation support boundaries.); T05.05.c (Distinguish language acceptance from linked-library availability.).

## Failure cases

Unavailable optional facilities must have a fallback or an explicit unsupported configuration. A probe that only parses code cannot claim runtime behavior. Keep restrict examples within valid alias contracts and compound literals within valid lifetimes.

## Acceptance and evidence

Supply exact probe sources, layer results and a C90-to-C99 regression comparison. Explain each C11 feature’s language/runtime boundary and one case where accepted syntax failed to link. If no such actual failure occurs, use the synthetic row as analysis and disclose that distinction.

Record contract, build/dependency evidence, independent cases, minimized failures and the specific evidence file for every linked objective. A passing synthetic oracle does not establish a passing implementation. Use {ref}`guide-assessment` for the review gate.
