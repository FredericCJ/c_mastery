# PR-T18-02: Owner, borrowed view and stable handle

## Contract

Build a fixed-capacity owner/view abstraction with a mutation epoch or generation handle. Caller storage owns the bytes; borrowed views never release them. Define invalidation for mutation, reset and destruction. Add a production-source reading comparison with SQLite result pointers and prepared-statement finalization.

The declared profile **B** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 6 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

The fixture owner starts at generation 4. Handles carry generations 4 and 3; only generation 4 is valid. After reset increments the owner generation to 5, both old handles are stale. Generation wrap/exhaustion needs an explicit application policy rather than modulo reuse.

## Failure cases

A borrowed pointer is never freed by the borrower. An alive owner may still invalidate prior views. Reject stale handles before access and prohibit generation wrap from silently making old handles valid. Shared or weak references require a stated separate protocol.
