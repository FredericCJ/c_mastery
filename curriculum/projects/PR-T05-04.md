# PR-T05-04: C23 probes with a portable fallback

## Contract

Create a versioned capability suite for selected C23 declaration/expression, preprocessing and library facilities. Include nullptr, typeof/inference, object constexpr, _BitInt, an enum/constant-expression case, __VA_OPT__, #embed, attributes, checked arithmetic and bit operations as separately reported probes. Maintain a baseline implementation for one useful operation and compare it with the supported enhancement.

The declared profile **A** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 8 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

The deterministic fixture gives required layers for #embed and checked arithmetic. #embed requires language plus an input artifact; checked arithmetic requires language/header/link/runtime. Missing input or header makes the corresponding row unusable even when language acceptance succeeds. Actual support is measured on installed tools.

The canonical fixture is `fixtures/language/PR-T05-04.json`. Preserve its supplied fields and add independent cases in your dossier. Run `python tools/verify_language_fixtures.py` from the curriculum root to verify the fixture oracle; then test your C component separately.

## Steps

Write positive and negative snippets, save exact embedded input bytes, and record feature macros/documented tests. Add three tiny spelling pairs: _Bool versus bool, _Alignas versus alignas, and two-argument _Static_assert versus static_assert. In strict C17, test underscored forms without the spelling headers and nonunderscored forms with <stdbool.h>, <stdalign.h> and <assert.h>, respectively; repeat nonunderscored forms without those headers as an expected rejection/extension diagnostic. In C23, test both forms without those headers as language spellings. Record whether a spelling is a keyword, header macro or accepted extension rather than inferring authority from acceptance alone. Build strict and explicitly declared extension modes in both compiler families where available. Distinguish compiler, C-library and target limits; record unavailable installations honestly. Compare overflow/failure behavior with the baseline.

Retain per-facility source, configuration, header/spelling distinction, expected constraints and actual compile/link/run results. For its three original objectives, record separate evidence references: T05.07.a (Investigate nullptr, typeof forms, inference, and constexpr object declarations.); T05.07.b (Analyze _BitInt, enum changes, and updated constant-expression facilities.); T05.07.c (Contrast C semantics with similarly named C++ constructs.).

Retain versioned capability tests, fallback behavior and a migration comparison with explicit extension use. For its three original objectives, record separate evidence references: T05.09.a (Use edition macros and documented capability tests.); T05.09.b (Test strict and extension dialects in both compiler families.); T05.09.c (Keep unsupported facilities behind explicit portability boundaries.).

## Failure cases

No mode flag or nominal probe certifies full C23. Do not import C++ constexpr semantics. Unsupported facilities are isolated behind an explicit selection boundary. Freestanding requirements are analyzed separately from hosted header availability.

## Acceptance and evidence
