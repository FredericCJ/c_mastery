## Contract

Extend the [T34 PMU ledger](PR-T34-05.md) for one reused kernel. Record a bounded permitted per-process observation, exact events, user/kernel scope and enabled/running values. Reuse its launch/result infrastructure. No global perf_event_paranoid change, new privilege grant or fabricated successful count is required. A denied or unsupported attempt completes the core observation boundary when accompanied by source-backed interpretation and the finite certificate.

Use 5 hours implementation and 3 verification. Prefer a co-scheduled instructions/cycles group when supported; preserve individual group identities and count-time fields. A hardware-event denominator or generic cache event cannot be assumed portable.

## Inputs and expected results

[The fixture](../../fixtures/performance/PR-T43-09.json) records raw instructions 1200 and cycles 3000 with enabled 20/running 10. Scaled estimates are 2400 and 6000 and co-scheduled CPI is 2.5. If running is zero, scaling is undefined. Denied or unsupported events are unavailable, not zero executed instructions. Equal numeric fields with different group identities do not justify a CPI ratio.

Scaling extrapolates the observed interval to the enabled window. It does not recover unobserved phases of a nonstationary workload. CPU_CYCLES may track frequency while reference-cycle support/meaning are target dependent.

## Steps

1. Freeze target CPU/core, kernel, perf/tool version, binary hash, flags, event spellings and permitted scope. Record the actual attempt and failure diagnostics if unavailable.

2. Capture raw grouped result fields and validate 0≤running≤enabled. Scale only positive running intervals; keep estimates distinct from raw counts.

3. Contrast instructions/branches/cache or sample attribution with the cost contract on the same workload. Verify target-specific event meaning if using an event beyond the inspected generalized definitions; otherwise keep that extension unassigned.

4. Compare one nonstationary phase with the whole-run estimate and explain why multiplexing and profiling overhead can change the interpretation.

## Failure cases

Reject impossible times, mixed group/scope ratios and unavailable counts disguised as zeros. An enabled interval with no running time supplies no estimate. Sampling attribution can differ from causal work ownership; the task makes no precise-skid claim. Container policy may deny access even when upstream paranoid documentation describes a permitted class.

## Acceptance and evidence

For .a provide identity/scope plus permitted or denied actual evidence. For .b supply raw fields, scale arithmetic, positive/zero-running and mismatched-group results. For .c relate one usable observed event to work or give an explicit unsupported-event explanation, and analyze nonstationarity/overhead. The oracle checks synthetic count/time semantics only; a captured fixture never proves this host has a PMU or that its cache-event definition is a load count.

## Hints and recovery

Begin with a small number of supported events; more events can increase multiplexing. Preserve group leader/member identity rather than dividing unrelated report lines. If tool output hides raw values, keep the original output and use a supported interface/report mode; do not reverse-engineer an exact raw count from a rounded estimate.
