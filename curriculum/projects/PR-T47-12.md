# PR-T47-12: VM and kernel storage boundaries

## Contract

Connect the VM host adapter or educational-kernel block adapter to the existing store, without copying its implementation. Execute a store operation, restart, recover and read the result through the same application boundary. Inject an indeterminate commit and propagate an application error; do not blindly retry. Record whether the actual kernel/VM route ran or remains not-run.

Budget 4 implementation and 2 verification hours. Reuse the same engine throughout; previous milestones are not charged again. The public API and original disk format are in the storage laboratory.

## Inputs and expected results

Use [the contract fixture](../../fixtures/storage/PR-T47-12.json) and the actual C tests `storage.vm`. The image has 67 pages of 4096 bytes; the tree owns 32 logical data pages. The reference transaction changes the complete map from {1:10,2:20} to {1:11,3:30}. Compare whole maps. No fixture asserts physical power-cut durability.

## Progressive execution

The immediate learner gate is `storage.vm`. Passes cover their finite mechanism only; retain the separate invariant, failure and transfer evidence.

## Steps

1. Predict the state transitions on paper, naming capacities, ownership and the earliest invalid state.
2. Implement this milestone in your external learner workspace; reveal only the next relevant stage of the hint table when blocked.
3. Run the named positive and negative C cases and preserve exact commands, source identity, seed/cut and return codes.
4. Explain one rejected result using the invariant, then repair and rerun the same trigger.
5. Revisit an unfamiliar variation without hints and record separate evidence for T47.12.a, .b and .c.

## Failure cases

Return success from a host service after failed commit publication, or omit a kernel flush. Reproduce why application completion and device completion are separate events.

An unavailable compiler, sanitizer runtime, syscall or device produces unavailable evidence; it never counts as a clean run. A wrong implementation must fail a semantic assertion after successful setup.

## Acceptance and evidence

Deliver the invariant/cost argument for .a, actual C/build/test transcript for .b, and minimized failure plus repaired and delayed transfer results for .c. Include the exact source-reading locator and fault assumptions. A CTest family pass supports its executed cases, not automatic completion of every objective. Use `tools/verify_storage_fixtures.py` for contract-index consistency; it neither compiles your C nor awards runtime mastery.

## Hints and recovery

The VM may invoke two narrow host services: encode an integer under vm-result and read it back. Host-call budget, storage capacity and persistence outcome are independent contracts. No arbitrary pointer or path crosses the bytecode interface. The kernel adapter exposes complete page read/write and flush operations for an exclusive image slice; it validates user buffers and device completion. Reusing the store core preserves its invariants only when the new adapter satisfies the same durability model. Component success does not automatically certify the VM or device integration.

The staged laboratory hints separate invariant, observation and repair direction. Keep the original failing image or key sequence and compare it with a clean control.

## Transfer challenge

Design a bounded transaction identifier for safe application reconciliation and state the new persistence obligation.
