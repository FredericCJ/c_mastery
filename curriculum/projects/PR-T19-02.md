# PR-T19-02: Generic storage and tagged result variants

## Contract

Build a fixed-capacity component in three small interface forms: a concrete typed wrapper, a void-pointer core with explicit size/alignment/lifecycle callbacks, and a generated or _Generic facade. Add a tagged integer/text/error result that validates discriminants and text lifetime. The goal is a contract comparison, not a full general-purpose container library.

The declared profile **C** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 8 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

The fixture variants integer 7, text abc and error -2 serialize to int:7, text:abc and error:-2. Tag unknown is rejected. Text is a borrowed length-bounded view in the learner API; the fixture strings are synthetic values with stable Python ownership.

## Steps

Define element copy/destruction and borrowed-text obligations. Implement one small operation in each generic form and compare compile-time diagnostics, runtime indirection and alignment checks. Add exhaustive variant handling and conversion that returns a valid error alternative rather than reinterpreting payload bytes.

For its three original objectives, record separate evidence references: T19.05.a (Represent alternatives with an explicit discriminant.); T19.05.b (Validate tag/payload consistency and exhaustive handling.); T19.05.c (Implement conversion and error variants without unsafe reinterpretation.).

## Failure cases

Invalid tags, element alignment or lifecycle callbacks are rejected before mutation. Failed construction releases only completed elements. Do not assume _Generic performs lazy semantic checking or that void * supplies type/lifetime safety.

## Acceptance and evidence

Submit equivalent-operation tests, variant output checks, negative type/tag cases and a resource/code-size comparison. Explain why the selected facade fits the caller and how its element ownership is enforced.

Record contract, build/dependency evidence, independent cases, minimized failures and the specific evidence file for every linked objective. A passing synthetic oracle does not establish a passing implementation. Use {ref}`guide-assessment` for the review gate.

## Hints and recovery

Use one integer and one small record type. Keep tag validation at the public boundary and switch exhaustively internally.

If stuck, separate the violated contract from the observed symptom and reduce the input before changing the implementation. Revisit the linked teaching section and retain the minimized case after repair.
