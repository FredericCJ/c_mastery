## Contract

Exercise aggregate copy/initialization, wide arithmetic, non-native atomics and verification instrumentation across declared compilers/optimizations. Inventory emitted helper requirements before and after linking. Choose linked, supplied or excluded support for each; sanitizer-only dependencies cannot enter production claims silently.

## Inputs and expected results

Load [`fixtures/systems/PR-T11-02.json`](../../fixtures/systems/PR-T11-02.json). Its `input` and `expected` define an exact synthetic case, not an observation from a real compiler, filesystem, board or concurrent run. Run `python tools/verify_systems_fixtures.py` from the curriculum root to recompute all declared fields. Keep input immutable for the reference comparison; store observed outputs separately. The fixture is one anchor, not exhaustive acceptance coverage.

## Steps

1. Write the operation/state/effects contract and predict the fixture result by hand.
2. Establish the smallest supported positive case and record environment/provenance.

- **T11.03:** Compile several fixed-size aggregate operations and inspect objects and LTO images for helper requirements.
- **T11.04:** Inspect a wide division and conversion on one instruction-rich and one constrained target.
- **T11.05:** Compare atomic and instrumented objects against production allowlists.

3. Add boundary and deliberate-failure cases before broadening the implementation.
4. Minimize each disagreement and retain the earliest broken invariant.

## Failure cases

- Challenge the mistaken claim: A source-level call census is a complete binary dependency audit. Preserve a minimal failing trace or explain the valid precondition that excludes it.
- Challenge the mistaken claim: Arithmetic expressions are always dependency-free. Preserve a minimal failing trace or explain the valid precondition that excludes it.
- Challenge the mistaken claim: Passing an instrumented build proves the production image has identical dependencies. Preserve a minimal failing trace or explain the valid precondition that excludes it.

Exercise empty/singleton or zero-progress states where the operation admits them, exact capacity, one beyond capacity, repeated completion/cleanup and a deliberately invalid precondition. For storage-owning work, inject acquisition failures and verify unchanged old ownership. For build/binary/source studies, inject a wrong edge, symbol, width, target assumption or unsupported environment and require a visible failure verdict. Never execute malformed pointers or privileged instructions just to demonstrate a negative case. Apply these cases to the declared operation; document any inapplicable case and its reason.

## Hints and recovery

Inspect objects before link-time resolution, then inspect the final map. An atomic operation may compile successfully while requiring a runtime helper that is unavailable or locking on the target.

Before changing the target, determine whether the disagreement is its semantics, an invalid test precondition, a boundary mismatch or an environment limitation. If the fixture oracle fails, stop and repair the fixture/oracle independently; do not change expected data to fit the target. Return to the named prerequisite module when ownership, width or ordering assumptions are missing.
