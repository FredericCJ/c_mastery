# PR-T45-01: Prediction and controlled observation contract

## Contract

Reuse the T32 test/supervisor harness for one small learner-owned extent or lifetime defect and its repaired version. Define a detection matrix for native assertions, ASan/UBSan, unsanitized Memcheck and any optional initialization/leak tool. Record monitored invariant, path, build/options, symbols, setup success and actual observation. Run negative and repaired variants separately under identical declared inputs. A report supports detection on that exercised trial; silence on a faulty trial is inconclusive. A repaired trial needs both semantic checks and the declared observation. No universal safety verdict is published.

## Inputs and expected results

The fixture has six synthetic manifests: reported/silent negative trials, silent/reported repair trials and two unavailable/failed setups. Expected dispositions are detected_this_trial, inconclusive, supports_this_trial, repair_failed, no_observation, no_observation. Exactly four manifests supply observations; universal_safety_proven remains false. These synthetic labels are not tool logs. Supply your own actual logs and classify them by this policy.

The supplied finite fixture is [fixtures/memory_lab/PR-T45-01.json](../../fixtures/memory_lab/PR-T45-01.json). Run `python tools/verify_memory_lab_fixtures.py` from the handbook source root for arithmetic/history/catalog checks. Actual C/tool/hardware evidence remains a separate learner obligation.

## Steps

1. Write the prediction and build the normal assertion-based control first.
2. Use one original owned defect with a minimum trigger. Record exact compile and link commands; retain a matching debug image.
3. Run native, ASan/UBSan and separate unsanitized Memcheck trials in supervised child processes. Confirm setup and bounded termination before interpreting the target.
4. Repair the violated contract without changing the input or oracle; repeat and compare semantic state, diagnostics and setup.
5. Explain a silent negative path or explicitly leave the missing observation open. Save a reproducible dossier template for the next milestones.

## Failure cases

Test a real reported negative, a valid repaired control, a deliberately failing semantic assertion and a setup failure. Never label an unsupported tool as successful absence of a defect. A later crash address, exact diagnostic wording or arbitrary UB return value is not a portable expected result.

## Acceptance and evidence

Deliver the completed coverage matrix, minimum trigger, original and repaired build identities, actual bounded logs, semantic check and open-claim list. Explain every fixture disposition independently. The reviewer must be able to reproduce one negative/repaired pair and distinguish unavailable evidence from silent faulty behavior. This project establishes the process; later projects supply each distinct mechanism.

## Hints and recovery

If both controls look identical, first inspect optimization, whether the relevant access survived compilation, runtime/link dependencies and whether the path actually ran. Use selected T32 instrumentation and regression leaves. Keep instrumentation overhead separate from native resource predictions.

## Transfer challenge

Change one tool setting or an exercised path. Predict how detection coverage changes before observing, and explain why the resulting log does not prove all memory accesses safe.

Use {ref}`guide-assessment` for criterion-specific remediation and {ref}`guide-laboratory` for environment evidence. Preserve the original fixture and minimum failing input; do not edit expected data to fit the target.
