# PR-T18-01: Transactional bounded-view API

## Contract

Implement a bounded byte-view append API with explicit units, capacity, aliasing and output-state rules. Success appends exactly the supplied bytes; insufficient capacity or forbidden overlap leaves content and logical length unchanged. Return a distinct status and valid length so that zero-length success cannot collide with an error sentinel.

The declared profile **C** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 8 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

The fixture has initial bytes [1,2], appended bytes [3,4] and capacities 3 and 4. Expected results are rejected/unchanged [1,2] at capacity 3 and success [1,2,3,4] at capacity 4. The fixture assumes disjoint logical inputs; overlap policy is tested separately by the learner.

## Failure cases

Reject invalid length/capacity relationships and forbidden overlap before mutation. Do not use a sentinel that collides with a valid zero result. Disabled assertions must not remove validation or argument evaluation required by the API.

## Acceptance and evidence
