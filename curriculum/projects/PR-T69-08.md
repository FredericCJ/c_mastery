# PR-T69-08: Opaque modules with explicit service injection and failure effects

## Contract

Implement an opaque DSModule factory backed by two actual typed instances and a borrowed DSService read operation. twice performs two reads then checked addition; publication is atomic but external read effects are not rolled back. Add an instance-local service dictionary containing clock and sink dependencies, passing only the required subset to each operation. Build a second implementation behind the same incomplete public type contract and test clients without private-header access.

The full required exercise is {ref}`X-T69-008`; its shared contracts, D1–D4, objective-specific rubric and delayed variant are part of this project. Eight hours is descriptive accounting, not a ceiling on required work.

## Failure cases

Hiding a struct definition narrows ordinary client access, but does not manage callback lifetime or make external effects transactional. Dependency injection should expose the actual retained services. Use a scripted service with explicit read values/statuses and compare full call trace plus output. Test maximum two live instances, close/reopen, and accidental use of a closed lease through a separate lifetime-token wrapper; never dereference an ended raw object as a test oracle. ## Hints and recovery

The factory owns the module slot; the service context remains borrowed. A second callback failure cannot undo the first read. An incomplete type pointer and an unnamed concrete return type have different storage and type relationships.
