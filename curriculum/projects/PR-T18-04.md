# PR-T18-04: Execution-context and compatible API evolution

## Contract

Create a versioned synchronous callback API and a separately named deferred adapter. Document allocation, blocking, retention, reentrancy, cancellation and callback-context lifetime. Preserve an earlier consumer through a deliberate compatibility boundary; do not silently change synchronous completion into deferred completion under the same promise.

The declared profile **B** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 8 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

The fixture old contract permits no allocation/blocking/retention and synchronous callbacks. Two candidate revisions are compared: one preserves all those obligations, while one permits retention and changes timing. Expected compatibility is true then false under the declared contract-comparison rule.

## Failure cases

Cancellation requests are not assumed complete until the adapter acknowledges that no callback can use the context. Reject prohibited reentry or make it safe explicitly. Audit transitive callbacks/callees before an allocation-free claim.

## Acceptance and evidence

Submit context/timing traces, versioned headers, independent-consumer evidence and a migration note. Compare source, ABI and ownership compatibility separately. Show one deliberate incompatible revision being isolated instead of hidden.

Record contract, build/dependency evidence, independent cases, minimized failures and the specific evidence file for every linked objective. A passing synthetic oracle does not establish a passing implementation. Use {ref}`guide-assessment` for the review gate.
