# PR-T21-01: Error translation and failure-complete construction

## Contract

Implement a small constructor that acquires three resources through injectable adapters, maps backend failures to stable public errors and rolls back exactly once. Compare early-return/nested cleanup with a narrowly scoped cleanup-label version. Record original cause independently of public classification.

The declared profile **A** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 10 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

The fixture resources are memory, channel and registration; acquisition fails at index 2 before registration is acquired. Expected acquired sequence is [memory,channel], release order [channel,memory] and no live resources. Every other failure index and full success become learner tests.

## Steps

Define error taxonomy/recovery actions. Write acquisition ownership states, implement stage tracking and translation, then inject each failure. Compare two cleanup structures against the same tests. Add repeated init/stop under a documented lifecycle policy and preserve the first cause through cleanup errors.

- **T21.01:** Define an error table for parser, allocator and transport failures with recovery class and context. Retain error/class/action matrix and tests for at least one outcome in each category. For its three original objectives, record separate evidence references: T21.01.a (Separate invalid input, contract violations, resource failures, and hardware faults.); T21.01.b (Define recoverable, retryable, terminal, and degraded outcomes.); T21.01.c (Preserve enough context to identify the original cause.).

- **T21.02:** Implement a bounded error record and backend-to-public mapping with an explicit unknown-error policy. Retain mapping tests, stable public codes and original-cause preservation across propagation. For its three original objectives, record separate evidence references: T21.02.a (Map backend errors into stable component-level results.); T21.02.b (Retain causal context without exposing unstable implementation details.); T21.02.c (Avoid silent information loss and ambiguous success codes.).

- **T21.03:** Inject failure after each of three acquisitions and check remaining ownership after rollback. Retain acquisition/rollback traces and repeated-init/cleanup tests. For its three original objectives, record separate evidence references: T21.03.a (Track resource acquisition order and completed initialization stages.); T21.03.b (Roll back safely after every possible failure point.); T21.03.c (Test repeated initialization and cleanup under injected failures.).

- **T21.04:** Implement the same small acquisition sequence with two cleanup structures and compare reviewability. Retain exactly-once release proof, failure-point tests and a justified style choice. ## Failure cases

A cleanup error must not erase the original construction failure. Release only acquired resources and do not publish an active object on partial construction. Unknown backend codes map deliberately, while internal contract violations remain distinguishable from expected exhaustion.

## Acceptance and evidence

Submit all failure-point traces, public/backend mapping, release counts and a cleanup-style decision. Test repeated cleanup and show stable consumer errors without exposing volatile backend details as the public ABI.

Record contract, build/dependency evidence, independent cases, minimized failures and the specific evidence file for every linked objective. A passing synthetic oracle does not establish a passing implementation. Use {ref}`guide-assessment` for the review gate.
