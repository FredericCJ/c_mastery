# PR-T66-06: Strong and weak ownership with atomic and non-atomic counts

## Contract

Implement the OwShared and OwAtomicShared APIs under the exact strong/weak contract. Initialize strong1,weak1; weak includes one implicit reference while the value is alive. Retain requires a live owned strong reference; downgrade creates an explicit weak reference. Upgrade from an owned weak reference atomically increments a nonzero strong count or returns `DEAD`. Reject count overflow. Last strong release destroys the value exactly once then removes the implicit weak; last weak reclaims the control exactly once. The non-atomic version requires exclusion. The atomic version uses declared acquire/release reasoning, and each drop requires an actually owned reference; double-drop is not an admitted racing input.

The full required exercise {ref}`X-T66-006`, its shared contracts and objective rubric are part of this project. Eight hours is descriptive author accounting, not a learner-time or scope ceiling.

## Inputs and expected results

Downgrade, retain, drop, drop yields strong0,weak1, one value destruction and no control reclamation. Upgrade now fails `DEAD`. Dropping the remaining weak reclaims the control once. Four threads each retain/drop5000 times while holding their own strong reference; after all owned strong references end, destruction occurs once, and a retained weak keeps the control available for a failed upgrade.

## Steps

- **T66.06:** Implement strong/weak ownership twice, first under exclusion and then with C17 atomics, documenting initialization publication, owned-reference preconditions, callback effects and each memory-order edge. Submit the exercise D1–D4 and retain prerequisite interfaces.

## Failure cases

Trace every strong/weak boundary with an independent counter model, test maximum-count refusal, and reject omission of the implicit weak release. Run the actual four-thread anchor, separate TSan if available, GCC/Clang optimized and ASan/UBSan builds, inspect atomic lowering and report lock-free status. A quiet ThreadSanitizer run does not prove the memory-order argument or reclaim safety for fabricated references.

## Acceptance and evidence

- **T66.06:** Prove the distinct value/control lifetimes, no-resurrection property and count-overflow behavior; distinguish reference-count synchronization from pointee synchronization and cycle collection. Every leaf has a separate rubric criterion in X-T66-006. Public test passage alone does not assess independent understanding.

## Hints and recovery

The implicit weak keeps the control alive until value destruction finishes. Then Increment only a nonzero strong count; zero is terminal for that value. Record the failed hypothesis before using further hints.

## Transfer challenge

Construct a two-node strong cycle and show retained values after external owners disappear; break one edge with a weak reference and account for both control blocks. Delayed assessment executes the last strong drop concurrently with weak upgrade using a synchronized start and a live weak owner: outcomes are successful ownership before destruction or `DEAD`, never resurrection.
