# PR-T47-09: Recovery and repeated interruption

## Contract

Implement reopen, generation selection, batch validation, replay and cleanup. Repeatedly crash recovery at each write/flush boundary and reopen again. Validate tree order, occupancy, reachability, allocation and complete application values after recovery. Preserve the failure image for diagnosis rather than rewriting it with a fresh format.

Budget 5 implementation and 3 verification hours. Reuse the same engine throughout; previous milestones are not charged again. The public API and original disk format are in the storage laboratory.

## Failure cases

Corrupt one committed WAL image while leaving a valid marker; reject the image before any home write. Fail a recovery read or flush and keep the handle unusable.

An unavailable compiler, sanitizer runtime, syscall or device produces unavailable evidence; it never counts as a clean run. A wrong implementation must fail a semantic assertion after successful setup.

## Hints and recovery

Recovery is a state machine that may itself fail. A valid newer marker names a complete after-image batch; every image is checked before the first home write. Full-page replacement is idempotent, so a second crash during replay can restart from intact log evidence. Generation mismatches, corrupted committed images and I/O failure are errors. Invalid incomplete marker bytes before any home writes can be ignored under the declared ordering model. Corruption after acknowledged persistence is a different fault class and must not be turned into an old-or-new success claim.

The staged laboratory hints separate invariant, observation and repair direction. Keep the original failing image or key sequence and compare it with a clean control.

## Transfer challenge

Explain why replaying set-page-to-image is idempotent while increment-page-counter is not.
