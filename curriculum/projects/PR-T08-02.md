## Contract

Build scalar and aggregate call boundaries with layout manifests. Demonstrate caller/callee preservation, hidden result storage where used, stack alignment and one optimization-dependent frame change. Reject a deliberately incompatible object interface before deployment; source compatibility and binary compatibility receive separate verdicts.

## Steps

1. Write the operation/state/effects contract and predict the fixture result by hand.

2. Establish the smallest supported positive case and record environment/provenance.

3. Add boundary and deliberate-failure cases before broadening the implementation.

4. Minimize each disagreement and retain the earliest broken invariant.

## Failure cases

- Challenge the mistaken claim: C source parameter order completely describes the machine call. Preserve a minimal failing trace or explain the valid precondition that excludes it.

- Challenge the mistaken claim: Source-level local sizes equal total frame size. Preserve a minimal failing trace or explain the valid precondition that excludes it.

- Challenge the mistaken claim: Equal sizeof values prove compatible layout. Preserve a minimal failing trace or explain the valid precondition that excludes it.

Exercise empty/singleton or zero-progress states where the operation admits them, exact capacity, one beyond capacity, repeated completion/cleanup and a deliberately invalid precondition. For storage-owning work, inject acquisition failures and verify unchanged old ownership. For build/binary/source studies, inject a wrong edge, symbol, width, target assumption or unsupported environment and require a visible failure verdict. Never execute malformed pointers or privileged instructions just to demonstrate a negative case. Apply these cases to the declared operation; document any inapplicable case and its reason.

## Hints and recovery

Start from one scalar call and add one aggregate. Inspect both caller and callee; a hidden result pointer changes the boundary even when the source-level parameter list looks unchanged.

Before changing the target, determine whether the disagreement is its semantics, an invalid test precondition, a boundary mismatch or an environment limitation. If the fixture oracle fails, stop and repair the fixture/oracle independently; do not change expected data to fit the target. Return to the named prerequisite module when ownership, width or ordering assumptions are missing.
