## Contract

Complete a physical CAN FD exchange between the Cortex-M4 external-controller route and an independent compatible FD peer. Reuse the validated controller boundary from PR-T38-11. Record nominal/data phase rates, transceiver topology, termination, clock assumptions and actual captures. Choose rates supported by every device and the measured wiring; a advertised maximum is not the lab configuration.

This milestone budgets six hours implementation and four hours verification. Equipment acquisition is an entry prerequisite. Readings are budgeted separately in T38.

## Inputs and expected results

Replay the prior metadata fixture with `python tools/verify_communications_fixtures.py`; its mathematical expectations establish only the shared software input contract. Actual electrical values and device responses must come from the recorded configuration and raw measurements. Use the inspected source scope R-V2-COM-MCP2518FD-B for the block/power boundary, then inspect exact implementation passages for the selected board.

## Steps

1. Predict valid DLC/payload pairs using PR-T38-10. Send zero, eight, twelve and sixty-four-byte payloads with sequence and end-to-end check fields.
2. Capture both no-BRS and BRS-enabled traffic. Identify arbitration and data phases, acknowledgement, retransmission and the observation point of software timestamps.
3. Exercise missing peer acknowledgement, filter rejection and bounded software queue exhaustion. Record counters, timeout and recovery behavior without using successful metadata validation as a wire-level verdict.
4. Repeat with a changed data-phase rate and a fresh payload generated by the independent peer. Compare intended and observed values and account for capture resolution.

## Failure cases

Incorrect supply/logic domains, stale interrupt status, impossible DLC/length, missing peer, wrong timing, buffer exhaustion and a timeout without a documented reset/recovery state. Explain which boundary detects each failure and preserves ownership.

## Acceptance and evidence

Reject missing ACK, wrong sequence or payload, unbounded retry and absent raw captures. Full closure needs peer receive evidence plus a physical capture and measured configuration; virtual CAN and internal loopback leave this claim not-run. Follow {ref}`guide-physical-evidence`. Preserve source/build identity, setup photograph or schematic, instrument configuration, raw capture, interpretation and a changed-condition repeat. Automated family tests do not close this milestone.

## Hints and recovery

First validate the lowest failed boundary: power and clock, then SPI command/response, controller state, transceiver and peer. Save the first contradictory observation before changing configuration. A known-good peer helps localize a fault but does not replace the learner driver.

## Transfer challenge

Explain the evidence that would need to be repeated after changing the oscillator or transceiver. Repeat one relevant measurement with the changed condition and preserve the earlier result for comparison.
