# PR-T03-01: Lifetime and aligned-storage atlas

## Contract

Create a memory atlas for three records stored automatically, statically and dynamically, plus a separately analyzed thread-storage record. Each observation names its object and lifetime. Implement an aligned caller-storage wrapper for one complete type and record object bytes through character access. The atlas is an experiment, not a claim that every host shares the measured layout.

The declared profile **A** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 8 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

Synthetic offsets 0, 1, 7 and 8 with alignment 8 require padding [0, 7, 1, 0]. The fixture checks arithmetic independently of host addresses. Learner measurements add sizeof, _Alignof, member offsets and member values for the actual target.

The canonical fixture is `fixtures/language/PR-T03-01.json`. Preserve its supplied fields and add independent cases in your dossier. Run `python tools/verify_language_fixtures.py` from the curriculum root to verify the fixture oracle; then test your C component separately.

## Steps

Draw creation/destruction timelines first. Compare member equality with representation equality, marking padding. Compute checked alignment padding, verify the target’s actual requirements and exercise rejection of insufficient capacity. Replace an escaped automatic pointer with a caller-owned destination.

- **T03.01:** Draw owner/view timelines for an escaped local, a thread-local object and an allocated buffer; replace the escaped local with caller storage. Retain timelines naming creation, legal uses and invalidation, plus a repaired interface with a stated owner. For its three original objectives, record separate evidence references: T03.01.a (Distinguish automatic, static, thread, and allocated storage duration.); T03.01.b (Track when objects begin and cease to exist.); T03.01.c (Find escaped pointers to expired local and temporary objects.).

- **T03.02:** Inspect a structure through unsigned char, compare its members separately and mark which bytes the layout leaves unspecified. Retain a field-wise equality check, byte observations labeled implementation-specific and a list of conclusions the bytes cannot support. For its three original objectives, record separate evidence references: T03.02.a (Inspect bytes without assuming every bit is value-bearing.); T03.02.b (Analyze padding, representation-dependent values, and edition-sensitive rules.); T03.02.c (Separate equality of values from equality of object representations.).

- **T03.03:** Compute alignment padding for synthetic addresses and implement a caller-storage interface that rejects insufficiently aligned storage using a target-documented check. Retain checked padding arithmetic, alignment requirements from the compiler and negative placement cases without invalid dereferences. For its three original objectives, record separate evidence references: T03.03.a (Derive alignment requirements for objects and array elements.); T03.03.b (Detect invalid casts from insufficiently aligned storage.); T03.03.c (Design portable alignment checks and aligned-storage interfaces.).

## Failure cases

No deliberately misaligned dereference is executed. Reject size overflow before computing the placement. Never inspect an object after its lifetime ends. Record thread lifetime as an analysis unless a declared thread harness is actually used.

## Acceptance and evidence

Supply timelines, a synthetic padding derivation, actual layout observations and a field-wise equality test. Show that storage capacity and alignment are independently checked. Label every byte-layout conclusion by implementation and edition.

Record contract, build/dependency evidence, independent cases, minimized failures and the specific evidence file for every linked objective. A passing synthetic oracle does not establish a passing implementation. Use {ref}`guide-assessment` for the review gate.

## Hints and recovery

Use remainder arithmetic rather than an overflowing address-plus-alignment expression. Keep representation dumps in the harness, outside the storage component.

If stuck, separate the violated contract from the observed symptom and reduce the input before changing the implementation. Revisit the linked teaching section and retain the minimized case after repair.

## Transfer challenge

Increase the alignment requirement and show whether the public storage representation still satisfies it.

Attempt the changed condition after a delay without copying the prior solution. Explain which invariant, lifetime, resource or dependency claims survive and which must be revised.
