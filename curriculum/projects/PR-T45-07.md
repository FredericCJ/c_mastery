# PR-T45-07: Resize, stale alias and release repair

## Contract

Repair a nonzero resize wrapper with explicit owner/borrow rules. Validate size first; store the result temporarily; on injected refusal preserve the old owner, size and contents. A successful resize publishes only the returned owner and invalidates every old derived alias, even when a model address token is reused. Extra grown bytes are initialized before publishing them as valid payload. The harness uses a declared refusing allocation adapter before a real call to exercise deterministic failure; this is not a claimed observed kernel/allocator out-of-memory event. The zero-size resize case is excluded. Faulty free/use experiments are isolated hosted own-program controls; the repaired path never passes an interior, foreign or stale pointer to a C allocator.

## Inputs and expected results

The model begins with generation 1, address 1000, size 8 and bytes 0102030405060708. Refusal preserves these values. Success gives generation 2, size 12, retaining eight bytes with four uninitialized tail bytes; addresses 1000 and 2000 are distinct model success cases and both invalidate generation 1 aliases. Release results cover valid free-null/no-effect, live owner release, repeated release/not-live, interior/not-base, foreign and stale-generation requests. Integer identities are the oracle; no invalid C pointer is inspected to compute these results.

Run `python tools/verify_memory_lab_fixtures.py` from the handbook source root for arithmetic/history/catalog checks. Actual C/tool/hardware evidence remains a separate learner obligation.

## Steps

1. Specify owner, borrow, zero-size exclusion, strong refusal behavior and successful alias invalidation. Save required sizes/contents before the call.

2. Implement the wrapper and adapter with a deterministic refusal point. Test old-owner preservation without calling the native allocator on the refusal path.

3. Exercise native successful nonzero resize and initialized-tail publication. After success use only the returned owner; do not compare or dereference the old pointer, even to discover whether it moved.

4. Drive the integer generation/extent model through failure, changed-address success and reused-address success. Rebuild borrowed references from the new owner under an explicit publication rule.

5. Observe original hosted double/invalid free, use-after-free and escaped-alias defects in separate children, then repair their first lifetime transition.

6. Test exactly-once release and alias expiration on repeated operations. Compare portable semantic results and separate dynamic reports.

## Failure cases

Include refusal, growth, shrink, alias into a subobject, repeated release, foreign allocator ownership and valid free(NULL). Clearing one owner must leave other aliases explicitly invalid. A stale-pointer comparison or diagnostic printf argument is itself an invalid repaired-code use; use saved integer model tokens instead. Do not depend on a particular native allocator address-reuse pattern.

## Acceptance and evidence

Submit before/after owner snapshots on refusal, returned-owner success traces, initialized-tail tests, alias-generation rejection, separate negative/repaired detector evidence and exactly-once cleanup. Show a same-token model case and explain why it gives no C alias-validity guarantee. The injected refusal and actual allocator observation must be separately labeled.

## Hints and recovery

Generation handles are debugging/model evidence, not automatic protection for raw pointers. The book's cleanup choice on failed resize is one policy; this wrapper promises to retain the old allocation, so its failure branch follows that contract. Revisit T03 invalidation and T16 resize without rebuilding the whole allocator.

## Transfer challenge

Resize a container whose saved element borrow points into the old storage. Change failure position and shrink size; demonstrate that every published borrower is rebuilt or denied independently of the numeric address.
