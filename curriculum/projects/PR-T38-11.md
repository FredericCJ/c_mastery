## Contract

Bring up an MCP2518FD external CAN FD controller connected to the existing Cortex-M4 route. Deliver a pin/power/clock ledger, bounded SPI transactions, error propagation and a captured controller identification/loopback transaction. Treat controller initialization and frame storage as a state machine with bounded waits. Keep the prior TCAN4550 synthetic fixture as a comparison; its command framing and supply limits do not describe this controller.

This milestone budgets six hours implementation and four hours verification. Equipment acquisition is an entry prerequisite. Readings are budgeted separately in T38.

## Inputs and expected results

Replay the prior metadata fixture with `python tools/verify_communications_fixtures.py`; its mathematical expectations establish only the shared software input contract. Actual electrical values and device responses must come from the recorded configuration and raw measurements. Use the inspected source scope R-V2-COM-MCP2518FD-B for the block/power boundary, then inspect exact implementation passages for the selected board.

## Steps

1. Record exact board revisions, schematic, oscillator and controller/transceiver revisions. Inspect the exact controller SPI, reset, RAM initialization, FIFO and interrupt passages before assigning register values; record their locators in the dossier.
2. Reuse the inspected SPI primitive with explicit chip-select ownership and timeout/error returns. Separate transport errors, device status and CAN errors.
3. Initialize the selected FIFO/RAM arrangement and verify configuration/readback before entering loopback. Capture the actual SPI command and response bytes.
4. Inject a disconnected controller and a deliberately mismatched mode in the isolated setup. Show bounded failure, then restore the known configuration.

## Failure cases

Incorrect supply/logic domains, stale interrupt status, impossible DLC/length, missing peer, wrong timing, buffer exhaustion and a timeout without a documented reset/recovery state. Explain which boundary detects each failure and preserves ownership.

## Acceptance and evidence

A register read returning all ones is not evidence of a valid device. No completion event before chip-select/transaction ownership is released. A valid internal loopback establishes controller-path behavior; it leaves the wire exchange for PR-T38-12. Follow {ref}`guide-physical-evidence`. Preserve source/build identity, setup photograph or schematic, instrument configuration, raw capture, interpretation and a changed-condition repeat. Automated family tests do not close this milestone.

## Hints and recovery

First validate the lowest failed boundary: power and clock, then SPI command/response, controller state, transceiver and peer. Save the first contradictory observation before changing configuration. A known-good peer helps localize a fault but does not replace the learner driver.

## Transfer challenge

Explain the evidence that would need to be repeated after changing the oscillator or transceiver. Repeat one relevant measurement with the changed condition and preserve the earlier result for comparison.
