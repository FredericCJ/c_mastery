# PR-T18-03: Lifecycle and representation alternatives

## Contract

Implement an object lifecycle in caller storage, with initialization, active use, stop, failure and destruction states. Compare exposed structure, opaque allocated object and caller-owned opaque representation on allocation policy, ABI, debug access and embedding. Choose one representation and publish real size/alignment requirements where needed.

The declared profile **C** applies to the boundary named here; specify harness versus component dependencies in {ref}`guide-profiles`. Budget 8 h for implementation and verification together. Start from your own sources and the listed fixtures, with prior modules as prerequisites; no starter repository or solved program is required.

## Inputs and expected results

The fixture transition table permits new -> active by init, active -> stopped by stop, stopped -> destroyed by destroy, and stopped -> stopped by stop. Starting new, events init, stop, stop, destroy produce active, stopped, stopped, destroyed with no illegal events.

Define legal operations before coding. Add injected failure after each initialization stage and document the failed state. Implement repeated shutdown according to the table. ## Failure cases

Invalid-state operations return a contract-status policy without touching nonexistent resources. Do not guess opaque storage size/alignment. A failed initialization releases only acquired resources; repeated stop must not duplicate release.

## Acceptance and evidence

Submit transition/operation matrix, failure-point release counts, representation alternatives and consumer builds. Demonstrate the chosen ABI/storage boundary and explain how a layout change would affect it.

Record contract, build/dependency evidence, independent cases, minimized failures and the specific evidence file for every linked objective. A passing synthetic oracle does not establish a passing implementation. Use {ref}`guide-assessment` for the review gate.
