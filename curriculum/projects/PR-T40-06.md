## Contract

Implement L5 independent of L4's transfer IDs. Session headers carry type, nonzero session ID, nonzero epoch and checkpoint. OPEN/OPEN_ACK negotiate schema 1, unit 1 and initial holder A; control records use checkpoint 0. DATA uses the next positive checkpoint per direction. Only the current holder sends DATA. A request transfers the token to B, B responds and transfers it back.

On sending TOKEN, enter TOKEN_PENDING and block new DATA until matching transport completion. Receiver changes holder once on complete TOKEN; repeats are idempotent. A lost ACK can pause progress but cannot permit both endpoints to send. Retained RAM stores committed checkpoint, bytes and response; close/reopen precedes wrap.

## Inputs and expected results

The fixture uses a session/epoch, a SET at checkpoint 1, the same DATA again, altered bytes at checkpoint 1, token pending/lost completion, compatible retained resume and peer reboot. Expected effects count is one, the changed duplicate is ERROR, DATA during pending is blocked, retained state resumes and absent state refuses.

Output state/events, token holder, pending flag, per-direction committed checkpoint and application effect count. A successful transport ACK is not by itself compatible negotiation or application authorization.

## Steps

1. Draw negotiation, READY, TOKEN_PENDING, retained-reset, resume-refused and CLOSED transitions.
2. Encode exact OPEN control fields and reject mismatched schema/unit/epoch before DATA delivery.
3. Commit a DATA checkpoint only after accepted upper handling; retain identical bytes and recorded response for duplicate suppression.
4. Lose the token-transfer ACK and attempt DATA at both nodes. Complete/repeat the transfer and prove at most one permission exists.
5. Reset only transport while keeping session RAM, then separately reboot the peer without RAM. Compare RESUME results and cleanup. Correlate session checkpoints with different L4 retry IDs in the log.

## Failure cases

Nonholder DATA, checkpoint skip/wrap, changed payload at the same checkpoint, stale epoch, incompatible unit/schema and rebooted peer state publish no new effect. CLOSE clears session authority; a new epoch cannot inherit an old receipt. An ERROR event may not silently restore token ownership. Neither checkpoint matching nor an epoch field supplies authentication or durable recovery.

## Acceptance and evidence

Submit the state diagram and exact OPEN/DATA/TOKEN/RESUME wire fields, lost-ACK token trace, duplicate effect count and retained-versus-reboot evidence. The three objectives require distinct negotiation/dialogue, checkpoint/effect and resumption-limit witnesses. Show where RAM state disappears and explicitly state that an effect surviving a reboot would need a different durable protocol.

## Hints and recovery

If both nodes appear permitted, inspect sender TOKEN_PENDING rather than inventing an extra timeout transfer. If a duplicate changes state, compare checkpoint plus payload and response before applying. If a reboot resumes, identify where the claimed retained state actually came from.

## Transfer challenge

Consider a power loss immediately after applying SET but before any durable record. Explain why this RAM-only design cannot promise durable exactly-once processing; propose requirements without adding an unverified persistence implementation.

For this milestone, retain three separately labeled evidence items:

- **T40.06.a:** Negotiate schema/units and enforce explicit dialogue-token ownership independently of transport state.
- **T40.06.b:** Use per-direction checkpoints to suppress repeated application effects after a retained-state resume.
- **T40.06.c:** Distinguish successful RAM-state resume from stale epoch, incompatible negotiation and reboot refusal.
