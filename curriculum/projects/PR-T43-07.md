## Contract

Extend the accepted [robust file adapter](PR-T23-02.md) in a temporary directory. Add accepted-byte and phase logs, a bounded scripted retry seam, and separate write-completion versus requested fsync timing. Keep the original short-transfer/error behavior and file-byte checks. Do not build another file-copy subsystem or require cache dropping, root access or a destructive power-loss experiment.

Use 7 hours implementation and 3 verification. The script makes interruptions/partial progress reproducible; native observations are separate. EAGAIN has a bounded readiness/retry policy, not an unbounded busy loop.

## Inputs and expected results

[The fixture](../../fixtures/performance/PR-T43-07.json) requests eight write bytes and returns 3,EINTR,2,EAGAIN,3: five attempts accept exactly eight. Write ends at 8 and successful requested file synchronization at 13; sync span is 5, end-to-end span 13. The separate synthetic device observation is 4096 bytes, giving 512 device bytes per accepted useful byte. File length eight does not imply eight physical bytes.

Other cases preserve three accepted bytes before EIO, stop a zero-progress write, recognize partial-read EOF, and exhaust two EAGAIN attempts. Their results differ even when the returned accepted count is zero. Native short transfers need not match these scripted durations.

## Steps

1. Add a response seam to the existing adapter and record remaining range, positive accepted count, errno policy and attempt limit. Verify output bytes have neither duplication nor gaps.

2. Run bounded native buffered read/write trials on a disposable file, with fixed byte count, consumed checksum and explicit setup/close lifetime. Label repeat-run warmth; do not pretend to know a universally cold cache.

3. Time requested fsync independently and preserve its result. If the requirement covers a newly created directory entry, discuss and, where permitted, observe directory-fd synchronization separately.

4. Reconcile userspace accepted bytes, file logical/allocated size and any available per-device counters. Keep observation scope and delayed-error possibilities in the report.

## Failure cases

A positive transfer consumes only that many remaining bytes. EINTR in this seam means no bytes transferred by that attempt. Stop terminal EIO and preserve progress; a later successful read cannot erase the error. read returning zero is EOF, while this bounded write adapter treats zero as no progress. Successful write alone is not requested durability; successful file fsync does not prove directory-entry synchronization or survival of every failure mode.

## Acceptance and evidence

For .a provide scripted traces and actual final byte checks, including terminal/zero/retry cases. For .b submit separate native buffered and synchronization samples with file lifetime/warm-state protocol. For .c submit file/device/return-boundary reconciliation and the persistence limits. The independent oracle certifies scripted counts and phase arithmetic only. Native fsync success is evidence of the requested OS boundary, not experimental proof of crash/power-loss durability.

## Hints and recovery

Advance the source offset only on positive accepted counts. Keep errno meaningful only for failed return, so stale errno cannot reclassify a success. If a sync duration dominates, report it separately before optimizing the copy loop. If device counters are shared, retain the contamination rather than attributing all bytes to this small file.

## Transfer challenge
