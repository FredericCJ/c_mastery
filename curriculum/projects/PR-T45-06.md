# PR-T45-06: Leak and acquisition-prefix repair

## Contract

Reuse a small T21 resource-owning component with three acquisitions and implement a lifecycle that publishes only after success and releases completed acquisitions in reverse dependency order. The heap harness may call the standard allocator; this project studies ownership, not a second allocator implementation. Track live, peak and retained byte ledgers. Separate a forgotten release, lost owner, indirectly retained child and intentional reachable retention. Preserve the first acquisition cause even if reporting/cleanup also fails. The native leak observation is independent of the finite graph and its conservative roots.

## Inputs and expected results

Resource sizes are 32, 48, 16. Failure before indices 0, 1, 2 yields peak 0, 32, 80; full acquisition yields 96. Cleanup sequences are empty, [0], [1,0], [2,1,0], with zero live resources after cleanup and publication only on full success. In the supplied acyclic graph, A (32 bytes) retains B (16 bytes) without a root, C (24 bytes) has a start root and D (8 bytes) an interior root. Declared classes are definite, indirect, reachable and possible respectively; a retention budget 16 is exceeded by reachable C by 8. These graph categories are a model, not promised Memcheck output.

The supplied finite fixture is [fixtures/memory_lab/PR-T45-06.json](../../fixtures/memory_lab/PR-T45-06.json). Run `python tools/verify_memory_lab_fixtures.py` from the handbook source root for arithmetic/history/catalog checks. Actual C/tool/hardware evidence remains a separate learner obligation.

## Steps

1. Draw the owner and release dependency for each acquisition and identify every publication point.

2. Inject refusal before each acquisition and successful full acquisition. Check reverse cleanup, unchanged externally published state on failure and repeated shutdown under a stated policy.

3. In separate owned child trials omit a release, overwrite the only handle and retain an object too long. Preserve the allocation/event history before relying on a shutdown leak report. Reuse the controlled resize-refusal adapter from PR-T45-07 when studying a lost resize handle; do not provoke uncontrolled system-wide exhaustion.

4. Repair the owner/cleanup policy and repeat every failure prefix and many bounded cycles.

5. Run separately configured Memcheck or supported LSan leak observations; record roots, suppressions, leak kinds and error policy.

6. Compare native reports with semantic live/retained ledgers. Account for caches, retained ownership and allocator/OS effects before interpreting RSS.

## Failure cases

Include failure at every stage, cleanup called after partial initialization, repeated cleanup, reporter failure and a reachable object exceeding its retention budget. An interior pointer is not automatically an owning handle. The finite graph is a declared acyclic graph; native root scanning may classify differently. The minimum trigger and first owner-loss event must remain available.

## Acceptance and evidence

Provide all acquisition/release traces, first-cause context, exactly-once release checks, peak/live/retained byte reports, native negative and repaired observations and the graph classification derivation. A reachable-retention repair must reduce its contract-bound lifetime or document a sufficient budget; suppressing a diagnostic is not the repair.

## Hints and recovery

Keep an acquired-stage ledger rather than only a final initialized flag. Reverse dependency order matters when releasing a parent would destroy the handle needed to release a child. Revisit T21 partial initialization and T16 lifetime architecture selectively. Do not equate all live-at-exit objects with the same application defect.

## Transfer challenge

Add a registration/callback resource whose cleanup can fail after a buffer is acquired. Preserve the first cause, prove no late borrower survives reclamation and recalculate peak and retained bytes.
