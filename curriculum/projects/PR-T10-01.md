## Contract

Decode the synthetic initial-stack schema and inspect one actual process at its entry breakpoint. Inventory startup object families and distinguish e_entry, PT_INTERP, kernel stack construction and C-call conventions. No executable entry is permitted to return through a nonexistent caller frame.

## Inputs and expected results

Load [`fixtures/systems/PR-T10-01.json`](../../fixtures/systems/PR-T10-01.json). Its `input` and `expected` define an exact synthetic case, not an observation from a real compiler, filesystem, board or concurrent run. Run `python tools/verify_systems_fixtures.py` from the curriculum root to recompute all declared fields. Keep input immutable for the reference comparison; store observed outputs separately. The fixture is one anchor, not exhaustive acceptance coverage.

## Steps

1. Write the operation/state/effects contract and predict the fixture result by hand.
2. Establish the smallest supported positive case and record environment/provenance.

- **T10.01:** Trace kernel loader source and inspect PT_INTERP and e_entry in three variants.
- **T10.02:** Decode the declared synthetic stack and inspect a debugger snapshot at entry.
- **T10.03:** Use driver output to inventory entry and initialization objects for each chosen build mode.

3. Add boundary and deliberate-failure cases before broadening the implementation.
4. Minimize each disagreement and retain the earliest broken invariant.

## Failure cases

- Challenge the mistaken claim: _start is called exactly like main. Preserve a minimal failing trace or explain the valid precondition that excludes it.
- Challenge the mistaken claim: argv strings must immediately follow their pointer table. Preserve a minimal failing trace or explain the valid precondition that excludes it.
- Challenge the mistaken claim: crt1.o always has the same role and content on every target. Preserve a minimal failing trace or explain the valid precondition that excludes it.

Exercise empty/singleton or zero-progress states where the operation admits them, exact capacity, one beyond capacity, repeated completion/cleanup and a deliberately invalid precondition. For storage-owning work, inject acquisition failures and verify unchanged old ownership. For build/binary/source studies, inject a wrong edge, symbol, width, target assumption or unsupported environment and require a visible failure verdict. Never execute malformed pointers or privileged instructions just to demonstrate a negative case. Apply these cases to the declared operation; document any inapplicable case and its reason.

## Hints and recovery

Decode argc first, then exactly argc argument pointers, their null terminator, environment pointers through their terminator and auxiliary-vector pairs through AT_NULL. Treat a pointer’s pointed-to bytes separately from stack words.

Before changing the target, determine whether the disagreement is its semantics, an invalid test precondition, a boundary mismatch or an environment limitation. If the fixture oracle fails, stop and repair the fixture/oracle independently; do not change expected data to fit the target. Return to the named prerequisite module when ownership, width or ordering assumptions are missing.
