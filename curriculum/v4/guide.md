# C Mastery 4: learn by growing useful systems

Start with a three-hour entry diagnostic, then grow a bounded record tool. The
curriculum assumes that you can already write elementary C; targeted remediation
is available when the diagnostic identifies a gap. A project is a coverage and
budget envelope. Your next action is a smaller working unit, usually one to three
hours, with a result you can explain and inspect before stopping.

The 56 domains and 429 projects remain the reference catalog. Their old numeric
order is not the v4 study order. Use the capability route and the CLI's readiness
explanations. A unit requires the capabilities and components it actually uses,
not every project in the domain where an earlier idea was taught.

## One session

1. Attempt two due recall sets, aiming for ten to fifteen minutes. Write or speak
   an answer before opening the prior implementation, notes or feedback.
2. Read the next unit's imported contracts, new boundary, assigned passages and
   stopping condition. Predict a normal, boundary and failure result.
3. At a designated design gate, compare the alternatives and seal the choice
   before the main implementation. A small comparison prototype is allowed.
4. Implement the narrow increment. Keep earlier regressions. Observe the first
   divergence before broad edits when a check fails.
5. Retain the actual source/trace and note assistance and active minutes. A unit
   completion is practice; component acceptance additionally needs its rubric,
   relevant contract recall and scoped execution evidence.

Do not write a new architectural dossier for every small unit. Carry forward an
unchanged decision and record the new assumption being tested. Setup, tool
discovery, wiring and capture are explicit tasks; equipment waiting is not
implementation time and does not block unrelated hosted study.

## Three systems and a shared toolbox

**Linux telemetry/service:** a record tool becomes a library consumer, then a
file/pipe service, then a bounded event-driven HTTP application. Slow peers,
malformed data, overload and shutdown repeatedly challenge the same ownership
rules. Numerical filters and measurements operate on its telemetry stream.

**Firmware acquisition gateway:** reuse record formats and portable algorithms
through reset/UART bring-up, MMIO drivers, interrupt/DMA handoff, layered serial
and Ethernet communication, original task scheduling, and H745 core ownership.
Model, emulator and physical observations are separate evidence.

**VM/store kernel appliance:** reuse byte access, allocation, generation handles,
algorithms and fault harnesses in a bytecode runtime and durable page store.
Bring up basic boot and exceptions before importing those finished services.
Later compose processes, channels, a single store owner and recovery.

The seven-layer educational stack, custom Ethernet-to-HTTP stack and HTTP server
over OS sockets remain distinct deliverables. Sharing a parser does not erase
their different physical, transport and lifecycle responsibilities.

## Progression without unnecessary waits

The nine capability phases overlap. The VM/store branch can proceed alongside
single-core task work. MCU and x86 branches require their own target knowledge
but need not wait for each other. Introductory SPSC publication follows the ring
and memory-model foundations; machine-level SMP/AMP revalidation comes later.

The route brings a working tool within twelve implementation/verification hours
after diagnosis and a real file or pipe boundary within forty-eight. These are
authoring targets, not guaranteed learner speeds. Each strand includes an
observable integration or adaptation within twenty-four assigned hours.

Advanced kernels, lock-free reclamation, real-time analysis and concurrent
services retain the required dispositions established in v3. All ten physical
communication-interface obligations and F439/H745 evidence remain in force.
Passing a host test, linking an image or completing recall cannot close them.
The final interface units register a manual `interface-bench` capture target;
it makes no compiler or simulator promise. Their reviewed raw captures identify
the actual interface, equipment and image. The MCU defense consumes those
accepted records and separate F439/H745 board records. SMP project milestones
require actual x86 guest receipts at one, two and four CPUs. You may continue
unrelated units while a physical project gate remains open.
The firmware capstone also requires its own current board captures at deployment,
fault/recovery and changed-condition defense. These are local observations of the
integrated application; the earlier interface and runtime portfolios remain
separate prerequisites. Integration stages consume the preceding stage's actual
component or design dossier, and the campaign preserves its learner workspace.
Run each SMP milestone with `--target x86-smp --cpus 1`, then repeat with two
and four CPUs. Selecting a target name does not itself establish guest execution;
the selected checks must include a real guest run. The archive milestone pairs
its host codec test with the earlier boot smoke test. The first Cortex-M
preemption gate likewise pairs its host scheduler check with the scoped image
and preemptive guest checks. Retain these receipts without requiring unfinished
later mechanisms to pass an entire family suite.

## Readings and references

Use the bounded passages on each unit card. Textbooks supply models and worked
reasoning; foundational publications explain the original mechanisms; standards,
architecture manuals and implementation documents establish applicable contracts.
The existing reference catalog records local library locators and source-inspection
limits. Read for the decision or experiment ahead, then retrieve the idea before
reopening a previous solution.

## What completion means

The CLI distinguishes practice, executable behavior, explanation, independence,
transfer, dependency closure and physical evidence. A self-assessment is visibly
self-assessed. Keep negative controls and the evidence a future reviewer would
need to challenge your claim. Historical success remains recorded when a changed
source, interface, target or recall failure reopens a particular claim.
