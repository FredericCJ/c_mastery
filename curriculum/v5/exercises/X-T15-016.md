Recovery and formatting require your completed X-T15-012 implementation and its exact PdTree contracts. ## Problem

Compile the shared literal/field/presence/list/static-include grammar into typed operations, then interpret it over a readonly four-field model. Implement nested list item shadowing/restoration, include-cycle detection and whole-output staging. Compare plain-text and HTML-text modes using synthetic <tag>&. Preserve actual model bytes and ensure braces in model values are data, never new directives.

## Necessity

Template syntax, model computation and output-context encoding are different mechanisms. A readonly-looking interface does not automatically enforce formal model-view separation. Repeating a first list item can pass singleton tests; recursive includes or nested expansion can exhaust resources without a pointer defect. Escaping appropriate for an HTML text node is not a universal sanitizer.

## Security

Template injection starts when bytes that were supposed to be data are read as structure. Here the model is the attacker: four fields of up to four printable values each, which may contain `<`, `&` or braces. The template text is trusted structure and is not attacker controlled. The target is your own template compiler and interpreter in `labs/text_composition/src/text.c`. No browser is started: the experiment is a comparison of output byte strings.

Why it matters here. In HTML-text mode the contract (`labs/text_composition/CONTRACTS.md`, template section) requires `&`, `<`, `>`, `"` and `'` in model values to become `&amp;`, `&lt;`, `&gt;`, `&quot;` and `&#39;`, without rescanning the entities just produced, and braces in a value must never be read as directives. Separately, an executed include cycle, deep nesting and nested loops over long values must end in `TC_CYCLE`, `TC_RANGE` or `TC_FUEL` with the caller's output unchanged, because expansion can be exponential.

What to try. Predict the HTML-mode and plain-mode strings for the program `[{*a}{.},{/}]{?b}{>1}{/}` with `<tag>&` and `B` in field a and `yes` in field b. Run `ctest -R text_composition.template`. Be careful what it pins: the HTML-mode bytes and the unchanged model, only the output length in plain mode, `{{a}}` as the literal `{a}`, `TC_CYCLE` for an executed cycle against `TC_OK` for an unexecuted one, `TC_FUEL`, and the `TC_SYNTAX` and `TC_RANGE` refusals (output or program unchanged only where the test says so). Then add what is missing: a model value that contains `{a}` and must stay data, values containing a double quote and an apostrophe, and the plain-mode bytes. Build two variants of your own, one that skips model encoding in HTML mode and one whose loop does not advance past the first item, and find which check rejects each.

What to capture and how to read it. Keep the `TC_ASSERT:<line>:<expression>` text and the raw output strings for every case; the markup-shaped string from the variant against `&lt;tag&gt;&amp;` from the correct build is the whole demonstration. If a variant survives the public test, say so and add the check that kills it. The assessor's mutation set also checks this invariant.

Impact class. The visible markup-shaped output is a `demonstrated-invariant-violation`, but only once you have built the variant. No browser or script engine exists in the experiment, so do not claim script execution or data theft.

Remediation and regression. Encode every model-derived byte at the single emission point, parse directives only from the compiled template and detect cycles with the active-template set. Keep the failing strings as permanent tests.

Limitations. This is HTML text-node encoding only: attributes, URLs, JavaScript and CSS need different contexts, and nothing here shows safety against a hostile template. The printable-ASCII model discipline is enforced by the caller, not by this code.
