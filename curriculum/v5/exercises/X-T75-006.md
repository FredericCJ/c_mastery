## Problem

Implement RZGate with separate closed/open/half-open health state and active-permit limit1..2. Two consecutive backend failures open for4 ticks; a single half-open probe decides recovery. Each permit carries owner, slot and nonwrapping generation; completion also uses its saved admission epoch so an old success cannot heal a new open period. Add a sliding-window failure-rate policy and a two-tenant bulkhead variant with explicitly reserved capacity, retaining neutral client-error outcomes.

Supplied artifacts: labs/resilience/include/resilience.h, deliberately incomplete labs/resilience/src/resilience.c, executable anchors, fixture PR-T75-06.json and the shared CONTRACTS.md. Expected example: With limit1, a second simultaneous admission returns BUSY even while CLOSED. Two classified failures open. An older outstanding success releases capacity but leaves the newer OPEN state unchanged. At cooldown equality one probe may enter, a second is BUSY, and successful probe closes. Repeated completion is STALE.

## Necessity

Health decisions summarize observations, while a bulkhead bounds admitted resource ownership. Conflating them allows an otherwise healthy slow backend to exhaust callers or an old completion to erase newer failure evidence.

## Security

**Why this matters here.** A breaker decides from past results whether new work may enter, so its attack surface is the completions that arrive late, twice, or with the wrong meaning. A success that was admitted before the breaker opened and finishes afterwards says nothing about the backend's present health and must not close the breaker. Completing the same permit a second time must not free capacity twice. A client error that is not the backend's fault must count as no evidence at all. A flood from one tenant must not consume the capacity reserved for another. Each of these is a counting or state rule, so each can be tested with a handful of calls.

**What to try.** Trace the consecutive-failure gate first (tests/tests.c:149-168). With limit 1 a second admission is RZ_BUSY and a repeated finish returns RZ_STALE. With limit 2, two classified failures open the breaker; an older outstanding success leaves phase 1; an admission at tick 3 is RZ_OPEN, at tick 4 one probe enters (phase 2), a second is RZ_BUSY and the successful probe closes the breaker. Then trace the windowed breaker with cooldown 4 (followthrough/breaker_test.c:70-171): the window opens with until==4, an old-epoch success at tick 4 leaves phase 2 and used==1, tenant 0 admitted at cost 2 makes another tenant-0 admission RZ_BUSY while tenant 1 is still admitted, a neutral completion records no health evidence, and an invalid outcome leaves the state byte-identical.

**Evidence to capture.** For each variant write down the property it violates, the file it lives in, and the test that can see it, then run that test and keep the stderr RZ_CHECK line. Note that the same failure, success, failure, success history leaves the consecutive-failure gate closed (!original.phase) and the windowed breaker open (phase 1, breaker_test.c:169): the two contracts are meant to disagree, and you should be able to say why. The oracle mode prints rows and compares nothing, so it is useful only once you have your own model to compare with.

**How to read the result.** A rejected variant is a wrong state transition, count or admission on synthetic backends: a demonstrated invariant violation in well-defined C. It does not show that any deployed service is protected, nor correctness under concurrent completions, and completing a permit does not cancel other in-flight effects. Epoch and generation spaces are deliberately small and fixed, so exhausting them retires slots (breaker_test.c:134-148) and is not a defect. The assessor's mutation set also checks this invariant, but that set is not part of what you receive.

Only your own implementation and the synthetic data of this lab are attacked; no external service, hardware or host setting is touched.
