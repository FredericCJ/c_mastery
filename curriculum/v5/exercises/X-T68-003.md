# X-T68-003: Policy composition with explicit failure semantics

## Prerequisites

Complete the earlier domain projects and retain the named prerequisite artifacts with their contracts, ownership ledger and tests. Required learner artifacts: containers.array. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [metaprog/CONTRACTS.md](../../../labs/metaprog/CONTRACTS.md).

## Problem

Implement mp_reduce over uint32 inputs and MPPolicy{limit,saturate}. Starting from0, sum mathematical values up to limit. saturate0 rejects any exceeding prefix and leaves output unchanged; saturate1 clamps tolimit. Invalid policy values fail. Empty input returns0; NULL input is allowed only when empty. Then generate two named specialized wrappers whose policy is fixed and compare with the dynamic function.

Concrete inputs and expected results: Inputs[7,5],limit10: rejecting policyfails unchanged; saturating policyreturns10. Empty inputreturns0 under eitherpolicy.

Supplied artifacts: labs/metaprog/include/metaprog.h, compiling unsolved src/metaprog.c, CTest metaprog.policies, fixtures/metaprog/PR-T68-03.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Explain how a policy changes the operation contract and therefore the permitted performance comparison; distinguish compile-time specialization from runtime policy dispatch. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Prove value<=limit before subtracting limit-value, and define how a single input greater thanlimit is handled. Inputs/outputs are disjoint. State no allocation, single-threaded execution and failure publication at the end. Compare a policy parameter with Rust const parameters/trait-associated behavior only at the documented boundary. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

## Deliverables

- D1: Explain how a policy changes the operation contract and therefore the permitted performance comparison; distinguish compile-time specialization from runtime policy dispatch.
- D2: Prove value<=limit before subtracting limit-value, and define how a single input greater thanlimit is handled. Inputs/outputs are disjoint. State no allocation, single-threaded execution and failure publication at the end. Compare a policy parameter with Rust const parameters/trait-associated behavior only at the documented boundary.
- D3: Run metaprog.policies and inject every prefix crossing the limit. Kill accidental-saturation-for-rejection and wrong-empty-identity mutants. Inspect specialized and dynamic assembly and benchmark only comparisons preserving the same overflow and empty-input contracts.
- D4: Compose reduction with a caller-defined projection and fallible element acquisition. Specify evaluation order, callback side effects, rollback limits and whether saturation may short-circuit without skipping required effects. Complete all thirteen cost/enforcement dimensions with evidence or a mechanism-specific non-applicability.
