# X-T14-015: Skip-list ordering, deterministic state and probabilistic limits

## Prerequisites

Know sorted maps, typed arrays, half-open bounds, unsigned arithmetic and strong failure publication. Bring a small exact map oracle and invariant traces from the retained container/search work. Tree work additionally requires ordinary B-tree splits and ownership/reachability; runs require stable merge and version ordering. No library may implement the assessed mechanism. These new required exercises do not inherit historical elective exclusions.

## Environment

The explicit [ordered storage contract1](../../../labs/corpus_storage/CONTRACTS.md) supplies all representations, operations, input/output domains, ownership, statuses, capacity/work bounds and security scope. Implement `src/storage.c`. Distinguish compiler helpers from target dependencies and host oracles. Changing ABI, optimization or execution environment requires revisiting stack/copy measurements and helper closure; no strict linked-image claim is made.

## Problem

Implement the six-level,32-node typed ordered map and explicit deterministic generator. Insert keys2,0,1 with promotion words0,1,3, scan[0,3), replace a key at capacity and erase every level. Use actual unbiased bounded selection to shuffle a32-key insertion history, then replay promotion states using affine jump-ahead. Produce the all-height-one counterexample to an unconditional logarithmic claim.

## Necessity

A sorted level-zero list can appear correct while upper links are absent or dangling. A generator with full state period can still have predictable low bits and correlated heights. Modulo reduction can bias bounded choices; rejection and finite fuel introduce separate progress semantics.

## Reasoning

Derive predecessor-path invariants and geometric-height expectations under stated independent-bit assumptions. Prove the chosen recurrence period from odd increment/multiplier1 modulo4 and derive affine composition without division. Explain low-bit alternation, rejection threshold, unchanged state on exhaustion and why deterministic replay is not independent sampling. State exact scan endpoint limitations and worst-case key comparisons. Provide preconditions, postconditions, representation/loop invariants, ownership, failure and complexity arguments. Distinguish ISO C guarantees, diagnostic checks, runtime admission, external proof/model evidence and caller discipline. Include one plausible incorrect explanation and a minimal counterexample.

## Security

Why this matters here. A skip list is fast only if node heights look random. Here the promotion words are an input and the generator is a plain linear congruential recurrence whose lowest bit alternates, so an adversary who chooses the words can make every node height one; the structure is then a sorted linked list and a lookup walks it. The test builds that history (eight keys put with bits = 1, then ss_skip_get(7) with cost at least 8). It asserts only the lower bound; the upper bound of 32 visited nodes follows from the owner's capacity and is yours to derive, so the defensible claim is "bounded by 32", never "logarithmic", and the generator must not be described as a source of secrets.

The integrity half. Level zero must hold every key once in increasing order, every live node must be linked at each level below its height, and erase must unlink all of them. skip_invariant() recounts the nodes reachable at each level after every put and every erase and compares with the number of nodes tall enough to be there (seen == eligible[l]). A key left linked at an upper level after erase, or a node missing from an upper level after put, breaks that equality. Replacement is subtler: the contract says it preserves height even at capacity, but the invariant never compares a height across a replacement, so a replacement that changes the height and relinks consistently would pass skip(). That check is yours to add.

What to try. Predict by hand which levels a key occupies for a given promotion word under both policies (the test loops over 1024 words) and what scan(2,6) returns on keys 0..7. Then build two causal variants of your own, each breaking a different structural rule, and add the direct before/after height comparison for replacement.

What to capture and how to read it. A failed check prints `SS_ASSERT:<line>:<expression>` on stderr and exits 41; keep that line for each variant and say which of the invariant, atomicity (owner bytes identical after a full put, a missing erase, an undersized scan or an exhausted generator budget), height-table or shuffle-replay checks it came from. A variant that survives is a gap in the public test, not a pass.

What this does and does not show. Wrong answers or work counts on synthetic keys, nothing more. Only the work-bound counterexample is demonstrated by a supplied artifact; ordering and deletion-visibility violations hold only once you build a variant. The assessor's mutation set also checks this invariant. Thread safety, atomic publication, durability, cryptographic randomness and real-service denial of service are not shown, and the 32-node cap is a resource limit, not a defence.
