## Security

Why this matters here. Positions are the one place where order matters. Rows [1,0] and [0,1] contain exactly the same terms, so a test that only asks whether both terms are present cannot tell them apart. Each posting holds a row and a mask of the positions where the term occurs (struct qi_posting in query.h), and a phrase is a shifted intersection: term q of the phrase must occur at position p + q for one common p. For phrase {0,1}, row [0,1] has term 0 at position 0 and term 1 at position 1, so the shifted masks meet; row [1,0] has term 1 at 0 and term 0 at 1, so they do not. A presence-only merge answers mask 3 (rows 0 and 1) where the correct answer is mask 2, and no memory error accompanies the wrong answer. Repeated terms add a second trap: row [1,1] must match phrase {1,1} and a row with a single 1 must not, because each phrase position consumes a distinct occurrence.

What to try. Before reading the test, work out by hand the masks for the three rows of postings() for phrase {0,1}, phrase {1,1}, near(0,0,1), near(1,1,1) and near(1,1,0). Implement, run `query_tests postings`, then build two variants of your own: one that accepts a phrase whose terms are present but not adjacent and in order, and one that lets one occurrence of a term serve as both ends of a repeated-term pair. Add a document with all phrase terms in reverse order to your own oracle inputs.

What to capture and how to read it. For each variant keep the stderr line `QI_CHECK:<line>` and map it to the check in labs/corpus_query/tests.c: phrase {0,1} equal to 2; near(0,0,1) equal to 0, near(1,1,1) equal to 4 and near(1,1,0) equal to 0; phrase {1,1} equal to 4; the empty phrase equal to 7; phrase {1,1} equal to 0 after slot 2 is replaced by a dead row; term 8 and nine terms returning QI_INVALID with the answer still 99; and the loop requiring strictly increasing posting rows. If a variant survives, say which input would have caught it and add it. Feed the same rows to the supplied query_driver (it prints masks and compares nothing) and compare against a model that scans raw token sequences rather than your postings.

What this does and does not show. A wrong phrase mask on synthetic rows. No supplied artifact demonstrates it, so the impact class holds only once you build the variant. The assessor's mutation set also checks this invariant. The domain is already-tokenized terms 0..7, at most 8 positions and 32 rows; normalization, ranking, streaming cursors, concurrency and persistence are not exercised.
