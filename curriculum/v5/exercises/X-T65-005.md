# X-T65-005: Bounded applicative validation and transactional configuration

## Prerequisites

Use the existing bytes.checked, parser.integer, io.stream and codec.records contracts as comparison boundaries. Complete C17 tagged-union, pointer-lifetime and function-pointer reasoning first. Preserve the learner's earlier implementations; do not import an assessor solution. Complete X-T65-004 first.

## Environment

C17, Linux x86-64, GCC and Clang with -Wall -Wextra -Wpedantic -Werror and extensions disabled. The exact shared contract is [errors/CONTRACTS.md](../../../labs/errors/CONTRACTS.md). C editions, language-level guarantees and implementation observations must be labeled separately.

## Problem

Implement er_validate for age0–150, quota0–1024 and denominator1–4096. Validate all three independent fields in that order. Invalid fields emit IDs1,2,3 into caller storage of capacity0–3; return total error count, stored count and truncated flag independently. A zero-capacity list may be null. A null output, capacity>3 or null nonzero-capacity error list is structural misuse: return total=SIZE_MAX,stored=0,truncated=0 without touching outputs. Publish the complete configuration only if no field is invalid. Other than output/error buffers, no input state changes.

Concrete expected cases: Input (-1,1025,0), capacity2 yields total3,stored2,truncated1 and error IDs[1,2], preserving the old configuration. Capacity0 still reports three errors. (150,1024,1) publishes successfully and emits none.

Supplied artifacts: labs/errors/include/errors.h, compiling unsolved src/errors.c, the named CTest errors.validation, and fixtures/errors/PR-T65-05.json. No installed package may supply the mechanism under assessment.

## Necessity

Explain why independent validation may accumulate errors while dependent checks require an admission order; define truncation independently of validity. An ordinary nominal call does not assess this distinction. The two isolated mutants and the changed-condition case expose different incorrect explanations.

## Reasoning

Implement bounded ordered diagnostics and all-or-nothing configuration publication, including structural-misuse behavior and output nonoverlap preconditions. State the preconditions, postconditions, valid representation states, ownership and failure effects before implementation. Derive operation and storage bounds; distinguish caller misuse from a reported operational failure. Compare the C protocol with the exact inspected source scope: C type compatibility and diagnostics do not supply automatic ownership, exhaustive matching or proof of a runtime predicate.

## Security

Only original local curriculum code in `labs/errors` and synthetic inputs; no network, real data, privilege changes or deployed target. 
Target: er_validate in `labs/errors` and the publish-early variant you build.

Adversary: you control only the three field values, the capacity 0..3 of the error list and, for structural misuse, null or oversized arguments. You do not control the published object except through er_validate, nor caller aliasing.

Violated property: no configuration with an invalid field may be published, and structural misuse must not write any output.

Evidence to capture: run `errors.validation` and `errors.validate_base`/`errors.validate_security` on the correct build and record, for {-1,1025,0} at capacity 2 and 0, the total, stored and truncated values, the error IDs written (1 and 2, third slot still 99) and the old configuration {7,8,9} still in place; the successful {150,1024,1} publication; and the NULL-output misuse result total SIZE_MAX with the error buffer untouched. Then build a variant that writes the output before completing the checks, and quote the `ER_CHECK:<line>:...` and `ER_CHECK EVV line<N>: ...` lines that reject it; that rejected overwrite of the canary configuration is the unauthorized publication.

Impact class: demonstrated-invariant-violation, shown only by the publish-early variant you build; the supplied tests pass on a correct build and no supplied artifact demonstrates it. A state-integrity violation of a synthetic object is not a claim of code execution, and a crash or sanitizer finding would be a weaker class. Do not use undefined execution as an oracle.

Remediation: validate every field before publication. The regression tests are the existing `errors.validation`, `errors.validate_base` and `errors.validate_security`; they must fail on your publish-early variant and pass on the repair.

Limitations: Alias, overlapping-storage and concurrent-caller behaviour are not tested and need external serialization; undefined execution is not used as an oracle; the demonstration shows only that a synthetic configuration object is or is not overwritten.
