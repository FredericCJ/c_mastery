## Problem

Implement the encoder, once-only decoder and generated-HTML-text dialect adapter for64 plain/384 encoded octets. Encode `&<>"'`, derive the exact25-octet result, then decode it. Predict decoding `&amp;lt;x&amp;gt;` and every incomplete prefix of the five entities. Fail every insufficient capacity without changing any output byte. Distinguish an actual apostrophe from literal `&#39;` in a template model. Render the real `{a}` template, expose the original event parser's rejection, then adapt the dialect and feed a single wrapped root at every split point.

## Necessity

A one-way encoder does not establish its inverse, and a binary framing escape is a different grammar. Repeated decoding can turn previously literal entity-looking data into syntax. Two correct components can disagree about a permitted entity spelling. Context-specific byte replacement is not universal sanitization, authentication or authorization.

## Reasoning

State preconditions, postconditions, the consumed-prefix invariant, exact error precedence and publication point. Prove the round-trip law only on the admitted domain and provide counterexamples to idempotence, repeated-decoding safety and arbitrary-HTML equivalence. Account for6n expansion, two stages in recoding, copied callback data and the absence of retained borrows. Separate ISO C guarantees, compiler diagnostics, runtime bounds, external finite-model evidence and caller discipline. Explain why emitted '<' is character data and why an adapter validating bytes does not establish their provenance.

## Security

Why this matters here. Escaping is what keeps text from becoming markup. The encoder turns the five characters & < > " ' into &amp; &lt; &gt; &quot; &apos; (five input octets become 25), and the decoder undoes each entity exactly once. Two mistakes are easy and quiet. An ampersand that is not escaped lets the text `&lt;` be read back as the character `<`. A decoder that rescans its own output turns `&amp;lt;x&amp;gt;` into `<x>` instead of the nine literal octets `&lt;x&gt;`, so data has become syntax. In this lab the consumer is the event parser from the earlier exercise, and the damage you can see is an extra element event or changed character data in a local ledger, not script execution in a browser.

What to try. By hand, decode `&amp;lt;x&amp;gt;` one entity at a time and stop after one pass; then write down what a second pass would produce. Work out why the template renders an apostrophe as the numeric `&#39;` while the event parser accepts only `&apos;`: composition.c shows that both es_decode and the parser reject the raw `&#39;`, and es_recode_html is the single adapter that converts the template's spelling, leaving a literal `&amp;#39;` as the text `&#39;`. Then build two variants of your own that each break one property (an ampersand left unescaped, and a repeated decode) and predict which assertion each trips.

What to capture and how to read it. A failed check prints `ES_ASSERT:<line>:<expression>`; keep it per variant and map it to the public check: the 25-octet encoding, the round trip to five octets, the nine-octet single-pass decode, the malformed list with the whole output object byte-identical (including padding), the capacity loops, the 65-octet range errors, and the es_recode_html cases. Each rejected call must leave the object identical under memcmp, even when the capacity is zero and the input is malformed, because validation comes before the capacity comparison. For the composition, build composition.c yourself and record the observation count it prints and the two rejections of the raw `&#39;`.

What this does and does not show. Data turning into markup in a local event ledger on synthetic ASCII. No supplied artifact demonstrates it, so the impact class holds only once you build a variant. The assessor's mutation set also checks this invariant. Escaping for generated HTML text does not authorize use in attributes, scripts, URLs or styles, this is not an HTML sanitizer or XML processor, and a parse failure is not an exploit.
