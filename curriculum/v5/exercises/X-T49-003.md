# Explain a failed fork

## Prerequisites

X-T49-002 supply the process, namespace or transport foundations for this investigation.

## Environment

Use the exported linux_supervision workspace and restore the pinned Linux guest with `python3 guest.py setup`. Start with the `pids` case in CONTRACTS.md and the fixture interfaces in PROTOCOL.md.

## Problem

Draw the leaf membership at the instant a second worker is requested. Predict the two outcomes with a limit of two and a limit of three.

## Necessity

Attribute a refused fork to the active task limit using counter deltas and a changed-limit control. Synchronize and account for each child admitted by the leaf. These observations give a reviewer enough information to distinguish different mechanisms that can yield the same visible outcome.

## Reasoning

A controller counts tasks in the leaf, including the namespace init. A fork error can have several causes. Support the diagnosis with the before/after max event, the occupancy, the actual limit and the otherwise identical successful trial. errno is meaningful only on the failing call.

## Deliverables

- D1. Record your prediction in `answers/pids.json`. Implement supervise_pids in src/pids.c. Hold the first worker on a pipe. Read pids.current and pids.events, attempt exactly one more fork, and save errno immediately on failure. Hold every admitted worker until after the second reading. Release and reap the admitted children. The fixture owns the limits and observes from outside the leaf.
- D2. Preserve your source, guest serial transcript and run identity. Write an explanation keyed to the measured fields in both the program and the independent outer observations.
- D3. Explain how releasing the first worker too early could invalidate the experiment even when the implementation compiled and every child was eventually reaped.

## Verification

Use `python3 submission.py observe pids --program build/learn/supervise --out build/first-pids` after building. Run the standard `cmastery check` command in CONTRACTS.md for a fresh graded execution. Explain any discrepancy with your original prediction.

## Rubric

- R1. Attribute a refused fork to the active task limit using counter deltas and a changed-limit control.
- R2. Synchronize and account for each child admitted by the leaf.

## Hints

Explain how releasing the first worker too early could invalidate the experiment even when the implementation compiled and every child was eventually reaped. Use the fixture barriers and monotonic deadlines to order observations; a sleep chosen by trial and error cannot establish readiness.

## Variants

V1 is an individually assigned changed condition after at least seven days. Record the prediction and the observations that would distinguish the alternatives before rerunning the program.

## Security

Use the course’s diskless, networkless guest. The fixture owns namespace creation, controller settings and teardown. The supervisor handles the bounded learner workload as an ordinary guest user.

## Validation

The live CTest checks the selected case against current guest and executable identities. Offline replay verifies trace structure and invariants. A reviewer grades the explanation and changed-condition transfer.
