# X-T15-011: SLR item sets, conflict witnesses and transactional derivation trees

## Prerequisites

Study T15.14 and PR-T15-09, T03 array/object lifetimes and T14 stack/set representations. Bring a hand trace of the shared grammar, bounds tests and a list of ordinary versus malformed inputs. LR additionally needs least fixed points and FIRST/FOLLOW; regular expressions need finite-state machines; Pratt needs expression trees; scannerless work needs rollback and three-result recognition. No unlisted accepted artifact import is required.

## Environment

The explicit [parsing depth contract1](../../../labs/parsing_depth/CONTRACTS.md) supplies the full typed API, exact languages, capacities, dependencies, ownership, admission/failure semantics and local security scope. Implement the supplied compiling `src/parsing.c` scaffold. The C mechanism cannot delegate to a mature parser library. Host independent oracles remain separate. ISO C type checks do not establish the semantic grammar/table or pointer-lifetime preconditions.

## Problem

Build nullable/FIRST/FOLLOW sets, LR(0) item closure/goto and a checked SLR table from the supplied bounded grammar representation. Parse the supplied arithmetic grammar into a typed derivation tree with token spans. Report a conflict for E->E+E|n instead of choosing a convenient action. Then implement the nullable delayed grammar and an action-budget failure without publishing a partial tree.

## Necessity

A recursive-descent exercise does not teach shift/reduce state construction or explain why FOLLOW sets restrict reductions. Overwriting conflicting table cells hides a language-design decision. Epsilon productions challenge FOLLOW propagation, stack popping and zero-length tree spans; malformed-input recovery must not become an unbounded loop.

## Reasoning

Prove closure as a finite least fixed point, goto as symbol advancement followed by closure, and FIRST/FOLLOW propagation through nullable suffixes. State the stack viable-prefix meaning and why reduction uses GOTO of the state exposed after popping. Separate grammar conflict, input syntax failure, capacity exhaustion and budget exhaustion. Bound item/state/table/tree storage and analysis iterations; explain that a conflict means not SLR under this construction, not necessarily ambiguous. Give the smallest concrete counterexample to one plausible incorrect explanation. Separate ISO C rules, the teaching language/grammar, compiler support and programmer-maintained invariants. State every pre/postcondition and no-publication failure boundary.

## Security

A table-driven parser is only as trustworthy as its table. If a conflicting cell is quietly resolved, the parser accepts input with a structure that the grammar never determined; if a reduction fires on a lookahead outside FOLLOW, the error is found at the wrong place or not at all; and if a half-built tree escapes a failed parse, the caller consumes a derivation that was never completed. The only target is your own `lr_build` and `lr_parse` in `labs/parsing_depth/src/parsing.c`, driven with the bounded grammars from `grammars.h` and synthetic token lists.

Why it matters here. `pd_grammar(1)` is `E->E+E|n`: after `E + E` with `+` as lookahead, both shifting and reducing are legal, so the SLR cell holds two actions. The contract (`labs/parsing_depth/CONTRACTS.md`, section X-T15-011) forbids preferring shift, so the only honest answer is `PD_CONFLICT` with the table untouched. Likewise the action budget is the only thing that stops a runaway sequence of reductions, so exhausting it must give `PD_FUEL` and leave the previous tree byte-for-byte as it was.

What to try. Build the FOLLOW sets for the expression grammar on paper first and predict the 12 states and the mask for E. Then run `ctest -R parsing_depth.lr`; the anchor pins the state count, `n+n*n` rooted at symbol 8 and ending at 5, budget 1 giving `PD_FUEL` with the tree unchanged, `n + *` failing at offset 2, `pd_grammar(1)` giving `PD_CONFLICT`, and the nullable grammar building and accepting `+` and `n n n +` while an empty token list is refused. Then build variants of your own: one that picks shift on a conflict, one that reduces on any lookahead, one that publishes the tree even when the budget ends. For each, pick the grammar and tokens on which it differs from the original.

What to capture and how to read it. Keep the `PD_ASSERT:<line>:<expression>` line and read the expression: it names the property that failed. Record the grammar, the token list, the budget, the status, the diagnostic offset and a before-and-after byte snapshot of the table or tree. If the anchor does not reject a variant, say so and use your own test as the evidence. The assessor's mutation set also checks this invariant.

Impact class. `demonstrated-invariant-violation`, and only after you build a variant and show the wrong status or published tree for a named grammar and token list. A conflict diagnostic, syntax error or sanitizer report alone is not code execution or privilege escalation.

Remediation and regression. Report `PD_CONFLICT` on the first double action, admit reductions only on FOLLOW, charge every action against the budget and publish the tree only after complete acceptance. Keep your smallest failing grammar and tokens next to the existing `parsing_depth.lr` assertions.

Limitations. A conflict is a statement about this SLR construction, not proof that the grammar is ambiguous. The action budget bounds work by refusal and is not a general parser-security guarantee, and a grammar that is LR(1) but not SLR is reported as a conflict, not parsed.
