# X-T73-010: Demand signaling, terminal events and bounded reentrancy

## Prerequisites

Explain C17 atomic ordering, POSIX wait predicates, existing queue ownership, async terminal completion and stable coroutine-frame registration; retain the named imported learner artifacts. Required learner artifacts: work.pool, sync.condition_queue, sync.spsc, io.async, io.deadline, testing.faults, coro.frame. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [messaging/CONTRACTS.md](../../../labs/messaging/CONTRACTS.md).

## Problem

Implement a serialized demand stream with unsigned additive demand, UINT64_MAX unbounded sentinel, next/error/complete signals and cancellation. Emit decrements finite demand before calling next. A next callback may request more or cancel, but recursive emit returns BUSY. Request0 signals terminal INVALID. Terminal notification occurs once and no later item is delivered. Integrate with a channel producer using demand credit, leaving overflow/drop policy to T75.

Concrete inputs and expected results: Emit with demand0 is EMPTY. Request1 then emit99 whose callback requests1 leaves demand1 without recursive delivery; emit7 consumes it. UINT64_MAX then request1 stays unbounded. Complete then error produces one terminal event; later emit is CLOSED. Cancellation prevents subsequent emits but does not establish cross-thread callback quiescence.

Supplied artifacts: labs/messaging/include/messaging.h, compiling unsolved src/messaging.c, CTest messaging.streams, fixtures/messaging/PR-T73-10.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Derive demand accounting, signal ordering, cancellation and reentrancy limits; compare the original C subset to selected Reactive Streams rules without claiming interface or certification equivalence. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Implement explicit demand/terminal/delivering state, saturating unbounded arithmetic and callback ownership; construct a channel adapter that never delivers more items than requested. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

## Deliverables

- D1: Derive demand accounting, signal ordering, cancellation and reentrancy limits; compare the original C subset to selected Reactive Streams rules without claiming interface or certification equivalence.
- D2: Implement explicit demand/terminal/delivering state, saturating unbounded arithmetic and callback ownership; construct a channel adapter that never delivers more items than requested.
- D3: Enumerate request/emit/cancel/end traces, test zero and maximum demand, callback requests/cancellation and recursive emission. Reject emission without credit and repeated-terminal mutants. Independently account for requested versus delivered finite items, retain callback context through return and test that end requires no demand.
- D4: Make signals originate on several threads: serialize them through one executor and retain the subscription until all in-flight signals quiesce. Delayed assessment introduces a slow subscriber and bounded channel capacity; compare blocking, dropping and failure policies under the same stated delivery contract, with T75 owning the overload decision. Complete all thirteen cost/enforcement dimensions with evidence or a mechanism-specific non-applicability.

2. Terminal events are not ordinary demand-limited items.
3. Cancellation may stop future delivery while a callback is still using the subscriber.
