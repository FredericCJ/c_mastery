## Security

Why this matters here. sd_load builds an image page by page, taking a free frame for each, and the failure case is the dangerous one: if the third allocation fails, the two frames already taken have to be given back, or the memory model quietly shrinks by one image per failure. Nothing crashes and no sanitizer fires, because the frames are rows of a fixed 16-entry table; the only visible symptom is a reference count that stays above zero. Copy-on-write has the mirror-image risk: a clone shares frames with its parent, so a write that is not redirected to a private copy changes the parent's data. Both are ownership-accounting errors, which is why the evidence is a count and a byte, not a fault.

What to try. Work out by hand what the 130-byte input occupies: three frames, the third holding bytes 129 and 130 followed by zeros. The injected failure `fail_after = k` refuses allocation number k, so k = 0 fails before anything is taken, while k = 1 and k = 2 fail with one and two frames already held. Ask which of those cases can reveal a leak, and why the test runs all three. Then trace the clone: after a successful sd_clone every shared frame has a reference count of 2, a denied allocation on a child write must return SD_FULL and leave the parent byte at 1, and an allowed write must give the child its own frame with 99 while the parent keeps 1. The rejected clones in the test come first and the successful clone checks `refs == 2` afterwards, so a rejected request that had already bumped a count would also show up there.

What to capture and how to read it. Run `service_depth-tests memory` on your build and keep the exact `SD_CHECK:<line>:<expression>` for each variant you build: one in which a failed load leaves frames owned, and one in which a write through the clone can be seen in the parent's frame. Map the line to the check in labs/service_depth/tests/tests.c (the refs loop after each injected failure, the byte comparison after the denied write, the all-references-equal-one check with four images loaded). If a variant passes, record that as a gap in the public test and say which extra input would expose it. The DENIED clone and the clone refused for a saturated reference count are followed by a byte-for-byte comparison of the parent image; the thread-count rejection is checked by status alone.

What this does and does not show. A wrong reference count or parent byte in a 16-frame model, on synthetic bytes. No supplied artifact demonstrates it, so the impact class holds only once you build a variant. The assessor's mutation set also checks this invariant. There are no page tables, TLB, concurrent fork or memory pressure here, the kernel adapter is derived on paper, and a crash or undefined behaviour from your variant would be a different, lesser finding.
