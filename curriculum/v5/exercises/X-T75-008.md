## Problem

Implement RZReceiver for a checked synthetic integer total, four retained requests, two authenticated-model client IDs and finite retention1..16 ticks. A request has client,id,fence,delta. Replays within retention return the original result; changed parameters conflict; stale fencing tokens reject at the protected receiver. Publish effect and dedup record together. Add an append-only local teaching journal with explicit crash points around record/effect publication, then replay recovery without claiming the in-memory anchor is durable.

Supplied artifacts: labs/resilience/include/resilience.h, deliberately incomplete labs/resilience/src/resilience.c, executable anchors, fixture PR-T75-08.json and the shared CONTRACTS.md. Expected example: Client0/id1/fence2/delta3 at0 applies total3. Its replay at1 returns3 without another effect; delta4 with that ID conflicts. Client1 at fence1 is stale. With retention4, the same id at4 is no longer retained and may apply again, producing6. This bounded window is not indefinite exactly-once execution.

## Necessity

Deduplication needs an identity contract and retention limit. A timed-out lease or a unique random value does not establish that an old writer is fenced off after a newer owner acts.

## Reasoning

T75.08.a: Derive request identity versus payload equality, finite retention, authentication assumption and monotonic fencing enforcement at the actual effect resource. Identify which failures make a result uncertain.

T75.08.b: Implement atomic in-memory record/effect publication, original-response replay, parameter mismatch rejection, no live-record eviction and checked arithmetic.

## Security

**Why this matters here.** An idempotent receiver turns an unsafe 'send again' into a safe one, but only inside a finite window and only if three things hold together. The effect, its record, the fence it was applied under and the reply must be published as one transition, or a crash leaves an effect with no record (and the retry applies it twice) or a record with no effect (and the retry is told it already happened). A changed parameter under a reused id must be a CONFLICT, not a quiet second effect. And a fencing token only protects the store if the store itself, here the receiver, checks it; a client that holds an old token must be refused at the receiver, whatever the client believes.

**What to try.** Start from the in-memory receiver (tests/tests.c:195-210): client 0, id 1, fence 2, delta 3 gives total 3; the replay a tick later returns 3 with duplicate set and the total still 3; delta 4 under the same id is RZ_CONFLICT; client 1 with fence 1 is RZ_STALE; and with retention 4 the same id applies again at tick 4 and returns 6. Then move to the journal, where the question becomes what a crash can leave behind. Read failure_cuts (followthrough/journal_test.c:240-306) and predict, for a cut inside the apply record, which totals recovery may show and what the replay must return. Finally read replica (:308-358), where two writers disagree about the current fence, and say which one is wrong and what the mirror does about it.

**Evidence to capture.** Build two broken variants, stated as properties: an effect published before its record is durable, and a receiver that takes a fence lower than one already issued. Be precise about where each can be seen: the first is invisible to the in-memory receiver, which has no durability boundary, and appears only in the journal tests with injected cuts. Predict the RZ_CHECK line, run resilience.receiver and resilience.receiver_journal, and keep the stderr line. Run the journal `cuts` and `oracle` modes if you want byte-level evidence; they print the durable image and compare nothing, so the model to compare with is yours. native_file uses a real file and a forked child, so run it under the same ASan/UBSan build and record that a passing run covers one crash point, not all of them.

**How to read the result.** A rejected variant is a doubled, lost or stale-token-accepted synthetic effect: a demonstrated invariant violation in well-defined C, and replica() is the one place where the lab itself already shows the stale-fence hazard. It does not establish indefinite exactly-once execution, durability across real power loss, authentication or globally monotonic fence issuance. The in-memory receiver does not survive a crash, and the journal is a teaching device. The assessor's mutation set also checks this invariant, but that set is not part of what you receive.

Only your own implementation and the synthetic data of this lab are attacked; the temporary files are unlinked as soon as they are made and no external service, hardware or host storage setting is touched.
