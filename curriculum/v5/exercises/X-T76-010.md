# X-T76-010: Consistent-hash ring views and distinct replica placement

## Prerequisites

Retain X-T76-007 hashing/anti-entropy reasoning and the completed RphSha byte-stream hashing artifact. Explain unsigned modular arithmetic, binary search, table identity, callback lifetime and output staging. This exercise adds placement/view interpretation needed when partitioned replicas compare ranges; it does not replace the existing Merkle repair contract.

## Environment

Use the exact C17 profile and finite capacities in [CONTRACTS](../../../labs/corpus_ring/CONTRACTS.md). Core tests run under GCC/Clang debug, optimized and ASan/UBSan profiles; original-helper Cortex-M4 object/link audits are separate. Actual reference adapter runs compile sha_adapter.c against the explicit preexisting RphSha header/source. A language-level interface can constrain method shape, but neither C17 nor C23 supplies placement laws, ownership or distributed membership authority.

## Problem

Implement admitted token views, clockwise successor lookup, one-owner addition/removal, distinct available replicas, byte-key hashing composition and an adjacent-view migration plan. The header and shared contract specify concrete inputs, outputs, capacities, exact collision order, statuses, epoch exhaustion and failure publication. Use the existing hash component rather than a library that already implements placement. Public scaffolds deliberately refuse. For tokens[(10,1,0),(30,2,0)], insert owner3 at20 and40; determine all changed positions before running the implementation.

## Necessity

A hash table does not maintain placement under a changing destination set. Virtual tokens are not distinct physical replicas. Stable membership does not imply balanced load, and a migration plan does not move data durably. Address these independent misconceptions with proofs, executable boundary cases and local adversarial layouts rather than claiming them from one ordinary lookup test.

## Reasoning

Derive successor from modular distance and prove insertion/removal monotonicity under unchanged existing tokens. Separate token identity, position collision, physical owner and view epoch. Show why reseeding, byte-order changes or forged public structs invalidate premises. Prove failure outputs stay unchanged, including migration-plan capacity exhaustion after earlier staged moves. Derive construction/lookup/replica/plan complexity and full stack/state costs. Compare Karger’s nearest-interval construction with the adopted clockwise ring and identify which probabilistic assumptions are absent. Explain why different Merkle range/view interpretations cannot be compared merely because each has a root.

## Deliverables

- D1: representation, invariants, monotonicity proof, source distinctions and static/runtime/caller enforcement dossier.
- D2: complete original ring provider, actual prior-hash adapter and migration-plan composition; retain the exact dependency interface and failure contract.
- D3: all-key movement checks, independent modular-distance oracle, compiled semantic defects, every finite failure boundary, source-bound target dependency audit and load/work/cost report.
- D4: independent degraded-view transfer with an explicit account of what a durable handoff would additionally need; record assistance and delayed evidence separately.

## Security

Target only the original ring in [labs/corpus_ring](../../../labs/corpus_ring) with synthetic membership and keys, in one local process.

- **Adversary.** You choose token positions, labels, ordinals, availability masks, byte keys and the order of membership changes, including equal positions and lists that fill capacity. You do not control the hash component, code or pointers, and you do not forge a ring after cr_build admitted it. Worked case (lookup anchor): three tokens share position 100, (owner 3, ordinal 0), (owner 2, ordinal 0) and (owner 2, ordinal 1), and the contract orders equal positions by owner then ordinal, so key 100 belongs to owner 2 (tests.c:16, 21).
- **Violated property.** Placement integrity. Lookup is the clockwise successor under the exact tie order. A change moves only the keys of the one owner it adds or removes, which is why every one of the 65,536 keys must keep its old owner or move to owner 3 (tests.c:52-58). Replicas are distinct available physical owners. A failed build, change or plan publishes nothing: an aborted change leaves the ring byte-identical (tests.c:45-49), and the supplied tests check the unchanged moves array only for capacity 1 (tests.c:65-66), not for capacity 0, which asserts only that n stays 99 (tests.c:64).
- **Experimental boundary.** One hosted process and in-memory structs, no thread, child, socket, file or network. Flawed variants of your own are compiled and run only in your disposable build; the supplied suite contains none.
- **Evidence to capture.** Predict first, including every changed key. Tokens {10,1,0} and {30,2,0} with owner 3 added at 20 and 40 and the keys {0,10,11,20,21,30,31,40,41}: key 0 and 10 stay with owner 1, 11 and 20 move from owner 2 to 3, 21 and 30 stay with owner 2, 31 and 40 move from owner 1 to 3, and 41 wraps to owner 1, so four moves, all to owner 3. Then run CTest corpus_ring.lookup, corpus_ring.membership, corpus_ring.replicas and corpus_ring.routing and record the quoted results in labs/corpus_ring/tests.c (owner 2 for the tied key 100, CR_ABORTED for cuts 0..4 with an unchanged ring, 4 moves all to owner 3, owners 1,2,3 then CR_UNAVAILABLE, CR_HASH_FAILED with unchanged output). Build your own variants as described in the header and record the `CR_CHECK:N` line that rejects each; if none does, you have found a gap in the supplied tests, and that is a result worth reporting.
- **Impact class.** demonstrated-invariant-violation, once you have built and run a variant. Observed load capture, duplicate replicas, stale routing or partial publication in a flawed variant is a broken invariant; it is not proved impact.
- **Remediation.** Identity validation, exact tie order, distinct available physical owners, publication only after all checks, and surfaced hash failure. The tests that reject the original defects are corpus_ring.lookup, .membership, .replicas and .routing; run each against your matching variant.
- **Limitations.** Admitted versus forged-state premises must be stated: reads trust the admitted ring. No Sybil resistance, Byzantine tolerance, authenticated membership, safe data movement or arbitrary code execution is shown.
