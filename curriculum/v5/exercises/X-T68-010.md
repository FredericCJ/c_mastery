# X-T68-010: Declarative build graphs and deterministic table generation

## Prerequisites

Complete the earlier domain projects and retain the named prerequisite artifacts with their contracts, ownership ledger and tests. Required learner artifacts: testing.faults, codec.records. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [metaprog/CONTRACTS.md](../../../labs/metaprog/CONTRACTS.md).

## Problem

Implement mp_build for0..8nodes with dependency bitmasks, source bytes, tool identity and configuration identity. Reject out-of-range dependencies/cycles; choose the lowest ready index deterministically. Compute each64bit FNV-1a key from length, source bytes, tool, configuration and ordered(dependencyindex,dependencykey) words. Encode words little-endian8bytes; output order/keys only after full success. Implement mp_emit_table for1..8keys as a bounded generated C uint64 array and compile the generated file in a temporary directory.

Concrete inputs and expected results: Two nodes0->1 executeorder[0,1]. Changingnode0configuration changes bothkeys. A cycle0<->1 fails with previous outputs unchanged. Generated source retains all64bits of eachkey and is reproducible byte-for-byte.

Supplied artifacts: labs/metaprog/include/metaprog.h, compiling unsolved src/metaprog.c, CTest metaprog.buildgraph, fixtures/metaprog/PR-T68-10.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Derive build ordering separately from action invalidation, identify hidden inputs, and explain why a content key is only as complete and collision-resistant as its declared input model. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Prove Kahn-style readiness and termination, show how dependency content propagates into consumers, and distinguish source identity from timestamp ordering. Compare Ninja explicit/implicit/order-only dependency semantics and command-line rebuild tracking. The educational FNV key is not collision-resistant; require full input equality or a suitable cryptographic digest before any untrusted shared cache use. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

## Deliverables

- D1: Derive build ordering separately from action invalidation, identify hidden inputs, and explain why a content key is only as complete and collision-resistant as its declared input model.
- D2: Prove Kahn-style readiness and termination, show how dependency content propagates into consumers, and distinguish source identity from timestamp ordering. Compare Ninja explicit/implicit/order-only dependency semantics and command-line rebuild tracking. The educational FNV key is not collision-resistant; require full input equality or a suitable cryptographic digest before any untrusted shared cache use.
- D3: Run metaprog.buildgraph and independent Python topological/hash reconstruction. Kill omitted-configuration and omitted-dependency-key mutants. Compile/run the generated C table consumer, permute input storage without changing logical IDs, and inject a missing implicit dependency to demonstrate stale generated metadata.
- D4: Introduce an incremental cache with toolchain, environment, include-file and schema dependencies. Simulate crashes during artifact publication and hash collisions; define atomic replacement and full-input verification. Compare a parallel scheduler only after establishing dependency and output ownership. Complete all thirteen cost/enforcement dimensions with evidence or a mechanism-specific non-applicability.

## Verification

Preserve predictions before execution, exact commands, source/input/toolchain identity and observed outputs. Explain independent-oracle assumptions and minimize disagreements. A supplied anchor or compiled mutant checks only its named property. Failure-side effects, ownership accounting and the required changed-condition result are pass/fail gates; finite tests cannot establish absolute mastery.

Apply the shared six-dimension rubric as well.

3. A fast noncryptographic hash cannot authenticate build inputs.
