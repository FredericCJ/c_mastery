# X-T69-004: Capture ownership and shared, mutable, consuming invocation

## Prerequisites

Bring pinned contracts and fresh recall for containers.array; prerequisite exercises: X-T03-003. Required knowledge includes C object lifetime, checked arithmetic, ownership, typed arrays and the selected source passages. The shared contract and modern-cost contract are explicit parts of this exercise. Existing project estimates describe author accounting; they impose no learner time ceiling.

## Environment

Use C17 hosted Linux with GCC and Clang, CMake and host Python. Record compiler/ABI versions, integer widths, sizeof/alignment and optimization. Mechanism code uses no library implementing the mechanism. Allocator callbacks are supplied dependencies with separate ownership. A strict freestanding port requires its own generated-code/link audit and is not established by the hosted run. Compare C11 draft/C17/C23 only where inspected normative evidence supports the claim; exact published C17 access remains a reference gap.

## Problem

Implement DSClosure init/call with shared, mutable and once modes. The concrete body performs checked int addition of capture and argument. Shared keeps capture, mutable stores a successful result, and once consumes on the first admitted attempt even if arithmetic fails. Add a typed closure holding a borrowed array slice and a once closure owning a synthetic resource with a no-fail release callback. Define capture lifetime, allowed invocation and failure cleanup explicitly for each.

Supplied artifacts: labs/dispatch/include/dispatch.h, deliberately incomplete labs/dispatch/src/dispatch.c, executable anchors, fixture PR-T69-04.json and the shared CONTRACTS.md. Expected example: Capture3 shared calls with2 return5 repeatedly without capture mutation. Mutable calls return5 then7. Once capture1 with2 returns3 and later DS_EMPTY. Once INT_MAX with1 returns DS_RANGE with unchanged output and becomes inactive.

## Necessity

Capture form and call capability answer different questions. A local runtime flag cannot make all aliases obey linear consumption, and error paths need a defined consumption policy.

## Reasoning

T69.04.a: Separate capture-by-value/reference from invocation capabilities and explain the documented Rust rule that move capture alone does not imply only FnOnce.

T69.04.b: Implement the three explicit modes with checked arithmetic, exactly-once consumption and clear borrowed/owned capture lifetimes; add borrowed-slice and owning-resource closures.

T69.04.c: Enumerate operation sequences including repeated calls, failed calls, reinitialization under its ownership precondition and copied-state misuse; compare state transitions with an independent finite model.

T69.04.d: Transfer to a retained asynchronous callback. Establish an environment outlives relation, cancellation ownership and reentrancy policy; show how copying an active C struct defeats a local consumed bit even when every ordinary call checks it.

State preconditions, postconditions, representation invariants, resource ownership, failure publication and complexity. For each guarantee identify ISO C rules, diagnostics, runtime checks, external verification and programmer discipline separately. Include a minimal counterexample to an overstated equivalence with the corresponding language/library abstraction. Apply all13 dimensions in modern-cost-contract.md, recording genuine non-applicability with reasons and unavailable measurements as gaps.

## Completion stage: borrowed slice and transferred resource

Implement `struct ds_borrow_closure`, `struct ds_owned_closure` and `struct ds_owned_result` from `dispatch_extensions.h`. Import the existing counted-int32 adapter and its actual T66/T70 dependencies. Borrowed calls use the identical final-sum policy, so `[INT32_MAX,1]` with argument0 fails without publishing and consumes once mode; argument-1 succeeds with INT32_MAX in shared mode. Keep the actual slice alive; derive the raw-pointer lifetime limit separately instead of executing an expired pointer.

For X-T69-004-DELAYED, use the original synthetic resource with live/drop/call counters. Invalid body admission must preserve the live closure and leave call count0. On admitted recoverable failure, clear the closure before invocation, return the still-live resource in `result.retry`, and leave drop count0. Transfer retry into a fresh inactive owner, explicitly clear the result, then call success and observe exactly one drop. Fatal body failure also consumes and drops exactly once; dropping an uninvoked owner drops once and repeated drop does nothing. Run `dispatch.owned_closure` and both mutants. D1 draws the two ownership transfers and distinguishes wrapper admission status from body outcome; D2 implements the result and drop policy; D3 logs every ownership transition; R1/R2/R3 require its precise failure semantics. R4's retained asynchronous environment still needs the separate cancellation protocol: this synchronous owner alone proves no asynchronous safety. The original seven-day independent variant remains an assessment condition, not author-run evidence.
