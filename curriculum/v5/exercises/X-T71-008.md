## Security

Target `pt_driver_start`, `pt_driver_complete` and `pt_driver_recover` in `labs/protocols` over the synthetic register and DMA port (no board is needed), using only synthetic values. No network service or hardware is involved.

- Adversary: scripts the fake port: start failure, completion while the device is still active, completion after quiescence and a repeated completion. It cannot alter quiescence facts or forge the borrowed pointer.
- Violated property: the buffer stays owned until quiescence is proved; a failed start enters PT_RECOVERY_REQUIRED holding the same pointer; a non-quiescent completion neither releases it nor feeds the watchdog.
- Boundary: in-process host model; harmless success is the illegal state change or counter recorded by the harness, never a crash left running.
- Evidence to capture: run `protocols.driver` (failed start gives PT_RECOVERY with d.buffer==b==port.borrow; recover is PT_PENDING until port.quiet; completion (0,0) is PT_PENDING with watch 0; (0,1) releases and sets watch 1; a repeat is PT_STATE with watch 1). Build an early-release variant as `labs/protocols/CONTRACTS.md` asks and record the premature release or watchdog event.
- Impact class: demonstrated-invariant-violation, from the learner-built defective variant only (no flawed variant is supplied and the supplied test passes on a correct build, so no supplied artifact demonstrates it); not a crash, sanitizer finding or undefined behaviour, and not a proved impact (no real DMA corruption).
- Remediation and regression: retain on uncertainty, one exit via recover, watchdog only on normal completion; `protocols.driver` must fail the variant.
- Limitations: real register ordering, cache maintenance, interrupt serialization and previous-boot epochs are outside the host model.
