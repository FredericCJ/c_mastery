# X-T15-017: Ordered runs, versioned merge and tombstone-safe compaction

## Prerequisites

Know sorted maps, typed arrays, half-open bounds, unsigned arithmetic and strong failure publication. Bring a small exact map oracle and invariant traces from the retained container/search work. Tree work additionally requires ordinary B-tree splits and ownership/reachability; runs require stable merge and version ordering. No library may implement the assessed mechanism. These new required exercises do not inherit historical elective exclusions.

## Environment

The explicit [ordered storage contract1](../../../labs/corpus_storage/CONTRACTS.md) supplies all representations, operations, input/output domains, ownership, statuses, capacity/work bounds and security scope. Implement `src/storage.c`. Distinguish compiler helpers from target dependencies and host oracles. Changing ABI, optimization or execution environment requires revisiting stack/copy measurements and helper closure; no strict linked-image claim is made.

## Problem

Implement a sorted four-entry memtable and three immutable32-record runs. Write key1=10 and flush, write key1=20 and flush, then delete key1 and flush. Compact only the two newest runs and show the old value stays hidden; then compact all active runs with empty memory and drop tombstones safely. Compare overwrite-heavy and distinct-key workloads, logical record writes and lookup probes.

## Necessity

Returning the first run match confuses physical age with version order. Dropping a tombstone during partial compaction can resurrect an old value outside the merge. Flush, merge, publication and durable persistence are different events; capacity backpressure and sequence exhaustion must remain observable.

## Reasoning

Derive the sorted-stream frontier invariant and maximum-sequence winner rule. Prove the conservative all-runs-and-empty-memory requirement for tombstone dropping. Account for memtable insertion shifts, merge comparisons, output record writes, read probes and fixed capacities under equal map semantics. Describe publication failure versus system reset and explain why the bounded RAM-run adaptation is not the original paper's entire disk engine. Provide preconditions, postconditions, representation/loop invariants, ownership, failure and complexity arguments. Distinguish ISO C guarantees, diagnostic checks, runtime admission, external proof/model evidence and caller discipline. Include one plausible incorrect explanation and a minimal counterexample.

## Deliverables

- D1: Representation and source-claim derivation, precise contract and misconception counterexample.
- D2: Original C implementation, costs for logical operations and actual storage/copies, and operation/failure ownership ledger.
- D3: Independent model, concrete boundary/injected-failure inputs and outputs, invariant snapshots and two causal semantic mutants.
- D4: Named delayed implementation/predictions, changed-assumption comparison under equal correctness contracts, and validation limits.

## Verification

Exercise empty flush, full memory replacement, no run slots, every record/publication cut, partial/full merges, invalid masks and sequence/counter exhaustion. Kill first-match lookup and partial tombstone dropping. Retain the original three-generation witness after repair. Run GCC/Clang debug, optimized and address/undefined sanitizer profiles. Preserve exact commands, logs, source identities and compiler configuration. The compiling learner stub must fail `corpus_storage.lsm` with `SS_ASSERT:`. A finite differential campaign supports the specified tested scope; it neither proves all histories nor replaces D1/D4.

## Hints

1. Treat a tombstone as a record with a sequence number until you prove no older value can reappear.
2. For each output key inspect the head of every selected sorted stream, then advance all matching heads.
3. Keep an unselected older run during your first deletion test; merging only the newest runs otherwise hides the defect.

## Security

Why this matters here. In a log-structured store a delete is not an erase but a newer record, a tombstone, and the newest sequence number wins. That makes compaction dangerous: merging some runs but not all, then discarding the tombstone because it "looks done", exposes an older value that sits in a run outside the merge. The data comes back to life with no error of any kind. The test builds exactly that history. Key 1 is written as 10 and flushed (run 0), written as 20 and flushed (run 1), deleted and flushed (run 2). Compacting mask 6 (runs 1 and 2) with drop 0 must keep the tombstone in the merged run, so ss_lsm_get(1) stays SS_MISSING; if the tombstone were discarded, the lookup would find 10 in run 0.

What to try. Trace by hand the three flushes and the mask-6 compaction, listing the records in each run and their relative sequence order, then the later compaction with mask 3 and drop 1: all active runs are selected and memory is empty, so the tombstone and everything it shadows may go. Work out which of those two conditions each rejected call in the test (mask 2, and a nonempty memtable) violates. Then build two causal variants of your own: one that lets a deleted key reappear after a compaction, and one that lets a lookup answer with something other than the newest version.

What to capture and how to read it. A failed check prints `SS_ASSERT:<line>:<expression>` and exits 41; keep it per variant. The mask-6 sequence is the resurrection check; the 20-versus-10 lookup is the newest-wins check. Note that the mask-2 rejection does not isolate the every-active-run rule, since a single-run mask is refused anyway; to see that rule, set up three live runs and compact two of them with drop 1. Keep the failure-ordinal results (flush and compaction ordinals 1 to 5 leave the owner identical), the full-memtable SS_FULL and the exhausted-sequence SS_EXHAUSTED, and the write and probe counts for overwrite versus distinct-key workloads, which are logical record counts, not device writes.

What this does and does not show. Deleted-value resurrection or a stale answer in a RAM model on synthetic keys. No supplied artifact demonstrates it, so the impact class holds only once you build a variant. The assessor's mutation set also checks this invariant. Durability, crash recovery, torn writes, concurrency, background compaction and physical devices are not demonstrated.
