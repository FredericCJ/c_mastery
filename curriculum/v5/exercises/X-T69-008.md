# X-T69-008: Opaque modules with explicit service injection and failure effects

## Prerequisites

Bring pinned contracts and fresh recall for io.stream, containers.array; prerequisite exercises: X-T69-003. Required knowledge includes C object lifetime, checked arithmetic, ownership, typed arrays and the selected source passages. The shared contract and modern-cost contract are explicit parts of this exercise. Existing project estimates describe author accounting; they impose no learner time ceiling.

## Environment

Use C17 hosted Linux with GCC and Clang, CMake and host Python. Record compiler/ABI versions, integer widths, sizeof/alignment and optimization. Mechanism code uses no library implementing the mechanism. Allocator callbacks are supplied dependencies with separate ownership. A strict freestanding port requires its own generated-code/link audit and is not established by the hosted run. Compare C11 draft/C17/C23 only where inspected normative evidence supports the claim; exact published C17 access remains a reference gap.

## Problem

Implement an opaque DSModule factory backed by two actual typed instances and a borrowed DSService read operation. twice performs two reads then checked addition; publication is atomic but external read effects are not rolled back. Add an instance-local service dictionary containing clock and sink dependencies, passing only the required subset to each operation. Build a second implementation behind the same incomplete public type contract and test clients without private-header access.

Supplied artifacts: labs/dispatch/include/dispatch.h, deliberately incomplete labs/dispatch/src/dispatch.c, executable anchors, fixture PR-T69-08.json and the shared CONTRACTS.md. Expected example: Two service reads of7 return14 with exactly two calls. Failure on the second read preserves caller output99 while the call count remains2. A third simultaneously open module returns full and preserves the output pointer. Closing ends the lease and all module aliases must be discarded.

## Necessity

Hiding a struct definition narrows ordinary client access, but does not manage callback lifetime or make external effects transactional. Dependency injection should expose the actual retained services.

## Implemented opaque and shared-owner continuation

The common `tests/modules.c` client uses only public headers and runs against the original `dispatch.c` implementation and a separately linked `module_alternative.c` with a different private `DSModule` representation. Implement the alternative behind the same public incomplete type and preserve the exact two-read contract. The fixture supplies75 combinations of input values and read-failure positions per implementation, including both signed extrema. A Python integer model independently predicts callback count, callback inputs, status and output. Three rejected translations attempt a private field access, a metric key supplied to a user map and a metric value supplied to a user map; the positive client compiles first.

For the owned delayed variant, import actual `cleanup.scope` from PR-T66-02 / X-T66-002 and `ownership.shared` from PR-T66-06 / X-T66-006 using the declared ownership source adapter. These are additional prerequisites for this continuation; the borrowed core needs only its earlier prerequisites. A stable `DSModuleRegistry` has two entries and finite generations1..3; a lease contains registry identity, slot and generation. Retain the read-context owner, then the clock/sink-context owner, then open the underlying module. Inject failures before the first retain, after each retain and after opening the module. Register each acquired obligation with the actual `OwScope` as ON_ERROR; rollback closes the module then releases IO and read owners. Success discards rollback entries and publishes the lease last. A full registry rejects before retaining dependencies; a full underlying module factory rolls acquired references back. Failure preserves the output lease and existing registry state.

Each operation receives only its required service: the opaque twice implementation retains the read interface; the clock leaf receives `DSClock`; the sink leaf receives `DSSink`. The controller retains the whole instance dictionary and selects these subsets. Context-to-owner correspondence remains a caller obligation. Clock output is staged on failure; sink failure does not undo an already observed write. Closing clears the live entry and advances its generation before closing/releasing resources; release IO then read. Generation4 is permanently retired, yielding at most six leases per registry lifetime. Reject an old lease while its slot is live with a new generation, not just while empty. Clients must keep the registry alive until every lease token is discarded and never reinitialize it while tokens survive.

`DSUserKey`/`DSUserValue` and `DSMetricKey`/`DSMetricValue` are distinct named struct facades over two four-entry maps. Valid keys are0..3; missing keys return DS_EMPTY and out-of-range keys DS_INVALID, preserving the output. Updates replace the selected value. These types enforce the finite declared key/value correlation at ordinary typed call sites. Casting/erasure can discard that relation; a runtime selected `void*` dictionary cannot manufacture arbitrary associated types or prove a contextual ownership relation. Explain how separately linking two private concrete implementations differs from a runtime existential package.

R1 requires the public/private type argument and lease lifetime; R2 requires staged publication plus irreversible callback traces; R3 requires both implementation runs, all four acquisition cuts, actual T66 reuse and expected compiler failures; R4 requires the correlated facades and a counterexample to stronger existential/ownership claims. Hints: register cleanup immediately after each acquisition; keep token generation outside the opaque object; give the clock leaf only its clock parameter. The two semantic controls for the alternative suppress the second read or publish the first result early; the shared-owner controls suppress rollback or ignore generation. All author observations remain distinct from an independently delayed learner attempt.
