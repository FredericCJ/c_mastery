## Necessity

Executing arithmetic during parsing destroys the distinction between a valid program and a failed semantic operation and risks C signed overflow.

Prove that right-associative exponent lowers its recursive threshold while left association does not. Bound recursion from token admission, prove child-before-parent tree construction and separate source-location, syntax and arithmetic failure contracts. ## Security

An expression evaluator is trusted to say what a number means. Two failures matter here: it can group the same bytes differently than the specification says, so `-2^2` or `2^3^2` changes value, and it can let an arithmetic result wrap and report success, so `2147483647+1` becomes a negative number with `PD_OK`. The only target is your own `pd_lex`, `pd_pratt` and `pd_evaluate` in `labs/parsing_depth/src/parsing.c`, on synthetic expressions.

Why it matters here. The contract (`labs/parsing_depth/CONTRACTS.md`, section X-T15-012) separates parsing from evaluation: `2147483647+1` is valid syntax and must parse, then `pd_evaluate` must widen before the addition and return `PD_RANGE` with the output untouched. Exponents must be integers 0..31, so `2^-1` is `PD_DOMAIN`. The binding powers (add and subtract 10, multiply 20, unary minus 30, exponent 40) and the caller's `right_power` flag decide whether `2^3^2` is 512 or 64.

What to try. Evaluate `-2^2`, `2^3^2` in both modes and `1+2*3` by hand with the stated powers, then run `ctest -R parsing_depth.pratt` and compare with the anchor. Next build two variants of your own. For the wrap, compute in `uint32_t` and convert the result back to `int32_t`: that arithmetic is defined, and the final conversion of an out-of-range value is implementation-defined (N1570 6.3.1.3p3), so record what your compiler does with it. For the grouping, change the binding powers so `-2^2` or `2^3^2` groups the other way. Keep a plain `int32_t` addition, which is signed overflow and undefined behaviour (N1570 6.5p5), out of the comparison: if you try it under UBSan, report the sanitizer message as a separate observation, because an optimizer is allowed to do anything with it.

What to capture and how to read it. Keep the `PD_ASSERT:<line>:<expression>` line, the expression, the mode, the status, the value, and the output before and after the call. Compare tree shapes against your separate operator-stack parser. A wrapped value with `PD_OK` against `PD_RANGE` is the whole demonstration; do not read a sanitizer report as more than it is. The assessor's mutation set also checks this invariant.

Impact class. `demonstrated-invariant-violation`, and only once you build a defined wrapping or mis-grouping variant and show it on a named expression. The specified evaluator never overflows, so it produces no crash or sanitizer finding of its own; the signed-overflow experiment is a separate undefined-behaviour observation.

Remediation and regression. Widen before add, subtract, multiply and negate, return `PD_RANGE` or `PD_DOMAIN` with the output unchanged, and keep parsing and evaluation separate. Keep your failing expressions beside the existing `parsing_depth.pratt` assertions.

Limitations. Finite cases do not prove the evaluator correct for every input, and this is not a sandbox for hostile expressions beyond the declared limits (256 bytes, 64 tokens, 64 nodes).
