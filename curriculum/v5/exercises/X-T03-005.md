# X-T03-005: Finite handle identity

## Prerequisites

Complete X-T03-003 and read T03.10/T03.13. Bring explicit owner lifetime and construction cleanup reasoning. If `memory.pool` is accepted, document how this typed-slot/generation adapter refines it; preserve that artifact's old contract and historical receipts. This exercise's fixed capacity and retirement policy are additive.

## Environment

Apply [shared contract v1](shared-contract.md). The pool is a real typed `struct fd_pool` object with three `struct fd_value` entries. No heap allocation, integer-to-pointer reconstruction or concurrency is used. All operations require the owner to remain alive at a stable address. Corrupted object representations and calls through dangling owner pointers are outside the callable contract.

## Problem

Implement `fd_pool_init`, `fd_pool_acquire`, `fd_pool_get` and `fd_pool_release`. The void initializer requires a live non-null pool owner. A handle contains owner pointer, index and generation. Initialization sets three available typed slots with generation 1. Acquire chooses the lowest-index available non-retired slot, copies a complete FDValue, marks live and publishes its handle; if none exists return `FD_FULL` without changing output.

Lookup copies the stored value only when owner matches the supplied live pool, index is below three, slot is live and generation matches. Otherwise return `FD_STALE` with unchanged output. Release applies the same identity test; it marks the slot not live and advances generation, except generation 3 is permanently retired. Never wrap a generation to 1. Null required control/output pointers return `FD_INVALID`. Repeated release rejects as stale. Initialization is allowed once per owner lifetime before handles are issued, not as a way to revive exhausted generations.

Create histories in which a handle is copied, released, and presented after the same slot is reused. Also use a handle belonging to a distinct simultaneously live pool; this must reject. All supplied handle owner pointers must themselves remain valid pointer values throughout the test.

## Necessity

A finite generation counter cannot provide unbounded unique identity under unrestricted reuse. Checking generation alone can miss wrong-owner mistakes. A handle is neither a lifetime-extending reference nor an authorization capability merely because its fields look valid.

## Reasoning

State the slot invariant over live/free/retired and generation. Derive why a released handle cannot become valid again during one permitted pool lifetime. Prove rejection occurs before indexed access, and characterize the finite cost of retirement: at most nine acquisitions succeed for this configuration without changing the contract.

Provide a state-history counterexample for wraparound and an analysis-only destroyed-owner example. Do not read or compare a dangling pointer just to produce the latter. Explain that a shallow C handle copy is allowed and its validity is checked at runtime, whereas the inspected Rust move rule applies to particular ownership-bearing values and does not automatically solve arbitrary logical identifier reuse. ISO C does not enforce this pool's owner lifetime or retirement policy.

Lookup/release are O(1); acquisition scans at most three entries, generalized O(capacity). Storage is O(capacity); no deallocation or destructor callback is required because FDValue owns no external resource. Relate that simplification to X-T03-003 rather than generalizing it to arbitrary values.

## Deliverables

- **D1:** abstraction/invariant, identity proof, invalidation table and finite exhaustion/counterexample analysis.
- **D2:** pool operations plus `memory.pool` compatibility note.
- **D3:** complete per-slot generation histories, stale/wrong-owner/index rejection, preserved-output evidence and retirement mutant regression.
- **D4:** owner-registry or epoch transfer with a new finite-identity proof and cost accounting.

## Verification

Run `foundation_depth.handles`. Hold and release every handle issued over all three generations, then demonstrate that no further acquire succeeds. Check stale handles after each transition, including duplicate release and full/retired states. Test index 3 and SIZE_MAX using live-owner handles and preserve get/acquire output sentinels on rejection.

Model one slot's transitions exhaustively and lift the argument to three independent slots plus allocation choice. Generate interleaved acquire/get/release histories against an independent symbolic model. A wrap-to-one mutant must compile and revive a retained generation-1 handle in the model/test; the repaired implementation must reject it. No thread interleavings are claimed in this single-threaded lab.

## Rubric

Assess owner assumptions, stale rejection, finite exhaustion and borrow validity separately. A counter that merely delays wraparound earns at most 1 for correctness. Claiming the pool remains safe after destruction fails the lifetime criterion. Level 3 requires an unfamiliar owner/epoch policy with explicit bounds.

## Hints

1. Keep a copy of the first handle while cycling the slot.
2. The end of the generation range is a state transition, not a reason to rely on unsigned wrap.
3. Trace the owner object itself; a valid slot number says nothing about that object's continuing lifetime.

## Variants

Delayed assessment identifier: `X-T03-005-DELAYED`. Attempt it at least seven days after the recorded studied event; the recommended interval is one to two weeks.

Replace copying lookup with a const borrowed pointer and define invalidation at release. Then design an external registry for multiple movable owners, including registry generation exhaustion. Delayed assessment proposes resetting retired slots at a maintenance boundary; accept it only after proving no prior handles can survive that boundary or rejecting the proposal with a counterexample.

## Security

Synthetic local pools only. Handles are not secret capabilities and do not authenticate users. Wrong-owner tests use two live owners, never dereference freed storage. No exploitation of real allocators or external systems is included.

## Validation

Authored finite model and typed implementation contract. No evidence of concurrency safety, indefinite identity, external registry correctness or physical validation is implied. The taxonomy's broader provenance-model comparison remains open beyond this bounded identity exercise.
