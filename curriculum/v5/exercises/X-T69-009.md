# X-T69-009: Authority attenuation, revocation and the limits of C tokens

## Prerequisites

Bring pinned contracts and fresh recall for memory.pool; prerequisite exercises: X-T03-005. Required knowledge includes C object lifetime, checked arithmetic, ownership, typed arrays and the selected source passages. The shared contract and modern-cost contract are explicit parts of this exercise. Existing project estimates describe author accounting; they impose no learner time ceiling.

## Environment

Use C17 hosted Linux with GCC and Clang, CMake and host Python. Record compiler/ABI versions, integer widths, sizeof/alignment and optimization. Mechanism code uses no library implementing the mechanism. Allocator callbacks are supplied dependencies with separate ownership. A strict freestanding port requires its own generated-code/link audit and is not established by the hosted run. Compare C11 draft/C17/C23 only where inspected normative evidence supports the claim; exact published C17 access remains a reference gap.

## Problem

Implement the original DSAuthority/DSCapability model over a synthetic int counter. Rights bits1(read) and2(add), owner identity and finite epochs enforce checked API requests. Issue and attenuation must never add rights; add requires both root and capability permission; revoke invalidates old epochs and retires after3. Attack only this cooperative local model by requesting a stronger mask, reusing a revoked capability and crossing owners. Then analyze a C client that directly forges exposed fields: explain why this violates the model and refutes a broader security claim. Design an opaque broker/process boundary that can enforce the stronger threat model.

Supplied artifacts: labs/dispatch/include/dispatch.h, deliberately incomplete labs/dispatch/src/dispatch.c, executable anchors, fixture PR-T69-09.json and the shared CONTRACTS.md. Expected example: A full-rights capability can add5. Its attenuated read-only capability cannot change the counter. Attempting to attenuate read-only rights to full rights rejects with output unchanged. After revocation, the former full capability returns stale and the counter remains5.

## Necessity

The attacker perspective reveals whether a token is actually authoritative or simply trusted data. A subset check is meaningful only under a threat model that prevents the caller from changing the checked authority metadata.

## Reasoning

T69.09.a: State the authority graph, permitted attacker actions and property: delegated rights remain a subset and revoked epochs cannot authorize a new effect. Distinguish a cooperative token from an unforgeable capability.

T69.09.b: Implement subset admission, owner/epoch validation, bounded revocation and checked effect publication without global ambient authority.

T69.09.c: Enumerate all rights masks, owner pairs and epoch transitions; demonstrate harmless unauthorized-counter change in the two explicit mutants and regression rejection in the repair.

T69.09.d: Transfer to delegation across an actual process boundary with opaque server-side IDs. Define authentication, replay, ID reuse, revocation and confused-deputy behavior, and show why a hidden C struct alone does not solve arbitrary in-process writes.

State preconditions, postconditions, representation invariants, resource ownership, failure publication and complexity. For each guarantee identify ISO C rules, diagnostics, runtime checks, external verification and programmer discipline separately. Include a minimal counterexample to an overstated equivalence with the corresponding language/library abstraction. Apply all13 dimensions in modern-cost-contract.md, recording genuine non-applicability with reasons and unavailable measurements as gaps.
