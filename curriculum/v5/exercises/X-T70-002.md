# X-T70-002: Inline bytes, allocator failure and explicit relocation

## Prerequisites

Bring pinned contracts and fresh recall for memory.pool, containers.array; prerequisite exercises: X-T03-003, X-T03-005. Required knowledge includes C object lifetime, checked arithmetic, ownership, typed arrays and the selected source passages. The shared contract and modern-cost contract are explicit parts of this exercise. Existing project estimates describe author accounting; they impose no learner time ceiling.

## Environment

Use C17 hosted Linux with GCC and Clang, CMake and host Python. Record compiler/ABI versions, integer widths, sizeof/alignment and optimization. Mechanism code uses no library implementing the mechanism. Allocator callbacks are supplied dependencies with separate ownership. A strict freestanding port requires its own generated-code/link audit and is not established by the hosted run. Compare C11 draft/C17/C23 only where inspected normative evidence supports the claim; exact published C17 access remains a reference gap.

## Problem

Implement the DSmall operations: init, append, truncate, compact, move, reset and borrowed data access. Inline capacity16 and maximum128 are part of the shared contract. Supply a fixed-capacity, typed byte-array allocator adapter that records requests and fails each requested allocation in turn; a host malloc adapter is an additional test only. Construct a separate fixed-capacity16-byte variant that always rejects spill. Compare its contract and owner size with DSmall. No string terminator, generic typed placement, automatic copy constructor or raw-struct move is supplied.

Supplied artifacts: labs/dod/include/dod.h, deliberately incomplete labs/dod/src/dod.c, executable anchors, fixture PR-T70-02.json and the shared CONTRACTS.md. Expected example: Appending16 bytes performs no allocation. A failed17th byte preserves length16 and all bytes. Successful spill followed by move leaves the source empty and transfers exactly one allocation. Truncating to8 and compacting frees that allocation once; resetting both owners performs no second free.

## Necessity

Small-buffer optimization introduces two ownership regimes and an often-hidden object-type problem. An address satisfying alignment is not proof that a declared unsigned-char array may be accessed through any desired struct pointer.

## Reasoning

T70.02.a: Derive the representation invariant for empty, inline and heap states and the exact invalidation events for borrowed views; explain why alignment of a character array alone does not permit arbitrary typed C objects.

T70.02.b: Implement all capacity transitions and a fixed-capacity alternative using allocator injection, with strong append rejection and exactly-once resource release under move/reset.

T70.02.c: Inject every allocation failure and test capacity16/17, maximum128, zero append, self move, nonempty destination, repeated reset and compact after truncation; compare byte sequences with an independent list model.

T70.02.d: Compare the documented LLVM inline-vector idea with this C byte representation and a typed-union alternative. Measure owner footprint, allocations, copy traffic and spill hysteresis rather than claiming universal zero overhead.

T70.02.e: Integrate dod.small_buffer with an erased closure byte capture: define which values can be encoded, which callbacks own external resources and why memcpy of a self-referential capture is not relocation.

State preconditions, postconditions, representation invariants, resource ownership, failure publication and complexity. For each guarantee identify ISO C rules, diagnostics, runtime checks, external verification and programmer discipline separately. Include a minimal counterexample to an overstated equivalence with the corresponding language/library abstraction. Apply all13 dimensions in modern-cost-contract.md, recording genuine non-applicability with reasons and unavailable measurements as gaps.
