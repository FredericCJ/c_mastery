## Security

The target is the learner's `b5_copy_to_user` in `labs/b05_depth/src/depth.c`, operating on an original 64-byte array split into four synthetic pages. The attacker controls the destination address, the count and the page permission flags in the fixture; the array, page size and the harness are fixed. No page table, kernel or host privilege exists in the experiment.

**Property.** A copy is all-or-nothing: if any page in the range lacks the required presence, user or writable permission, or the address plus count overflows, the status is an error and every byte of the array is unchanged.

**Experiment and evidence.** Predict first. The public test `copy` in `labs/b05_depth/tests/tests.c` (CTest `b05_depth.copy`) pins that a 4-byte copy at address 14 crosses the page boundary and succeeds, that with page 1 not writable a 2-byte copy at 15 returns B5_CONFLICT and `p[0].bytes[15]` keeps its old value, that address 64 with count 0 succeeds, that address 64 with count 1 and `SIZE_MAX` with count 2 return B5_RANGE, and that a missing user flag returns B5_CONFLICT. The public test checks only that one byte, so take a snapshot of all 64 bytes before and after yourself. Build the incremental-write mutant the brief asks for, capture its non-empty diff next to the empty diff of the correct build, and record which CHECK rejects it.

**Impact class.** A visible prefix after a rejected request is a `demonstrated-invariant-violation` in the model once you build and run the incremental-write mutant; no supplied artifact demonstrates it. It is neither a crash nor a privilege escalation, because there is no privilege boundary here to cross.

**Repair and limits.** Repair by preflighting every page in the range, including overflow checks, before the first write, then keep byte-for-byte array equality after each rejection as the regression, which must reject the mutant. State that real MMU behaviour and check-versus-copy races are outside this lab.
