## Security

The target is the learner's `b5_recover` in `labs/b05_depth/src/depth.c`, run on copied synthetic record arrays. The attacker controls the fixture records: generation, value, XOR checksum and commit flag. The checkpoint and the model's crash cuts are fixed by the harness, and no real disk is involved.

**Property.** Recovery returns the value of the contiguous committed prefix after the checkpoint and ignores older generations. A corrupted committed record produces CONFLICT with the output preserved. A checksum detects accidental damage; it does not authenticate the writer, and the lab must say so.

**Experiment and evidence.** Predict first. The public test `recover` in `labs/b05_depth/tests/tests.c` (CTest `b05_depth.recover`) shows the committed prefix recovered for every length, a flipped checksum bit returning B5_CONFLICT with the output untouched, an uncommitted record stopping recovery, and the weak-checksum case: a committed record of generation 9 and value 200 recovers 200 against checkpoint (8,100), but flipping the low bit of both generation and value leaves the checksum valid and recovery returns 100 with no error, so the committed update is silently dropped. Capture both outputs. Enumerate the payload-durable, commit-durable and acknowledged cuts yourself; the lab has no harness for them.

**Impact class.** A checksum-preserving paired corruption that silently discards a committed update is a `demonstrated-invariant-violation` of integrity, shown by the supplied weak case of `b05_depth.recover` (tests.c:58-66) on a conforming implementation, so no variant is needed (the crash cuts are yours to build), bounded to a synthetic array. It is not a crash and it is not a proved impact on any file system.
