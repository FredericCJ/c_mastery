## Security

**Why this matters here.** A moving collector is correct only if every copy of a reference moves together. The CVM names objects by index and generation, so a copy you forget to relocate does not turn into a wild pointer: it becomes a stale value that cvm_field refuses with CVM_STALE, or a frame that is half old and half new. The adapter's job is therefore transactional. Validate the whole root map and every derived offset first, then relocate every copy, leave scalar slots alone, and honour the one-past offset. This is modelled heap/lifetime integrity of an index-based heap, not memory safety of real addresses.

**What to try.** You choose the frame (tagged versus scalar slots, slot lengths, derived offsets including offset 8 against length 8, which is legal, and offset 9, which is not), the registration order and the target base. Check three behaviours by hand before running: a map that omits a tagged slot is refused with OR_INVALID (tests/tests.c:255), offset 9 is refused with the frame byte-identical (:263), and a full 216-slot map relocates every copy and not just a representative one (tests/vm_ext.c:139, stats.slots==216). In vm_roots, an old unregistered copy must read CVM_STALE (vm_ext.c:86) while the registered copy reads 77; work out why that asymmetry is the contract and not a defect.

**Evidence to capture.** Build two broken adapters, stated as properties: one after which some root copy still holds the old base, and one that changes part of a frame before it discovers that the map or offset is invalid. Predict which OR_CHECK line in object_runtime.safepoint or object_runtime.vm_roots rejects each, run both tests, and keep the stderr line. Run `object-runtime-vm oracle` if you want a larger sweep; it prints rows and compares nothing, so the comparison with your own model is your work. Failed collection must leave the Cvm bytes unchanged (vm_ext.c:67-78), which is a separate property from correct relocation.

**How to read the result.** A rejected variant is a demonstrated invariant violation: a stale base or a partially relocated synthetic frame, found through well-defined C. It is not exploitation, because no attacker-controlled memory ever receives the stale value. An out-of-bounds access that only ASan reports would be a sanitizer finding, a lower class. The LLVM statepoint artifact is a separate compiler-dependent deliverable and no security demonstration is claimed for it; unregistered copies and forged tickets are outside the contract. The assessor's mutation set also checks this invariant, but that set is not part of what you receive.

Only your own implementation and the synthetic data of this lab are attacked; no external service, hardware or host setting is touched.
