# X-T66-005: Interior-mutability cells and guard escape boundaries

## Prerequisites

Complete the earlier domain projects and retain the named prerequisite artifacts with their contracts, ownership ledger and tests. Required learner artifacts: memory.pool, containers.array, testing.faults, bytes.checked, io.async, errors.result. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [ownership/CONTRACTS.md](../../../labs/ownership/CONTRACTS.md).

## Problem

Build OwCell over the previous borrow book initialized with extent1. Read requires a live token whose range is exactly[0,1); write additionally requires a writer token. Replace admits no active guards and writes the old output only after all checks. Return STALE for a dead token, INVALID for a token range/mode that cannot authorize the operation, and BUSY for replacement while borrowed. All cell operations are single-threaded or externally excluded; do not return an unchecked persistent pointer into the value.

Concrete inputs and expected results: Cell value9, old-output sentinel71 and one reader: replace(4) returns BUSY, leaves value9 and sentinel71. Read succeeds with9; write through that reader returns INVALID. After release, reading with the old token returns STALE and replace publishes4 while returning old9.

Supplied artifacts: labs/ownership/include/ownership.h, compiling unsolved src/ownership.c, CTest ownership.cell, fixtures/ownership/PR-T66-05.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Explain how dynamic borrow guards permit controlled mutation through a shared interface without making const a global immutability or thread-safety guarantee. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Implement guarded read/write and transactional replacement, composing the range guard protocol without bypassing its identity or exclusivity checks. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

## Deliverables

- D1: Explain how dynamic borrow guards permit controlled mutation through a shared interface without making const a global immutability or thread-safety guarantee.
- D2: Implement guarded read/write and transactional replacement, composing the range guard protocol without bypassing its identity or exclusivity checks.
- D3: Test shared readers, exclusive writer, stale/released token, zero-length and partial-range tokens, failed replacement output canaries and every allowed guard-release order. Reject replacement that ignores an active guard. Analyze an escaped raw-pointer API as a contract counterexample rather than treating a clean sanitizer run as proof.
- D4: Add reentrant callbacks that read the cell while an update is in progress: choose an explicit rejection or snapshot policy and test it. Delayed assessment moves to multiple threads; derive the synchronization and guard lifetime changes rather than merely making the value atomic. Complete all thirteen cost/enforcement dimensions with evidence or a mechanism-specific non-applicability.

A supplied anchor or compiled mutant checks only its named property. Failure-side effects, ownership accounting and the required changed-condition result are pass/fail gates; finite tests cannot establish absolute mastery.

## Hints

1. A live token alone does not prove that it covers the whole cell.
2. Validate exclusivity before writing either value or old output.
3. Atomic storage of the payload does not make a non-atomic guard table safe.
