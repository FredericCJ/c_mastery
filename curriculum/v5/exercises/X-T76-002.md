## Problem

Implement RPProjection with sixteen retained applied events, a contiguous count and int64 total of int32 event values. Admit positions1..16 in order. A byte-independent semantic duplicate (same position,key,value) succeeds without mutation; conflicting payload at an old position returns RP_CONFLICT; a gap returns RP_GAP. Publish total, retained event and cursor as one serialized transition. Supplied pthread adapter holds one mutex across this entire call; two threads each deliver the same ordered1..16 stream.

Concrete inputs and expected results: Apply(1,0,7) twice yields total7,count1. Reuse position1 with8 conflicts; position3 before2 is a gap. Two synchronized threads each delivering values1..16 yield count16,total136;128 fresh concurrent runs test the adapter.

Supplied artifacts: labs/replicated/include/replicated.h, compiling unsolved src/replicated.c, CTest replicated.projection, fixtures/replicated/PR-T76-02.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Separate query-model choice from delivery semantics. Establish exactly-once application only within one serialized projection and one retained immutable log identity; reject the stronger claim of exactly-once external effects. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Prove the invariant count=k implies exactly the first k events contributed once and applied[i].position=i+1. A 16-term int32 sum fits int64 on the declared target. Retain history for conflict checks rather than trusting a reused position from a new log. The caller must associate a projection with one log identity. Explain why a mutex around cursor alone is insufficient, and why an external email/file effect cannot become atomic with this state by naming it CQRS. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

## Security

Target only RPProjection in [labs/replicated](../../../labs/replicated), the supplied pthread adapter in `tests/tests.c`, and the supplied flawed external-effect protocol in `outbox/native.c`.

- **Adversary.** You control the delivered stream of (position, key, value) events: duplicates, reordering, omission and a conflicting payload at an old position, and you may run two delivery threads. You do not control the mutex, cursor storage, pointers or the scheduler policy. Worked trace: after (1,0,7) the projection has count 1 and total 7; a second (1,0,7) must succeed without changing either (a semantic duplicate), (1,0,8) must fail with RP_CONFLICT and total 7, and (3,0,2) must fail with RP_GAP because the next position is 2.
- **Violated property.** Exactly-once ordered admission inside one serialized projection: total, retained event and cursor change as one transition. A mutex around the cursor alone would let a second thread read a new cursor next to an old total. The same property does not reach outside the projection: an email or file effect has its own commit point, so exactly-once application is not exactly-once effect.
- **Experimental boundary.** The projection test is one process with 128 fresh two-thread runs (tests.c:81-92). The outbox test forks children, uses an AF_UNIX socketpair and unlinked mkstemp files under /tmp (native.c:145-160, 182-185, 226-229); nothing else leaves the process tree. TSan, if you configure it with CMASTERY_TSAN, runs on a disposable build only.
- **Evidence to capture.** Predict first: both threads deliver 1..16 with value i, so after a run count must be 16 and total 136 (the sum 1+...+16). Run CTest replicated.projection and record the CHECKs: duplicate keeps total 7 and count 1 (tests.c:73-75), RP_CONFLICT (76-77), RP_GAP with count 1 and total 7 (78-79) and the 128 runs ending at 16 and 136 (89-90). Build the two variants named in the header, run replicated.projection against each, and record the `RP_CHECK line N` it prints; it stops at the first failing CHECK. Then run replicated.outbox_native and read external-duplicate=2: a child standing in for the receiver bumps the counter byte and exits with status 45, and the retry bumps it again (native.c:232-247), while the inbox log holds each event once (dedup=2 total=5). If you enable TSan, record that the report covers only the executed schedules.
- **Impact class.** demonstrated-invariant-violation. For your projection variants the violation exists only once you build and run them; for the duplicate external effect it is shown by the supplied replicated.outbox_native, on a synthetic counter. TSan output, if any, is a sanitizer finding for that schedule only and is not impact.
- **Remediation.** Accept an old position only for an identical payload, require the next contiguous position, and serialize the whole transition under one mutex. For the external effect the residual requirement is an effect commit that is atomic with, or idempotent against, the receiver state. The test that rejects the original projection defect is replicated.projection.
- **Limitations.** A TSan pass observes these executions only; it does not certify all schedules, crash atomicity between query-state and cursor persistence (which must be modelled), authenticated senders, or any deployed target. The external-effect demonstration is one local synthetic counter, not a claim about email or a real file.

Run replicated.projection including real pthread schedules under GCC TSan when available, make the two variants fail on semantic assertions, and record mutex boundaries.
