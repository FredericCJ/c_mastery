# X-T76-002: CQRS projection admission and atomic position advancement

## Problem

Implement RPProjection with sixteen retained applied events, a contiguous count and int64 total of int32 event values. Admit positions1..16 in order. A byte-independent semantic duplicate (same position,key,value) succeeds without mutation; conflicting payload at an old position returns RP_CONFLICT; a gap returns RP_GAP. Publish total, retained event and cursor as one serialized transition. Supplied pthread adapter holds one mutex across this entire call; two threads each deliver the same ordered1..16 stream.

Concrete inputs and expected results: Apply(1,0,7) twice yields total7,count1. Reuse position1 with8 conflicts; position3 before2 is a gap. Two synchronized threads each delivering values1..16 yield count16,total136;128 fresh concurrent runs test the adapter.

Supplied artifacts: labs/replicated/include/replicated.h, compiling unsolved src/replicated.c, CTest replicated.projection, fixtures/replicated/PR-T76-02.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Separate query-model choice from delivery semantics. Establish exactly-once application only within one serialized projection and one retained immutable log identity; reject the stronger claim of exactly-once external effects. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Prove the invariant count=k implies exactly the first k events contributed once and applied[i].position=i+1. A 16-term int32 sum fits int64 on the declared target. Retain history for conflict checks rather than trusting a reused position from a new log. The caller must associate a projection with one log identity. Explain why a mutex around cursor alone is insufficient, and why an external email/file effect cannot become atomic with this state by naming it CQRS. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.
