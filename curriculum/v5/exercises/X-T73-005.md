# X-T73-005: Supervision trees with restart budgets and ordered quiescence

## Prerequisites

Explain C17 atomic ordering, POSIX wait predicates, existing queue ownership, async terminal completion and stable coroutine-frame registration; retain the named imported learner artifacts. Required learner artifacts: work.pool, sync.condition_queue, sync.spsc, io.async, io.deadline, testing.faults, coro.frame. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [messaging/CONTRACTS.md](../../../labs/messaging/CONTRACTS.md).

## Problem

Implement the four-child MsgSupervisor plan generator with ONE/ALL/REST strategies, reverse stop order, forward start order and a sliding-window restart limit1..4. Times are monotonic ticks; reject backwards time. Failure exceeding the budget permanently escalates and stops all children. Execute plans over original MsgActors, waiting for each child to quiesce before restart; inject start failure at every action and specify containment.

Concrete inputs and expected results: REST failure at child1 yields[-4,-3,-2,2,3,4]. With limit2/window10, failures at0 and1 restart; failure at2 escalates with[-4,-3,-2,-1]. With limit1/window10, failures at1 and11 are both admitted because the older event is outside the strict window.

Supplied artifacts: labs/messaging/include/messaging.h, compiling unsolved src/messaging.c, CTest messaging.supervision, fixtures/messaging/PR-T73-05.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Derive restart topology, intensity accounting and the error-kernel boundary; explain why restarting healthy siblings may be necessary and why unlimited restart can amplify faults. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Implement ordered restart plans with bounded timestamp storage and an actor execution adapter that preserves quiescence and accounts for partial restart failure. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

## Deliverables

- D1: Derive restart topology, intensity accounting and the error-kernel boundary; explain why restarting healthy siblings may be necessary and why unlimited restart can amplify faults.
- D2: Implement ordered restart plans with bounded timestamp storage and an actor execution adapter that preserves quiescence and accounts for partial restart failure.
- D3: Independently enumerate all12 strategy/failed-child selections, test exact window boundary, backwards time, maximum timestamps and escalation permanence. Reject forward-stop and omitted-start mutants. Inject handler and restart failures, compare emitted action order and prove no restarted child observes a dependency that is still stopped.
- D4: Replace the flat four-child group with a two-level tree and distinct parent/child budgets. Delayed assessment makes child2 depend on child1 initialization and fail during restart; derive whether to escalate, roll back already restarted children or retain a documented degraded state. Complete all thirteen cost/enforcement dimensions with evidence or a mechanism-specific non-applicability.

3. A plan is not evidence that stopped children have actually ceased execution.
