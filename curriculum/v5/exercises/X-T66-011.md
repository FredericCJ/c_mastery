# X-T66-011: A parsed update across typed allocator and owner publication boundaries

## Prerequisites

Complete X-T65-002, X-T65-004, X-T66-002, X-T66-009 and retain the actual named learner artifacts. Reconcile their ownership and error contracts before writing the adapter.

## Environment

Actual learner errors/ownership/coroutines/messaging implementations via explicit source imports. No replacement parser, allocator or coroutine library. Python, CMake and sanitizers are host verification tools. Read the shared contract for platform, serialization and valid-pointer assumptions. ISO C does not enforce moves, borrow lifetimes or quiescent callbacks.

## Problem

Implement mc_publish_pair using the actual er_parse_pair, V4Allocator, ow_construct and ow_publish artifacts. The public result preserves separate parsing and allocation outcomes. A successful parse stages three separately owned int32_t cells (sum, operand count, source length), publishes them together, then disposes of the old owner. The supplied allocator has eight blocks, so both three-block versions fit; inject failure at each staged allocation. Use the exact comma-free colon grammar and state transitions in the shared contract. Do not substitute malloc or duplicate the parser/owner mechanisms.

Supplied files: composition.h, the compiling unsolved adapter, public CTests, the expected-state fixture and explicit source-dependency CMake options.

With old cells90,91,92, input3:7 publishes10,2,3 and leaves exactly three live cells. Input3:x performs zero allocations and preserves old pointers and values. Failure on staged attempt1,2,3 releases respectively0,1,2 temporary blocks while all three old blocks remain live. Destroying the final owner leaves zero live blocks and zero invalid releases.

## Necessity

A parser with unchanged output and an allocator with rollback do not automatically give a composition failure atomicity. Destroying the prior object before staging or overwriting its owning pointers after staging violates different parts of the contract. A single success/error tag also loses the distinction between syntax failure and storage failure.

## Reasoning

Derive the parse/storage/commit product state and explain why unchanged parser output does not preserve a separately destroyed owner; identify the atomic publication point and callback restrictions.

Implement the adapter with the actual typed allocator and owner operations, preserving old pointer identity and values on every precommit failure and releasing old storage after successful publication.

Predict and execute all three allocation failures, invalid and range syntax, empty input and successful replacement; account for temporary versus old releases and reject both adapter mutants at their named assertions.

Replace the nonfailing release callback with a fallible external resource close; derive a recovery-required result and retained ownership instead of asserting that memory rollback reverses an external effect. State entry ownership, postconditions on each failure, the publication/notification point and peak live resources. Compare C programmer/runtime discipline with the inspected language-level ownership/coroutine guarantees; provide a counterexample to automatic equivalence.
