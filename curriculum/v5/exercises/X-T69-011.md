# X-T69-011: Quiescent hot reload with staged state handoff and retirement

## Prerequisites

Bring pinned contracts and fresh recall for io.stream, containers.array, measurement.capture; prerequisite exercises: X-T69-010. Required knowledge includes C object lifetime, checked arithmetic, ownership, typed arrays and the selected source passages. The shared contract and modern-cost contract are explicit parts of this exercise. Existing project estimates describe author accounting; they impose no learner time ceiling.

## Environment

Use C17 hosted Linux with GCC and Clang, CMake and host Python. Record compiler/ABI versions, integer widths, sizeof/alignment and optimization. Mechanism code uses no library implementing the mechanism. Allocator callbacks are supplied dependencies with separate ownership. A strict freestanding port requires its own generated-code/link audit and is not established by the hosted run. Compare C11 draft/C17/C23 only where inspected normative evidence supports the claim; exact published C17 access remains a reference gap.

## Problem

Implement DSHost reload/collect with current and one retired DSLoaded owner, integer state and non-wrapping generation0–3. Stage candidate migration from old schema/state, then atomically transfer ownership and publish state only on success. The previous module remains owned in retired until explicit collection. Reject reload while current/candidate borrows exist, retired remains occupied or generation is exhausted. Plugin1 preserves state; plugin2 doubles admitted state0–500. Add a failure-injecting loader backend model for collection failure without passing invalid real loader handles.

Supplied artifacts: labs/dispatch/include/dispatch.h, deliberately incomplete labs/dispatch/src/dispatch.c, executable anchors, fixture PR-T69-11.json and the shared CONTRACTS.md. Expected example: Starting state7, load schema1 then schema2: state becomes14, generation2, candidate becomes empty and the former module is retired. Collect releases retired. With old state600, migration rejects and retains state600, generation2, current and candidate ownership unchanged.

## Necessity

Hot reload is a lifetime and state-compatibility transaction. Swapping a function pointer is insufficient when old callbacks, data schemas or cleanup failures remain live.

## Reasoning

T69.11.a: Derive prepare/commit/retire states and the quiescence condition covering every borrowed code/data pointer; distinguish rejected migration from committed reload with pending cleanup.

T69.11.b: Implement staged migration, source ownership consumption, finite generations and explicit retired collection, preserving the old service on every precommit failure.

T69.11.c: Explore reload/borrow/release/collect/fail sequences against an independent ownership/state model, verifying no duplicated or lost handle and no state publication before migration succeeds.

T69.11.d: Transfer to asynchronous plugin callbacks and owned variable-size state. Define snapshot/serialization, cancellation acknowledgement, allocator boundaries and bounded retirement; measure pause time and retained resources without claiming transparent live-code replacement.

State preconditions, postconditions, representation invariants, resource ownership, failure publication and complexity. For each guarantee identify ISO C rules, diagnostics, runtime checks, external verification and programmer discipline separately. Include a minimal counterexample to an overstated equivalence with the corresponding language/library abstraction. Apply all13 dimensions in modern-cost-contract.md, recording genuine non-applicability with reasons and unavailable measurements as gaps.

## Hints

1. Keep the old service owned until the new state is fully admitted.

3. Every cache, thread-local object, queued callback and allocator callback is part of quiescence if the design permits it.
