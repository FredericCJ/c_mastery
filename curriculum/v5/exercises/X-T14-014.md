## Security

Why this matters here. The zone summary lets qi_range skip a group of four slots without reading them, which is safe only if the stored [minimum, maximum] encloses every live, non-null value in the group. An exact replacement can rebuild the enclosure. A lazy replacement cannot afford to rescan, so it may only widen: add the new value at whichever end it exceeds and mark the group inexact. A too-wide enclosure costs extra work (a candidate group that yields nothing); a too-narrow one silently drops a true match and still returns a plausible-looking mask. The test shows both sides. After slot 1 is lazily replaced by 100, a query for 100 must return mask 2. After slot 1 is lazily replaced by a dead row the answer is 0 but cost.groups is still 1, because the stale enclosure stays conservative; only qi_rebuild_zones brings groups back to 0.

What to try. By hand, for values 0..31 in zones of four, decide which group and how many rows a query for 4..4 examines (the test expects one group and four rows), and what a query for 3..4 touches. Then build two variants of your own: a lazy replacement whose enclosure can fail to cover the new value, and a pruning test that disagrees with the inclusive range exactly at a zone's minimum or maximum. The public test raises only a maximum, because 100 is above every old value in the group, so a variant that widens only the upper end still passes it. Write the lazy replacement that creates a new minimum as an extra case, and let your raw-row oracle decide the expected mask.

What to capture and how to read it. For each variant keep the stderr line `QI_CHECK:<line>` and map it to the check in labs/corpus_query/tests.c: the 4..4 query with its group and row counters, the query for 100 after the lazy replacement, the dead-row replacement with groups still 1, the rebuild with groups 0, the oversized replacement leaving the index bytes identical, and the rejected range 4..3 leaving answer and cost untouched. For the sorted versus permuted measurement, build labs/corpus_query/measure.c yourself (it is not a CMake target) and read groups and rows as work counters; the tick column is process CPU time on this machine only, so neither is an asymptotic or board-performance claim.

What this does and does not show. A lost true match on synthetic rows. No supplied artifact demonstrates it, so the impact class holds only once you build the variant. The assessor's mutation set also checks this invariant. Concurrent mutation, persistence, corrupted summaries and timing channels are not exercised, and overlap of an enclosure with the query never proves that a match exists.
