# X-T66-004: Runtime borrow tracking, range splitting and finite token identities

## Prerequisites

Complete the earlier domain projects and retain the named prerequisite artifacts with their contracts, ownership ledger and tests. Required learner artifacts: memory.pool, containers.array, testing.faults, bytes.checked, io.async, errors.result. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [ownership/CONTRACTS.md](../../../labs/ownership/CONTRACTS.md).

## Problem

Implement OwBorrows for one declared element extent and four active loan slots. ow_borrow accepts offset,length and writer exactly0/1, validates bounds using subtraction, and rejects overlap whenever at least one overlapping nonempty loan is a writer. Readers may overlap; empty ranges touch no element. A successful acquisition returns slot plus a fresh uint32 serial. Release consumes exactly the matching live token. A slot at maximum serial is retired rather than wrapped. ow_split consumes one live writer and creates adjacent left/right writers covering the same range; invalid length, serial exhaustion or insufficient slots must leave the book and both output tokens unchanged.

Concrete inputs and expected results: A writer[0,8) blocks a reader[3,4). Splitting it at3 creates[0,3) and[3,8), invalidates the parent token and admits no gap or overlap. A writer[8,8) may coexist because it touches no element. A released token cannot release a later loan in the same slot.

Supplied artifacts: labs/ownership/include/ownership.h, compiling unsolved src/ownership.c, CTest ownership.borrows, fixtures/ownership/PR-T66-04.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Derive reader/writer interval exclusion separately from pointer lifetime, then explain finite identity exhaustion and why a runtime token does not prevent illicit raw aliases. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.
