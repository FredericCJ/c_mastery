# X-T66-006: Strong and weak ownership with atomic and non-atomic counts

## Prerequisites

Complete the earlier domain projects and retain the named prerequisite artifacts with their contracts, ownership ledger and tests. Required learner artifacts: memory.pool, containers.array, testing.faults, bytes.checked, io.async, errors.result. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [ownership/CONTRACTS.md](../../../labs/ownership/CONTRACTS.md).

## Problem

Implement the OwShared and OwAtomicShared APIs under the exact strong/weak contract. Initialize strong1,weak1; weak includes one implicit reference while the value is alive. Retain requires a live owned strong reference; downgrade creates an explicit weak reference. Upgrade from an owned weak reference atomically increments a nonzero strong count or returns DEAD. Reject count overflow. Last strong release destroys the value exactly once then removes the implicit weak; last weak reclaims the control exactly once. The non-atomic version requires exclusion. The atomic version uses declared acquire/release reasoning, and each drop requires an actually owned reference; double-drop is not an admitted racing input.

Concrete inputs and expected results: Downgrade, retain, drop, drop yields strong0,weak1, one value destruction and no control reclamation. Upgrade now fails DEAD. Dropping the remaining weak reclaims the control once. Four threads each retain/drop5000 times while holding their own strong reference; after all owned strong references end, destruction occurs once, and a retained weak keeps the control available for a failed upgrade.

Supplied artifacts: labs/ownership/include/ownership.h, compiling unsolved src/ownership.c, CTest ownership.shared, fixtures/ownership/PR-T66-06.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Prove the distinct value/control lifetimes, no-resurrection property and count-overflow behavior; distinguish reference-count synchronization from pointee synchronization and cycle collection. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Implement strong/weak ownership twice, first under exclusion and then with C17 atomics, documenting initialization publication, owned-reference preconditions, callback effects and each memory-order edge. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

## Deliverables

- D1: Prove the distinct value/control lifetimes, no-resurrection property and count-overflow behavior; distinguish reference-count synchronization from pointee synchronization and cycle collection.
- D2: Implement strong/weak ownership twice, first under exclusion and then with C17 atomics, documenting initialization publication, owned-reference preconditions, callback effects and each memory-order edge.
- D3: Trace every strong/weak boundary with an independent counter model, test maximum-count refusal, and reject omission of the implicit weak release. Run the actual four-thread anchor, separate TSan if available, GCC/Clang optimized and ASan/UBSan builds, inspect atomic lowering and report lock-free status. A quiet race detector does not prove the memory-order argument or reclaim safety for fabricated references.
- D4: Construct a two-node strong cycle and show retained values after external owners disappear; break one edge with a weak reference and account for both control blocks. Delayed assessment races the last strong drop with weak upgrade using a synchronized start and a live weak owner: outcomes are successful ownership before destruction or DEAD, never resurrection. Complete all thirteen cost/enforcement dimensions with evidence or a mechanism-specific non-applicability.

## Hints

1. The implicit weak keeps the control alive until value destruction finishes.
2. Increment only a nonzero strong count; zero is terminal for that value.
3. Making the count atomic does not make arbitrary payload mutations race-free.
