# X-T75-007: Hedged responses and ownership of losing work

## Prerequisites

Bring pinned contracts and fresh recall for io.async, communications.tcp_fault, measurement.capture; prerequisite exercises: X-T75-001, X-T75-005, X-T75-006. Required knowledge includes C object lifetime, checked arithmetic, ownership, typed arrays and the selected source passages. The shared contract and modern-cost contract are explicit parts of this exercise. Existing project estimates describe author accounting; they impose no learner time ceiling.

## Environment

Use C17 hosted Linux with GCC and Clang, CMake and host Python. Record compiler/ABI versions, integer widths, sizeof/alignment and optimization. Mechanism code uses no library implementing the mechanism. The T73 channel backend supplies its declared POSIX synchronization; the virtual-time model itself supplies no OS clock, sleep or hidden scheduler. A strict freestanding port requires its own generated-code/link audit and is not established by the hosted run. Compare C11 draft/C17/C23 only where inspected normative evidence supports the claim; exact published C17 access remains a reference gap.

## Problem

Implement RZHedge for original attempt0 and one delayed attempt1. Choose the first acceptable response before the shared deadline, request cancellation of outstanding attempts, and track their actual terminal completions separately. Expose result availability independently from quiescence. Add a completion arbiter with two concurrent workers in the dedicated local harness, each retaining its own response storage, and integrate deduplicated effects when both attempts reach the receiver.

Supplied artifacts: labs/resilience/include/resilience.h, deliberately incomplete labs/resilience/src/resilience.c, executable anchors, fixture PR-T75-07.json and the shared CONTRACTS.md. Expected example: A rejected response7 at1 does not win. Start the hedge at2; acceptable8 at3 wins. If original0 remains outstanding, result8 is available but quiescent is false and cancel_requested includes0. Its later response7 cannot replace8; only its completion makes the operation reclaimable.

## Necessity

Returning a fast answer does not reclaim the slow attempt. Treating cancellation as completion creates lifetime defects, while treating any response as a winner can return a quick error instead of a valid result.

## Reasoning

T75.07.a: Separate first response from first acceptable response, result commitment from quiescence, and cancellation request from completed losing work. State prerequisites for safe hedging of side effects.

T75.07.b: Implement exactly one winner and separately owned attempt lifetimes, with expiry, late response, repeated completion and unstarted-attempt rejection.

T75.07.c: Implement and verify a synchronized two-worker completion arbiter, exercising both simultaneous success orders and winner/cancellation/timeout races under a controlled scheduler plus sanitizer checks.

T75.07.d: Measure tail latency and total backend work under explicit independent versus correlated delay models. Transfer to a slow loser that completes after the client abandons its wait; preserve cleanup and prevent a stale generation from completing a new request.

State preconditions, postconditions, representation invariants, resource ownership, failure publication and complexity. For each guarantee identify ISO C rules, diagnostics, runtime checks, external verification and programmer discipline separately. Include a minimal counterexample to an overstated equivalence with the corresponding language/library abstraction. Apply all13 dimensions in modern-cost-contract.md, recording genuine non-applicability with reasons and unavailable measurements as gaps.
