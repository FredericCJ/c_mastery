# X-T68-004: Portable C17 variadic machinery and single evaluation

## Prerequisites

Complete the earlier domain projects and retain the named prerequisite artifacts with their contracts, ownership ledger and tests. Required learner artifacts: . Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [metaprog/CONTRACTS.md](../../../labs/metaprog/CONTRACTS.md).

## Problem

Implement mp_variadic as an inspectable demonstration of a nonempty1..4argument macro selecting typed inline functions; arity0 uses a separate explicit empty operation. Each argument is evaluated exactly once and arithmetic is uint32 modulo. The supplied demo evaluates seed+i and reports the exact count. Use separate counters for distinct argument expressions so the test itself does not contain unsequenced writes to one scalar.

Concrete inputs and expected results: seed7 andarity0..4 produce sums0,7,15,24,34 with evaluation counts0,1,2,3,4. Arity5fails preserving bothoutputs. No argument-order claim is made.

Supplied artifacts: labs/metaprog/include/metaprog.h, compiling unsolved src/metaprog.c, CTest metaprog.variadic, fixtures/metaprog/PR-T68-04.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Derive a bounded1..4argument dispatch macro without __VA_OPT__ or GNU comma deletion, and distinguish single evaluation from the unspecified order of function arguments. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Show token substitution, rescan, selector position and parentheses for each admitted arity. Explain why an empty token argument differs from omitted variadic arguments in C17, and why this lab deliberately has a distinct zero-argument entry. Compare N3033 proposal semantics without presenting a proposal as the inspected final C23 standard. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

- D2: Show token substitution, rescan, selector position and parentheses for each admitted arity. - D3: Run metaprog.variadic, inspect -E output, and compile strict C17 probes. Kill duplicate-evaluation and incorrect-zero-identity mutants. - D4: Build a bounded logging dispatcher that optionally attaches source metadata, with a distinct zero-field operation. Preserve single evaluation and type checking while making expansion limits explicit; diagnose unsupported arity without compiler-specific comma extensions.
