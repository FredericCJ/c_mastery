Recovery and formatting require your completed X-T15-012 implementation and its exact PdTree contracts. Bring grammar traces, failure snapshots and the public `parsing_depth` workspace; dependency import is explicit. Template evaluation additionally needs lexical scope and bounded graph traversal. No library implements the new mechanism for you.

## Environment

The explicit [text-composition contract1](../../../labs/text_composition/CONTRACTS.md) gives all input types, operations, exact grammar, capacities, ownership, failure/resource and local security rules. ## Problem

Implement typed NIL/TEXT/LINE/CAT/NEST/GROUP documents and the specified bounded layout interpreter. Include the pending continuation when choosing flat groups. Implement tc_expression_doc over an actual successful PdTree and reparse every width to the same syntactic tree, even when evaluation overflows. At width4, group(nest(2,a LINE b)) CAT zzz must emit a newline and two spaces; width6 can flatten it.

## Necessity

Concatenating preformatted strings loses grouping and indentation semantics. A group that fits alone may overflow when followed by unbreakable text. Equal evaluated values do not prove that formatting preserves syntax, and an acyclic shared DAG can unfold to far more work than its unique node count.

## Reasoning

Derive the CAT unit/associativity, flattening and nesting laws, and the explicit pending-frame invariant. Explain the precise greedy probe rule and why it is not a claim of global optimality or a lazy language implementation. Prove failure atomicity and termination under node/fuel/output bounds, including cumulative nesting and repeated DAG references. For expression formatting preserve operator kinds and child structure, not source offsets or merely values. Supply pre/postconditions, loop/stack invariants, ownership, failure and complexity arguments. Classify guarantees supplied by ISO C, diagnostics, runtime checks, external models and caller discipline separately.

## Security

A formatter is trusted not to change what the program means. The risk is a layout rule that looks harmless but, applied at one particular width, moves a break or drops a parenthesis so the reprinted text parses to a different tree. A second risk is availability: a document DAG that shares a child can unfold into exponentially many visits. The attacker supplies the expression bytes (given to the real `parsing_depth` parser), the width 0..120 and the sharing structure of the document. The target is your own layout code and `tc_expression_doc` in `labs/text_composition/src/text.c`; the 256-entry frame and probe arrays, the fuel and the output capacity are fixed by the harness.

Why it matters here. In `group(nest(2, "a" LINE "b")) CAT "zzz"`, whether the group stays flat depends on the text after it: at width 4 the answer is `a`, newline, two spaces, `bzzz`, and at width 6 it is `a bzzz`, because the probe must count the pending `zzz`. For expressions the contract (`labs/text_composition/CONTRACTS.md`, document algebra section) requires full parenthesization so reformatting `(8-3)-2` and `8-(3-2)` at every width reparses to the same tree, even for `1+2147483647`, whose evaluation overflows but whose syntax is valid.

What to try. Work out by hand the flat length of the fixture and predict where the break appears as the width sweeps 0..30. Run `ctest -R text_composition.layout`: it pins widths 4 and 6, the width and indent sweep (a break exactly when width < 10), the parse-format-parse loop over six expressions at widths 0..23, fuel 0 giving `TC_FUEL`, a CAT node pointing at itself giving `TC_INVALID`, a 512-byte shared CAT chain giving `TC_RANGE` and fuel 2 giving `TC_FUEL`, and an oversized tree giving `TC_RANGE`. Then build two variants of your own, one that decides flat-or-broken without the text after the group and one that loses nesting or tree-preserving parentheses, and find the width and document where each first misbehaves.

What to capture and how to read it. Keep the `TC_ASSERT:<line>:<expression>` text; for the sweep, the failing width and indent are the counterexample. For a tree-changing format, show the original and the reparsed tree side by side. For a fuel or range refusal, show the output buffer byte-identical before and after. Record commands and source hashes. The assessor's mutation set also checks this invariant.

Impact class. A different tree or break decision is a `demonstrated-invariant-violation` once you have built the variant and shown it on a named document. A fuel exhaustion is an availability control working, not an exploit. Do not describe either as a crash, memory fault or code execution.

Remediation and regression. Include the pending continuation in the probe, parenthesize from tree structure and charge fuel on every render and probe visit. Keep the failing width and document as a permanent regression.

Limitations. The layout is the contract's deterministic greedy choice, not optimal line count or full Wadler or Oppen equivalence. No real formatter is attacked and nothing is claimed about comments, quoted strings or other grammars.
