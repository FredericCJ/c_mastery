# X-T75-004: Overflow-safe token buckets and competing rate contracts

## Prerequisites

Bring pinned contracts and fresh recall for io.deadline, measurement.capture; prerequisite exercises: X-T04-001, X-T75-001. Required knowledge includes C object lifetime, checked arithmetic, ownership, typed arrays and the selected source passages. The shared contract and modern-cost contract are explicit parts of this exercise. Existing project estimates describe author accounting; they impose no learner time ceiling.

## Environment

Use C17 hosted Linux with GCC and Clang, CMake and host Python. Record compiler/ABI versions, integer widths, sizeof/alignment and optimization. Mechanism code uses no library implementing the mechanism. The T73 channel backend supplies its declared POSIX synchronization; the virtual-time model itself supplies no OS clock, sleep or hidden scheduler. A strict freestanding port requires its own generated-code/link audit and is not established by the hosted run. Compare C11 draft/C17/C23 only where inspected normative evidence supports the claim; exact published C17 access remains a reference gap.

## Problem

Implement RZBucket with integral capacity/rate1..16 and costs1..capacity. Refill lazily under monotonic uint64 ticks, saturating before a potentially overflowing multiplication. A rejected spend retains elapsed-time refill but spends no tokens. Extend to fractional fixed-point replenishment without rounding away long-term credit, then compose a second peak bucket with rollback of admission when either bucket denies.

Supplied artifacts: labs/resilience/include/resilience.h, deliberately incomplete labs/resilience/src/resilience.c, executable anchors, fixture PR-T75-04.json and the shared CONTRACTS.md. Expected example: Capacity4/rate1 starts with4. Spending4 at0 succeeds; another1 at0 is FULL. At1 one token is available and exactly-cost admission succeeds. Advancing to UINT64_MAX fills only to4 without arithmetic overflow. Backward time is INVALID without mutation.

## Necessity

Multiplication can wrap before a clamp notices it, and repeatedly rounding refill can silently suppress credit. A rate limit also does not stop an unlimited number of slow admitted calls from remaining active.

## Reasoning

T75.04.a: Derive the burst-plus-rate admission bound, initial credit, dimensional units and distinction between a policer, shaper, peak limit and concurrency limit.

T75.04.b: Implement overflow-safe lazy refill and fixed-point fractional credit, specifying rounding, numeric horizon and which state changes persist on a rejected spend.

T75.04.c: Exhaust small capacities/rates/time jumps against arbitrary-precision arithmetic and adversarial boundary costs; verify cumulative admitted cost bounds and kill free-refill/equality-rejection mutants.

T75.04.d: Compose average and peak limits with atomic admission across both budgets. Compare token bucket and fixed/sliding windows under the same burst policy, and identify when different results arise from different contracts rather than implementation quality.

State preconditions, postconditions, representation invariants, resource ownership, failure publication and complexity. For each guarantee identify ISO C rules, diagnostics, runtime checks, external verification and programmer discipline separately. Include a minimal counterexample to an overstated equivalence with the corresponding language/library abstraction. Apply all13 dimensions in modern-cost-contract.md, recording genuine non-applicability with reasons and unavailable measurements as gaps.
