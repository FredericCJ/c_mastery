# X-T03-003: Typed storage lifecycle

## Prerequisites

Complete X-T02-001 and read T03.01, T03.03, T03.07–T03.08. Bring the semantic prediction notebook. Understand callbacks, an allocator's alignment contract and ownership versus borrowing. The exercise refines PR-T03-03's concrete single-type wrapper; it does not import a prebuilt generic container.

## Environment

Apply [shared contract v1](shared-contract.md). The profile C component calls only its explicitly supplied allocation and lifecycle callbacks. The hosted profile A allocator supplies actual allocated storage of at least sizeof(FDValue), aligned for FDValue. Its standard `malloc` adapter may be used because implementing the allocator is not this exercise's mechanism. A declared aligned character array is not an interchangeable backing store for arbitrary typed lvalue access.

## Problem

Implement `fd_slot_acquire`, `fd_slot_initialize`, `fd_slot_publish` and `fd_slot_reset` for `FDValue { int32_t value; uint32_t serial; }`. Start with `FD_SLOT_INITIALIZER`. States are EMPTY, ACQUIRED, INITIALIZED and PUBLISHED.

Acquisition from EMPTY requests sizeof(FDValue) and _Alignof(FDValue), retaining the allocator needed to release it. Null allocation returns `FD_NOMEM` and leaves EMPTY. Initialization from ACQUIRED calls the supplied initializer exactly once. The initializer returns zero only after establishing a complete FDValue; if it returns nonzero it must already have rolled back any resources it acquired. On initializer failure, free the backing allocation, return `FD_INIT_FAILED`, and restore EMPTY without calling the full-object destructor.

Publication from INITIALIZED returns a borrowed const FDValue pointer and enters PUBLISHED; publication from PUBLISHED returns the same live borrow. No earlier state may publish. Reset calls a supplied destructor only for successfully initialized values, then releases acquired storage exactly once and returns EMPTY; repeated reset is a no-op. Null reset is a no-op. Invalid arguments return `FD_INVALID`; forbidden state transitions return `FD_STATE` without changing state or output. Allocator and initializer callbacks must be non-null; the destructor may be null when no destruction action is needed. All callbacks must be non-reentrant, normally returning, and must not retain ownership of the slot or its storage. Callback context must stay live until reset. The borrowed publication expires at reset.

Supply deterministic initializer success/failure and allocator failure on a selected call. Use a live-value serial and callback event log to distinguish initialization, destruction and backing-storage release.

## Necessity

Allocation success does not establish initialized semantic state. Failed constructors and delayed publication expose cleanup errors hidden by a successful create/destroy pair. Alignment alone does not establish access type or ownership; copying a wrapper can duplicate cleanup responsibility even if its state enum is valid.

## Reasoning

Give a full state/API transition table and effective-type timeline for typed writes, character observation and copying a live FDValue representation. Explain why an all-zero byte pattern is not a generic constructor. Prove every failure prefix returns to its declared state; distinguish initializer-owned partial cleanup from full-object destruction.

State O(1) wrapper storage/work plus separately bounded callback costs and one outstanding allocation. Explain that ISO C checks function types, ordinary diagnostics can catch some mismatches, state checks reject some ordering errors, and caller discipline/external verification preserve unique ownership and borrow lifetime.

Compare this C protocol with the inspected Rust move and destructor mechanisms. Show a C wrapper copy that the compiler accepts but that violates ownership; analyze it without performing a duplicate free. Also rebut “Rust guarantees every destructor always runs” using the documented suppression/termination cases. The exercise does not claim its C wrapper recreates Rust's safety rules.

## Deliverables

- **D1:** state/access/ownership diagrams, callback obligations, C-versus-Rust enforcement table and failure-prefix proof.
- **D2:** lifecycle functions, host allocation adapter, instrumented initializer/destructor and borrowed consumer.
- **D3:** event-log assertions, acquisition/initialization failure injections and illegal-transition tests.
- **D4:** typed-array variant and two-resource initialization transfer with resource ledger.

## Verification

Run `foundation_depth.lifecycle`. Cover every state with every operation, checking error class, unchanged state/output and callback counts. Require allocation failure: zero destructor/free calls; initialization failure after allocation: one release, no full destructor; successful initialized or published reset: one destructor before one release; empty/repeated reset: neither. Confirm failed publication preserves an output sentinel.

Independently model states as symbols and compare generated operation sequences to actual event logs. Do not test false alignment contracts by dereferencing bad allocations. A compiling premature-publication mutant must fail state/output checks; a destructor-on-failed-init mutant must fail the callback log. Use sanitizer/leak observations only as supplementary executed-path evidence.

## Rubric

Objective criteria assess access typing, lifecycle and independent cleanup rather than only returned statuses. Publishing before initialization or any ownership ambiguity fails mandatory correctness/memory gates. Level 3 requires a typed-array backing or partial-resource failure contract with a fresh proof.

## Hints

1. Draw backing allocation and initialized value as different facts.
2. Ask which state knows enough to call a full destructor; failed initialization may not.
3. Store the release callback together with the acquired allocation, then identify the single event that revokes borrowed views.

## Variants

Delayed assessment identifier: `X-T03-003-DELAYED`. Attempt it at least seven days after the recorded studied event; the recommended interval is one to two weeks.

Replace the allocator with storage from an array of actual FDValue objects; remove deallocation while preserving publication/borrow rules. Next make initialization acquire a second synthetic resource and fail after that acquisition; specify which callback rolls it back. Delayed assessment transfers ownership between wrappers and requires proving source invalidation without assuming a C assignment implements a language-level move.

## Security

All resources are synthetic local allocations. Analyze stale borrow and copied-owner counterexamples without executing invalid accesses or duplicate frees. No production allocator attack or privileged target is involved.

## Validation

Authored B01 specification; failure-injection observations and reviewer scores require receipts. This does not claim a complete generic allocator, foreign-language ownership system or physical target validation. C17 zero-size realloc is a separately labeled comparison; this slot never requests zero-size storage.
