# X-T73-009: Sequence validation without racing ordinary C payloads

## Prerequisites

Explain C17 atomic ordering, POSIX wait predicates, existing queue ownership, async terminal completion and stable coroutine-frame registration; retain the named imported learner artifacts. Required learner artifacts: work.pool, sync.condition_queue, sync.spsc, io.async, io.deadline, testing.faults, coro.frame. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [messaging/CONTRACTS.md](../../../labs/messaging/CONTRACTS.md).

## Problem

Implement a one-writer sequence lock over two atomic unsigned payload words. All operations begin SC. Writer publishes odd sequence, both payloads, then even sequence; refuse exhaustion before wrap. Reader performs at most its supplied retry budget and publishes outputs only after equal even sequence observations. Analyze the plausible repair “copy ordinary payload then discard if changed” and explain its C data-race defect. Do not execute a racy program as a portable value oracle.

Concrete inputs and expected results: With sequence1, three attempts return BUSY and outputs stay[99,99]. Writing[7,14] then reading succeeds. Zero attempts is BUSY. SequenceUINT_MAX-1 rejects a new write without modification. The threaded anchor writes10000 pairs[i,2*i] and rejects any successfully returned incoherent pair.

Supplied artifacts: labs/messaging/include/messaging.h, compiling unsolved src/messaging.c, CTest messaging.sequences, fixtures/messaging/PR-T73-09.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Separate storage race freedom, coherent snapshot validation, writer serialization, retry bounds and counter lifetime; identify what SC proves and what a later weakened implementation must re-establish. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Derive the atomic representation and SC ordering argument, implement bounded retry and nonwrapping writer publication, and account for every output and failure effect. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

## Hints

1. Discarding a value does not erase an earlier language-level data race.
2. An odd sequence is a state, not merely a changed numeric value.
3. A snapshot retry loop does not keep pointed-to objects alive.
