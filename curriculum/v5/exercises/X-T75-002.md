## Problem

Implement RZQueue/RZOffer with four copied unsigned messages and BLOCK, REJECT, DROP, OVERWRITE and DEGRADE policies exactly as CONTRACTS.md specifies. A blocked offer is a retained operation to retry, not a hidden sleeping thread. Degrade coalesces newest by max and reports reduced semantics. Implement rz_forward using your actual T73 nonblocking channel send and remove the head only on acceptance. Then add a bounded two-producer readiness adapter that registers before checking readiness, acknowledges cancellation and never creates an unbounded waiting-producer list.

Supplied artifacts: labs/resilience/include/resilience.h, deliberately incomplete labs/resilience/src/resilience.c, executable anchors, fixture PR-T75-02.json and the shared CONTRACTS.md. Expected example: Queue[1,2,3,4] plus DROP9 remains[1,2,3,4]; OVERWRITE9 becomes[2,3,4,9]; DEGRADE10 changes newest to10 and reports DEGRADED. BLOCK retains pending ownership. Expiry before a later retry terminates that offer without enqueuing it. A full imported channel leaves the local head in place.

## Necessity

A fixed queue does not bound memory if arbitrary producers wait while retaining payloads. Overload policy changes the service contract and cannot be compared using throughput alone.

## Security

**Why this matters here.** Overload policy is a data-integrity decision. When four slots are full, the policy chosen for the next offer decides what is lost: the incoming value (DROP), the oldest queued value (OVERWRITE), the newest queued value in exchange for the incoming one (DEGRADE), nothing yet (BLOCK, which keeps ownership with the producer until it retries) or the offer itself (REJECT, which returns RZ_FULL). Each policy has an outcome you can state exactly, and a defect shows up as a message that is lost, duplicated, reordered or admitted after its deadline. A blocked producer is a retained operation, not a thread, and that is what keeps the waiting bounded.

**What to try.** Fill the queue with [1,2,3,4] and offer 9 under each policy. BLOCK returns RZ_PENDING and the offer stays pending; DROP returns RZ_DROPPED with the head still 1 and the count 4; OVERWRITE evicts 1, so the next pop yields 2; DEGRADE returns RZ_DEGRADED with 10 in the newest slot; an expired BLOCK offer returns RZ_EXPIRED and the queue is identical to its snapshot (tests/tests.c:29-62). Then repeat the sweep for the owned-value queue, every policy and every count from 0 to 4, where the value must be owned exactly when the result is RZ_PENDING and the made and dropped counters must match after draining (followthrough/pressure_test.c:115-165).

**Evidence to capture.** Build two broken variants, stated as properties: a pump that consumes the queue head although the channel refused it, and an offer path that enqueues after its deadline. Be careful about where each is rejected. resilience.pressure never calls rz_forward, so a forwarding defect in the plain queue code is invisible to it; head loss is only observable through rzp_forward in resilience.pressure_owned, which reaches rz_forward only because your adapter must call it (PRESSURE.md:25, OUTBOX.md:65); no test calls rz_forward directly. Predict the RZ_CHECK line that rejects each variant, then run it and keep the stderr line. Run `resilience-pressure policy` and `resilience-pressure pump`, which print rows and compare nothing, and diff the rows against a model of your own.

**How to read the result.** A rejected variant is a lost, duplicated or reordered synthetic message in a four-slot model: a demonstrated invariant violation in well-defined C, not a measured denial of service or a fairness or real-time guarantee. Raw aliases, malicious allocator callbacks and concurrent mutation of the queue are outside the bounded contract. A crash or sanitizer finding in the same code would be a lower class and is recorded separately. The assessor's mutation set also checks this invariant, but that set is not part of what you receive.

Only your own implementation and the synthetic data of this lab are attacked; no external service, hardware or host setting is touched.
