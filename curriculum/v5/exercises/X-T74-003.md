## Security

A hidden class (shape) says where each property lives in an object. If two objects with different property orders share a shape, a lookup cached on that shape reads the wrong field. The attacker chooses nonzero uint8 keys, their insertion order, updates of existing keys, a fifth distinct key and the point where the shape arena runs out, and may delete a key in a dictionary variant. The target is your own shape arena, transition lookup and `or_property_set` in `labs/object_runtime`: a 16-shape arena with four-field objects that it does not let the attacker corrupt or recycle.

Why it matters here. The contract (`labs/object_runtime/CONTRACTS.md`, shapes section) keys a transition by the pair (parent shape, key). If either part is ignored, the order 1-then-2 and the order 2-then-1 can end on the same shape although key 1 sits at offset 0 in one object and offset 1 in the other. The new shape must also be committed to the receiver. Exhaustion has to preserve both arena and object, and four-key objects may still update existing keys at full capacity.

What to try. Draw the transition tree for keys 1,2 and for 2,1 and predict which objects share a shape. Run `ctest -R object_runtime.shapes`; its `shapes` function pins `a.shape == b.shape` for the same order, `c.shape != a.shape` for the opposite order, `or_property_get` returning 60 for key 1 on `c`, and a fifth distinct key on a four-key object returning `OR_FULL` with the object byte-identical. That last case is the per-object four-key limit; the test neither fills the 16-shape arena nor compares the arena, so write that case yourself for the arena-rollback half of the contract. Then build two variants of your own: one where a transition is found without considering where it started, and one where the receiver is not moved onto the new shape. Record which CHECK stops which; do not assume.

What to capture and how to read it. Keep the `OR_CHECK:<line>:<expression>` text, the shape IDs of each object, the property values read back and byte snapshots of the object and arena around each `OR_FULL`. Two layouts under one shape ID, or a changed object after `OR_FULL`, is the demonstration. Record commands and source hashes. The assessor's mutation set also checks this invariant.

Impact class. `demonstrated-invariant-violation`, only against a variant you build: shapes shared across different layouts, or an object changed after `OR_FULL`, are broken invariants on synthetic data. Nothing beyond a wrong layout result is shown and nothing crashes or hits undefined behaviour.

Remediation and regression. Key each transition by parent shape plus key, commit the receiver's new shape and leave arena and object untouched on exhaustion. Keep your arena-exhaustion test beside the `shapes` CHECKs.

Limitations. Deletion, prototypes and dictionary invalidation are bounded contracts here. Type confusion in a real JIT, concurrent mutation and shape retirement with live caches are not demonstrated.
