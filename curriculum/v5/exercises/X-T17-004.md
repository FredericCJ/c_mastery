# X-T17-004: Exact money, rational rounding and conservative settlement

## Prerequisites

Retain X-T04-001 integer boundary reasoning and the existing PR-T17-02 widening/rounding dossier. Explain signed overflow, uint64 modular conversion, array lifetimes and output staging before coding. No existing Money library may supply the mechanism. Earlier value/rounding/allocation implementations become the actual settlement dependencies.

## Environment

Use the C17 profile and complete runtime restrictions in [CONTRACTS](../../../labs/corpus_money/CONTRACTS.md). Run hosted GCC/Clang debug, optimized and ASan/UBSan profiles; audit Cortex-M4 generated objects and linked images separately. The N3096 draft comparison changes only the checked-integer primitive and must not be reported as execution of published C23 or a currency type system.

## Problem

Implement every operation in money.h from original integer primitives: validate a currency/scale value, checked addition, exact rational rescaling with three rounding modes, largest-remainder signed allocation, and a staged multi-account settlement. Inputs and outputs, finite capacities, rounding examples, ownership, failure statuses, cut semantics and all representation assumptions are specified in the shared contract. Construct a harmless local counterexample for each violated property. The initialized workspace contains a deliberately refusing provider, public assertions, driver and fixtures; assessor code is separately selected.

## Necessity

A number of cents alone cannot prevent mixed units. A wider intermediate can still overflow before division; floating conversion can lose exact integer units; individually rounded shares can destroy conservation. Transaction-shaped code can debit before a later credit fails. These are different mechanisms and must be assessed separately rather than treating one addition test as coverage of Money.

## Reasoning

Derive M=q*d+r, prove the original long-divider invariant and exact product decomposition, and handle the asymmetric signed range without negating INT64_MIN. Prove tie-to-even for both signs. Establish allocation's deficit bound and conservation using mathematical integers. State how tie order and signed symmetry differ from other policies. Define settlement pre/postconditions and a publication point, explain all retained ownership, and compare O(n squared) selection with stable sorting under the same result contract. Distinguish static C types, runtime checks, external proofs and programmer lifetime/serialization obligations. Explain why checked integer arithmetic alone cannot supply currency identity or atomicity.

## Deliverables

- D1: value representation, rounding derivation, invariants and failure/ownership dossier with independently computed examples.
- D2: complete original provider and actual value-to-allocation-to-settlement composition; unchanged public API and explicit target helper closure.
- D3: boundary, invalid-input, compiled defect and failure-cut evidence, independent Fraction oracle, generated-code/stack audit and equal-contract cost measurements.
- D4: an independent changed-condition assessment, including policy counterexamples and the named delayed settlement package; record hints and assistance separately.

Pass requires correct tags, both signed extrema, all rounding modes, nonzero and overflowing weight sums, zero weights, stable ties, exact conservation, duplicate/invalid recipients, every settlement cut and late credit overflow. Compare against a rational/big-integer model, not the C decomposition. Reject each compiled wrong implementation for its intended assertion. Report tool versions, seeds, bounds, code size, stack and timing scope; sanitizer silence is not proof of arbitrary correctness.

## Security

The only target is the original `labs/corpus_money` synthetic-account provider (`src/money.c`) in a local process. There are no real accounts, credentials, network targets or host security changes.

Adversary. The attacker chooses currency codes, scales and amounts, allocation weights (zero and overflowing sums included), destination indices (duplicates and invalid ones included), the rounding mode and the failure cut passed to `cm_settle`. The attacker cannot write account storage or pass bad pointers.

Violated property. Values of different currency or scale must never be added or allocated together, balances must be conserved on success, no intermediate stage may become visible, and an aborted or overflowing settlement must leave all accounts unchanged. The anchors `corpus_money.currency` and `corpus_money.settlement` check a mismatched currency or scale add returning `CM_INVALID`, cuts 0 to 3 returning `CM_ABORTED`, a duplicate destination, insufficient funds and a late credit overflow, each with unchanged accounts. Build a defective variant (mixed-unit add accepted, or accounts written before all credits are checked) and show an anchor rejects it.

Boundary. Synthetic accounts with small amounts and the signed extrema, built in a disposable CMake directory. Harmless success is a printed balance or snapshot that differs from the model.

Evidence to capture. Run `ctest -R corpus_money`. Capture the `CM_CHECK:<line>` text for each defective variant, balances and totals before and after, status codes, and the expected balances from your independent rational model.

Impact class. `demonstrated-invariant-violation`, demonstrated only by the defective variants you build, since the supplied anchors pass on a correct provider and no flawed provider is supplied. A semantic credit violation is not a crash or sanitizer finding, and not a proved impact, since it shows no arbitrary code execution, external authentication bypass or crash durability.

Remediation and regression. Check units first, preflight allocations and credits before writing, and publish only after the whole stage succeeds. The anchors' mismatch-add, cut, duplicate-destination and late-overflow CHECKs must reject your variants.

Limitations. A synthetic ledger, not a payment system; finite cases and sanitizer silence do not prove arbitrary correctness.
