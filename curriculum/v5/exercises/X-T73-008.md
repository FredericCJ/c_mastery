# X-T73-008: Multiversion visibility, reader pins and bounded reclamation

## Prerequisites

Explain C17 atomic ordering, POSIX wait predicates, existing queue ownership, async terminal completion and stable coroutine-frame registration; retain the named imported learner artifacts. Required learner artifacts: work.pool, sync.condition_queue, sync.spsc, io.async, io.deadline, testing.faults, coro.frame. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [messaging/CONTRACTS.md](../../../labs/messaging/CONTRACTS.md).

## Problem

Implement MsgVersions with eight complete two-field versions, four generation-tagged reader pins and one mutex. A snapshot pins current time; reads return the newest version no later than that time. Publish adds one whole version. Reclamation retains current plus every active pin’s visible version. Reject fifth pin, stale generation and exhausted clock without changing caller outputs. Derive why at most five distinct versions are retained and the eight-slot representation can admit a next publication.

Concrete inputs and expected results: PinA at[0,0], publish[1,2], publish[3,4]: A still reads[0,0]. DropA and reuse its pin slot forB: old handleA is STALE and B reads[3,4]. A clock at UINT64_MAX refuses publish. Snapshot visibility is repeatable for the two-field value; no multi-object serializability or durability is claimed.

Supplied artifacts: labs/messaging/include/messaging.h, compiling unsolved src/messaging.c, CTest messaging.snapshots, fixtures/messaging/PR-T73-08.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Derive version visibility and retention from reader lifetimes, distinguish repeatable snapshot reads from stronger isolation, and identify how a forgotten pin creates resource retention. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Implement timestamped publication, exact pin identity, visible-version selection and reclamation with a bounded-space proof under the four-reader assumption. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.

## Deliverables

- D1: Derive version visibility and retention from reader lifetimes, distinguish repeatable snapshot reads from stronger isolation, and identify how a forgotten pin creates resource retention.
- D2: Implement timestamped publication, exact pin identity, visible-version selection and reclamation with a bounded-space proof under the four-reader assumption.
- D3: Enumerate pin/publish/read/drop traces against an independent immutable-history model, test four pins at different versions and a fifth refusal, stale slot reuse and generation retirement. Reject pin-ignorant collection and missing-generation mutants. Track retained version counts before/after releases and compare the mutex cost with read-copy-update assumptions.
- D4: Give each version separately owned payload storage whose clone can fail; publish only after full construction and preserve old readers on failure. Delayed assessment adds independent keys and predicate queries: construct write skew under snapshot isolation and explain what validation or locking would establish the stronger requested property. Complete all thirteen cost/enforcement dimensions with evidence or a mechanism-specific non-applicability.

## Hints

1. Retain the version visible to each pin, not every historical version.
2. A reused reader slot needs an identity beyond its array index.
3. Repeatable reads do not by themselves imply serializable transactions.
