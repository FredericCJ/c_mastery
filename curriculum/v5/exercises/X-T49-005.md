# Bind the same port twice

## Prerequisites

X-T49-004, U-T24-02-04 supply the process, namespace or transport foundations for this investigation.

## Environment

Use the exported linux_supervision workspace and restore the pinned Linux guest with `python3 guest.py setup`. Start with the `network` case in CONTRACTS.md and the fixture interfaces in PROTOCOL.md.

## Problem

Can two running listeners bind 127.0.0.1:39073 while using the same executable? Predict the outcome of binding twice within one namespace and once in each of two namespaces.

## Necessity

Prove two simultaneous listeners occupy independent network namespaces. Relate same-namespace bind failure, client identity and complete socket I/O to the service lifecycle. These observations give a reviewer enough information to distinguish different mechanisms that can yield the same visible outcome.

## Reasoning

A successful bind after the previous process exits demonstrates port reuse over time. The readiness barrier and the outer socket observations establish overlap. Use each local client’s marker to connect listener identity with the returned payload. TCP may deliver a frame over several reads.

## Deliverables

- D1. Record your prediction in `answers/network.json`. Implement supervise_network in src/network.c. The fixture provides two concurrent network namespaces with loopback up. Each process binds and listens with reuse disabled, attempts a duplicate bind, and reaches the supplied barrier with its listener still open. Exchange the namespace marker and the eight-octet T24 request over loopback; encode its sum in four big-endian bytes. Close both connections and the listener.
- D2. Preserve your source, guest serial transcript and run identity. Write an explanation keyed to the measured fields in both the program and the independent outer observations.
- D3. Explain which evidence would still hold if the two servers ran sequentially, and which observation rules that interpretation out.

## Verification

Use `python3 submission.py observe network --program build/learn/supervise --out build/first-network` after building. Run the standard `cmastery check` command in CONTRACTS.md for a fresh graded execution. Explain any discrepancy with your original prediction.

## Rubric

- R1. Prove two simultaneous listeners occupy independent network namespaces.
- R2. Relate same-namespace bind failure, client identity and complete socket I/O to the service lifecycle.

## Hints

Explain which evidence would still hold if the two servers ran sequentially, and which observation rules that interpretation out. Use the fixture barriers and monotonic deadlines to order observations; a sleep chosen by trial and error cannot establish readiness.

## Variants

V1 is an individually assigned changed condition after at least seven days. Record the prediction and the observations that would distinguish the alternatives before rerunning the program.

## Security

Use the course’s diskless, networkless guest. The fixture owns namespace creation, controller settings and teardown. The supervisor handles the bounded learner workload as an ordinary guest user.

## Validation

The live CTest checks the selected case against current guest and executable identities. Offline replay verifies trace structure and invariants. A reviewer grades the explanation and changed-condition transfer.
