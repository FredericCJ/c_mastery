## Security

A tagged value packs several types into 64 bits, so the dangerous question is which bit patterns an outsider can produce. Here the integer tag lives inside the quiet-NaN space: if a numeric NaN with the integer prefix reaches the runtime unchanged, it reads back as an int32 that no program ever stored. The attacker supplies 64-bit numeric encodings (for example NaNs carrying the `0x7ff9` prefix), integer words and pointer addresses with chosen low bits. The target is your own `or_number_bits`, `or_integer`, `or_integer_get`, `or_pointer_tag` and `or_pointer_untag` in `labs/object_runtime`; it cannot change library code, make a misaligned pointer legal or keep a pointer alive after its object.

Why it matters here. The contract (`labs/object_runtime/CONTRACTS.md`, value section) maps every exponent-2047 nonzero-fraction encoding to the single quiet NaN `0x7ff8000000000000`, leaves infinities, signed zero and subnormals bit-exact, and makes `or_integer_get` accept only the exact prefix with the reserved bits 32..47 clear. A pointer tag needs its low two bits free, so a misaligned address must be refused rather than tagged into a word that loses information.

What to try. Predict by hand what `0x7ff9000000000042` becomes, and what `or_integer_get` would return if it were not canonicalized (the payload 0x42, which is 66). Run `ctest -R object_runtime.value`: the `value` function pins that canonicalization, bit-exact infinity and negative zero, the INT32_MIN and INT32_MAX round trips, `0x7ff9000100000000` returning `OR_INVALID` with the output left at INT32_MAX, an aligned pointer round trip and `data + 1` with tag 1 returning `OR_INVALID`. It never decodes a canonicalized NaN as an integer, so add that check yourself. Then build two variants of your own: one that lets a numeric NaN keep the integer prefix, and one that loses the sign of a negative payload.

What to capture and how to read it. Keep the failing `OR_CHECK:<line>:<expression>` text, the 64-bit input and output in hex, and for the NaN case the `or_integer_get` result of your added check. A value of 66 decoded from an input that was meant to be a double is the demonstration. Record commands and source hashes. The assessor's mutation set also checks this invariant.

Impact class. `demonstrated-invariant-violation`, only against a variant you build: a number read as a tagged integer is a wrong synthetic scalar. No memory or authority is reached, and nothing crashes or hits undefined behaviour, so it is not proved-impact.

Remediation and regression. Canonicalize every exponent-2047 nonzero-fraction encoding, accept integers only on the exact prefix with zero reserved bits and check both low pointer bits before tagging. Keep the decode-after-canonicalize check beside the original `value` CHECKs.

Limitations. A tag check is not authentication: forged words and stale pointer provenance are analysed, not demonstrated, and the double bridge holds only for the format verified on this host.
