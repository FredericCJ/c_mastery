## Security

A continuation token is a capability to run the rest of a computation, and the effect device here is single-shot: each token may be redeemed once. If a stale copy is accepted a second time, the handler can make the same question be answered twice and get two different results from one frame. The attacker is the handler: it chooses the order of start, resume and abort calls, picks both answers (the second may make the checked addition overflow) and may keep copies of any token. The target is your own `struct co_effect` implementation in `labs/coroutines`; the frame memory and the host are not under its control and it cannot forge pointers.

Why it matters here. A token is only an owner address plus a generation, and C will happily copy it, so the library cannot stop copying; it can only refuse a copy whose generation is no longer current. The contract (`labs/coroutines/CONTRACTS.md`, resumable effect section) therefore advances the generation on every consumption and rejects stale copies while the frame is live. It also requires the overflowing second answer to leave token, frame and output unchanged, so the handler can retry with another answer or abort.

What to try. Trace the sequence by hand: start gives question 1 with a token, resume with 12 gives question 2 at a new generation, resume with 30 gives `CO_DONE` and 42. Copy the first token before resuming and predict what a second resume with the copy must return. Run `ctest -R coroutines.effect`; its `effect` function pins exactly that stale-copy case (`CO_STATE`, output still 91), the 12-then-30 run ending in `CO_DONE` with output 42 and no owner left, and start-then-abort leaving `pc` at 4 with no owner. It does not test the overflow-then-retry path or reuse of a completed frame, so add those yourself. Then build two variants of your own: one that admits a token it has already consumed, and one that loses the first answer. See which CHECK stops each.

What to capture and how to read it. Keep the `CHECK` failure text and line, and record the token owner and generation, the status and the output before and after each call. For overflow, snapshot frame, token and output before the failing resume and compare them byte for byte afterwards. Record the commands and source hashes. The assessor's mutation set also checks this invariant.

Impact class. `demonstrated-invariant-violation`, only against a variant you build: a duplicate or wrong result on synthetic values shows the single-shot property broken. No confidentiality, authorization or memory consequence is shown, and nothing here crashes or triggers undefined behaviour, so do not describe a wrong result as code execution.

Remediation and regression. Check owner address and generation on every resume and abort, advance the generation on consumption and do the checked addition before changing anything. Keep your overflow-then-retry test beside the existing stale-token CHECK.

Limitations. Copying tokens, dangling frames and reinitialization with the same address (ABA) are outside what C can prevent, so they are analysed rather than executed. Nothing here shows multi-shot capture, native-stack continuations or concurrency safety.
