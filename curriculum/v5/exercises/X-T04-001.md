# X-T04-001: Transactional extent arithmetic

## Prerequisites

Read PR-T04-01's integer limit, conversion and overflow teaching. Explain count versus offset. Bring a source-bound revision of `bytes.checked` if already accepted: `f_checked_size(n,w,e,out)` corresponds to `fd_extent(e,n,w,SIZE_MAX,out)`. It is optional as a prerequisite because this exercise can produce that artifact; the new work must still supply its own proof.

## Environment

Apply [shared contract v1](shared-contract.md). Use `size_t`, `intmax_t`, `uintmax_t` and their standard limits. No wider arithmetic library or overflow builtin may implement the first-principles version; those belong in separate comparative adapters or host oracles. The shared family wire-header octet restriction is a scaffold assumption, not a requirement of the abstract extent algorithm. Record 32-bit/Cortex-M compilation separately when available.

## Problem

Implement `fd_extent(offset,count,width,limit,out)` from the supplied `depth.h`: succeed exactly when mathematical `offset + count * width <= limit`, writing the exact result. On rejection preserve `*out`. Null output is `FD_INVALID`; rejected arithmetic is `FD_RANGE`; otherwise return `FD_OK`. Zero count and zero width are admitted, including `count=SIZE_MAX,width=0`, provided the offset is within the limit. Offset beyond limit always rejects.

Implement `fd_from_signed(value,out)`: succeed only for a nonnegative `intmax_t` mathematical value representable as `size_t`; reject before lossy conversion, with unchanged output. It cannot undo a conversion already performed by the caller.

Supplied artifacts: header, unsolved source, public CTest `foundation_depth.extent` and the family fixture oracle. Hand-derive `(16,3,4,255)->28`, `(16,60,4,255)` rejection, `(8,SIZE_MAX,0,8)->8`, and `(9,0,4,8)` rejection. Inputs are mathematical offsets, not machine addresses.

## Necessity

Wrapped products can authorize less storage than the logical request requires. Zero width falsifies an unconditional division check. Explain why “unsigned overflow is defined, therefore this size calculation is safe” confuses language semantics with an application invariant.

## Reasoning

Derive the mathematical admission predicate before choosing C expressions. Prove that each intermediate check is representable. Separate the range of `size_t` from the application's smaller limit. State the writable output object's lifetime and why passed-by-value inputs allow output to alias a caller variable safely. Never justify overlap through an incompatible cast.

Bound work and temporary storage by O(1) in a word-RAM model; separately account for division and compiler helpers. Compare manual C17 checks with the inspected GCC extension and N3096 C23-draft macros, both of which write their result. A failure flag does not imply unchanged output; design temporary-result adapters with equivalent contracts.

## Deliverables

- **D1:** typed-expression and admission proofs, signed-conversion proof and source/edition comparison.
- **D2:** both functions and an adapter note to `bytes.checked`.
- **D3:** independent arbitrary-precision predicate, exhaustive reduced-domain evidence, actual-type boundaries and a wrapped-product counterexample.
- **D4:** generated-code/dependency report and changed-limit/type experiment.

## Verification

Run the named CTest and an independent Python unbounded-integer predicate. Enumerate offset/count/width/limit from 0 through 15: 65,536 tuples. Include actual `SIZE_MAX`, `SIZE_MAX-1`, quotient-boundary neighbors, `limit=0`, null output, zero combinations and signed negatives. Check unchanged output on every rejection.

Isolated mutants must compile and be rejected for: multiplying before checking, skipping offset admission for count zero, and writing output before final admission. Show the property and smallest counterexample killing each. Reduced-domain enumeration alone does not establish actual-width correctness.

Run GCC/Clang debug, optimized and sanitized configurations. Probe overflow builtins and `<stdckdint.h>` in separate files. Missing C23 header support is an unavailable experiment, not permission to invent a result.
