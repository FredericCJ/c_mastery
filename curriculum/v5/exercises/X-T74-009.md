## Security

**Why this matters here.** A collector with ephemerons and finalizers makes two promises that fail quietly. A value may stay alive only while its key is alive, and a finalizer must run at most once even when it brings its own object back to life. Handles in this lab are slot-and-generation indices into a fixed array of sixteen objects, so a broken promise never becomes a wild pointer; it appears as a live or dead mask that disagrees with the reachability you derived. That is why the property is called modelled heap/lifetime integrity and not memory safety: nothing outside the model is corrupted, and the attack is worth running because it shows which sentence of the specification each CHECK defends.

**What to try.** Choose the graph, the root set, the order in which the four pairs are registered, which objects carry a finalizer or a synthetic resource, and whether the callback allocates, fails or roots its own object. Begin with the graphs the tests already use: pairs 2->3 then 1->2 under root 1 (the second pair makes the first pair's key reachable, so a single pass over the pairs is not enough) and a pair whose value points back at its own key (a cycle cannot bootstrap itself). Work out on paper which live and dead mask each must give before you read the weak test in tests/tests.c or ephemeron in tests/finalizers_ext.c, then compare.

**Evidence to capture.** Build two broken variants of your own implementation, stated as properties rather than recipes: one in which a pair's value can be lost although its key is reachable, and one in which a finalizer can run twice for the same identity. Predict which CHECK rejects each (the first-run checks at tests/finalizers_ext.c:112-113 look at state after one orf_run_one only, so a duplicate finalization that happens later is rejected further down the test), run object_runtime.ephemeron_graph and object_runtime.finalizers, and keep the stderr line OR_CHECK:<line>:<expression> that appears. Then run `object-runtime-finalizers oracle` against your correct implementation, save its 25,600 rows (64 graphs x 16 root sets x 25 conditional targets, each row 'F graph mask v0 v1 live dead') and diff them against a model you wrote without reading the collector. That mode only prints: it is not a CTest and the repository stores no expected rows, so a clean exit proves nothing until your own comparison has run.

**How to read the result.** A rejected variant is a demonstrated invariant violation in well-defined C: the answer is wrong (a live mask short of 15, or a callback count other than one), nothing crashed. Do not call it exploitation, because the model holds no authority, secret or real resource. If a sanitizer report or crash turns up while you work, record it separately as a lower class. Enumeration over at most 16 identities does not cover every graph, and concurrency, hostile allocators and corrupted state are outside the contract. The assessor's mutation set also checks this invariant, but that set is not part of what you receive.

Only your own implementation and the synthetic data of this lab are attacked; no external service, hardware or host setting is touched.
