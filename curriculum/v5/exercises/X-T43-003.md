# Bind a native PMU result to the code that ran

## Prerequisites

Complete X-T43-002 before beginning.

## Environment

Use native Linux x86-64 with per-thread PMU access, your completed PMU component and the public runner under `labs/performance_followthrough/`. The measured collector has its own build manifest. Record the CPU and toolchain reported by the runner.

## Problem

Collect fresh paired native observations of your own completed PMU and workload implementations. Predict the direction of one metric, record the exact CPU domain, and point to specific instructions in the measured binary that could explain the result.

## Necessity

Identify the CPU, event, attachment and permissions of the actual observation. An output value by itself omits the evidence that connects this claim to a particular build.

## Reasoning

Use the supplied native runner's doctor, protocol, build, run and report commands. Select an allowed CPU for the same event domain used in counting. Record binary identity, workload/seed, compiler flags, event ID mapping, count units, elapsed times and calibration. Disassemble the measured function with objdump and cite its instructions. Compare both orders and evaluate acquisition, scheduling, calibration and interpretation separately.

## Deliverables

- D1. Write your prediction before running the relevant inspection tools. Record the commands, file identities and observations in `answers/live.json`. Include `prediction`, `explanation` and the fields `report`, `measured_image`, `measured_function`, `report_sha256`, `pairs`, `interpretation`.
- D2. In your explanation, cite the bytes, instruction, header field or counter row supporting each inference in the reasoning exercise.
- D3. Repeat with a changed N or access domain, retain both reports, and explain whether the prediction survives. If the kernel denies the request, submit the doctor output as an unavailable observation and continue other exercises. Live measurement stays pending.

## Verification

Run `python3 inspect_lab.py check live --cc gcc`. Retain the exact report with the submission. A reviewer reads the written reasoning alongside the machine-checked observations.

## Rubric

- R1. Identify the CPU, event, attachment and permissions of the actual observation.
- R2. Recompute paired counter gates for the measured executable.
- R3. Correlate a bounded cost claim with instructions and workload in the exact measured binary.

## Hints

Read the native runner help for required component paths. A filtered kernel event, zero-running row, software clock or historical replay cannot provide a fresh instruction/cycle measurement.

## Variants

V1 is a delayed independent transfer on a changed artifact, at least seven days after the first attempt. Derive the result from the supplied inputs and identify the evidence needed for each claim.

## Security

Use the supplied original program and locally generated files. Keep measured images, host details and observation logs in the local workspace.

## Validation

The checker compares selected artifact facts. The assessor separately evaluates the derivation, changed condition and whether an independent transfer took place.
