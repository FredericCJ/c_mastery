## Problem

Implement RPSequence with16 nodes{id,parent,byte,tombstone}. id is globally unique and positive, parent<id; parent0 is the root and every nonzero parent must already exist. Concurrent siblings render in descending ID order by depth-first traversal; tombstoned parents remain traversable. Duplicate identity with identical parent/value is idempotent; conflicting reuse fails. Missing dependencies return RP_GAP unchanged. Render stages output and fails transactionally if capacity is insufficient. Also implement two-concurrent-insert position transformation with distinct priority tie-breaks; no full network OT control algorithm is supplied.

Concrete inputs and expected results: Insert A(id1,parent0),B(id2,parent0),C(id3,parent1) in either admissible arrival order: render BAC. Delete id1: render BC, retaining descendant C. Two inserts at position0 with priorities1 and2 transform the higher-priority-number insertion to position1.

Supplied artifacts: labs/replicated/include/replicated.h, compiling unsolved src/replicated.c, CTest replicated.sequence, fixtures/replicated/PR-T76-06.json, and the shared contracts. State every additional backend assumption before running it.

## Security

Target only RPSequence and the two-insert transformation in [labs/replicated](../../../labs/replicated), in a local process.

- **Adversary.** You control arrival order, duplication and omission of inserts and deletes, identity reuse with a different parent or byte, deletion subsets and the render capacity. You do not control code, memory or priorities beyond the stated distinct values. Worked trace: A(id 1, parent 0), B(2, 0) and C(3, parent 1) are concurrent siblings 1 and 2 under the root, so descending identity puts B first, then A, then A's child C: "BAC" whichever of the two orders replica a or b received them in (tests.c:171-180).
- **Violated property.** Convergence and rejection integrity: all admissible orders render the same text, a tombstoned ancestor keeps its descendants (removing id 1 renders "BC", not "B", tests.c:181-183), reusing id 3 with another byte is RP_CONFLICT, an absent parent is RP_GAP and a too-small buffer is RP_FULL. CONTRACTS.md:77 says only that RP_GAP is returned unchanged, that conflicting reuse fails, and that render fails transactionally; it does not promise that every rejected insert leaves state unchanged. The supplied test checks the unchanged state only after RP_GAP and checks only n == 2 after RP_FULL; asserting that RP_CONFLICT and a failed render change nothing is your own addition and your own specification, not a contract promise.
- **Experimental boundary.** One hosted process, sixteen nodes, byte payloads, no fork, socket, file or network. The oracle you write enumerates topological orders and deletion subsets; only the two-insert OT case is covered.
- **Evidence to capture.** Predict first: for rp_ot_insert(0,2,0,1) and rp_ot_insert(0,1,0,2) the transformed positions are 1 and 0, and the render into a 1-byte buffer reports n == 2. Run CTest replicated.sequence and record the CHECKs at tests.c:177-188. Build the two variants from the header and record the `RP_CHECK line N` each produces. Then extend sequence_test with CHECKs for the sequence after RP_CONFLICT and for the output buffer after RP_FULL, and say which of your variants those CHECKs would catch.
- **Impact class.** demonstrated-invariant-violation, once you have built and run a variant. Divergent rendering for one operation set is a violated property in the model, not a crash or a fault of real memory.
- **Remediation.** Descending-identity sibling order, traversal through tombstones and validation before mutation. The regression that rejects the original defect is replicated.sequence; run it against both of your variants.
- **Limitations.** The OT diamond does not generalize; provide the three-operation counterexample. No authenticated identity allocation or network ordering is shown.
