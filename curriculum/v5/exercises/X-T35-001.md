# X-T35-001: Independent decoder defense

## Prerequisites

Complete X-T04-001, X-T03-001 and X-T03-002. Bring their source-bound revisions, contracts and independent tests; this integration must reuse them or a documented compatible adapter. Read T35.01–T35.03 and PR-T35-01. The accepted project's opcode/count payload protocol is preserved: this exercise adds a separately named eight-byte record protocol, never silently changes `f_packet` or its receipts.

## Environment

Apply [shared contract v1](shared-contract.md). Run an original local profile A teaching harness with a profile C decoder/commit core. The target has no network, files, credentials or privileged effects. An attacker input is a local byte sequence and its length. Authorization is a separate trusted harness argument and cannot be granted by an input flag.

## Problem

Implement `fd_apply(wire,length,authorized,synthetic_counter)`. Use X-T03-002's exact record format. Compute the mathematical proposed counter `old + count * value`; only an int32_t-representable result may commit. Count is the number of synthetic units, not a payload extent. All flags 0–3 are permitted syntax but none grants authority. All successful requests require `authorized != 0`. Validation/range errors precede `FD_DENIED`; any failure preserves the old counter. Null counter or wire is `FD_INVALID`. The input pointer denotes a real array of its advertised length.

Reuse the checked-extent and cursor mechanisms to admit/read the eight-byte record before decoding; provide a dependency/adapter trace showing actual calls, not a heading claiming reuse. The supplied family includes a deliberately flawed teaching variant whose publication occurs before all admission gates. First seal a property and predicted witness, then demonstrate a harmless counter change from a denied request in that target. Repair the publication boundary and replay the identical witness.

For example, trusted old counter 10 and bytes `01 00 00 02 00 00 00 03` request a proposed result 16. With authorization denied, the correct output remains 10. An unauthorized result of 16 is a demonstrated violation of this laboratory's property, not arbitrary code execution.

## Necessity

Parsing correctness, arithmetic correctness and authorization do not compose automatically if side effects happen too early. A check placed after publication can reject with the right status while still violating integrity. Sanitizers need not report a perfectly defined premature state change.

## Reasoning

Write the invariant: every non-successful call leaves the protected counter unchanged, and successful calls arise only from a complete valid authorized request with representable arithmetic. Mark parse, compute, authorization and commit stages. Prove all intermediate arithmetic using int64_t or another explicitly sufficient mathematical bound; count<=65535 and int32_t value make the product plus int32_t old value fit int64_t, but the final counter can still reject.

Explain the fixed eight-byte O(1) work/storage bound and why this does not cover variable-length attacker work. Trace how an extent mistake would become an out-of-bounds access in a variable-payload variant; keep that hypothetical analysis separate from the actually demonstrated state violation. The caller retains input ownership; the function retains no input or partial state after return.

## Deliverables

- **D1:** threat/property/containment model, sealed witness prediction and commit/integer proofs.
- **D2:** composed defended core with exact prerequisite source identities and adapters.
- **D3:** flawed-versus-fixed replay, counter before/after/status, regression and independent state oracle.
- **D4:** delayed incremental-framing state machine, cancellation/reset analysis and bounded-resource defense.

## Verification

Run `foundation_depth.defense`. Test authorized/denied valid records; each truncation length; trailing bytes; invalid version/flags; zero count; both signs; int32_t counter extrema; and proposed-result underflow/overflow. Compare status and unchanged state for every reject. The host oracle uses unbounded integers and a separate trusted authorization value.

The primary negative control is a compiling defined-behavior premature-commit mutant. Require a witness that changes the synthetic counter while returning rejection; then require the repaired target to preserve it for the same input. Add a mutant trusting a wire flag for authority and demonstrate rejection by the permission matrix. Fuzz only original targets with bounded local byte arrays; minimize failures and record seed/count/time. Fuzzing is supplemental, not an independent-assessment receipt.

## Security

The target is the learner's `fd_apply` decoder (`labs/foundation_depth/src/depth.c`), compared with the deliberately flawed `vulnerable` function in the supplied control `labs/foundation_depth/drills/authorization.c`. Both live in that one executable (target `depth-authorization`, built in every configuration; its CTest registration `foundation_depth.authorization_observation` exists only in assessor builds, so run the executable directly); there is no separate flawed executable and nothing in `labs/foundation_followthrough` is used. The attacker chooses the eight-byte record, the declared length and the order of requests; trusted code supplies the authorization flag and the counter pointer.

**Property.** The synthetic counter is integrity-protected: it changes only after the whole record is admitted, authorization is nonzero and `old + count * value` fits in `int32_t`. Any other outcome, including `FD_DENIED`, `FD_INVALID` and range failures, leaves the old value. This matters because a decoder that publishes first and checks authorization afterwards reports the refusal truthfully while the state has already changed, so a caller that trusts the status alone never learns the counter moved.

**Experiment and evidence.** Seal the prediction before running anything: with counter 10, bytes `01 00 00 02 00 00 00 03` (version 1, flags 0, count 2, value 3, so the proposed change is 2 * 3 = 6 under the layout in labs/foundation_depth/CONTRACTS.md, section Canonical eight-octet record) and authorization 0, what does each path return and leave? The control (authorization.c:43-57) answers it: `vulnerable` returns FD_DENIED but leaves 16, because it assigns the counter at line 32 before testing `allowed` at line 33, while `fd_apply` returns FD_DENIED and leaves 10. Run the executable `depth-authorization` directly from your build directory and record the printed statuses and counters and the exit status: it exits 0 only when both statuses are FD_DENIED and the flawed path ends at 16 and the repaired path at 10 (authorization.c:55-57). The learner-visible test `defense` in `labs/foundation_depth/tests/tests.c` (CTest `foundation_depth.defense`) requires counter 10 after denial, then FD_OK with 16 on authorization, FD_RANGE for lengths other than 8 and for the overflow record, FD_INVALID for a bad opcode byte or flag bit, and the zero-delta record leaving 10, always with the counter unchanged on refusal. It tests `fd_apply` only; to see it catch the flaw, write a commit-first `fd_apply` yourself and record the CHECK line that fails.

**Impact class.** An unauthorized change of the counter is a `demonstrated-invariant-violation` of this laboratory's property, shown by the supplied control. It is a defined logic error, so a sanitizer will not report it, and it is not arbitrary code execution or a proved impact on any real system.

**Repair and limits.** Repair by delaying the single commit until every gate passes, then replay the identical witness plus the malformed and overflow cases as regression tests. Limits to state: caller pointer validity, single-threaded use and the trusted authorization are assumptions, and nothing is shown about production protocols.
