## Security

**Why this matters here.** Trial deletion is a counting argument. Copy the counts, subtract every edge whose source lies inside the candidate set, and treat any candidate with a positive residual as held from outside, together with everything reachable from it. If the subtraction or the rescue is wrong, the collector either frees an object that something outside still references or leaks a true cycle. The heap here is sixteen indexed slots, so the failure appears as a dead mask that disagrees with your count, never as a dangling pointer. The property to defend is the invariant orr_invariant checks at every operation boundary: each live count equals its roots plus incoming edges plus queued decrements.

**What to try.** Pick candidates and queued decrements adversarially: a two-object cycle with counts 1,1 and no outside holder (must be reclaimed, tests/tests.c:226), the same cycle with counts 2,1 so one object has an outside holder (nothing may be reclaimed, :234), an object whose only remaining reference comes from a surviving candidate, a ninth queued decrement while eight are pending, and one more retain after 255 roots on a single identity. Write the dead and live masks you expect before you read the CHECKs, and note that dead and live are bitmasks over slots, not counts.

**Evidence to capture.** Build two broken trial deletions, described by the property each violates: one that reclaims an object still referenced from outside the candidate set, and one that reclaims an object reachable only from a candidate with a positive residual. Predict which OR_CHECK line in object_runtime.trial rejects each, run it, and keep the stderr line. For the concurrent adapter, run object_runtime.rc_concurrent on your own implementation; its worker threads (tests/rc_ext.c:200-252) are the only place in this lab where scheduling matters, and one passing run says nothing about other interleavings. Run `object-runtime-rc oracle`, which prints 65,536 rows and compares nothing, and diff the rows against a model you wrote yourself.

**How to read the result.** A variant rejected by a dead-mask CHECK is a demonstrated invariant violation in well-defined C, not a memory-safety finding: no freed memory is reused and nobody controls it. A stale access that only ASan reports would be a sanitizer finding, a lower class, and should be recorded separately. The mutex gives exclusion for the documented calls only; atomic counts, memory-order claims and unbounded schedules are not demonstrated. The assessor's mutation set also checks this invariant, but that set is not part of what you receive.

Only your own implementation and the synthetic data of this lab are attacked; no external service, hardware or host setting is touched.
