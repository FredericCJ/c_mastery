## Security

Why this matters here. The caller of sd_apply sometimes gets SD_UNCERTAIN: the operation was interrupted and the caller cannot tell whether it took effect. The only safe response is to retry with the same operation ID, and that is safe only if the journal answers a duplicate from the stored receipt instead of applying the delta again. In the test, an interruption at cut 4 happens after the commit is durable, so recovery reports last = 1 and value = 7 and the retry must return 7, not 14; at cuts 1 to 3 recovery reports last = 0 and value = 0 and the retry applies the delta once. The same ID with a different delta is a conflict, and an older ID is stale. A related property is the direction of acknowledgement: if recovery would not find the operation committed, the caller must not have been told it succeeded.

What to try. Trace the four cuts by hand, writing for each what recovery finds and what a retry must return. Then follow the integer cases: ID 2 with delta -3 gives 4, ID 1 again is SD_STALE, an INT32_MAX delta followed by +1 is SD_FULL with the output unchanged because the overflow is refused before the journal is touched. Then build two variants of your own: a retry that applies its effect twice, and an acknowledgement that does not agree with what recovery would find.

What to capture and how to read it. Run `service_depth-tests journal` and keep the `SD_CHECK:<line>:<expression>` each variant reaches, mapped to the check in labs/service_depth/tests/tests.c: the uncertain status with `out == 99` at every cut, the recovered receipt per cut, the retry value, the conflict, the stale ID, the overflow refusal, the SD_CORRUPT result after the byte flip `j.durable[1][12] ^= 1` (recover leaves the receipt untouched at 99), and the alternating-slot loop for IDs 1 to 3. Explain separately why a changed commit marker or a recomputed checksum is not covered: the checksum detects accidents, not tampering, and clearing a commit marker makes a record look uncommitted.

What this does and does not show. A doubled or falsely acknowledged integer in a modelled atomic-flush journal, on synthetic data. No supplied artifact demonstrates it, so the impact class holds only once you build a variant. The assessor's mutation set also checks this invariant. Real storage, power loss, sector tears, concurrent writers and authentication are outside the model, and the file-channel-journal composition in labs/service_depth/tests/composition.c is a separate check.
