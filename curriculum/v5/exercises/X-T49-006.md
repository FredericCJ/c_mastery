# Diagnose a slow telemetry service

## Prerequisites

X-T49-002, X-T49-003, X-T49-004, X-T49-005 supply the process, namespace or transport foundations for this investigation.

## Environment

Use the exported linux_supervision workspace and restore the pinned Linux guest with `python3 guest.py setup`. Start with the `telemetry` case in CONTRACTS.md and the fixture interfaces in PROTOCOL.md.

## Problem

An operator sees a slow batch of telemetry requests. Predict the counters and application events that would discriminate a CPU bandwidth limit from a paused downstream consumer.

## Necessity

Distinguish measured CPU throttling from downstream backpressure for the same workload. Preserve every accepted frame across partial I/O, write refusal and downstream recovery. These observations give a reviewer enough information to distinguish different mechanisms that can yield the same visible outcome.

## Reasoning

Read the cgroup CPU counters around the measured work. Compare the change in throttling periods with actual write refusals and subsequent successful transfers. A checksum catches loss or duplication even when the counters appear plausible. Explain what a run with no discriminating signal permits you to conclude.

## Deliverables

- D1. Record your prediction in `answers/telemetry.json`. Implement supervise_telemetry in src/telemetry.c. Use the common finite input, checksum protocol and digest recurrence in PROTOCOL.md for all three trials. Run the same loopback request/reply service in the baseline, quota and stalled conditions. In the stalled trial use the fixture contract to withhold pipe draining until the first nonblocking refusal, then resume and finish the same batch. Preserve the raw observations, pair each diagnosis with the discriminating signal and check payload conservation.
- D2. Preserve your source, guest serial transcript and run identity. Write an explanation keyed to the measured fields in both the program and the independent outer observations.
- D3. Explain how two similar elapsed times could result from different mechanisms and identify a measurement that would falsify your diagnosis.

## Verification

Use `python3 submission.py observe telemetry --program build/learn/supervise --out build/first-telemetry` after building. Run the standard `cmastery check` command in CONTRACTS.md for a fresh graded execution. Explain any discrepancy with your original prediction.

## Rubric

- R1. Distinguish measured CPU throttling from downstream backpressure for the same workload.
- R2. Preserve every accepted frame across partial I/O, write refusal and downstream recovery.

## Hints

Explain how two similar elapsed times could result from different mechanisms and identify a measurement that would falsify your diagnosis. Use the fixture barriers and monotonic deadlines to order observations; a sleep chosen by trial and error cannot establish readiness.

## Variants

V1 is an individually assigned changed condition after at least seven days. Record the prediction and the observations that would distinguish the alternatives before rerunning the program.

## Security

Use the course’s diskless, networkless guest. The fixture owns namespace creation, controller settings and teardown. The supervisor handles the bounded learner workload as an ordinary guest user.

## Validation

The live CTest checks the selected case against current guest and executable identities. Offline replay verifies trace structure and invariants. A reviewer grades the explanation and changed-condition transfer.
