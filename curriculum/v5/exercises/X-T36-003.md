# X-T36-003: All-overlapping binary matches with atomic capacity failure

## Problem

Implement sc_matches for text0..64 bytes and pattern0..16 bytes. Numeric zero is data. Text [0,97,0,97,0], pattern [97,0] produces [1,3]; pattern [0,97,0] produces [0,2]; empty pattern produces [0,1,2,3,4,5]. For text aaaa and pattern aa return [0,1,2]. A capacity one below the required match count returns SC_FULL and preserves count and every output byte. A longer pattern returns success with count0. The earlier algo_match exposes only a first-match index. The original parent project asks for a required count on failure; this additive API deliberately preserves the count too. Supply a separate documented adapter if the parent interface is required, computing required count through a read-only pass before publishing that different result. Do not claim API equivalence.

## Necessity

The repository audit found a concrete contract/execution mismatch: the earlier algorithms family implements idempotent AVL duplicates and first-match bytes, and explicitly excludes a clocked instruction engine. This additive exercise preserves baseline contracts and accepted evidence while exposing the missing behavior. Selected A/B/C/D/F/H/I/J families assess derivation, construction, boundaries, diagnosis, falsification, resource arguments and changed assumptions without manufacturing irrelevant allocation or network failure modes.

## Reasoning

Advance candidate starts by one, even after a match. Prove m<=n before n-m, so unsigned subtraction never wraps. An empty pattern compares zero bytes at all n+1 boundaries; it does not mean missing. The first pass establishes enough output capacity, while immutable input makes the second pass observationally identical. Count publication and byte publication form one logical success contract under single-owner execution. The algorithm is O((n-m+1)m) for nonempty patterns and O(n+1) for empty patterns; it does not establish expected hash-table performance or provide the parent assembly lookup kernel. State preconditions, postconditions, ownership, failure publication and complexity for each API. Identify what ISO C enforces, what the runtime checks, and what remains programmer discipline. Refute a plausible incorrect explanation with a minimal input.
