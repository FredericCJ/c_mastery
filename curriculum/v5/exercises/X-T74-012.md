# X-T74-012: Weak binary symbols across moving collection and fallible rehash

## Prerequisites

Complete X-T74-002's copied binary table, X-T74-008's actual ORXHeap and X-T66-009's typed counting allocator. Bring those learner source revisions and contracts. Supply the ownership workspace through CMASTERY_OWNERSHIP_ROOT; copy/adapt your own earlier object_runtime implementation in this same family. Record each adaptation. Original project imports are not silently satisfied by assessor code. This later integration completes T74.02's weak/moving transfer without adding an earlier-to-later prerequisite cycle.

## Environment

Use C17, CHAR_BIT8 and the shared exact-width types, GCC/Clang hosted profiles and explicit T66 allocation callbacks. No hashing, interning or collector library may implement the mechanism. Python dictionaries are independent host verification tools only. The actual target has eight typed cells, not an operating-system heap or external service. The old portable-core target build does not validate this integration.

## Problem

Implement ORXIntern from the public object_runtime_ext.h using the Weak hash interning section of EXTENSIONS.md. Accept counted binary keys of length0..15, with NULL permitted only at length0. Return one retained slot/generation handle per successful lookup. Buckets start absent, grow4 to8 to16 above half occupancy, probe after hash=(hash*33+byte) mod256 and compare full length/bytes. Buckets are genuine allocated int32 objects. A hit allocates nothing. Stage replacement buckets before allocating the symbol; failure returns the old table, heap and output unchanged and releases every private allocation.

The table is weak. Collecting the heap makes get/reserve reject until sweep removes dead generations and rebuilds the probe chains in place. Moving live cells changes neither handle identity nor bucket membership. Closing frees buckets but never consumes caller roots. Inputs, outputs and live controls must occupy distinct storage; allocator callbacks cannot reenter. See the shared contract for exact status and finite retirement policy.

Concrete witness: keys {0,97} and {97,0} collide under the fold but receive distinct identities. Retain the first, release the second, collect, pack and sweep. The retained first key must keep its handle; reinterning the second must not revive the stale generation. Inject the next growth allocation failure and require the old first lookup still succeeds without an allocation. Supplied extensions.json, tests/extensions.c and the independent Python oracle define additional exact inputs.

## Necessity

An integer symbol ID is neither an ownership token nor an address. Treating weak table membership as a root leaks; treating a hash match as equality conflates binary inputs; publishing rehash storage before pool admission loses rollback. This exercise composes these failure boundaries with actual allocator and moving-pool state.

## Reasoning

Derive valid probe chains, unique live canonical identity, external root conservation and the collect/sweep epoch barrier. Locate the private-acquire/publication/release frontier. Derive worst-case16 bucket probes, at most8 live symbols, linear full rehash, and transient two-array ownership. Explain that unsigned arithmetic and typed accesses are ISO C mechanisms, whereas epochs, ownership and callback discipline are library contracts. Compare strong linear retention with weak hash retention only after stating their different lifetime contracts.

## Deliverables

- D1: State and ownership diagrams, key/handle identity proof, failure-prefix table and a counterexample to hash equality or bit-copy ownership.
- D2: Learner implementation, actual allocator adapter and explicit imported artifact revisions; preserve the original linear implementation for the comparison.
- D3: Source-bound compiler/sanitizer runs, exact independent10000 observation comparison, snapshots, allocation live/peak counts and minimized witnesses for both compiled mutants.
- D4: Retained-symbol/moving/fallible-rehash transfer, closed resources and the shared13-dimension COST_REVIEW with measured allocator counts and precise unsupported claims.

Independently derive expected identities and allocation attempts for empty/embedded-NUL inputs, collision pairs, capacity boundaries, allocation failures and pool exhaustion. Fail on changed rejection output, leaked private arrays, stale-epoch admission or identity revival. Cross-check allocator live count reaches zero after close; caller roots remain separately owned. The scope report binds actual sources; finite cases do not prove all inputs or learner mastery.

A root/ownership error or false ISO safety claim fails the applicable criterion regardless of total score.

2. A failed pool admission can occur after replacement buckets were allocated.
3. Rebuild probe chains after removing stale generations; deleting a bucket in place without repairing a chain can hide later colliding keys.

## Security

**Why this matters here.** An intern table answers 'have I seen these bytes before?' with a handle, so its whole security story is identity. The same bytes must give the same live handle, different bytes must never share one, and a symbol that died and was swept must return under a new generation. The table must also survive an allocation failure in the middle of growth without changing the old table, the heap or the output. Keys are counted binary strings, so an embedded NUL and the empty string are ordinary keys and strlen-style comparison is wrong.

**What to try.** The fixture's deliberate collision is {0,97} against {97,0}. Fold them by hand with hash = (hash*33 + byte) mod 256 from 0 (EXTENSIONS.md:101-102): the hashes are 97 and 129, which differ by 32, so under the assumption that the probe start is hash mod capacity (equivalently hash & (capacity-1)), which EXTENSIONS.md:101-102 does not state because it says only linear probing, they collide at every permitted capacity 4, 8 and 16 even though the full hashes differ. Then follow the test: a third key with the allocator armed to fail returns OR_FULL and leaves heap bytes, bucket pointer and live allocation count unchanged (tests/extensions.c:168-174); a collected but unswept table refuses lookups with OR_INVALID (:183); a failed reserve(16) leaves capacity 8; and reinterning y after the sweep returns the same slot with a different generation (:207-208).

**Evidence to capture.** Build two broken tables, stated as properties: one that returns the same handle for two different keys sharing a probe start, and one that hands back an old generation after a sweep. Predict which OR_CHECK line in object_runtime.ext_intern rejects each, run the test, and keep the stderr line. The `oracle` mode in the same file (tests/extensions.c:296-363) prints allocation-failure (I) rows, pack (P) rows and binary32 (V) rows and compares nothing; run it against your implementation and diff all three kinds of row against a model you wrote yourself.

**How to read the result.** A rejected variant shows identity conflation in a synthetic table of at most 16 buckets, found through well-defined C. It is not hash-flooding denial of service, a timing channel or memory corruption, and cooperative in-process handles do not resist arbitrary memory writes. Allocator behaviour beyond the injected failures is not modelled. The assessor's mutation set also checks this invariant, but that set is not part of what you receive.

Only your own implementation and the synthetic data of this lab are attacked; no external service, hardware or host setting is touched.
