# X-T68-009: A bounded hygienic token expander written in C

## Prerequisites

Complete X-T68-008 and implement the retained mp_expand primitive in this project. The successor imports that actual leaf transformer; no unrelated owner or formatting ABI is required. Do not import an assessor implementation.

## Environment

Implement mechanisms locally using declared typed storage/callbacks; hosted harness and diagnostic runtimes are separate. See laboratory contract for exact dependencies. Use C17 with extensions disabled and warnings treated as errors. A diagnostic extension is identified explicitly and does not become an ISO guarantee. The full platform, pointer, callback and concurrency preconditions are in [metaprog/CONTRACTS.md](../../../labs/metaprog/CONTRACTS.md).

## Problem

Implement mp_expand for at most32template tokens. kind0 is a literal token whose context is retained;kind1 substitutes argument indexsymbol and preserves the argument token completely;kind2 is an introduced binding/reference token whose symbol is retained but context becomes one fresh expansion context. Validate kinds, argument indices, capacity and context exhaustion before publishing output/used or incrementing next_context. Context0 andUINT_MAX are rejected; all supplied objects are disjoint and live. This bounded token model does not parse C or implement the complete Rust macro grammar.

Concrete inputs and expected results: Pattern[introduced7,arg0,introduced7],argument(symbol7,context5),next12 producescontexts12,5,12 andnext13. ExhaustedUINT_MAX, insufficient output capacity or bad argument index leaves state unchanged.

Supplied artifacts: labs/metaprog/include/metaprog.h, compiling unsolved src/metaprog.c, CTest metaprog.hygiene, fixtures/metaprog/PR-T68-09.json, and the shared contracts. State every additional backend assumption before running it.

## Necessity

Explain variable capture using symbol identity plus syntax context, and distinguish preserving call-site argument context from assigning a fresh context to introduced bindings. The misconception and changed-condition case below are separately assessed; ordinary successful execution alone does not cover them.

## Reasoning

Define identifier equality as(symbol,context), track binding/reference identities through an expansion, and show how call-site symbol7/context5 remains distinct from introducedsymbol7/context12. Explain nested expansion context retention and finite namespace exhaustion. Compare the inspected Rust mixed-site hygiene rules precisely; the model uses an explicit stronger uniform context scheme for introduced names. Give the abstraction function, admitted states, pre/postconditions, ownership graph, failure effects and complexity before implementation. Identify the enforcement boundary of every safety claim using the shared modern-cost contract. Distinguish an invalid caller object from an operational failure admitted by the API.
