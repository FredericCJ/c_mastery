# X-T14-017: Stable compaction, owning tails and physical erase

## Prerequisites

Know array bounds, typed object lifetime, value versus reference arguments, callback contracts and resource ownership. Bring an ordinary vector mutation/invalidation trace from PR-T14-02 and a simple sequence model; no allocator or library filter may implement this mechanism. This is an additional required contract, not a claim that the retained vector was absent.

## Environment

The explicit [contract1](../../../labs/corpus_erase/CONTRACTS.md) supplies representations, all operations/statuses, capacities, pointer premises, callback effects, resource costs and containment. Implement `src/erase.c`. The C core is Profile C. Hosted C++17 and Python are separate comparison/oracle dependencies. Record actual C and C++ compiler selections independently and do not infer strict freestanding closure from a host build.

## Problem

First compact `[1,2,1,3]` by value1, returning a stable prefix, logical end and assignment count without changing array extent. Then construct IDs1..4 with values1,2,1,3, evaluate a predicate borrowing the first original value, and produce the retained IDs2,4 while retaining removed rights1,3 in a pending tail. Physical erase must drop exactly1,3; clear must later drop exactly2,4. Fail each predicate call, reuse an old tail, clear a pending tail and exhaust epoch headroom. Implement every operation in the shared API; provide the exact state/output/drop ledger at each step.

## Necessity

A correct-looking retained prefix can hide leaked or duplicated rights. Logical removal does not shrink a container; an unspecified tail is not a reliable list of removed original objects. Moving an owning C++ value may destroy an overwritten resource before physical erase. Aliasing the comparison value can change later decisions. These are distinct mechanisms with separate counterexamples.

## Reasoning

Derive the read/write frontier invariant for scalar stable compaction. For the owning adaptation, prove that every original ID appears exactly once across retained and removed partitions, decisions finish before publication, and failure preserves owner/output while callback observations remain. State all preconditions, postconditions, ownership transfers and complexity bounds. Explain generation headroom and why public token fields do not provide unforgeable capabilities or protection after owner lifetime. Compare ISO C guarantees, diagnostics, runtime checks, external models and caller discipline with the inspected C++ contracts; include an incorrect claim and a minimal counterexample for each rubric criterion.

## Security

Why this matters here. er_remove_if and er_erase split a removal into two steps, as std::remove_if and vector::erase do, but with a defined tail: the retained records are moved to the front in their original order, the removed records follow in their original order, and nothing is released until er_erase is called with the matching token. The point of the split is the resource ledger. Each removed right must be dropped exactly once and only for a removed ID, and the order of the retained records is observable by every later caller. Both properties can be wrong while the array looks plausible, and neither involves real memory: the "resource" is an ID recorded by the test's drop callback, so a violation shows up as a ledger entry, not a crash.

What to try. Work out by hand er_compact on [1,2,1,3] removing 1 (end 2, two moves, prefix 2,3) and then, for a length-4 owner with IDs 1..4 and a removal mask, where each record sits after er_remove_if and which IDs er_erase must drop. Then build two variants of your own that each break one property: a retained order that differs from the original, and a drop of IDs that were not removed. Write down before running which assertion each should trip.

What to capture and how to read it. A failed check prints `ER_ASSERT:<line>:<expression>` and exits 41. Retained order is read from the check on items[kept].id after the filter for every length through 8 and every mask; the ledger is read from c.drops[i + 1] against the mask. Because drop() asserts that an ID is dropped at most once, a double release stops inside the callback (the expression names the drops count) rather than in the main loop; note which of the two you observe. Also keep the results for the failing-predicate positions (owner bytes and token unchanged), the stale token after a second erase, the predicate that borrows the first original value, and the exhausted epoch. The registered corpus_erase.cpp_comparison test is a separate hosted C++ experiment on one library implementation; do not generalize it.

What this does and does not show. A wrong order or ledger on synthetic IDs. No supplied artifact demonstrates it, so the impact class holds only once you build a variant. The assessor's mutation set also checks this invariant. Forged owners, dangling owner pointers, owner-address reuse, nonlocal exits and callback reentry are caller obligations that the scalar epoch cannot enforce, and nothing here demonstrates a real use-after-free or code execution.
