# T06: Preprocessing and metaprogramming

## Purpose and outcomes

Use preprocessing as token transformation with a verifiable evaluation contract. Debug expansion directly, keep registries authoritative, and choose between macros, typed functions and external generation based on diagnostics and maintenance rather than cleverness.

## Entry check and remediation

Read function declarations and sequencing from T02. If macro output is surprising, inspect -E output before editing types. Complete the T05 __VA_OPT__ support prelude before the optional C23 form; the portable baseline must have a deliberate empty-argument policy.

## Component progression

**A single registry, several generated views.** Follow tokens through preprocessing; compare expansion with evaluation. Generate declarations and dispatch from one small registry and test bad configuration values.

Before implementation, predict this discriminating case: **A side-effect argument used twice by a superficially type-correct macro.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T06.01 — Translation phases

Translation phases explain why line splicing, comment replacement and tokenization affect later expansion. A backslash-newline can join physical lines before a comment is recognized; comment text is not a reliable macro separator after tokenization. Preprocessed output reveals tokens, while later semantic analysis still belongs to the compiler.

Investigation: Create line-splice/comment/literal examples and compare physical source, logical tokens and -E output.

Misconception to resolve: Macro expansion is not arbitrary string replacement over the original file bytes.

Observable evidence: A phase timeline and minimal sources that explain each surprising token result. Evidence is developed in {ref}`PR-T06-01`.

### T06.02 — Macro expansion

Function-like macros expand when followed by the invocation parentheses; object-like macros replace tokens directly. Arguments generally undergo prescan, substitution and rescanning, with special handling around # and ## and recursion suppression. Track tokens at each stage rather than guessing the final spelling.

Investigation: Trace nested replacement lists and a macro name used without parentheses, then check the preprocessor output.

Misconception to resolve: A macro that expands to its own name does not recurse forever under normal suppression rules.

Observable evidence: A token-stage table and actual -E observations with no semantic inference from text alone. Evidence is developed in {ref}`PR-T06-01`.

### T06.03 — Stringification and token construction

Stringification preserves an argument’s token spelling at that step; an extra macro layer is needed when prior expansion is intended. Token pasting must produce valid preprocessing tokens. Generating a plausible identifier does not guarantee that its eventual declaration or type is valid.

Investigation: Build two-level stringify/paste helpers and one intentionally invalid token combination as a negative preprocessing case.

Misconception to resolve: Pasting is not a way to create arbitrary punctuation or bypass type checking.

Observable evidence: Exact token/string results and a separated preprocessing-versus-semantic diagnostic ledger. Evidence is developed in {ref}`PR-T06-01`.

### T06.04 — Variadic preprocessing

Variadic macros need a stated empty-argument policy. C23 __VA_OPT__ conditionally contributes tokens when variadic arguments are present; older comma-swallowing forms are implementation extensions. Evaluation obligations belong to the resulting C expression, so count each argument occurrence after expansion.

Investigation: Implement a trace wrapper with baseline and supported C23 forms, testing empty/nonempty arguments and side-effect counts.

Misconception to resolve: A convenient variadic spelling does not guarantee single evaluation.

Observable evidence: Expansion vectors, capability checks and observed evaluation counts for defined calls. Evidence is developed in {ref}`PR-T06-01`.

### T06.05 — Macro safety

Parenthesizing operands and the result handles precedence, but cannot prevent duplicated effects. Statement macros commonly use do/while(0) to behave as one statement; internal names can still collide and reserved identifiers remain off limits. Prefer static inline when types and single evaluation fit.

Investigation: Repair a minimum macro and a dangling-else statement macro; compare a typed function alternative.

Misconception to resolve: A fully parenthesized macro can still evaluate an argument twice.

Observable evidence: A side-effect counter test, scope/collision review and a documented remaining contract. Evidence is developed in {ref}`PR-T06-01`.

### T06.06 — X-macros and registries

An X-macro registry stores one row per authoritative item and derives enums, names and tables by redefining the row macro. Completeness includes duplicate identifiers, missing mappings and value constraints. Generated artifacts should be checkable against the registry rather than manually synchronized.

Investigation: Generate command IDs, names and dispatch metadata from one list and test round-trip name/ID consistency.

Misconception to resolve: One source list reduces duplication but does not automatically validate its contents.

Observable evidence: Duplicate/unknown checks and a complete generated table comparison. Evidence is developed in {ref}`PR-T06-02`.

### T06.07 — Type-directed interfaces

_Generic selects by compatible type without runtime dispatch, but association expressions still need valid syntax and constraints. Selecting function designators and calling the result often avoids invalid type-specific expressions in unselected branches. Array conversions and qualifiers need deliberate interface tests.

Investigation: Implement two typed operations with generic dispatch and compare a static-inline-only interface; add unselected-association negative tests.

Misconception to resolve: Generic selection is not a lazy parser for arbitrary invalid branches.

Observable evidence: Type-selection tests, diagnostics and generated-code evidence for the selected call. Evidence is developed in {ref}`PR-T06-02`.

### T06.08 — Configuration architecture

Build configuration determines compilation choices; public contracts describe supported behavior. Validate incompatible features early and include configuration identity in artifacts. A generated config header needs input provenance and stable ordering so rebuilds can be explained.

Investigation: Create a small feature matrix with required and forbidden combinations and a reproducible config manifest.

Misconception to resolve: An undocumented -D option can change ABI or semantics even if every source still compiles.

Observable evidence: Positive/negative configuration builds and artifact identities linked to inputs. Evidence is developed in {ref}`PR-T06-03`.

### T06.09 — External code generation

External generation suits structured schemas whose validation exceeds preprocessing. The generator’s contract includes accepted schema, deterministic output and failure behavior. Compare debugging, dependency tracking and review cost with macros; neither method is inherently more maintainable.

Investigation: Generate a protocol/register description from a validated JSON schema and compare generated constants with the schema oracle.

Misconception to resolve: Generated code is not correct merely because the generator ran successfully.

Observable evidence: Schema rejection tests, deterministic regeneration and artifact-to-input traceability. Evidence is developed in {ref}`PR-T06-03`.

## Mastery gate and feedback

Explain an unseen expansion stage by stage, prove the evaluation count of a public macro and diagnose an invalid generic association. Rebuild registry/configuration artifacts from one authority and detect a duplicate or forbidden combination.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

After a delay, add a registry row and a new feature constraint without manually editing derived tables. Compare a macro solution with a small generator on error messages and reviewability.

## Environment and limits

Use the recorded hosted laboratory in {ref}`guide-laboratory` and the per-project boundary in {ref}`guide-profiles`. C17 is the baseline; edition/extension experiments are isolated and capability checked. Supplied fixture oracles validate mathematical or declared synthetic expectations. They do not execute the learner’s C, prove all language behavior or certify target hardware. Record actual commands, versions, observations and unresolved limits separately.
