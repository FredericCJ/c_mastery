## Purpose and outcomes

Develop a diagnosis that survives a changed input, build or environment. T44 turns symptoms into replayable evidence, locates the first violated contract, tests competing causes and verifies a causal repair. It reuses existing components and tool practices; new hours cover the intentional defect, dossier and transfer. Ten projects of 4–12 hours total 82 hours; with reading 18 hours, assessment 8 hours and consolidation 6 hours, the module totals 114 hours. The 82 hours are implementation 56+verification 26, not an additional allocation.

## Entry check and remediation

After T03/T07, explain a valid object/lifetime, compile a two-function C program and test a boundary without executing UB. Complete only the named T21 assertion/logging and T32 fixture/replay leaves for the first milestone. If a learner cannot distinguish observed output from a hypothesis, use the defined assignment/counter faults in PR-T44-01/03 and repeat one discriminating test. The first three milestones need no completed T24/T25/T27/T31/T33 or T45 module. Later briefs list their exact selected preludes and reused artifacts; prerequisite time belongs to those existing exercises. A full-program order may place T44 later, while this novice diagnostic route selects only its entry leaves.

Use {ref}`guide-entry`, {ref}`guide-profiles` and {ref}`guide-roadmap` for entry/dependency policy. Every project keeps predicted, observed, inferred and open claims distinct. A tool absence has a supported alternate environment or a narrower model task, with the dependent runtime claim left open.

## Component progression

**A diagnosis that discriminates competing causes.** Seal the prediction, establish a same-failure reproducer and choose an observation before editing. Preserve the earliest supported invalid transition and an adjacent case rejecting a symptom-only patch.

Before implementation, predict this discriminating case: **A delayed variant with a different root cause but the same visible crash.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T44.01 — Observation, contracts and replay identity

A symptom is an observation; a cause is an explanation that survives discriminating tests. Record the expected contract before the first run: input range, state/effect limits, output on failure and finite completion policy. Preserve source revision, compiler/flags, image hash, input hash, configuration, platform and timeout. A log paired with the wrong image is not the same experiment. PR-T44-01's image A / input abc record matches, whereas image B with image A symbols does not. Its digest identifies bytes, not their authenticity.

Predict two causes before editing: for an accepted out-of-range request, either validation was removed or validation changed the input. Observe the parameter immediately before/after validation to separate them. Keep expected, observed, inferred and open claims in separate fields. An isolated deterministic harness makes hypotheses cheap to test; a synthetic expected history remains a model. A build that happened to print the expected value says little about an untested boundary. Retain the first useful cause separately from secondary cleanup/logging failures and reduce one diagnostic variable at a time.

- `T44.01.a`: Write an observation record that separates actual output, expected contract, inference and an untested hypothesis.

- `T44.01.c`: Predict two competing causes and select a discriminating observation before changing the program.

### T44.02 — Build diagnostics, assertions and bounded logs

The faulty admissible function in PR-T44-01 assigns n=0 in its condition, then accepts every supplied value. This is a defined logic error, so its source transition is suitable for a first novice investigation. A warning is a lead: parenthesizing the assignment may silence it while preserving the defect. External validation must survive NDEBUG. Assertions express internal promises, and their expressions must not perform a required operation. Reuse T21's three-record ring with overflow policy and an independent first-cause field: four events retain the last three while the first cause stays E_INPUT. Disable each diagnostic channel independently, then verify no diagnostic-only side effect is evaluated and required validation still runs. Bounded logs can drop events and change timing; retain those limits and compare a release build. A clean warning build or debug-only repair is not a correctness certificate.

### T44.03 — Minimal reproducers and input reduction

PASS means the selected contract holds; FAIL means the selected failure persists; UNRESOLVED means a malformed candidate, another symptom, or an unclassified replay. Treating UNRESOLVED as PASS can produce an invalid alleged minimality result. The inspected ddmin algorithm tries subsets and complements, keeps a failing smaller configuration and increases partition granularity when no reduction works. Use at most 16 chunks, bounded work/time, a stable configuration identity and cached test outcomes. Reuse the T32 replay harness; write only the new reducer and small original input grammar.

The eight-chunk fixture fails when it contains 1, 7, 8 together or 2, 3 together; a partial 1/7/8 group without either complete trigger is unresolved. The candidate 1, 7, 8 fails and all three single deletions are unresolved, so it is 1-minimal. Yet 2, 3 is a smaller failing input. Exhaustive finite enumeration is the independent fixture oracle, distinct from the learner reducer. Check every remaining single deletion and retain the actual replay classification. The reduced input localizes a trigger; inspect the first invalid code transition separately to explain the repair.

### T44.04 — Stepping, scopes and call stacks

The faulty condition used>capacity admits a fifth record at capacity 4; the counter reaches 5 without requiring an invalid memory access. `break try_acquire if *used == cap` can stop before this transition when symbols permit it. Use step to enter, next to stay at the current source level, finish to return and stepi/nexti for machine instructions. State which transition each command observes; source stepping is not an instruction-by-instruction history.

Frames and scopes select different objects. In the supplied synthetic two-frame example, probe's status 7 differs from caller's status 2. Use bt full, frame 0 and frame 1, then inspect the appropriate name/argument. A selected frame's locals may be incomplete in a machine prologue or absent after optimization. Save the command transcript and exact image/symbol identities; an unavailable value is not evidence that its source variable was zero. ### T44.05 — Conditional breakpoints and watchpoints

Choose a stopping mechanism from a hypothesis. A pure breakpoint condition used==capacity tests the admission boundary without calling code that changes inferior state. A watch on a live, initialized object tests a particular value change. Avoid dereferencing a guessed address or an expired local. Hardware watches typically stop at the responsible instruction, while software watches can stop at the next statement and are much slower. GDB's current manual states that software watches observe only the current thread; they do not establish another thread's writes.

The fixture requests an eight-byte watch on a four-byte-width target and three watches with only two slots. Both exceed its declared geometry; those numbers are a model, not F439 capabilities. Actual hardware availability and insertion/resume errors must be collected. Narrow the watched valid object, use a pure breakpoint, or add a bounded replay log when unsupported. This changes the claim's granularity and perturbation. A watchpoint shows a change, which may occur after the first invalid state; compare it with the contract transition and retain the earliest corroborated violation. Document object lifetime, scope expiry, thread focus, width and slot limits.

### T44.08 — I/O, errno and descriptor failure histories

A stream cursor advances by each positive byte count, not by the requested count or the last count alone. For seven bytes and results 2, EINTR, 2, EAGAIN, 3 the retained offsets are 2, 2, 4, 4, 7. EINTR before progress and EAGAIN/EWOULDBLOCK leave the cursor unchanged; a successful short result already accounts for progress. A positive-count stream read 0 means EOF, while a zero write requires the declared zero-progress policy and a finite bound. Reuse T24's cursors and event state rather than write another event loop. Reject impossible adapter counts before arithmetic.

Capture errno immediately after the operation indicates failure, before logging can overwrite it. ENOSPC followed by logging EIO still has original cause ENOSPC. Pthread functions return direct statuses, so that layer does not use this errno rule. EPIPE with default SIGPIPE may terminate before the return is observed; an explicitly handled/ignored signal disposition makes a different experiment. Positive write means local acceptance, not durable storage or peer consumption. On Linux, close releases the descriptor early, so retry after an error can close a reused number/generation. The inspected POSIX.1-2024 EINTR rule differs; label this exercise Linux. Use an injected/capped EMFILE ledger first; any actual exhaustion test is limited to the isolated learner process, at most eight owned records, with cleanup and no system-wide ENFILE campaign.

Apply in [PR-T44-06](../projects/PR-T44-06.md). Evidence must separately address these objective checks:

### T44.09 — Concurrency, deadlock and lost events

Reproduce a schedule before drawing a timing conclusion. If A holds lock L and waits for B's lock R while B holds lock R and waits for A's lock L, the finite wait-for graph has a cycle. Whole-thread backtraces can corroborate a stopped instance; the graph and one run are not every future schedule. A non-atomic write and read to the same object on different threads, without a happens-before edge, are an unordered conflict in the fixture. Its repaired ownership/mutex argument must supply the edge; volatile and longer sleeps do not supply it. A data race has no promised final value.

The lost-wakeup fixture has consumer check false, producer set true/signal, consumer waits. Fixing only the sleep length leaves that window. Reuse T25's predicate-under-the-same-mutex protocol: the wait releases atomically, the producer changes state while holding the mutex, and the consumer rechecks after reacquisition and every wakeup. Save forced schedules, thread identities, direct API statuses and a written ordering/lifetime argument. Supported detector runs and stress add exercised evidence. Halting or logging can hide a race; a detector's silence and one deterministic history do not close all schedules or establish fairness.

### T44.10 — Bare-metal startup, faults and asynchronous state

Reuse the selected F439 startup/image and basic exception decoder. The fixture reset word 0x08000101 denotes Thumb entry 0x08000100. IRQ 3 corresponds to exception 19 and vector 0x0800004C. EXC_RETURN 0xFFFFFFFD selects the scoped basic PSP/Thread return; with aligned pre-PSP 0x20001000 and no padding, eight words start 0x20000FE0. Optional extended FP frames, padding and nested-handler details need their own supported interpretation rather than this simplified model.

CFSR 0x8200 indicates precise BusFault plus BFAR valid; HFSR 0x40000000 records forced escalation. The imprecise 0x400 case has no valid BFAR, so the stale address is not usable evidence and stacked PC is not promised to identify the responsible access. Compare bad startup, peripheral clock/pin sequencing and invalid ownership as competing hypotheses. Do not inspect arbitrary side-effecting MMIO in the debugger. The policy model's configure-before-enable violates its stage invariant; actual peripheral effects require device evidence/measurement. DMA cancellation request leaves ownership with DMA until stop acknowledgment; the third CPU write is invalid even if the core is halted. The selected F439 SRAM/DMA path has no core data-cache maintenance requirement. Static arithmetic, emulator observations and physical fault/electrical observations remain separately labelled.

### T44.12 — Causal repair, regression and delayed blind transfer

A causal repair prevents the first invalid transition. A symptom patch may only hide its final effect. At used 4/capacity 4, reject-before-commit keeps state valid and reports full; clamp-after-commit temporarily reaches 5 before restoring 4. The identical final count does not make the histories equivalent. Test the minimized trigger, normal/boundary/invalid neighbors, failure cleanup and matched debug/release/instrumented images. A fix whose check only exists in an assertion fails the release contract. Save raw observations and remaining scope limits instead of matching diagnostic wording.

Progress through guided investigation, symptom-only investigation, then delayed transfer. The supplied public fixture/oracle is visible, so it is guided practice, not a blind assessment. A peer/reviewer supplies a genuinely withheld new variant, or a solo learner commits to an unopened seeded variant and reveals its oracle only after submitting the predictions, first-invalid-state evidence and repair. Revisit after at least seven days. Self-authored faults retain limited independence even when delayed; state this and use an independent reviewer when possible. Remediate the mistaken inference or invariant, then retry a different withheld variant rather than rereading every module.

Model outcomes are not runtime observations.

## Mastery gate and feedback

For every a/b/c objective, supply its explanation, evidence and scope. A complete dossier includes expected contract; pre-run competing predictions; source/image/configuration/environment identities; finite replay/actual observation; earliest invalid transition; discriminating hypothesis test; minimized tri-state trigger; invariant repair/limits; regression matrix and changed variant. The novice gate requires one warning/validation investigation and one counter / watch investigation. The later gate requires a systems/firmware dossier with its selected preludes, a tool-disagreement explanation and a causal-repair counterexample. Missing runtime capability leaves that claim open instead of passing a different property silently.

Use guided→symptom-only→delayed assessment. Visible public fixtures/oracles are guided, not blind. A reviewer/peer withholds a new variant, or a solo learner commits to an unopened seeded variant and reveals its oracle only after the submitted dossier. Separate this from self-authored fault practice, whose independence is limited. Feedback names the faulty inference, state transition or contract; the retry uses another variant.

## Consolidation and transfer

After at least seven days, diagnose a withheld new boundary, cleanup, schedule or stale-generation variant without reopening the old answer. Predict which image/input/tool/target evidence must be recollected. Retain rejected hypotheses and an example symptom patch that final-state checks would miss. Summarize the actual remaining claims rather than treating one successful transfer as every-case correctness.

## Environment and limits

GDB's inspected 19.0.50.20261009-git manual is a current development snapshot. Installed compiler/debugger, target watch resources, permissions, core generation and tool platforms must be recorded. Watchpoints can expire or miss other threads; optimization can erase variables; logs/stops/instrumentation perturb timing. Dynamic tools observe supported executed paths, static tools require context and may alarm conservatively, and cores omit history/memory. Undefined behavior and data races have no prescribed symptom. Linux close/EINTR policy is not a portable generic POSIX rule. The F439/basic-frame/static model excludes unsupported FP/padding/board effects; the selected F439 SRAM/DMA path has no core data-cache maintenance requirement. No fixture or emulator certifies physical timing, peripheral effects or electrical behavior.
