## Purpose and outcomes

Use Linux/POSIX interfaces as resource/lifetime protocols. Own descriptors and mappings, handle partial operations and separate visible state from durability and implementation-specific behavior. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce.

## Entry check and remediation

Track two handles sharing one abstract offset and explain a short byte transfer. Revisit T18 ownership/error contracts and T07 environment setup if either result is treated as a simple all-or-nothing call. Use {ref}`guide-entry` for diagnostic evidence and {ref}`guide-roadmap` for route choices. Domain numbers are coverage IDs, not an instruction to study them numerically.

## Component progression

**A process and descriptor ownership ledger.** Trace creation, inheritance, sharing, close, mapping and synchronization at actual system-call boundaries. Keep returned bytes, file offsets and persistence claims distinct.

Before implementation, predict this discriminating case: **An inherited write descriptor keeping a pipe alive after the apparent producer exits.** Carry its evidence into the projects below. ## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T23.01 — Process model

A process combines identity, an address space and credentials; threads share some of that state while keeping their own execution state. Arguments, environment and limits are inputs, not universal constants.

Investigate: Capture a child process context and label which facts are POSIX contracts and which are Linux observations. A common mistake is: A process and a thread are interchangeable isolation units. Evidence: A context manifest explains working directory, environment, limits and declared interfaces. Develop that evidence in [PR-T23-01](../projects/PR-T23-01.md).

### T23.02 — Process lifecycle

fork duplicates an execution context while exec replaces its program image. A failed exec returns in the child and must report failure without accidentally continuing the parent workflow. Threaded fork adds restricted child-side obligations.

Investigate: Implement a spawn/wait utility with a dedicated child-error channel and explicit inherited descriptors. A common mistake is: Successful fork implies successful execution of the requested program. Evidence: Exit and error records distinguish launch failure, child result and wait failure. Develop that evidence in [PR-T23-01](../projects/PR-T23-01.md).

### T23.03 — Descriptors and open-file descriptions

A descriptor is one table entry; an open-file description contains shared offset/status state. Duplication can share that state while ownership of the descriptor numbers remains separate.

Investigate: Trace dup and fork inheritance, set close-on-exec deliberately and audit closure paths. A common mistake is: Duplicated descriptors have independent file offsets. Evidence: The synthetic ledger and observed positioned/sequential reads distinguish shared offset from handle lifetime. Develop that evidence in [PR-T23-01](../projects/PR-T23-01.md).

### T23.04 — Robust byte I/O

I/O adapters maintain progress and choose retry policy for the specific operation. EOF differs from would-block; a failed operation is not automatically safe to repeat unchanged.

Investigate: Implement robust byte-copy using scripted short transfers, interruptions and terminal failures. A common mistake is: read or write either handles the whole buffer or transfers nothing. Evidence: The output byte sequence and progress ledger contain neither omissions nor duplicate writes. Develop that evidence in [PR-T23-02](../projects/PR-T23-02.md).

### T23.05 — Paths and filesystem objects

A pathname is a lookup request through directory entries, not an object identity. An open handle can survive a rename/unlink, and a check-then-open sequence can race with namespace changes.

Investigate: Use a directory-relative operation and compare a renamed open file with a fresh path lookup. A common mistake is: Checking a path once authorizes all later uses of that name. Evidence: An identity/lookup trace states symlink policy and avoids unsupported race-free claims. Develop that evidence in [PR-T23-02](../projects/PR-T23-02.md).

### T23.06 — Metadata and permissions

Creation permissions combine requested mode with a mask and the actual authorization environment. A successful lookup says nothing by itself about permission for the next operation.

Investigate: Predict mode bits for a synthetic umask case and compare creation/metadata behavior in a temporary directory. A common mistake is: Requested mode is always the final mode. Evidence: Expected bit arithmetic and actual metadata are separated from ownership/ACL/environment effects. Develop that evidence in [PR-T23-02](../projects/PR-T23-02.md).

### T23.07 — File positioning and representation

Sequential operations update shared offset state; positioned I/O supplies an explicit offset without using that cursor. Sparse holes affect logical size without storing every byte physically.

Investigate: Build a bounded sparse-file experiment and validate offset conversions before calling interfaces. A common mistake is: Logical file size equals allocated disk space. Evidence: Byte contents, offset state and reported storage quantities are recorded independently. Develop that evidence in [PR-T23-02](../projects/PR-T23-02.md).

### T23.08 — Virtual memory

A virtual mapping reserves address ranges and protection, while residency depends on page faults and backing. Copy-on-write separates modifications after fork without requiring immediate eager copies.

Investigate: Compare untouched/touched anonymous pages and one protection change in a disposable child. A common mistake is: mmap success proves every page is physically resident. Evidence: The report labels virtual extent, fault observations and residency measurements by their limits. Develop that evidence in [PR-T23-03](../projects/PR-T23-03.md).

### T23.09 — Memory-mapped files

A mapping borrows a bounded file extent whose backing can change. Truncation can make a formerly mapped access fault; cleanup owns both mapping length and descriptor policy.

Investigate: Implement a bounded mapped-reader contract and exercise truncation only inside a disposable child. A common mistake is: Mapping a file permanently freezes its size and contents. Evidence: Failure classification, mapping bounds and cleanup ownership are explicit before any access. Develop that evidence in [PR-T23-03](../projects/PR-T23-03.md).

### T23.10 — Shared memory

Shared bytes require shared representation and a synchronization contract. A process-local pointer cannot be interpreted at another mapping address; offsets plus checked bounds make layout relocatable.

Investigate: Design a versioned shared record with offsets and analyze initialization/participant failure states. A common mistake is: Shared mapping alone makes concurrent metadata updates coherent. Evidence: Two differently based views decode identical logical contents and an explicit synchronization protocol owns publication. Develop that evidence in [PR-T23-03](../projects/PR-T23-03.md).

### T23.11 — Pipes and terminal I/O

Pipeline ends must close unused descriptors or EOF can never arrive. Backpressure is ordinary flow control; terminal modes add line processing that should be restored after use.

Investigate: Build a two-stage pipeline and a pseudoterminal experiment with an explicit restoration path. A common mistake is: An idle reader always gets EOF when the visible writer exits. Evidence: Descriptor closure diagrams explain blocking, broken-pipe behavior and terminal-state restoration. Develop that evidence in [PR-T23-04](../projects/PR-T23-04.md).

### T23.12 — Persistence and crash consistency

Buffered success, interprocess visibility and durable storage are distinct claims. A replacement protocol needs an ordered sequence and filesystem-specific durability assumptions.

Worked update boundary: after writing and synchronizing a temporary file, renaming it changes the visible namespace. Synchronizing the containing directory is a separate step for the directory entry. Termination between those operations creates different evidence obligations; a test that observes the new content after ordinary process termination is not a power-loss experiment. A stable separate lockfile avoids changing the locked inode during replacement.

Investigate: Specify a temporary-file/write/synchronize/rename protocol and inject interruption at each declared step. A common mistake is: A successful write or rename universally proves durable data. Evidence: A crash-state matrix states old/new/partial possibilities and names unverified filesystem guarantees. Develop that evidence in [PR-T23-05](../projects/PR-T23-05.md).

### T23.13 — Time, resources, and scheduling interfaces

Elapsed deadlines need a clock whose adjustments match the intended contract. Affinity and scheduling requests can fail for permissions or limits; a requested policy is not a response-time guarantee.

Investigate: Compare monotonic deadline accounting with a synthetic wall-clock jump and inspect actual resource limits. A common mistake is: Setting a priority establishes a hard scheduling bound. Evidence: Measurements name clock domain, failures and observed delay without claiming scheduler guarantees. Develop that evidence in [PR-T23-06](../projects/PR-T23-06.md).

### T23.14 — POSIX/Linux boundary

Feature-test macros expose declarations at compile time; runtime capabilities and permissions still need checks. Linux-specific interfaces require a fallback or an explicit unsupported result.

Investigate: Tag the utility’s interface inventory and simulate a missing optional capability. A common mistake is: A visible declaration guarantees runtime support. Evidence: A portability table links each interface to its standard/platform scope and tested failure path. Develop that evidence in [PR-T23-01](../projects/PR-T23-01.md).
