## Purpose and outcomes

Build a bounded command service and defend its trust, memory, process, resource and artifact boundaries. Security claims must name a deployment/threat model and actual enforcement evidence.

## Entry check and remediation

Review caller-storage bounds/lifetimes, checked integer arithmetic, Linux descriptor/process ownership and T32 failure/instrumentation work. Repair only the failed leaf before the dependent project. Identify a private nonprivileged sandbox and synthetic tokens; no personal files, production keys or elevated service is required.

Use {ref}`guide-entry` for the diagnostic policy and {ref}`guide-roadmap` for route order. Only the stated prelude leaves must precede a dependent project.

## Component progression

**A bounded authority and resource boundary.** Validate framing and sizes before granting effects. Model who may request operations, which resources they consume and how overload or corruption is contained.

Before implementation, predict this discriminating case: **A syntactically valid request causing unbounded retention or accessing a descriptor beyond its authority.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T35.01 — Threat and failure models

A threat model names assets, controlled inputs, trust boundaries and permitted effects; a failure model also includes accidental corruption and unavailable services. For the teaching command service, untrusted bytes may request only bounded operations and authorization is separate from syntax. Write abuse and accident cases before coding. The misconception is that every valid packet is authorized. Evidence identifies the consequence prevented, residual risks and the exact isolated test environment.

Apply this mechanism in [PR-T35-01](../projects/PR-T35-01.md).

### T35.02 — Memory safety

Length arithmetic can turn a representation defect into an invalid access. Track capacity, used extent, lifetime and ownership together; validate count before multiplication and bounds before publishing a view. Implement a bounded caller-storage command representation rather than carrying unrelated pointer/length guesses. A return-code check cannot repair an already performed out-of-bounds write. Evidence uses sentinels, rejected extreme counts and a lifetime/ownership ledger.

Apply this mechanism in [PR-T35-01](../projects/PR-T35-01.md).

### T35.03 — Input validation

Validation checks syntax, cross-field consistency and policy in that order before effects. The fixture's packet has an opcode, count and fixed-width elements; trailing bytes, mismatched count and unauthorized operation are rejected without modifying caller output. Set maximum work and nesting even for syntactically valid inputs. Evidence includes malformed and valid-but-denied cases. Sanitizing a string without validating its structured meaning is not this contract.

Apply this mechanism in [PR-T35-01](../projects/PR-T35-01.md).

### T35.04 — Integer and format vulnerabilities

Checked size calculations must use a bound before count*width can overflow; signed/unsigned conversions and narrowing need separate range checks. A format string is trusted program data, not an input packet. Implement the fixture's capped count parser with exact decimal syntax and fixed formatting specification. Evidence includes negative, leading-sign, oversized and boundary inputs plus correctly typed output. Accepting a compiler warning-free call does not establish semantic authorization.

Apply this mechanism in [PR-T35-01](../projects/PR-T35-01.md).

### T35.05 — Filesystem and process boundaries

Filesystem names can change between check and use; descriptors name already-open objects. In the controlled Linux worker, use exclusive creation, atomic close-on-exec semantics and explicit argument vectors, then inspect which descriptors the child inherits. Pass a read-only log descriptor, read its bytes and attempt a write: record the actual EBADF failure and unchanged bytes. Keep reopening the path as a separate residual-authority test. Evidence also includes a competing-name case and partial-failure cleanup.

Apply this mechanism in [PR-T35-02](../projects/PR-T35-02.md).

### T35.06 — Resource-exhaustion resistance

Resistance to exhaustion requires bounded admission, queues, allocation/work, retries and nesting. A syntactically valid request can still be too expensive. Implement per-request and total quotas with a fail-before-effect policy and a finite retry/recovery budget. Evidence includes a burst, pathological valid input and recovery under continued overload. Retrying faster cannot create capacity; state which requests are dropped, coalesced or rejected and how callers learn that outcome.

Apply this mechanism in [PR-T35-03](../projects/PR-T35-03.md).

### T35.07 — Binary hardening

Hardening changes generated code and runtime expectations. Audit ASLR policy and repeated process mappings, ELF PIE type, GNU_RELRO plus eager binding, stack-protector code/runtime symbol, fortification at supported optimization and non-executable stack/load segments. Compare a plain and a hardened hosted build; inspect actual bytes/headers rather than the command alone. Evidence also lists libc/compiler-helper dependencies and overhead. These Linux facilities are not portable replacements for bare-metal bounds or ownership.

Apply this mechanism in [PR-T35-04](../projects/PR-T35-04.md).

### T35.08 — Privilege and isolation

Privilege and isolation require an OS or hardware mechanism with a stated scope. The nonprivileged worker uses an inherited read-only log descriptor: the OS enforces that writes through this descriptor fail, while application policy denies write-config before effects. A private directory and CLOEXEC control names and inheritance but do not remove ordinary user filesystem or network authority. Compare the child’s separate address space and this narrow descriptor restriction with a logical module and an MPU design at awareness depth. Evidence includes the denied write and a residual-authority table; do not claim a complete sandbox.

Apply this mechanism in [PR-T35-02](../projects/PR-T35-02.md).

### T35.09 — Sensitive data and timing

Secrets can persist in copies, logs and compiler-eliminated clearing. Use synthetic test tokens only, enumerate copies/lifetime and inspect generated code for a deliberate clearing policy supported by the selected environment. Compare early-exit and fixed-work toy comparisons, observing input-dependent work before any physical timing claim. Fixed source-loop length is not proof of constant-time machine execution. Evidence states compiler/ISA and excludes production cryptography or a claim that Bernstein's old host mechanism exists on F439.

Apply this mechanism in [PR-T35-05](../projects/PR-T35-05.md).

### T35.10 — Concurrency and resilience

Validation can become stale if another context changes the validated state. Use an immutable accepted request/ownership transfer and finite fail-safe state transitions; inject an update between validation and effect and require rejection or coherent generation checking. Recovery must preserve invariants under repeated failure, not loop forever. Evidence includes adversarial logical schedules, one terminal outcome per request and a bounded recovery trace. A lock protecting a flag alone may leave the actual invariant exposed.

Apply this mechanism in [PR-T35-03](../projects/PR-T35-03.md).

### T35.11 — Supply chain and artifact integrity

Artifact identity is a hash comparison, while authenticity requires a trusted signing/verification chain and rollback policy. Compute fixture hashes and reject incompatible versions or uncommitted update slots, then record the source/tool/dependency release identities for your real image. An attacker able to replace both bytes and checksum defeats checksum-only authenticity. Evidence distinguishes consistency, signer trust, freshness and reproducibility; no homemade signature algorithm is part of this project.

Apply this mechanism in [PR-T35-06](../projects/PR-T35-06.md).

### T35.12 — Security review and limits

A security review needs a concrete checklist derived from the component's actual boundaries: lengths, arithmetic, lifetimes, effects, quotas, privileges, sensitive data and artifact trust. Map each property to a regression, static/proof argument or explicit gap. Review a deliberately flawed design ledger and revise one implementation accordingly. Evidence retains residual risks and unsupported attacker/fault assumptions. A passing fuzz campaign and a collection of hardening flags do not establish complete security.

Apply this mechanism in [PR-T35-06](../projects/PR-T35-06.md).

**Shared scope limit — GCC program instrumentation options, selected verification and hardening contracts:** Selected options only, not every instrumentation feature. Flag availability and effective dependencies vary with installed compiler/target. GNU/Linux hardening aggregate is not a bare-metal recipe; instrumentation changes resource/timing behavior.

**Shared scope limit — GNU ld option contracts for stack execution, eager binding and RELRO:** Moving manual snapshot, not an installed-linker identity. A requested property is not proof of final image/runtime enforcement; no linker execution.

**Shared scope limit — Linux proc_sys_kernel(5), ASLR policy subsection:** Linux-specific, architectural/kernel support and actual configuration still require observation. Read-only policy audit is assigned; no system-wide ASLR modification.

**Shared scope limit — Cache-timing attacks on AES:** Historical Pentium III/OpenSSL experiment; it neither proves a Cortex-M4 leakage mechanism nor supplies production cryptography. The paper itself labels this a preliminary version. Use only a controlled educational threat model.

**Shared scope limit — CBMC training: What is loop unwinding?:** Training examples do not select a release or prove a hardware environment. Pin tool version, check defaults and report assumptions, reachability and every unwinding result. The old CPROVER manual routes returned navigation only.

## Mastery gate and feedback

Reject malformed/unauthorized/overbudget requests before effects, audit actual hardening and descriptor/privilege boundaries, and preserve finite recovery/integrity policies. Review the service against a concrete checklist with residual risks. Flags, fuzz volume and checksum agreement alone do not establish security.

For every linked objective, retain a separately labeled explanation, implementation/analysis artifact and check. Use {ref}`guide-assessment` for the rubric; one passing fixture does not establish all three objectives of a topic.

## Consolidation and transfer

Change one trust boundary, count limit or update rollback policy and predict which prior evidence becomes insufficient. Replay a race/failure regression and re-audit a compiler-changed image, keeping toy timing experiments separate from production cryptography.
