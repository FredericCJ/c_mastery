# T63: Memory safety offense and defense in original teaching programs

## Purpose and outcomes

Analyze attacker-controlled lengths, identities and operation codes against small original targets. Demonstrate bounded integrity or confidentiality violations, distinguish them from undefined behavior or arbitrary code execution, repair their mechanisms and test residual limits.

## Entry check and remediation

Explain array bounds, object lifetime, integer conversion and ownership. Construct a harmless sentinel overwrite entirely inside an allocated teaching arena and explain why that model differs from an actual C out-of-bounds access.

## Study sequence and teaching

### T63.01 — Spatial bounds and a harmless overwrite witness

An attacker can exploit a mismatch between physical allocation and logical object extent even when every C access lies inside one large array. This model makes the security property observable without requiring abnormal process termination or an evaluation with undefined behavior.

Derive subtraction-form bounds without overflow and distinguish logical isolation from ISO C allocated-object bounds. State why a sentinel violation proves integrity failure only within the teaching model.

Misconception and counterexample: Repair capacity confusion and post-write checks. A canary that detects corruption afterward does not restore overwritten data or authorize the write.

Investigation: Implement md_write(arena,logical_capacity,offset,input,n) for an original32-byte arena. Reject capacity>31, offset>capacity or n>capacity-offset before any write; write only the admitted span. Byte31 is a sentinel outside the logical object. Compare with the supplied faulty teaching path that validates only the32-byte physical extent; attacker controls offset/n/data and harmless success is sentinel change.

Evidence: Split the logical object into a real heap allocation and run the isolated faulty path under ASan; compare deterministic model evidence with observed effects of undefined behavior and the effects of mitigations; ISO C guarantees no particular result after undefined behavior.

### T63.02 — Allocation arithmetic and truncation

An attacker-controlled element count can produce a small allocation followed by a larger copy when multiplication or narrowing changes the extent. The defect is a disagreement between two representations of the same request.

Derive the allocation and subsequent access extents in the same value domain. Identify every narrowing conversion and the branch that incorrectly authorizes it.

Misconception and counterexample: The original local mutant requests8193 elements of8 bytes, validates a truncated8-byte allocation and would later copy65544 bytes. Demonstrate the admitted size mismatch without performing the dangerous copy.

Investigation: Implement md_extent(count,stride,limit,out) using uint32_t inputs and uint64_t arithmetic; accept only product<=limit and product<=UINT32_MAX, publish the product on success, otherwise preserve out. Compare against a teaching allocator that truncates product to16 bits before checking. Do not actually allocate attacker-sized memory.

Evidence: Change data model and add alignment/header overhead; rederive all multiplication/addition/conversion bounds and explain whether the same attacker input still reaches the defect.

### T63.03 — Temporal identity and stale access

A recycled storage address can hold a different object. Comparing addresses therefore cannot establish identity across a release/reuse transition. Generation counters help only when wrap and owner identity are part of the contract.

Prove a stale token cannot authorize current-incarnation access, state the trusted token origin and require retirement before generation wrap. Compare with an actual heap use-after-free sanitizer target without treating allocator reuse as guaranteed.

Misconception and counterexample: The mutant ignores generation and reveals a new occupant’s synthetic byte through an old token. This demonstrates a confidentiality violation in the target, not a read primitive against another process.

Investigation: Implement md_read(arena,claimed_generation,index,out): require live==1, matching generation and index<16 before publishing a byte. Failed reads leave out unchanged. The original arena remains allocated, so the stale-handle witness is defined C behavior; attacker retains an old token across reuse and attempts to read a new synthetic occupant.

Evidence: Add asynchronous completion retaining a token, then release/reuse the slot before completion. Design cancellation and retirement so old callbacks cannot expose the new occupant.

### T63.04 — Owned arena views and authorization

Memory bounds and access authority are separate properties. A valid pointer or generation does not prove that the caller is permitted to read the object. C structs do not make capability tokens unforgeable.

Specify representation, operations, ownership and failure semantics of a checked view. Identify exactly what runtime checks enforce and what trusted-caller discipline or external verification must guarantee.

Misconception and counterexample: The mutant validates generation and bounds but ignores principal ownership. The attacker can read another synthetic principal’s object without any memory error or sanitizer report.

Investigation: Implement md_authorize(arena,principal,generation,begin,length): require live1, exact owner and generation, begin<=16 and length<=16-begin; return admission only, without exposing a pointer on failure. principal is supplied by a trusted harness channel, not copied from request bytes. Define the trusted boundary and compare with a forged-request owner field.

Evidence: Compare the C view with a language-enforced borrow or capability mechanism; provide a concrete C counterexample showing forged structs or escaped pointers defeat an overstated equivalence claim.

### T63.05 — Bounded control-flow corruption analysis

A changed function pointer or operation index can redirect behavior, but the achievable effect depends on target layout, writable state, reachable functions and mitigations. A local dispatcher permits a harmless action witness without invoking external commands.

State attacker control, target-local effect and limits. Distinguish data-only unauthorized dispatch from demonstrated arbitrary code execution; analyze control-flow integrity separately from operation authorization.

Misconception and counterexample: A valid indirect-call target can still perform an unauthorized operation. Bounds checks and a control-flow whitelist do not replace the grant check.

Investigation: Implement md_dispatch(op,grant,sentinel) with op0 read-only no-op and op1 set sentinel77, allowed only when trusted grant==1. Reject unknown op and nonboolean grant before mutation. Analyze the supplied intentionally flawed dispatcher that checks only op range; attacker-controlled op1 without grant must change only the synthetic sentinel in the faulty build.

Evidence: Add a table of three trusted callbacks and a corrupted index inside the original program; compare range checks, read-only dispatch tables and compiler CFI while recording only observed target effects.

### T63.06 — Format-string authority and byte-preserving logging

A format interpreter treats certain bytes as instructions rather than data. Passing untrusted text as the format transfers authority over conversions. A bounded destination does not by itself remove this semantic confusion.

Identify which argument is interpreted as a format and prove the repaired path treats attacker bytes as data. Discuss embedded NUL, truncation policy and logging integrity separately.

Misconception and counterexample: Blindly replacing percent with a question mark suppresses the witness but corrupts the required logged bytes. The real repair separates interpreter control from untrusted data.

Investigation: Implement md_log_copy(input,n,output,capacity) copying exact bytes and appending NUL, requiring n<capacity and no overlap; failure leaves output unchanged. Percent bytes have no interpretation. Compare an original isolated printf(user_format) target using the fixed synthetic string%n and a supplied local integer pointer with printf("%s",user_text); the harmless witness is only that integer changing.

Evidence: Add structured binary logging with explicit length and escaping at display time; test embedded NUL and terminal-control bytes without confusing storage fidelity with safe rendering.

### T63.07 — Exactly-once release and error cleanup

Double release is often created by composing individually plausible cleanup paths. A successful transfer of ownership must change which path may destroy the resource; an error label cannot infer ownership from a nonnull address alone.

Prove ownership conservation and exactly-one destructor call under every failure prefix. Explain why nulling one alias cannot revoke another copied raw pointer.

Misconception and counterexample: The faulty cleanup path releases twice after ownership moved to a callback. Demonstrate the duplicate counter first, then separately observe an actual original double-free target under ASan.

Investigation: Implement md_release(MDOwner) requiring owned exactly1, setting owned0 and incrementing releases once. Repeat release returns0 unchanged. Reject a release counter atUINT_MAX before state change. Build an allocation/failure schedule with caller, queue and callback owners and record every transfer.

Evidence: Introduce reentrant destruction and partial object construction; define callback restrictions or use detached cleanup state so recursive calls cannot double release.

### T63.08 — Observable work, timing and mitigation limits

Early-exit comparisons reveal the first mismatch position through work performed; a full scan removes that particular algorithmic difference. It does not automatically prove constant execution time on every compiler and microarchitecture.

Separate functional equality, source-level work count, emitted branches and measured timing. State memory-validity, compiler and CPU assumptions and residual cache/power/speculation channels.

Misconception and counterexample: The early-exit mutant reports only one step for a first-byte mismatch, leaking a prefix relation. ASan can remain clean because the defect is confidentiality, not invalid memory access.

Investigation: Implement md_equal(a,b,n,steps) scanning all n bytes, accumulating bitwise exclusive-or difference, reporting steps=n and returning equality. Empty spans compare equal without dereference. Compare with an intentionally early-exit mutant using synthetic secrets only. Inspect optimized code and measure distributions without treating equal loop counts as a universal constant-time guarantee.

Evidence: Change optimization, vectorization and unequal-length policy; derive what remains observable and compare hardened library behavior only as an external benchmark, not a replacement for the first-principles implementation.
