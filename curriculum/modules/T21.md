# T21: Error handling, resource management, and observability

## Purpose and outcomes

Make failure behavior part of correctness. Errors carry causes, acquisition can stop partway, mutation has a guarantee, cancellation has an in-flight owner, and diagnostics consume resources. The projects connect resource rollback to bounded observability and distinguish crash evidence from validated recovery.

## Entry check and remediation

Use T18 output/lifetime contracts and T20 effect boundaries. Before coding an error path, name acquired resources and externally visible state. If cleanup is duplicated in several branches, draw the acquisition stack and verify exactly-once release before choosing a control-flow style.

## Study sequence and teaching

### T21.01 — Error taxonomy

Invalid external input, internal contract violation, resource exhaustion and hardware fault need different policies. Recoverable, retryable, terminal and degraded describe application outcomes, not merely numeric codes. Preserve the original operation/resource context so diagnosis can distinguish symptom from cause.

Investigation: Define an error table for parser, allocator and transport failures with recovery class and context.

Misconception to resolve: Every nonzero result should not trigger the same retry or panic policy.

Observable evidence: Error/class/action matrix and tests for at least one outcome in each category. Evidence is developed in {ref}`PR-T21-01`.

### T21.02 — Propagation and translation

Translation maps unstable backend errors into a stable public taxonomy while retaining causal context. A component can expose a portable timeout status and store a backend detail for diagnostics. Success must not be ambiguous with partial failure, and overwriting the first cause can destroy useful evidence.

Investigation: Implement a bounded error record and backend-to-public mapping with an explicit unknown-error policy.

Misconception to resolve: Abstraction does not require discarding all cause information.

Observable evidence: Mapping tests, stable public codes and original-cause preservation across propagation. Evidence is developed in {ref}`PR-T21-01`.

### T21.03 — Partial initialization

Partial initialization acquires a prefix of resources. Track completed stages and roll back in reverse dependency order. Repeated init/cleanup requires a state policy; a failed object may permit cleanup without permitting active operations.

Investigation: Inject failure after each of three acquisitions and check remaining ownership after rollback.

Misconception to resolve: A final “initialized” flag is insufficient to describe every intermediate owner.

Observable evidence: Acquisition/rollback traces and repeated-init/cleanup tests. Evidence is developed in {ref}`PR-T21-01`.

### T21.04 — Cleanup control flow

Early returns, nested cleanup and narrowly scoped cleanup labels are tools for proving release exactly once. Choose the structure that makes resource state visible and minimizes duplicated obligations. A forward jump to cleanup can be clearer than deeply nested success paths; it is not arbitrary control flow.

Investigation: Implement the same small acquisition sequence with two cleanup structures and compare reviewability.

Misconception to resolve: A blanket goto ban or blanket goto preference does not establish correctness.

Observable evidence: Exactly-once release proof, failure-point tests and a justified style choice. Evidence is developed in {ref}`PR-T21-01`.

### T21.05 — Transactional mutation

The strong guarantee leaves observable state unchanged on failure; the basic guarantee keeps invariants while allowing changes. Stage allocations/copies before commit where strong behavior is required. Retry is idempotent only if repeated requests cannot duplicate externally visible effects.

Investigation: Implement a staged configuration update and compare strong/basic failure contracts.

Misconception to resolve: Returning an error does not imply rollback happened.

Observable evidence: Before/after snapshots, commit-point proof and repeated-request checks. Evidence is developed in {ref}`PR-T21-02`.

### T21.06 — Cancellation and timeouts

Timeout says a deadline expired; cancellation completion says the operation will no longer use retained resources. An in-flight callback can arrive after a timeout, so identify requests and define one completion owner. Context cannot be reclaimed merely because the caller stopped waiting.

Investigation: Model timeout, cancel request, late callback and cancel acknowledgment, rejecting stale/duplicate completion.

Misconception to resolve: Timeout and successful cancellation are not interchangeable.

Observable evidence: Ownership/timing traces, exactly-once completion and no stale-context access. Evidence is developed in {ref}`PR-T21-02`.

### T21.07 — Assertions and fault policy

Assertions check developer invariants under a fault policy; required validation must remain when assertions disappear. Decide whether a fault returns, panics, enters safe state or resets, with target-specific implications. Expressions inside removable checks must not carry required side effects.

Investigation: Build assertions on/off and inject an invalid input plus an internal invariant defect under distinct policies.

Misconception to resolve: An assert is not a durable external-input validator.

Observable evidence: Equivalent required validation, explicit fault behavior and disabled-side-effect audit. Evidence is developed in {ref}`PR-T21-03`.

### T21.08 — Logging and trace design

Logging uses storage, time and transport. Bounded records need severity, timestamp units, operation identity and an overflow/backpressure policy. Error reporting must not recursively allocate or fail through the same broken backend without a bounded fallback.

Investigation: Implement a fixed ring of event records with a stated drop policy and rate limit.

Misconception to resolve: More logs do not automatically improve diagnosis if they can destroy timing or recurse on failure.

Observable evidence: Exact overflow/rate traces, resource bounds and reporter-failure tests. Evidence is developed in {ref}`PR-T21-03`.

### T21.09 — Developer and integrator diagnostics

White-box developer instrumentation and stable integrator diagnostics serve different audiences. Give them independent switches and supported contracts. Disabled instrumentation that promises no evaluation/storage cost needs preprocessor/code/binary evidence; a runtime if may preserve argument evaluation.

Investigation: Build four switch combinations and inspect expression counts, symbols and record storage.

Misconception to resolve: A disabled sink does not necessarily mean disabled call arguments or static buffers.

Observable evidence: Independent toggle matrix, no-evaluation checks and stable black-box output contract. Evidence is developed in {ref}`PR-T21-03`.

### T21.10 — Crash evidence and recovery

Crash evidence needs minimal bounded context and a build identity that resolves against matching symbols. Persistence has its own atomicity/reset/lifetime assumptions. A captured symptom supports diagnosis; recovery requires restoring validated state and testing the resumed behavior under the fault model.

Investigation: Encode/decode a small checksummed fault record and test corrupt/stale-build rejection plus a separate recovery policy.

Misconception to resolve: A readable crash record is not proof that continuing execution is safe.

Observable evidence: Corruption/build-correlation tests and recovery evidence explicitly separated from collection. Evidence is developed in {ref}`PR-T21-04`.

## Mastery gate and feedback

Inject every acquisition failure, one mutation failure and a timeout/late-callback sequence. Prove release and completion exactly once. Demonstrate bounded diagnostics with instrumentation disabled and distinguish recorded fault context from actual recovered correctness.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

After a delay, add a resource and reduce diagnostic capacity. Re-derive rollback/overflow policies and show the original cause survives the new failure paths.
