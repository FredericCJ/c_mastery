## Purpose and outcomes

Make the build an inspectable dependency computation. Leave with reproducible commands, deliberate target/runtime selection, portable exported library boundaries and failure evidence that another repository can reproduce. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce.

## Entry check and remediation

Given two source files and one generated header, predict which stage fails for an undeclared identifier, an unresolved reference and a stale object. If those are conflated, revisit T02 translation and compile a single-file example before the first graph project. Use {ref}`guide-entry` for diagnostic evidence and {ref}`guide-roadmap` for route choices. Domain numbers are coverage IDs, not an instruction to study them numerically.

## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T07.01 — Build pipeline

A translation pipeline transforms a token stream into machine instructions and then resolves references between objects. The driver orchestrates those stages; an object file is not an executable merely because it contains code.

Investigate: Stop a two-file example at .i, .s and .o, then reconstruct the final link command. A common mistake is: Compilation success implies link success. Evidence: A diagram names the producer and consumer of each artifact, and the reconstructed binary agrees with the driver build. Develop that evidence in [PR-T07-01](../projects/PR-T07-01.md).
### T07.02 — Compiler driver and target selection

A target triple selects a toolchain family; CPU tuning, enabled instructions and calling convention are additional choices. The machine running the compiler need not be the machine running its output.

Investigate: Inventory driver include paths, sysroot, startup objects and target libraries; classify every discovered tool as host or target. A common mistake is: Changing -march alone creates a correct cross-toolchain. Evidence: A manifest explains each implicit input and rejects an incompatible object before execution. Develop that evidence in [PR-T07-01](../projects/PR-T07-01.md).
### T07.03 — Diagnostics policy

Diagnostics are part of the build contract: a warning depends on language edition, compiler version and what the compiler can establish. Suppression moves an obligation to review rather than repairing behavior.

Investigate: Create one positive, one expected-warning and one expected-failure translation unit; justify one narrow suppression. A common mistake is: Warning-free means defined behavior. Evidence: Versioned logs distinguish the expected diagnostic class from brittle exact wording. Develop that evidence in [PR-T07-01](../projects/PR-T07-01.md).
### T07.04 — Optimization and debug profiles

Debug information, optimization and instrumentation are independent settings. Inlining changes frames; instrumentation adds runtime support; size optimization need not minimize every function.

Investigate: Build debug, sanitizer, release and size configurations of the same defined program and compare symbols and disassembly. A common mistake is: A debug dependency audit also covers release or LTO. Evidence: A table separates stable semantic output from configuration-dependent code and runtime dependencies. Develop that evidence in [PR-T07-02](../projects/PR-T07-02.md).
### T07.05 — Make fundamentals

A Make rule is a dependency assertion. File prerequisites trigger rebuilding; order-only edges establish sequencing without making their timestamps a reason to rebuild. Phony names represent actions.

Investigate: Break a generated-header edge deliberately, then repair it with compiler-generated dependency files. A common mistake is: Listing a directory as an ordinary prerequisite expresses only creation order. Evidence: Touch and delete inputs in a controlled matrix and predict every rebuild before observing it. Develop that evidence in [PR-T07-02](../projects/PR-T07-02.md).
### T07.06 — CMake target model

A target has requirements for its own compilation and requirements for consumers. PUBLIC participates in both; PRIVATE affects the implementation; INTERFACE describes consumers. Exported paths must survive relocation.

Worked dependency transfer: a producer exports Tiny::tiny with install-relative include/tiny and its public compile definition. A consumer links that imported target in a different source root. If hiding the producer breaks configuration, inspect the exported paths before adding a consumer include flag: that flag can conceal a defective package.

Investigate: Package a two-library component, install it to a temporary prefix and consume it from a separate tree. A common mistake is: Global include directories are a substitute for interface requirements. Evidence: The consumer builds after moving the install prefix, without references to the original build directory. Develop that evidence in [PR-T07-03](../projects/PR-T07-03.md).
### T07.07 — Generated inputs and configuration

Generated inputs belong in the graph just like handwritten inputs. Configuration probes can compile target code without running it; cross-build checks must not accidentally execute target binaries on the host.

Investigate: Generate a header from a small schema and provide explicit configuration answers for a non-runnable target. A common mistake is: A file produced once during configuration cannot become stale. Evidence: Clean and incremental builds record generation order and do not invoke the target during host configuration. Develop that evidence in [PR-T07-02](../projects/PR-T07-02.md).
### T07.08 — Ninja and compilation databases

Ninja consumes an explicit graph and tracks compiler-discovered header edges. A compilation database records translation commands, not necessarily the full link or generation workflow.

Investigate: Replay one database command outside the front end, then inspect why a header change rebuilds only its dependents. A common mistake is: compile_commands.json is a complete reproduction recipe. Evidence: The replay uses the same directory, defines and include paths, and its object provenance is recorded. Develop that evidence in [PR-T07-03](../projects/PR-T07-03.md).
### T07.09 — Cross-toolchain configuration

A cross build has two search universes: utilities that run now and headers/libraries for the target. A sysroot does not by itself choose the correct multilib or floating-point convention.

Investigate: Write a toolchain manifest and classify compiler, generator, target archives and linker script separately. A common mistake is: Successful linking proves that all ABI choices agree. Evidence: Compile/link probes plus object attributes expose a deliberately mismatched library. Develop that evidence in [PR-T07-04](../projects/PR-T07-04.md).
### T07.10 — Dependency acquisition

A dependency pin identifies both a revision and the bytes actually obtained. Vendoring changes availability and review duties; system packages change the provenance boundary.

Investigate: Compare system, vendored and fetched acquisition of one tiny dependency; demonstrate an offline build. A common mistake is: A branch name is an integrity identifier. Evidence: A clean-room checklist names every external input and fails visibly when one is absent. Develop that evidence in [PR-T07-05](../projects/PR-T07-05.md).
### T07.11 — Testing and CI integration

Tests exercise configurations as well as functions. A negative-build test passes only when a prohibited construct fails for the intended reason; a target test needs an execution environment.

Investigate: Register semantic, expected-failure and target-only tests with explicit skip reasons. A common mistake is: A skipped on-target test is a successful hardware result. Evidence: CI artifacts retain the compiler identity, command, failure log and binary for a deliberately broken case. Develop that evidence in [PR-T07-05](../projects/PR-T07-05.md).
### T07.12 — Reproducible artifacts

Reproduction requires control over embedded paths, timestamps, ordering and generated IDs. A hash mismatch is a starting point for locating differences, not automatic evidence of semantic divergence.

Investigate: Build in two clean directories and classify every byte difference before introducing path/timestamp controls. A common mistake is: The same source revision necessarily produces the same binary. Evidence: A provenance record and a byte-difference report explain both eliminated and retained variability. Develop that evidence in [PR-T07-06](../projects/PR-T07-06.md).

## Mastery gate and feedback

Explain one positive path and one failure/counterexample for every subtopic without reading your implementation. Submit each project’s leaf-objective checklist with a distinct evidence item; shared runs may support several items only when the relation is explained. Re-run the saved independent fixture verifier, then reproduce at least one artifact from a clean environment. Passing those checks is evidence within their scope, not full-domain certification.

If an invariant, lifetime or environment claim cannot be defended, return to its project’s smallest trace and remediate the named entry knowledge. If a tool result disagrees with reasoning, minimize before changing expected results. A module passes when all core projects and awareness duties are accepted; elective implementation gaps remain visible. Use {ref}`guide-assessment` and {ref}`guide-audit` for review records.

## Consolidation and transfer

After at least one day, reconstruct a selected contract and failing trace from memory, then apply one changed capacity/backend/target assumption. Explain which evidence survives and which must be regenerated. Transfer the dependency, ownership, representation or ordering ledger into the next project rather than copying an unexplained implementation. Record the delayed correction in the consolidation budget; see {ref}`guide-integrations` and {ref}`guide-workload`.

## Environment and limits

Use the declared Linux x86-64 environment for hosted observations and profile-specific adapters for portable components. Record compiler, linker, OS/library, architecture and configuration. Synthetic fixtures certify their declared static/reference calculations only. Unavailable target runs, unsupported instrumentation and hardware-dependent results are reported explicitly; emulator results do not prove STM32 electrical/peripheral behavior. No privileged host operation is required by a core project. See {ref}`guide-laboratory`, {ref}`guide-profiles` and {ref}`guide-inventory` before changing a boundary.
