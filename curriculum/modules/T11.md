## Purpose and outcomes

Construct small portable components and runtime support under precise dependency restrictions. Separate freestanding compilation from no-library, no-allocation and whole-image claims, then audit actual emitted support. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce.

## Entry check and remediation

List what the compiler and linker add to a source file. Recover one unresolved helper from an object. Revisit T07/T09 until component and executable dependency boundaries are distinguishable. Use {ref}`guide-entry` for diagnostic evidence and {ref}`guide-roadmap` for route choices. Domain numbers are coverage IDs, not an instruction to study them numerically.

## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T11.01 — Dependency profiles

Hosted, freestanding, libc-free, allocation-free and custom-startup claims restrict different dimensions. A component promise is weaker than a whole-executable promise because the harness and callbacks have their own effects.

Investigate: Write an allowlist for headers, symbols, callbacks, storage and OS services at two boundaries. A common mistake is: Omitting stdlib.h removes runtime dependencies. Evidence: The contract labels every requirement by its exact scope and makes unknown transitive callees explicit. Develop that evidence in [PR-T11-01](../projects/PR-T11-01.md).
### T11.02 — Compiler and linker controls

Freestanding flags change compilation assumptions; startup and default-library exclusions act during linking. Header search paths form a third independent axis.

Investigate: Build a controlled option matrix and compare unresolved symbols, selected startup inputs and final dependencies. A common mistake is: -ffreestanding is equivalent to -nostdlib. Evidence: A matrix explains which stage each control affects and retains the actual driver commands. Develop that evidence in [PR-T11-01](../projects/PR-T11-01.md).
### T11.03 — Compiler-generated memory operations

Aggregate copy and initialization may be lowered into memory-helper calls even without a source call. The generated form depends on size, optimization and target.

Investigate: Compile several fixed-size aggregate operations and inspect objects and LTO images for helper requirements. A common mistake is: A source-level call census is a complete binary dependency audit. Evidence: An emitted-call ledger names the support implementation or a documented compiler configuration that avoids it. Develop that evidence in [PR-T11-02](../projects/PR-T11-02.md).
### T11.04 — Arithmetic support

Integer division and soft-float operations can require compiler-runtime routines. Avoiding a source library function does not provide the missing instruction or helper contract.

Investigate: Inspect a wide division and conversion on one instruction-rich and one constrained target. A common mistake is: Arithmetic expressions are always dependency-free. Evidence: Each helper is classified as deliberately linked, implemented under an explicit contract, or excluded from supported operations. Develop that evidence in [PR-T11-02](../projects/PR-T11-02.md).
### T11.05 — Atomic and instrumentation support

Atomics, stack protection and instrumentation can introduce state and out-of-line calls. Verification builds may intentionally carry support absent from production, but those differences need evidence.

Investigate: Compare atomic and instrumented objects against production allowlists. A common mistake is: Passing an instrumented build proves the production image has identical dependencies. Evidence: Separate audit reports name helper symbols, alignment and actual lock-free observations without inferring universal support. Develop that evidence in [PR-T11-02](../projects/PR-T11-02.md).
### T11.06 — Minimal memory primitives

A byte-copy contract excludes overlap, while move must preserve the original source bytes when ranges overlap. Zero length must be decided before any access. Compiler recognition can turn a helper implementation into its own external call.

Investigate: Implement copy, move, set and lexicographic byte compare without external C-library calls. A common mistake is: A forward copy works for every overlapping range. Evidence: Snapshot-based oracle cases cover both overlap directions; object inspection excludes accidental self-recursive helper calls. Develop that evidence in [PR-T11-03](../projects/PR-T11-03.md).
### T11.07 — Environment adaptation

An embedded library asks the environment for services such as stream output or storage extension. Semihosting redirects requests through a debugger and therefore changes standalone behavior.

Investigate: Specify a small service adapter with a refusing heap policy and a transport stub; classify debugger-dependent paths. A common mistake is: Successful output under a debugger proves the board can print independently. Evidence: The adapter reports unsupported operations explicitly and its dependency table distinguishes test backend from board service. Develop that evidence in [PR-T11-04](../projects/PR-T11-04.md).
### T11.08 — Runtime entry contracts

Entry establishes a contract for stack, initialized storage, exception state and any retained TLS/hooks. A reusable component should consume this contract rather than silently repairing the whole environment.

Investigate: Write a platform entry checklist and test the component with one intentionally uninitialized service excluded. A common mistake is: Link success establishes a valid runtime entry state. Evidence: The checklist names each initializer and every hosted facility deliberately unavailable. Develop that evidence in [PR-T11-04](../projects/PR-T11-04.md).
### T11.09 — Automated dependency audit

An object exposes unresolved requirements before linking, whereas final linking can hide them by supplying code. Audits therefore need both undefined symbols and final maps/disassembly.

Investigate: Automate allowlist checks over debug/release and GCC/Clang outputs, including one deliberate forbidden call. A common mistake is: No undefined symbols in an executable means no forbidden dependency. Evidence: The failing fixture is rejected and statically resolved support is still visible in the final closure report. Develop that evidence in [PR-T11-05](../projects/PR-T11-05.md).
### T11.10 — Runtime validation

A hosted reference is useful for checking semantics while the tested component remains under its stricter profile. Boundary tests and failures need a backend that does not rely on the component being verified.

Investigate: Run differential byte-operation tests plus failure injection and then rerun selected cases in the restricted environment. A common mistake is: Using libc in the test oracle violates the component boundary. Evidence: The component/harness boundary is documented, disagreement is minimized and unsupported targets are listed rather than silently skipped. Develop that evidence in [PR-T11-03](../projects/PR-T11-03.md).

## Environment and limits

Use the declared Linux x86-64 environment for hosted observations and profile-specific adapters for portable components. Record compiler, linker, OS/library, architecture and configuration. Synthetic fixtures certify their declared static/reference calculations only. Unavailable target runs, unsupported instrumentation and hardware-dependent results are reported explicitly; emulator results do not prove STM32 electrical/peripheral behavior. No privileged host operation is required by a core project. See {ref}`guide-laboratory`, {ref}`guide-profiles` and {ref}`guide-inventory` before changing a boundary.
