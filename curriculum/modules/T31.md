## Purpose and outcomes

Diagnose a bare-metal failure from image identity through machine state, then preserve deployment and recovery evidence. A useful crash record should make a causal claim checkable with matching symbols.

## Entry check and remediation

Read an ELF/map/vector address, identify a basic exception frame and explain UART/DMA ownership. Repair those selected T27–T29 mechanisms first. Establish probe/server/board identities from the laboratory guide rather than guessing a target configuration.

Use {ref}`guide-entry` for the diagnostic policy and {ref}`guide-roadmap` for route order. Only the stated prelude leaves must precede a dependent project.

## Study sequence and teaching

### T31.01 — Debug connection

Debug connection depends on probe firmware, physical SWD/reset wiring, target identity and server configuration before it depends on application C. Record these separately and progress from device-ID read to halt/reset to programming. A flash failure and an application reset loop demand different diagnosis. Capture exact tool versions and commands from the laboratory setup; never infer that a generic Cortex-M4 configuration selects F439 Flash. Evidence is a classified connection log and repeatable reset strategy.

Apply this mechanism in [PR-T31-01](../projects/PR-T31-01.md).

### T31.02 — Source and machine debugging

Optimized machine code can combine, move or remove source operations, so source stepping is a hypothesis aid rather than a source-order trace. Inspect registers, instruction addresses and memory for one simple numerical/driver routine at debug and release optimization. Hardware breakpoints/watchpoints have finite supported resources. Evidence links the actual ELF to disassembly and explains one optimized-out local; disabling all optimization is not the final diagnosis.

Apply this mechanism in [PR-T31-01](../projects/PR-T31-01.md).

### T31.03 — Fault decoding

A fault report needs fault status, saved frame interpretation and the offending instruction/address. Decode synthetic CFSR bits before trying a target injection, then capture the core's applicable status registers and EXC_RETURN in a minimal handler. Avoid printing through a failing peripheral or using a corrupt stack in recovery. A secondary handler fault can obscure the first. Evidence distinguishes captured valid fields, unavailable fields and the causal access reconstructed from the matching ELF.

Apply this mechanism in [PR-T31-02](../projects/PR-T31-02.md).

### T31.04 — Stack integrity

Stack corruption may arise from overflow, misalignment, bad returns or nested handlers. Reserve a region, establish ABI alignment and use canary/watermark observations alongside a static depth budget; use guards/MPU only if verified supported/configured. The fixture shows a valid watermark coexisting with a possible unexercised deeper call. Evidence includes a controlled overwrite detection and a quantified tested high-water mark without labeling it a universal bound.

Apply this mechanism in [PR-T31-02](../projects/PR-T31-02.md).

### T31.05 — Peripheral and bus faults

A peripheral that stays silent may have the wrong clock, mode, pin route or sequencing even when software reads plausible values. Inject one synthetic configuration defect at a time and classify status versus external-signal expectations. For USART, TXE alone does not establish final wire completion; for SPI, paired receive handling matters. Evidence ties an ordered register trace to a board signal capture where available. Do not 'fix' a bus by changing unrelated timeouts together.

Apply this mechanism in [PR-T31-03](../projects/PR-T31-03.md).

### T31.06 — DMA and concurrency diagnosis

DMA diagnosis starts with ownership epochs and memory placement. Trace submit, enable, partial progress, complete, cancel request and confirmed stop, then locate a stale-buffer or premature-reuse defect. Debugger halts may stop a core while peripherals continue, changing the interleaving. Evidence includes reproducible logical schedules and a target run with the probe's freeze policy recorded; a debugger-only success cannot settle a physical race.

Apply this mechanism in [PR-T31-03](../projects/PR-T31-03.md).

### T31.07 — Trace and timing tools

Trace has capacity, timestamps and a cost. Design fixed-size records with sequence numbers and a drop counter, then correlate samples against a known counter frequency. Use a verified target cycle counter only after recording enable/configuration/wrap rules; do not assume every emulator models it. Evidence measures tracing-on versus tracing-off disturbance and accounts for missing records. The trace itself must not block the critical path it measures.

Apply this mechanism in [PR-T31-04](../projects/PR-T31-04.md).

### T31.08 — Image deployment

Deployment identifies the bytes, address map and matching symbols before flashing. Produce a release manifest with image hash, vector address, sizes, compiler/link settings, ELF and map identity; verify programmed bytes where the selected probe supports it. Repeat standalone power-on operation. A file named release.bin is not evidence of the deployed image. Keep the synthetic fixture's offset checks separate from actual target flash verification.

Apply this mechanism in [PR-T31-04](../projects/PR-T31-04.md).

### T31.09 — Boot and update interfaces

An update protocol needs image length/version/address compatibility and an interruption policy before transfer of control. Use two logical slots with a commit marker written last; a partially written candidate must leave the previous committed image selectable. The checksum fixture detects accidental corruption but supplies no authenticity. Evidence includes every power-loss boundary and the stack/vector/interrupt responsibilities at handoff; do not implement a security-sensitive production bootloader from this small exercise.

Apply this mechanism in [PR-T31-05](../projects/PR-T31-05.md).

### T31.10 — Fault injection and recovery

Fault injection tests containment, not just detection. Corrupt a retained record, freeze progress, return a timeout and inject an invalid adapter response in isolated trials. Preserve a bounded crash record and stop after the declared recovery count, keeping outputs in the specified safe state. A reboot that repeats the hazardous action is not recovery. Evidence records the initial fault, detection latency where measured, recovery transition and residual consequences.

Apply this mechanism in [PR-T31-05](../projects/PR-T31-05.md).

**Shared scope limit — Cortex-M4 Devices Generic User Guide:** Generic core document; optional features and device integration require ST evidence. **Shared scope limit — STM32F427/437 and STM32F429/439 device errata:** An erratum applies only under its listed conditions and revision applicability. No physical board revision was read. DSB and dummy-read remedies must not be generalized to unrelated devices.

**Shared scope limit — STM32 Nucleo-144 boards (MB1137):** Inspected Rev 8, not current Rev 11. Board revision, actual solder bridges and clock population must be recorded on physical hardware; described defaults are not a measurement of the learner's board.

## Mastery gate and feedback

Decode a controlled fault with matching ELF, diagnose one bus/ownership defect, audit a deployed release and demonstrate bounded recovery. A physical release gate includes standalone power-on and programmed-byte verification where supported. If a handler obscures the first fault, shrink the handler before adding diagnostics.

For every linked objective, retain a separately labeled explanation, implementation/analysis artifact and check. Use {ref}`guide-assessment` for the rubric; one passing fixture does not establish all three objectives of a topic.

## Consolidation and transfer

Investigate the same defect in optimized firmware, then with tracing enabled/disabled. Predict debugger and trace disturbance, preserve artifact identities and explain any unreproduced physical consequence.

## Environment and limits

Use {ref}`guide-profiles` to declare the dependency boundary, {ref}`guide-laboratory` for installed tools and hardware, and {ref}`guide-audit` for image/call-graph evidence. Fixtures are original deterministic mathematical or synthetic-protocol data. Run `python tools/verify_embedded_fixtures.py` from the curriculum root to recompute their expectations. This oracle checks fixtures, not learner code.

Host adapters establish only their declared state-machine semantics. QEMU mps2-an386 establishes its Arm FPGA machine behavior; it does not implement STM32F439 registers. Physical-board completion requires the exact board/revision/pin/clock evidence. RM0090 Rev21 and UM1974 Rev8 are the inspected revisions; newer portal revisions require delta review before adopting changed procedures. No simulated timing or analog result is a physical measurement.
