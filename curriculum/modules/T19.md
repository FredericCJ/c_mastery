# T19: Higher-level abstractions implemented in C

## Purpose and outcomes

Build higher-level abstractions from explicit state, operations and lifetime protocols. C does not require one object pattern; plain structures, opaque objects, tables, tags and cursors are choices with measurable costs. The module makes those costs and contracts visible rather than treating dynamic dispatch as an automatic improvement.

## Entry check and remediation

Complete T18 contract/ownership gates and T06 typed interface reasoning. If an abstraction hides who owns context or how a partial operation reports progress, expose those facts before adding another layer. T14 container implementation may proceed in parallel after its selected prerequisites.

## Component progression

**Abstractions with visible machine costs.** Derive an operation-table interface from two concrete users. Compare typed and erased representations while tracking indirection, lifetime and invalid states.

Before implementation, predict this discriminating case: **A retained callback context outliving its owner although the function pointer remains valid.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T19.01 — Objects as state and operations

An object is state plus operations constrained by invariants; no hidden language runtime is required. Construction, active operations and destruction have separate responsibilities. Plain structs expose representation while opaque interfaces centralize invariant enforcement, so choose based on caller needs.

Investigation: Implement the same small counter/session as a plain struct and an opaque interface with explicit lifecycle.

Misconception to resolve: A function naming convention alone does not enforce object invariants.

Observable evidence: State transitions and an interface comparison showing where validation occurs. Evidence is developed in {ref}`PR-T19-01`.

### T19.02 — Function-table interfaces

An operation table pairs exact signatures with a context pointer. Immutable shared tables can be reused across instances while mutable state remains per instance. Optional operations require presence/version/size rules; calling a null slot is not an optional-feature policy.

Investigation: Implement two backends with one versioned operation table and a deliberately absent optional operation.

Misconception to resolve: A table entry cast cannot repair a signature mismatch.

Observable evidence: Backend conformance tests, shared-table/per-instance diagram and optional-slot checks. Evidence is developed in {ref}`PR-T19-01`.

### T19.03 — Closures and callbacks

A closure-like callback pairs function and explicit context. Registration creates a lifetime relationship; removal must specify whether a callback can still be in flight. Reentry and callbacks during cancellation/destruction require a protocol, often deferred removal or generation validation.

Investigation: Build a bounded callback registry with self-removal and a destruction-time policy.

Misconception to resolve: Removing a registration does not automatically reclaim a context still used by an active callback.

Observable evidence: Registration/in-flight traces and exact context reclamation rules. Evidence is developed in {ref}`PR-T19-01`.

### T19.04 — Generic components

Generic components move type checks and costs differently: void-pointer interfaces need runtime size/alignment/copy/destruction contracts; generated macros specialize source; _Generic selects compatible typed operations. None can ignore ownership or element lifecycle.

Investigation: Compare one fixed-capacity component in typed, void-pointer and generated forms.

Misconception to resolve: Element byte size alone is not a complete generic element contract.

Observable evidence: Diagnostics, alignment/lifecycle checks and code-size/indirection comparisons. Evidence is developed in {ref}`PR-T19-02`.

### T19.05 — Tagged unions and variants

A tagged union couples a discriminant to a permitted payload. Operations must validate that relationship and handle every alternative. Conversion should produce a new valid variant or an error variant, not reinterpret unrelated bytes through a guessed tag.

Investigation: Implement integer/text/error variants with exhaustive handling and bounded borrowed-text lifetime.

Misconception to resolve: A union’s current bytes do not identify the active logical alternative without a contract.

Observable evidence: Tag/payload checks, exhaustive dispatch and invalid-tag rejection. Evidence is developed in {ref}`PR-T19-02`.

### T19.06 — State and strategy patterns

State and strategy patterns separate transition decisions from effects or configurable operations. Switches, tables and function dispatch have different visibility, extensibility and code costs. Use dynamic strategy only when variation at runtime justifies it.

Investigation: Implement one transition model with a pure core and compare switch/table dispatch plus one injected strategy.

Misconception to resolve: Adding function pointers does not inherently improve architecture or performance.

Observable evidence: Equivalent transition outputs, effect boundaries and a reasoned dispatch choice. Evidence is developed in {ref}`PR-T19-03`.

### T19.07 — Iterators and ranges

An iterator specifies order, end state and mutation invalidation. Pull cursors let callers control progress; push callbacks invert that control and introduce callback lifetime/reentry obligations. Both can use bounded storage, but early stop and mutation policies must be explicit.

Investigation: Implement cursor and callback traversal over a fixed-capacity collection with epoch invalidation.

Misconception to resolve: An index within capacity is not valid after arbitrary mutation if the traversal contract forbids it.

Observable evidence: Order/early-stop cases, stale-iterator checks and bounded temporary storage. Evidence is developed in {ref}`PR-T19-03`.

### T19.08 — Streams and composable I/O

A stream operation can report partial progress separately from terminal error or backpressure. Composing framing, checksumming and transport must preserve those distinctions and retain only explicitly owned bytes. Buffering adds capacity and flush policies, not an excuse to assume one call consumes all data.

Investigation: Compose a bounded frame/checksum writer with a short-write transport adapter.

Misconception to resolve: A successful write need not consume the entire request.

Observable evidence: Progress traces, exact reconstructed bytes and backpressure/ownership checks. Evidence is developed in {ref}`PR-T19-04`.

### T19.09 — Reference and handle abstractions

Reference counts keep objects alive under a release protocol but do not prevent cycles or concurrent data races. Generation handles reject stale identities until generation exhaustion, which needs an explicit policy. Select reclamation and overflow behavior before copying references or reusing slots.

Investigation: Implement generation-counted fixed slots and analyze a reference-counted cycle as an alternative.

Misconception to resolve: Shared ownership is not concurrent access synchronization.

Observable evidence: Stale/overflow/reuse tests and separate lifetime versus access-safety claims. Evidence is developed in {ref}`PR-T19-04`.

### T19.10 — Abstraction cost analysis

An abstraction’s cost includes instance bytes, table bytes, indirect calls, branches, copies, allocations and cache behavior. Inspect generated code under recorded optimization, then measure relevant paths against a simpler baseline. Remove a layer only if evidence and maintainability support the change.

Investigation: Compare direct and table-dispatched versions with identical contracts and workloads.

Misconception to resolve: A microbenchmark does not justify deleting an abstraction across unrelated workloads.

Observable evidence: Size/code/resource ledger, repeated measurements and a bounded decision record. Evidence is developed in {ref}`PR-T19-04`.

## Mastery gate and feedback

Implement the abstraction without hidden ownership or progress assumptions. Demonstrate stale callback/iterator/handle rejection, partial writes and valid tagged alternatives. Defend the chosen generic/dispatch design with both diagnostics and cost evidence.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

Change backend, element type or transport chunk size after a delay. Reuse conformance tests to show semantic equivalence and revise resource bounds before optimizing.
