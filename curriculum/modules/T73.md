# T73: Structured concurrency, channels and actors

## Purpose and outcomes

Build and explain the representations and state transitions below, preserving the imported artifact contracts. The complete exercises are core work; descriptive hours do not cap depth. Distinguish ISO semantics, implementation diagnostics, runtime checks and programmer discipline.

## Entry check and remediation

Derive ownership through a failed acquisition and a retained borrow using the prerequisite artifacts. If a cancellation request is mistaken for completion, revisit io.async before admitting a storage reuse argument.

## Environment and limits

Use profile A: hosted ISO C17 on Linux x86-64, with POSIX pthreads, mutexes and condition variables as explicit backend dependencies. The [messaging laboratory contract](../../labs/messaging/CONTRACTS.md) and messaging.h define actual storage, callback and concurrency preconditions. GCC and Clang debug, release, ASan/UBSan and separate TSan profiles are declared. CMake and Python are host verification tools. Construct the channel, actor, scheduler and transaction mechanisms locally; a ready-made implementation cannot replace them.

The nursery has eight owned child slots, the hub has two channels of capacity zero through four, and the work-stealing deque has eight atomic-value slots. Rendezvous success requires receiver acknowledgement; close/drain and terminal cancellation have different semantics. The finite STM uses four atomic cells and sequentially consistent accesses; version snapshots have eight stored versions and four reader pins. Actors, sender/receiver operation states and demand streams retain their separately stated serialized protocols. Stable addresses, callback lifetime and quiescent destruction are mandatory. Cooperative cancellation neither bounds join latency nor proves that a callback has stopped accessing storage.

The arguments under sequential consistency do not validate weaker atomic orders, arbitrary pointer reclamation, durable transactions or fairness. Check actual atomic lowering and lock-free observations instead of inferring progress from a type name. Real pthread stress and TSan cover executed schedules only; required coroutine, asynchronous-I/O and existing learner-artifact adapters need their own evidence. Experiments stay within original local processes and synthetic messages. These hosted campaigns do not validate a kernel, bare-metal target, physical timing, independent learner performance or every interleaving; published C17 text remains an explicit source-access gap.

## Study sequence and teaching

### T73.01 — Scope-owned child tasks and cooperative cancellation

A task nursery owns its admitted children and retains their contexts until every join completes. Each cooperative checkpoint observes the cancellation flag and allows normal cleanup; a child that never reaches one can prevent timely joining, so cancellation does not imply a bounded shutdown latency.

Explain scope-owned task lifetime, failure aggregation and cooperative cancellation, including why a cancellation flag does not establish completion or a bounded join latency.

Spawn result5 then result0: after join, both slots are joined, cancellation is true and result is5. Fail admission at attempt2: exactly one child remains admitted, its context is retained until join and no second thread handle is joined. An uncooperative infinite child is a bounded external-timeout experiment, not silently declared cancelled.

Construction: Derive admission/closing/quiescent states, implement spawn/join and deterministic error selection, then compose with the existing work.pool artifact without detached tasks or prematurely released contexts. The full assessed work is {ref}`X-T73-001`.

Misconception: Setting an atomic flag cannot interrupt arbitrary blocking code.

Evidence: Inject failure before every admission, record thread/context ownership, join zero/one/eight children, reject ninth admission and late spawn. Use a barrier-controlled failure with siblings acknowledging cancellation and compare accepted/completed counts. Reject both missing-cancellation and swallowed-result mutants. Run separate TSan and demonstrate that eventual cancellation needs child checkpoints.

### T73.02 — Bounded CSP channels, rendezvous and atomic select

Selection registration must connect the readiness check to waiting without an unprotected notification gap. The hub's common mutex and condition variable provide that exclusion boundary: recheck readiness in a loop after every wakeup, including a spurious one.

Derive readiness, linearization, close/drain and cancellation semantics; compare deterministic selection with Go ready-case randomness and distinguish rendezvous acknowledgment from merely enqueuing an offer.

Capacity2: send7,close,send8 gives OK,OK,`CLOSED`; the first receive returns7 and the next `CLOSED`. Two ready channels alternate preference. A capacity0 sender of42 returns OK only after select consumes42. Close before acknowledgment returns `CLOSED` to sender; an acknowledged send remains successful if cancellation arrives before sender resumes.

Construction: Implement buffered/rendezvous operations and select with a single predicate-registration boundary, explicit spurious-wakeup loops, finite tickets and quiescent destruction; retain coroutine frames until generation-specific disarm. The full assessed work is {ref}`X-T73-002`.

Misconception: A condition-variable wakeup does not prove its predicate.

Evidence: Test full/empty, both ready, one closed, all closed, close with buffered values, cancellation with blocked sender/receiver and accepted-versus-unaccepted rendezvous. Repeatedly inject spurious broadcasts. Capture event histories and verify no lost/duplicated accepted values. Reject send-after-close and skipped-buffer mutants; independently model sequential traces and use TSan for actual threads.

### T73.03 — Senders, receivers and immovable operation-state lifetimes

Operation completion ownership determines who may release the connected state at the terminal callback. Because that callback may free the state, the completing backend must retain everything it needs beforehand and perform no further access through the consumed state afterward; a stop request alone does not transfer this right.

Separate sender recipe, connected operation storage, start permission and completion ownership; identify the dated C++ proposal guarantees that an exposed C struct does not enforce.

Complete before start is INVALID. Start then stop leaves `STARTED` with cancellation requested. Complete CANCELLED,3 invokes one receiver and reaches `DONE`. Duplicate complete on a still-live test state is INVALID and leaves callback count1. A separate heap-owned completion test frees the state inside its receiver without later access.

Construction: Implement the serialized state protocol and backend lifetime adapter, including synchronous completion, competing cancellation and completion transitions, callback reentrancy policy and exactly-once terminal release. The full assessed work is {ref}`X-T73-003`.

Misconception: A C typedef does not make a state noncopyable or immovable.

Evidence: Enumerate invalid start/complete orders, value/error/stopped alternatives and cancellation-before-completion. Use a receiver that frees a heap state to detect post-callback access under ASan. Reject duplicate-completion and cancel-as-completion mutants. For a concurrent adapter, use one atomic winner and demonstrate that losers never inspect reclaimed storage without their own retained reference.

### T73.04 — Actor incarnations, copied mailboxes and failure boundaries

Explain mailbox ownership, actor identity across restart, run-to-completion serialization and the limit of let-it-crash recovery when effects have already escaped the actor.

Enqueue2,99,3 for generation1, where handler99 fails. Step2 adds2, step99 fails and queued3 is discarded. Restart creates generation2; generation1 messages are STALE and cannot affect the new actor. Recursive step while a handler is active returns `BUSY`.

Construction: Implement admission, dispatch, death and reincarnation with finite generation retirement; design the channel-to-actor executor boundary and message-drop ownership. The full assessed work is {ref}`X-T73-004`.

Misconception: Restart does not undo an already emitted external effect.

Evidence: Test full mailbox, stale identity, nested step, failure with queued work, restart while alive and generation exhaustion. Reject stale-generation admission and retained-dead-mailbox mutants. Record effects before failure to show they are not rolled back. Compare actor serialization to a mutex-protected shared object under the same observable ordering.

### T73.05 — Supervision trees with restart budgets and ordered quiescence

Restart intensity counts qualifying failures inside the declared sliding time window and escalates when its finite budget is exhausted. Restart dependency order is a separate invariant: stop affected children in reverse order, establish quiescence, then start them forward so no restarted dependent uses an old live dependency.

Derive restart topology, intensity accounting and the error-kernel boundary; explain why restarting healthy siblings may be necessary and why unlimited restart can amplify faults.

REST failure at child1 yields[-4,-3,-2,2,3,4]. With limit2/window10, failures at0 and1 restart; failure at2 escalates with[-4,-3,-2,-1]. With limit1/window10, failures at1 and11 are both admitted because the older event is outside the strict window.

Construction: Implement ordered restart plans with bounded timestamp storage and an actor execution adapter that preserves quiescence and accounts for partial restart failure. The full assessed work is {ref}`X-T73-005`.

Misconception: A plan is not evidence that stopped children have actually ceased execution.

Evidence: Independently enumerate all12 strategy/failed-child selections, test exact window boundary, backwards time, maximum timestamps and escalation permanence. Reject forward-stop and omitted-start mutants. Inject handler and restart failures, compare emitted action order and prove no restarted child observes a dependency that is still stopped.

### T73.06 — Bounded work stealing with an explicit C memory-order proof

Identify linearization and ownership in competing owner and thief operations, last-item arbitration, finite-index exhaustion and stale slot reads; distinguish correctness under sequential consistency from weak-order proof and actual lock-free progress.

Push7,push8,pop,steal,steal returns OK,OK,8,7,`EMPTY`. Eight live entries fill capacity and a ninth push leaves state unchanged. Empty pop preserves its output canary. Starting quiescent top=bottom=SIZE_MAX-1 makes push return OVERFLOW. Two thieves plus owner process4000 distinct IDs exactly once in the supplied threaded anchor.

Construction: Derive a circular representation with monotonic nonwrapping indices and atomic slots; implement push/pop/steal with a proof for empty, full, last-item and reused-slot states. The full assessed work is {ref}`X-T73-006`.

Misconception: Atomic indices do not legalize a racing ordinary slot load.

Evidence: Differentially compare1095 bounded sequential traces with Python deque, include repeated empty pops and capacity reuse, record concurrent invocation/response histories and check small histories for legal linearizations. Reject wrong-pop and omitted-steal-CAS mutants. Run TSan, inspect generated instructions and report atomic_is_lock_free; do not infer weak-memory correctness from x86 stress.

### T73.07 — TL2-style software transactions over actual C17 atomics

The transaction read version is the snapshot timestamp captured at begin. Each admitted read must reject a locked cell or a version newer than that timestamp; commit validation then checks the retained read dependencies while the write locks protect publication. Speculative external effects are not rolled back by aborting these cells.

Derive snapshot validation, write-set locking, abort restoration and the distinction between transaction isolation, atomic C accesses and memory reclamation; explain inconsistent-read hazards before commit.

TransactionA starts, B writes cell0=7 and commits: A reading cell0 returns `CONFLICT` without changing output99. If A reads7 before B commits8, then stages cell1=9, A commit conflicts and cell1 remains0 with its lock clear. Two concurrent increment transactions over two equal cells produce2000 committed increments and never expose unequal admitted reads.

Construction: Implement bounded read/write sets, read-your-writes, nonblocking lock acquisition and validated commit using the declared sequentially consistent baseline; prove failed commits leave payload unchanged while allowing timestamp gaps. The full assessed work is {ref}`X-T73-007`.

Misconception: Atomic cells do not make a multi-cell snapshot atomic by themselves.

Evidence: Force conflict before a read, after a read and during partial lock acquisition; test repeated writes, empty/read-only transactions and timestamp exhaustion. Reject missing read validation and missing commit validation mutants. Use an independent serial-history model for small schedules, TSan for actual threads and fault hooks for every commit phase. Explain why atomic individual loads alone do not provide a coherent transaction.

### T73.08 — Multiversion visibility, reader pins and bounded reclamation

Visible-version retention preserves the current version and the version selected by each live snapshot pin. It does not preserve every historical version: compute the retained set explicitly before reusing a slot, and show why dropping a stale generation cannot remove a current reader's retention claim.

Derive version visibility and retention from reader lifetimes, distinguish repeatable snapshot reads from stronger isolation, and identify how a forgotten pin creates resource retention.

PinA at[0,0], publish[1,2], publish[3,4]: A still reads[0,0]. DropA and reuse its pin slot forB: old handleA is STALE and B reads[3,4]. A clock at UINT64_MAX refuses publish. Snapshot visibility is repeatable for the two-field value; no multi-object serializability or durability is claimed.

Construction: Implement timestamped publication, exact pin identity, visible-version selection and reclamation with a bounded-space proof under the four-reader assumption. The full assessed work is {ref}`X-T73-008`.

Misconception: Repeatable reads do not by themselves imply serializable transactions.

Evidence: Enumerate pin/publish/read/drop traces against an independent immutable-history model, test four pins at different versions and a fifth refusal, stale slot reuse and generation retirement. Reject pin-ignorant collection and missing-generation mutants. Track retained version counts before/after releases and compare the mutex cost with read-copy-update assumptions.

### T73.09 — Sequence validation without racing ordinary C payloads

Separate storage race freedom, coherent snapshot validation, writer serialization, retry bounds and counter lifetime; identify what sequential consistency proves and what a later weakened implementation must re-establish.

With sequence1, three attempts return `BUSY` and outputs stay[99,99]. Writing[7,14] then reading succeeds. Zero attempts is `BUSY`. SequenceUINT_MAX-1 rejects a new write without modification. The threaded anchor writes10000 pairs[i,2*i] and rejects any successfully returned incoherent pair.

Construction: Derive the atomic representation and sequentially consistent ordering argument, implement bounded retry and nonwrapping writer publication, and account for every output and failure effect. The full assessed work is {ref}`X-T73-009`.

Misconception: A snapshot retry loop does not keep pointed-to objects alive.

Evidence: Test odd/even transitions, zero retry, interrupted writer state, output canaries and counter exhaustion. Reject odd-sequence acceptance and omitted-payload-write mutants. Run actual concurrent stress and TSan while explaining that clean runs do not prove weak-order correctness. Inspect disassembly and compare lock-free status and fences with an equivalent mutex snapshot.

### T73.10 — Demand signaling, terminal events and bounded reentrancy

A terminal signal reports the stream's final success or error and needs no item demand credit. It must be delivered at most once without overlapping another signal; after it, no item is admitted. Cancellation follows its separate suppression rule and is not evidence of cross-thread callback quiescence.

Derive demand accounting, signal ordering, cancellation and reentrancy limits; compare the original C subset to selected Reactive Streams rules without claiming interface or certification equivalence.

Emit with demand0 is `EMPTY`. Request1 then emit99 whose callback requests1 leaves demand1 without recursive delivery; emit7 consumes it. UINT64_MAX then request1 stays unbounded. Complete then error produces one terminal event; later emit is `CLOSED`. Cancellation prevents subsequent emits but does not establish cross-thread callback quiescence.

Construction: Implement explicit demand/terminal/delivering state, saturating unbounded arithmetic and callback ownership; construct a channel adapter that never delivers more items than requested. The full assessed work is {ref}`X-T73-010`.

Misconception: Cancellation may stop future delivery while a callback is still using the subscriber.

Evidence: Enumerate request/emit/cancel/end traces, test zero and maximum demand, callback requests/cancellation and recursive emission. Reject emission without credit and repeated-terminal mutants. Independently account for requested versus delivered finite items, retain callback context through return and test that end requires no demand.
