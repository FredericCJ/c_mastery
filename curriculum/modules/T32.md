## Purpose and outcomes

Build evidence that survives changes to implementation and environment. Testing progresses from independent contract oracles to model histories, fuzz/failure campaigns, supported instrumentation and reproducible diagnosis.

## Entry check and remediation

Write normal/boundary/invalid cases for a caller-storage component and explain output ownership after failure. Repair T07/T12/T18 interface/lifetime skills selectively. Confirm a supported Linux environment for Valgrind and GCC condition coverage; tool absence must be resolved for the dependent activity rather than treated as a pass.

Use {ref}`guide-entry` for the diagnostic policy and {ref}`guide-roadmap` for route order. Only the stated prelude leaves must precede a dependent project.

## Component progression

**Tests that reject plausible wrong mechanisms.** Start from a contract, then combine boundary examples, stateful generation, metamorphic relations, mutation and reduced reproducers. Keep oracle independence visible.

Before implementation, predict this discriminating case: **A high-coverage suite accepting a deliberately corrupted invariant because it asserts only nominal outputs.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T32.01 — Test architecture

A test architecture separates a portable contract from adapters and the harness that observes it. The harness may allocate and print even when the component is profile B/C. Build a caller-owned bounded queue/parser with a scripted adapter and a genuinely independent list/grammar oracle. A mock's deterministic convenience can hide physical side effects. Evidence is the dependency boundary, fixture manifest and a map of which properties need real OS/target execution.

Apply this mechanism in [PR-T32-01](../projects/PR-T32-01.md).

### T32.02 — Unit testing

Unit tests should observe contracts rather than struct layout. Partition empty, full, normal, invalid and failure cases; sentinel storage detects unintended writes outside the declared extent. Implement table-driven tests for a component's public API and critical invariants. Merely obtaining the expected return value does not establish preserved ownership or unchanged output on failure. Evidence includes both result checks and state/effect checks, with the smallest reproducer retained.

Apply this mechanism in [PR-T32-01](../projects/PR-T32-01.md).

### T32.03 — Integration and system testing

An integration test crosses an actual boundary: framing to partial I/O, driver to adapter, or application to shutdown logic. Reuse vectors while substituting scripted and real backends, but retain backend-specific expectations. A simulated successful write is not evidence of Linux short-I/O or physical UART behavior. Evidence is a complete acquisition-to-release workflow with partial progress, one failure and deterministic cleanup, plus a declared environment scope.

Apply this mechanism in [PR-T32-01](../projects/PR-T32-01.md).

### T32.04 — Property and model-based testing

Model-based testing generates operation sequences and compares implementation state to a simpler model after every operation. For a bounded queue, the list oracle is intentionally unlike a ring's index arithmetic. Enumerate short push/pop sequences and add seeded longer runs; minimize the first failing prefix. Random volume does not replace a stated invariant. Retain the seed, sequence and model/implementation disagreement, including a wraparound and full-queue case.

Apply this mechanism in [PR-T32-02](../projects/PR-T32-02.md).

### T32.05 — Differential and metamorphic testing

Differential testing is useful only when both implementations share the same contract; two copies of the same algorithm are weak independence. Metamorphic relations can supply checks without a complete expected output: scaling a linear FIR input scales its output, and splitting a stream into chunks preserves stateful results. Apply relations to the supplied filter/queue data and include a transformation that is intentionally invalid for saturation. Evidence explains why each relation holds and the assumptions it needs.

Apply this mechanism in [PR-T32-02](../projects/PR-T32-02.md).

### T32.06 — Fuzzing

A fuzz harness takes bytes, bounds memory/work, resets state and avoids nondeterministic external effects. Start with valid short packets and malformed length/truncation seeds, then mutate deterministic bytes and persist the smallest failing case. Code coverage feedback is optional machinery, not the oracle. Evidence includes maximum input/work limits, timeouts, corpus identities and crash-versus-contract-failure triage; a clean campaign establishes only its explored execution scope.

Apply this mechanism in [PR-T32-03](../projects/PR-T32-03.md).

### T32.07 — Fault injection

Failure injection turns hidden cleanup paths into controlled contracts. Number acquisition points and fail each in turn; for I/O also inject zero progress, partial progress and timeout. A callback returning an invalid count must be contained before pointer arithmetic uses it. Implement rollback with an observable live-resource ledger. Evidence requires every prefix to release only acquired resources and leave the caller's output in the declared failure state.

Apply this mechanism in [PR-T32-04](../projects/PR-T32-04.md).

### T32.08 — Dynamic instrumentation

Dynamic tools have different detection mechanisms and environments. Compare a native ASan/UBSan build with an unsanitized debug binary under Valgrind Memcheck on a supported Linux setup; include heap overrun, use-after-free and an uninitialized value used in a branch. ASan alone is not an initialized-value detector. Also scope separate thread instrumentation where supported. Record reports, runtime/stack dependencies and slowdowns; an unsupported host is a route-to-supported-environment issue, not a passing test.

Apply this mechanism in [PR-T32-05](../projects/PR-T32-05.md).

### T32.09 — Static analysis

Warnings and static analysis inspect executions through models and approximations. Run high-value compiler diagnostics and Eva or another supported path-sensitive analyzer on a bounded routine, then classify alarms by actual preconditions and configuration. Suppress only with a written contract argument and a regression test. Removing an alarm by assuming the failing input away changes the claim. Evidence includes the before/after code, analyzer configuration and the remaining uncertainty.

Apply this mechanism in [PR-T32-05](../projects/PR-T32-05.md).

### T32.10 — Coverage

Coverage counts execution events, not correctness. For decision allow=length_ok && authorized, use TT, FT and TF to show each condition independently changes the decision while the other is fixed. Build a targeted MC/DC evidence table and compare statement, branch and condition-tool reports; short-circuit evaluation may leave a condition unevaluated. Evidence includes the independent-effect pairs and unreachable/excluded rationale. A 100% branch report alone is not this MC/DC argument.

Apply this mechanism in [PR-T32-06](../projects/PR-T32-06.md).

### T32.11 — Mutation testing

Mutation testing asks whether an oracle notices meaningful wrong behavior. Change <= to < at a capacity boundary, omit a cleanup and invert authorization; run retained tests and explain survivors. Some mutations are equivalent under the declared domain and require reasoning rather than arbitrary new cases. Evidence distinguishes equivalent, killed, surviving and unexecuted mutations, and strengthens one previously weak oracle without coupling it to internal implementation details.

Apply this mechanism in [PR-T32-06](../projects/PR-T32-06.md).

### T32.12 — Interactive debugging

Interactive debugging should discriminate hypotheses. Reduce the input, state a predicted register/memory observation, set a breakpoint/watchpoint and test it before changing several variables. Compare debug and optimized builds with matching symbols; concurrent stepping changes timing. Evidence is a short hypothesis log with one rejected explanation and the minimal repaired defect. A debugger can show a particular state without proving all paths reach that state safely.

Apply this mechanism in [PR-T32-07](../projects/PR-T32-07.md).

### T32.13 — Host, simulator, and target evidence

Allocate evidence by modeled behavior: host logic for grammar/ownership, an identified emulator for its implemented core/board behavior, and real hardware for physical bus, analog and timing properties. The same bytes can be reused across these environments while the expected observation differs. Build an evidence matrix and deliberately reject a simulated ADC-accuracy claim. Passing all host fixtures does not close the board-specific obligations.

Apply this mechanism in [PR-T32-07](../projects/PR-T32-07.md).

### T32.14 — Regression and reproducibility

Regression artifacts are a replay package: exact input, expected relation, binary/symbol identity, versions, flags, command, seed and limitations. Automate a representative debug/release/instrumented matrix and preserve failures before repairing code. Logs from a different image can mislead diagnosis. Evidence must link each claimed property to its test/proof/measurement artifact and show that a fresh replay reproduces both an injected failure and its repaired result.

Apply this mechanism in [PR-T32-07](../projects/PR-T32-07.md).
