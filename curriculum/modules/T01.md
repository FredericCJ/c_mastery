# T01: Entry diagnostic and foundational consolidation

## Purpose and outcomes

Establish a trustworthy starting point. The diagnostic asks for predictions before execution, a reproducible build, and a small contract with boundary tests. Existing experience can shorten remediation, but evidence still matters: a program that prints the right nominal answer can hide a wrong model of C.

## Entry check and remediation

Complete a mandatory quick check of six tasks, at most 30 minutes each (3 h total), before choosing remediation: (1) trace a three-element iterative/recursive sum, state its invariant/termination and work/space; (2) convert 173 between decimal/binary/hex and produce a two-flag truth table; (3) classify a one-past access, an uninitialized read and a conflicting side-effect expression, then describe repairs; (4) order source/object/executable/process stages and classify four failures; (5) rebuild a tiny existing program from the shell, record versions/commands and show one replayable version-control change; (6) specify a bounded sum tool and select normal/boundary/invalid/empty cases plus a minimized regression. Preserve predictions before execution. If all six groups meet the rubric, proceed with only the 3 h assessment. Otherwise use PR-T01-01 for failed groups 1–2, PR-T01-02 for group 3, and PR-T01-03 for groups 4–6, with reading and delayed consolidation only for the failed groups. The full 25 h module budget is a conditional remediation maximum; it is not the mandatory entry duration.

## Component progression

**A bounded sum with a repair history.** Predict each intermediate sum, reject an overflowing prefix, compile a minimal program and explain one failure before changing it.

Before implementation, predict this discriminating case: **An input whose final mathematical sum fits while an intermediate prefix does not.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T01.01 — Algorithmic reasoning

A trace names the state before and after each transition. For a prefix sum, after k elements the accumulator equals the sum of the first k inputs; k advances toward n. This proves partial correctness and termination separately. Machine arithmetic adds a preservation condition: every accepted prefix must fit the result type. A final sum fitting does not rescue an overflowing earlier prefix; INT_MAX, 1, -1 has that defect. Check each addition before executing it, and stage bounded results before publishing output. A recursive call adds a live activation, so linear work need not mean constant auxiliary space.

Investigation: Trace a loop and recursive sum on [3, -1, 4]; count additions, iterations and maximum live calls, then state the invariant and decreasing measure. Reject a cancellation case whose intermediate prefix exceeds the declared bounds.

Misconception to resolve: Counting source lines does not establish time complexity, and an invariant alone does not establish termination or representable intermediate arithmetic.

Observable evidence: A state table, an induction argument, checked-prefix rejection evidence, and separate O(n) work / O(1) iterative / O(n) recursive stack claims. Evidence is developed in {ref}`PR-T01-01`.

### T01.02 — Representation prerequisites

A representation maps finite patterns to values. Eight binary digits encode 256 patterns, regardless of the chosen signed interpretation. Hexadecimal groups four bits, making masks visible. For flags, (x & mask) != 0 asks whether any selected bit is present, while (x & mask) == mask asks whether all are present.

Investigation: Convert decimal 173 to binary and hexadecimal, then build a truth table for two flags and compare any/all predicates.

Misconception to resolve: A mathematical integer has no fixed wrap point; a machine representation and its C operation rules must both be specified.

Observable evidence: Conversions checked by reconstruction and a complete truth table including neither, each and both flags. Evidence is developed in {ref}`PR-T01-01`.

### T01.03 — Basic C diagnostic

C expressions operate on objects with bounds, initialized values and sequencing rules. An array index at its length can form a one-past address but cannot read an element. A function parameter written as an array is adjusted to a pointer. Precedence groups operators; it does not schedule their evaluations.

Investigation: Write small examples of array traversal, a pointer parameter and nested calls; predict defined behavior, reject an uninitialized read, and rewrite a conflicting modification into separate statements.

Misconception to resolve: An observed result for an undefined expression is not an answer to a semantic prediction question.

Observable evidence: A prediction ledger classified as defined, unspecified or undefined, with repaired examples and new boundary cases. Evidence is developed in {ref}`PR-T01-02`.

### T01.04 — Execution model primer

Translation creates object files; linking combines definitions and runtime requirements; loading and startup create a running process. Registers and stack frames are implementation mechanisms, while an address space is a process-level mapping. Keep those mechanisms separate from the C abstract machine when explaining a local variable.

Investigation: Compile one source to an object, link it with a second source, run the executable and sketch one call with parameters, return value and live storage.

Misconception to resolve: An object file is not a running process, and a missing symbol is not a runtime bounds error.

Observable evidence: Four saved artifacts or observations and a failure-stage classification for syntax, missing definition, bad entry setup and invalid runtime input. Evidence is developed in {ref}`PR-T01-03`.

### T01.05 — Development workflow

A useful workflow preserves the command, tool version, input and output beside the change that produced them. Version control provides a replayable sequence, not a substitute for tests. A regression is a previously accepted case that fails after a change, so keep its input rather than only a screenshot.

Investigation: Create a small repository, make one deliberate defect and one fix, and rebuild each revision from a clean directory using explicit C17 flags.

Misconception to resolve: A successful IDE run does not describe how another person can reproduce the build.

Observable evidence: A command transcript, two meaningful commits and a clean-checkout replay of the failure and repair. Evidence is developed in {ref}`PR-T01-03`.

### T01.06 — Specification and test habits

Turn prose into a total contract: what inputs are allowed, what output is required, and what happens when limits are exceeded. For a sum parser, empty input, malformed tokens and overflow are different cases. Diagnose the smallest failing case first so that the repair addresses a cause rather than an accidental symptom.

Investigation: Specify a bounded list-sum tool, partition normal/boundary/invalid/empty cases, then preserve one minimized regression when deliberately breaking a limit check.

Misconception to resolve: Adding random tests without an oracle does not strengthen a vague requirement.

Observable evidence: An input partition table, exact status/output contracts and an independently computed expected sum. Evidence is developed in {ref}`PR-T01-03`.

## Mastery gate and feedback

Explain the loop invariant, the finite representation and every rejected C expression without relying on the last run. Rebuild from a clean checkout and diagnose a new injected off-by-one defect before editing. Pass the common rubric in {ref}`guide-assessment`; failed checks trigger only the relevant remediation, followed by a fresh case.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

After a delay, rebuild the bounded parser with a smaller capacity and reproduce its invariant without the earlier source. Keep the diagnostic results in the entry dossier; they establish the prerequisites used by later modules.
