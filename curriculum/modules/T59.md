# T59: Firmware lifecycle and recoverable updates

## Purpose and outcomes

Derive a firmware lifecycle from byte programming through trial boot, confirmation, rollback policy and dual-core quiescence. The original model exposes every persistence boundary without treating a hosted array as real flash.

## Entry check and remediation

Explain flash erase/program asymmetry and reconstruct a recoverable page-store commit. Distinguish reset, power loss, brownout and interrupted CPU execution before proposing an update protocol.

## Study sequence and teaching

### T59.01 — Flash programming as a constrained state change

Programming flash generally clears selected bits; restoring bits requires an erase operation. A RAM assignment hides this restriction. Validate the entire requested update before modeling a transaction, then split it explicitly to investigate interruption.

Prove admission catches every forbidden bit transition and prevents a partially modified prefix. Derive physical program-unit alignment and erase-sector dependencies separately.

Misconception and counterexample: Repair a model that silently ANDs an illegal request and reports success. Its resulting bytes differ from the requested image even without a reset or power interruption.

Investigation: Implement lc_program(dst,src,n) on live disjoint octet spans: reject if any new byte requests a0-to-1 transition, leaving all bytes unchanged; otherwise program with bitwise AND. n0 succeeds. This is an atomic admission model, not a claim that physical multi-byte programming is atomic.

Evidence: Replace whole-span admission by per-program-unit persistence and cut power after each unit; derive which metadata must stay uncommitted until image completion.

### T59.02 — Integrity without authenticity

A checksum detects selected accidental corruptions; an attacker who controls the payload can recompute it. Keep transport integrity, image authentication and anti-rollback as separate decisions.

Derive one byte update by polynomial division and state the initialization/reflection/finalization conventions. Explain collision possibility and absence of a secret authentication key.

Misconception and counterexample: A verifier omits the final complement and rejects valid images; another accepts attacker-recomputed CRC as a signature. Only the first defect is covered by numeric test anchors.

Investigation: Implement lc_crc using reflected CRC-32 polynomial0xedb88320, initial state0xffffffff and final complement, processing bytes low-bit first. No CRC library. Verify empty input and123456789, then construct an altered payload with a recomputed checksum and explain why it still lacks authorization.

Evidence: Add a separately verified signature API that returns an explicit verdict and key identifier; inject fail-open and stale-key responses without implementing production cryptography in this exercise.

### T59.03 — Authenticated image admission

Image length validation must happen before checksum/signature operations consume bytes. A signature over one extent cannot authorize another. Separate parsing from the trusted verifier and do not let a malformed header select arbitrary memory.

Specify exactly which bytes and metadata the trusted verifier authenticates; derive bounded extent arithmetic and the immutable authority for the rollback floor.

Misconception and counterexample: The intentionally faulty admission ignores a failed verifier verdict. Harmless success is selection of a synthetic unauthorized image; no real key or deployed bootloader is targeted.

Investigation: Implement lc_admit(length,slot_capacity,version,floor,signature_ok): accept only length1..capacity, version>=floor and signature_ok exactly1. The verifier verdict is injected by the harness; it is not derived from a learner-controlled flag in a real image. Return0 for all invalid requests before any slot selection.

Evidence: Introduce key rotation and a revoked signing key; show why a numerically newer version with a valid old-key signature may still be inadmissible.

### T59.04 — Trial boot, confirmation and rollback

A new image that starts once may fail before it can provide a service. Trial boot retains the old confirmed image until the new application explicitly confirms health. Reversion after a failed trial and rejection of security downgrades serve different goals.

Prove repeated unconfirmed resets eventually return to a known confirmed slot. Identify the exact persistence point before transferring control and the risk if it occurs afterward.

Misconception and counterexample: The faulty state machine retries the unconfirmed image forever, causing a boot loop. A watchdog reset alone cannot repair an incorrect persistent selection policy.

Investigation: Implement lc_select on LCBoot with active and trial slots0/1, confirmed and attempted booleans. If confirmed select active. If unconfirmed and not attempted, select trial and persist attempted1. On later unconfirmed reset select active. Reject invalid fields before output. The model treats attempted persistence as one atomic record; later projects remove that assumption.

Evidence: Require two-core health confirmation on H745 and inject one core failing after the other confirms; define a joint image-generation commit and recovery protocol.

### T59.05 — Redundant journal and torn commit records

A persistent record becomes authoritative only after all its fields are valid and its commit marker is complete. Redundancy helps only if the selection algorithm excludes torn or inconsistent candidates.

Enumerate power interruptions after each field write and before/after marker programming. State why the bitwise exclusive-or check is a synthetic torn-write control, not an authentication mechanism or robust error code.

Misconception and counterexample: Repair selection of an uncommitted newer record and ambiguous equal-generation records. Numerical sequence comparison is invalid after uncontrolled wrap.

Investigation: Implement lc_journal_select over two LCJournal records. A valid record has commit0xa5 and `check == (seq ^ value ^ 0x5a5a5a5a)`. Select the valid record with greatest nonwrapping seq; equal valid seq with unequal values is ambiguous and rejects. Return selected index through output only on success. Sequence exhaustion requires a migration policy, not wraparound.

Evidence: Replace the atomic marker with a multi-byte program unit that can tear; derive a coding/validation rule and prove at least one old or new valid record survives each allowed fault.

### T59.06 — Monotonic security floor

Display version and security epoch need not advance together. A monotonic floor prevents reintroducing an older vulnerable generation; moving it too early can make the fallback unbootable before the new image is confirmed.

Derive the invariant floor never decreases and analyze the confirmation/floor ordering under reset. State the threat model for storage tampering and what a RAM model cannot enforce.

Misconception and counterexample: The faulty update accepts a smaller floor from an otherwise valid image. A signed image is not permission to weaken anti-rollback policy.

Investigation: Implement lc_raise_floor(current,candidate,confirmed,out): require confirmed exactly1 and candidate>=current; publish candidate on success. Reject rollback or unconfirmed advancement transactionally. Compose it with boot confirmation and identify the trusted persistence needed in real firmware.

Evidence: Introduce a finite monotonic counter that reaches exhaustion; design a fail-closed recovery/key-rotation protocol without silently wrapping its security epoch.

### T59.07 — Dual-core update quiescence

A core reset invalidates assumptions about peer-owned buffers and cached metadata. A notification is not the payload and does not prove every old-generation operation completed. Update coordination needs generation and quiescence together.

Prove no old-generation peer can retain writable storage at update commit. Separate cache visibility, notification delivery and logical acknowledgement.

Misconception and counterexample: Repair acceptance of a stale acknowledgement after independent peer reboot. A memory barrier cannot repair the missing generation check.

Investigation: Implement lc_peer_ready(local_epoch,ack_epoch,outstanding) accepting only equal epochs and zero outstanding transfers. Use it in a two-core shutdown model: close admission, drain DMA/IPC owners, obtain an epoch-specific acknowledgement, then permit update. A stale acknowledgement must never unlock a new generation.

Evidence: Move shared metadata from noncacheable SRAM to cacheable SRAM; derive cache-line ownership/maintenance and repeat physical traces on the dedicated H745 board.

### T59.08 — Fault capture and recovery evidence

Fault records must survive a subsequent reset without being mistaken for fresh normal data. A partially written record cannot be trusted merely because a magic field was stored first. Capture itself must use bounded operations safe in the failure context.

Define record validity, persistence assumptions, reset-reason interpretation and ownership of storage during recovery; corrupted PC values must never become executable addresses.

Misconception and counterexample: Repair a record reader that accepts a committed but corrupted payload. A synthetic check detects only its modeled faults; physical retention and fault-entry register capture remain separate.

Investigation: Implement lc_capture_valid(words,n) for exactly4 uint32_t words [reason,pc,check,commit], `check = reason ^ pc ^ 0x9e3779b9` and commit0xc0de. Reject wrong count, invalid check or missing marker. Build a minimal firmware fault record producer that writes commit last and never allocates, then cut the model after every store.

Evidence: Add nested faults and a full fault log; choose preserve-first versus preserve-latest policy, prove bounded writes and assess what diagnostic information is lost.

F439 and H745 board profiles require their actual reference manual, silicon errata, linker map and board revision before a physical run. No flashing is performed by this batch. Real erase/program granularity, torn writes, cache maintenance, boot ROM interaction, watchdog reset and physical power-interruption evidence remain required on dedicated boards. Model success is not secure-boot certification. New hours are descriptive additions; accepted historical hours and receipts are immutable and do not limit study depth.
