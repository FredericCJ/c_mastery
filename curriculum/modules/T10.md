## Purpose and outcomes

Understand where Linux process entry becomes a C program. Build a deliberately restricted custom-entry executable and make every retained runtime/syscall service explicit. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce.

## Entry check and remediation

Explain program headers versus sections and the chosen call ABI. Decode a pointer table with explicit bounds. If that fails, repeat T09 ELF structure and T08 alignment; do not guess at entry stack addresses. Use {ref}`guide-entry` for diagnostic evidence and {ref}`guide-roadmap` for route choices. Domain numbers are coverage IDs, not an instruction to study them numerically.

## Component progression

**A Linux executable owning its entry.** Decode the real initial stack, establish the ABI before entering C and wrap only declared syscalls. Record partial progress and exit behavior without importing hosted startup assumptions.

Before implementation, predict this discriminating case: **A short write followed by interruption, where resending the original span duplicates bytes.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T10.01 — Kernel-to-userspace handoff

exec replaces a process image; the kernel chooses mappings and an entry address, possibly first entering the dynamic loader. No caller has pushed a normal C return address for the executable entry point.

Investigate: Trace kernel loader source and inspect PT_INTERP and e_entry in three variants. A common mistake is: _start is called exactly like main. Evidence: A handoff diagram assigns mappings, relocations, stack setup and language startup to their actual owners. Develop that evidence in [PR-T10-01](../projects/PR-T10-01.md).

### T10.02 — Initial process stack

The initial stack encodes argc, pointer arrays, terminators and an auxiliary vector according to the selected ABI. Pointer values refer to separately placed strings rather than an assumed packed layout.

Investigate: Decode the declared synthetic stack and inspect a debugger snapshot at entry. A common mistake is: argv strings must immediately follow their pointer table. Evidence: Decoded counts, terminators, alignment and auxv entries agree without reading beyond declared bounds. Develop that evidence in [PR-T10-01](../projects/PR-T10-01.md).

### T10.03 — Startup object families

CRT filenames describe toolchain conventions rather than one universal runtime interface. Startup fragments and compiler CRT support can change with static, PIE and shared configurations.

Investigate: Use driver output to inventory entry and initialization objects for each chosen build mode. A common mistake is: crt1.o always has the same role and content on every target. Evidence: A manifest associates each object with its provider, mode and observed symbol contribution. Develop that evidence in [PR-T10-01](../projects/PR-T10-01.md).

### T10.04 — C runtime initialization

Runtime startup prepares facilities that retained library calls may assume: TLS, canaries, environment, initialization hooks and loader state. Omitting one service narrows the supported application contract.

Investigate: Compare the inspected glibc and musl startup paths and name the services a custom entry will retain. A common mistake is: Calling a libc symbol from custom startup is safe because it links. Evidence: A dependency ledger follows every retained service to an initialization obligation or explicit exclusion. Develop that evidence in [PR-T10-02](../projects/PR-T10-02.md).

### T10.05 — Process termination

Returning from main lets the runtime choose process termination and cleanup; a raw Linux syscall follows kernel semantics. Thread exit and process-wide exit are distinct. A custom entry must not fall through into unknown bytes.

Investigate: Compare buffered output and handlers under hosted exit paths, then define a non-returning custom-entry finish path. A common mistake is: Every exit mechanism flushes streams and runs handlers. Evidence: The report distinguishes observed cleanup, declared syscall use and behavior of the impossible return path. Develop that evidence in [PR-T10-02](../projects/PR-T10-02.md).

### T10.06 — Syscall ABI

The x86-64 syscall convention changes the fourth argument register to r10 and destroys rcx/r11. Raw negative error values must be translated explicitly if a wrapper promises errno-style results.

Investigate: Map a six-argument synthetic call and check both success and negative-error decoding. A common mistake is: C-call register assignments can be reused unchanged for syscalls. Evidence: A register/clobber diagram and error table match the declared ABI, not an accidental successful run. Develop that evidence in [PR-T10-03](../projects/PR-T10-03.md).

### T10.07 — Minimal output and input

A byte operation reports progress, not a promise to transfer its full request. A wrapper must keep a cursor, recognize EOF and choose an operation-specific EINTR/would-block policy.

Investigate: Implement a write-all adapter and a bounded read loop over a scripted transfer backend. A common mistake is: Retrying every error from the beginning is safe. Evidence: Transferred bytes occur exactly once, and zero progress terminates visibly rather than spinning. Develop that evidence in [PR-T10-03](../projects/PR-T10-03.md).

### T10.08 — Minimal executable variants

Dynamic, static and static-PIE images select different relocation and startup mechanisms. Minimality is a supported-service claim plus a dependency audit, not a competition for smallest file.

Investigate: Build a custom-entry output program in a supported mode and compare its ELF metadata with hosted variants. A common mistake is: No PT_INTERP means the image needs no runtime support. Evidence: Undefined/resolved helpers, relocation records and entry assumptions form a complete declared audit boundary. Develop that evidence in [PR-T10-04](../projects/PR-T10-04.md).

### T10.09 — Runtime expansion

Adding parsing or formatting expands the dependency and failure surface. Keeping service layers separate makes each new effect observable.

Investigate: Add checked integer argument parsing and a caller-owned buffer to the minimal program in two audited increments. A common mistake is: One initial no-libc audit covers all future features. Evidence: Each increment has a dependency diff, storage budget and explicit supported/unsupported behavior. Develop that evidence in [PR-T10-04](../projects/PR-T10-04.md).

### T10.10 — Startup failure diagnosis

Before-main faults often belong to entry alignment, relocations or omitted initialization, not application logic. An entry breakpoint and minimal image reduce the number of possible owners.

Investigate: Inject one malformed stack/alignment assumption into a controlled variant and repair it with a recorded trace. A common mistake is: A missing main breakpoint proves main itself is defective. Evidence: The minimized reproduction identifies the earliest violated startup contract and the corrected handoff. Develop that evidence in [PR-T10-04](../projects/PR-T10-04.md).
