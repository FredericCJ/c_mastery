# T20: Modular and system architecture

## Purpose and outcomes

Choose architecture by hidden decisions, ownership and observable requirements. A portable deterministic core, explicit adapters and an execution model let the same behavior move between Linux and firmware without pretending the platforms are equivalent. Architecture decisions remain hypotheses tested under changing workloads and faults.

## Entry check and remediation

Use T18 contracts and T19 state/stream/dispatch mechanisms. Draw current dependencies before adding layers. For hardware-specific execution, complete the relevant embedded laboratory prerequisites before the physical adapter run; the architecture laboratory can implement and test the core/adapter protocol with a declared synthetic backend first.

## Study sequence and teaching

### T20.01 — Module boundaries

A module groups cohesive responsibility and owns a decision, representation or resource. Public interfaces should reveal required behavior while hiding unstable platform details. Dependency cycles make changes and tests harder because neither side can be understood independently.

Investigation: Draw a dependency graph for a record-processing service and reorganize it around format, storage and transport decisions.

Misconception to resolve: Processing stages alone do not necessarily make good module boundaries.

Observable evidence: An acyclic interface graph and a change-impact comparison with the original decomposition. Evidence is developed in {ref}`PR-T20-01`.

### T20.02 — Mechanism and policy

Mechanism supplies a capability; policy selects how or when it is used. A queue is mechanism, drop-oldest versus reject is policy. Allocation, clock, transport and scheduling choices should be explicit parameters or configuration, with their lifetime/effect contracts preserved.

Investigation: Inject clock/transport/overload policies and compare compile-time and runtime selection.

Misconception to resolve: Hard-coded deployment decisions inside a reusable algorithm are not free simplifications when variation is required.

Observable evidence: Policy alternatives sharing mechanism tests, plus dependency and cost comparisons. Evidence is developed in {ref}`PR-T20-01`.

### T20.03 — Functional core and effects

A functional core maps explicit state/input to state/output; effects sit at identifiable boundaries. This enables deterministic tests without pretending a fake device is a complete emulator. The returned effect request still needs a policy for ordering, failure and ownership.

Investigation: Implement a pure record/state transform that returns output/effect requests and drive it with recorded inputs.

Misconception to resolve: Pure decision logic does not eliminate the need to handle failed effects.

Observable evidence: Deterministic replay and separate adapter-failure tests. Evidence is developed in {ref}`PR-T20-01`.

### T20.04 — Ports and adapters

A port specifies semantics such as time units, partial progress, ownership and errors; adapters implement those semantics for a platform. Linux, board and test adapters can share signatures yet disagree on monotonicity, blocking or buffer retention. Conformance tests must expose those differences.

Investigation: Implement a hosted file adapter, a board-input adapter around the selected peripheral boundary and a synthetic test adapter; apply one conformance suite.

Misconception to resolve: Matching function pointer types is weaker than matching behavior.

Observable evidence: Adapter conformance records, declared environment limits and semantic equivalence at the core boundary. Evidence is developed in {ref}`PR-T20-01`.

### T20.05 — HAL, BSP, driver, and service layers

Register access belongs near a driver, board pin/clock wiring near BSP, and application meanings near a service. A vendor HAL can own substantial device mechanics, while a minimal layer owns only selected requirements. Keep register addresses, polarities and vendor types out of portable decisions.

Investigation: Map a sensor/indicator path through register, driver, board and service responsibilities, then compare vendor and minimal layer choices.

Misconception to resolve: A generic name on a register wrapper does not automatically create a useful HAL.

Observable evidence: A responsibility table, dependency direction and a portable-service header free of board layout. Evidence is developed in {ref}`PR-T20-02`.

### T20.06 — Execution architecture

Superloops, event loops, tasks and thread pools differ in scheduling, queueing, ownership and latency. Choose against arrival/service assumptions and resource ceilings. A queue changes where overload occurs; it does not remove overload. Separate analytical bounds from measured latency.

Investigation: Compare a bounded event loop with a polling superloop and a task/thread-pool design for the same arrival trace.

Misconception to resolve: More threads do not inherently provide lower latency or bounded work.

Observable evidence: Queue/ownership models, overload results and a justified execution choice. Evidence is developed in {ref}`PR-T20-03`.

### T20.07 — State-machine composition

Cooperating state machines need an event-order contract, not reliance on incidental callback order. Deferred events and cancellation require identity and retention limits. Hierarchy helps when shared transitions are real, but can obscure behavior if used only to reduce switch size.

Investigation: Compose acquisition and transport machines with explicit event ordering and stale-event rejection.

Misconception to resolve: Two locally correct machines can compose incorrectly when their event/lifetime assumptions disagree.

Observable evidence: Product/cooperation traces, cancellation cases and order-perturbation tests. Evidence is developed in {ref}`PR-T20-03`.

### T20.08 — Configuration architecture

Build-time features alter binaries and possibly ABI; runtime parameters alter active policy within a supported configuration. Validate both, give the configuration an identity and trace it to tests/artifacts. Avoid parallel sources of truth between generated headers and handwritten defaults.

Investigation: Generate a build identity and validate runtime capacity/time limits with versioned schemas.

Misconception to resolve: A config file being parseable does not mean its combination is supported.

Observable evidence: Invalid-combination tests and artifact-to-configuration traceability. Evidence is developed in {ref}`PR-T20-04`.

### T20.09 — Fault containment

Logical modules share memory and privilege unless a real boundary says otherwise. A bad adapter can corrupt a process despite clean interfaces. Specify failure propagation, degradation and restart, then distinguish contract-checking from memory isolation. Supervision needs its own failure/resource policy.

Investigation: Inject adapter errors and malformed results, define containment within the logical model and document what requires process/MPU isolation.

Misconception to resolve: An interface boundary is not a memory-protection boundary.

Observable evidence: Fault/degradation traces and a precise isolation limit. Evidence is developed in {ref}`PR-T20-04`.

### T20.10 — Architecture evaluation

Architecture evaluation records alternatives, assumptions and decision criteria against requirements. Trace latency, capacity, portability and recovery to concrete boundaries. Revisit the choice when workload or target changes instead of defending a diagram detached from evidence.

Investigation: Write a decision record comparing two decompositions/execution models and perturb one assumption.

Misconception to resolve: A visually tidy layering diagram does not establish fitness for the workload.

Observable evidence: Requirement-to-boundary/test mapping and a revised decision supported by the perturbation. Evidence is developed in {ref}`PR-T20-04`.

## Mastery gate and feedback

Defend the dependency graph, policy injection and execution model against a changed transport, overloaded arrival stream and failed adapter. Show identical portable-core semantics across adapters with honest physical/emulated/synthetic limits. Distinguish logical containment from protection.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

After a delay, replace one backend and alter the arrival rate. Update the decision record and resource ceilings, then repeat conformance and fault tests.
