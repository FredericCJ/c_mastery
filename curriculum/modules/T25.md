## Purpose and outcomes

Design sharing and lifetimes before synchronization. Protect invariants, explain ordering edges and validate concrete schedules without treating a race detector or fast benchmark as proof. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce.

## Entry check and remediation

Draw the lifetime of a work item from creator to last consumer and identify a shared ordinary write/read pair. Review T18 ownership, T02 sequencing, T03 lifetime and T05 C11 atomic facilities before choosing memory orders. Use {ref}`guide-entry` for diagnostic evidence and {ref}`guide-roadmap` for route choices. Domain numbers are coverage IDs, not an instruction to study them numerically.

### T25.01 — Thread lifecycle

Creating a thread acquires execution and join/detach obligations. A joinable handle needs one join owner; detached execution instead needs an independent lifetime protocol for shared arguments. C and POSIX provide distinct start/result/status interfaces, whose handles and callbacks must not be interchanged.

Interface mapping for the selected C17 lesson: C thread facilities are optional; record __STDC_NO_THREADS__ and actual header/library support separately from POSIX availability. The inspected N3096 text is a later-draft cross-check, not an exact C17 edition. C uses thrd_t, thrd_create(thrd_t*, int (*)(void*), void*) and thrd_join(thrd_t, int*): the start returns an int, creation returns thrd_success/thrd_nomem/thrd_error and joining reports the integer result. POSIX uses pthread_t, pthread_create(pthread_t*, const pthread_attr_t*, void* (*)(void*), void*) and pthread_join(pthread_t, void**): null attributes request defaults, the start returns a pointer, and creation/join return zero or an error number directly. Keep the result pointee live independently; do not diagnose a nonzero pthread result by assuming errno contains it. Neither family supplies a portable representation cast to the other. Never mix their creation/start/join contracts, and do not join a detached or already-joined thread. PR-T25-01 implements one POSIX worker and supplies this comparison plus availability probes, rather than two worker implementations.

Investigate: Implement one POSIX worker lifecycle with explicit result storage; compare C/POSIX signatures, statuses and support through the bounded mapping below and compile-only availability probes. A common mistake is: A function argument remains live until any thread using it finishes, or C and POSIX thread APIs are interchangeable. Evidence: A lifetime table and failure paths show every shared argument/handle owner; the separate interface/support table preserves integer versus pointer results, optional C17 facility support and direct POSIX error statuses. Develop that evidence in [PR-T25-01](../projects/PR-T25-01.md).
### T25.02 — Shared-state design

Reducing shared mutable state makes ordering obligations smaller. Immutable inputs, per-thread results and explicitly transferred work items need different ownership transitions.

Investigate: Partition a workload and transfer caller-owned work items through a bounded queue. A common mistake is: Every object visible to several threads needs a fine-grained lock. Evidence: The shared-state ledger contains only deliberate shared fields and names the last user of each item. Develop that evidence in [PR-T25-01](../projects/PR-T25-01.md).
### T25.03 — Mutexes and invariants

A mutex protects an invariant spanning several fields. Locking each assignment separately can expose a state that satisfies neither the old nor the new invariant; lock ordering prevents a different class of failure.

Investigate: Protect a balance/queue-count invariant and establish a global lock order. A common mistake is: Atomic field updates automatically preserve a compound invariant. Evidence: A forced interleaving finds the broken split-lock version, and initialization/destruction waits for all users. Develop that evidence in [PR-T25-02](../projects/PR-T25-02.md).
### T25.04 — Condition variables

A condition variable is a notification mechanism, while a predicate under the mutex decides whether work may proceed. Wait releases and reacquires the mutex; successful return can still leave the predicate false.

Investigate: Implement a bounded producer/consumer queue with while-predicate waits, shutdown and an absolute timeout policy. A common mistake is: One signal transfers ownership of a guaranteed item. Evidence: Spurious wake and signal-before-wait schedules both preserve progress and shutdown ownership. Develop that evidence in [PR-T25-02](../projects/PR-T25-02.md).
### T25.05 — Other synchronization primitives

A semaphore counts available permits; a barrier coordinates a phase; a read/write lock separates access classes; once initialization establishes one publication boundary. Each needs its own fairness and failure assumptions.

Investigate: Compare them on fixed traces and implement one phase or permit example. A common mistake is: The API with the fewest calls necessarily matches the invariant. Evidence: A primitive-selection table states required semantics and avoids assuming fairness from mutual exclusion. Develop that evidence in [PR-T25-02](../projects/PR-T25-02.md).
### T25.06 — Data races and happens-before

Happens-before combines sequencing with the relevant synchronization relation. Race freedom orders conflicting ordinary accesses, but it does not establish an application invariant or a valid lifetime.

Investigate: Draw an execution graph and identify one missing edge, then repair publication. A common mistake is: No detected data race proves the algorithm is correct. Evidence: Graph reachability, lifetime annotations and a separate logical invariant support the conclusion. Develop that evidence in [PR-T25-03](../projects/PR-T25-03.md).
### T25.07 — Atomic objects and operations

Atomic operations make one object’s accesses participate in an atomic model. The implementation may use helper calls or locks for widths/alignment it cannot lower natively.

Investigate: Initialize/load/store/RMW an atomic counter and inspect its target-specific lock-free result and object dependencies. A common mistake is: Every atomic type is lock-free on every target. Evidence: A target report states size/alignment, lock-free evidence and any out-of-line support. Develop that evidence in [PR-T25-03](../projects/PR-T25-03.md).
### T25.08 — Memory-order reasoning

Relaxed ordering preserves atomicity but does not publish unrelated data. A release followed by an acquire that observes its publication can order those data accesses; seq_cst adds a specified order, not universal synchronization magic.

Worked publication: writer W initializes ordinary payload, then release-stores ready=1; reader R acquire-loads the value 1 from that store before reading payload. The read-from link supplies the synchronization edge and orders those payload actions. An acquire load that reads the initial zero does not supply that edge, and a later mutation still needs its own ownership/ordering protocol.

Investigate: Implement and diagram one single-owner publication handoff, then analyze a relaxed-only counterexample. A common mistake is: A larger observed counter automatically orders every associated payload write. Evidence: The diagram names the exact read-from and synchronizes-with edge; consume/fence questions remain edition-sensitive. Develop that evidence in [PR-T25-03](../projects/PR-T25-03.md).
### T25.09 — Compare-exchange

Compare-exchange updates expected on failure, and weak operations may fail spuriously. Failure order applies to the load side and cannot request release behavior. Ownership transfers only at the successful transition.

Investigate: Implement a bounded CAS state transition with a scripted spurious failure backend. A common mistake is: A failed CAS leaves expected unchanged or transfers the object anyway. Evidence: Retry traces show expected-value updates, valid order pairs and exactly one ownership transfer. Develop that evidence in [PR-T25-03](../projects/PR-T25-03.md).
### T25.10 — Progress and scheduling hazards

Deadlock forms a wait cycle; livelock changes state without useful progress; starvation denies a particular participant service. Scheduler priorities can also invert effective access to a resource.

Investigate: Construct one trace for each hazard and repair a two-lock order violation. A common mistake is: Short critical sections prove fairness or bounded response. Evidence: A wait-for graph and participant-level progress accounting distinguish the guarantees actually supplied. Develop that evidence in [PR-T25-04](../projects/PR-T25-04.md).
### T25.11 — Cache and locality effects

Different variables can contend through one cache line even without a language-level race. Partitioning and batching can reduce traffic, but padding choices depend on the measured platform and object alignment.

Investigate: Compare adjacent versus separated per-thread counters after controlling useful work. A common mistake is: Cache-line separation changes the correctness memory model. Evidence: The measurement records layout, synchronization work and useful computation separately. Develop that evidence in [PR-T25-04](../projects/PR-T25-04.md).
### T25.12 — Concurrency validation

Race detectors observe supported executions and instrumentation; stress explores schedules; deterministic scheduling makes a failure repeatable. None replaces an ordering and lifetime argument.

Investigate: Run the queue through forced schedules and a supported race detector, preserving minimized failures. A common mistake is: A clean sanitizer run is a proof for all schedules. Evidence: The evidence bundle combines explicit invariants, schedule traces and bounded tool claims. Develop that evidence in [PR-T25-05](../projects/PR-T25-05.md).
