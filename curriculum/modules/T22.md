# T22: Production-quality libraries and repositories

## Purpose and outcomes

Turn a working component into a reviewable, consumable library. Organize source and contracts, trace requirements, test installation and FFI boundaries, pin dependencies, and release with reproducible evidence. Packaging and documentation are correctness work when they define what an independent consumer can safely assume.

## Entry check and remediation

Use T18 API contracts and T21 error/diagnostic evidence. Start from a small component already built in earlier modules, not an unrelated large repository. If an independent consumer cannot identify the public header, minimal build and ownership rules, repair those before adding release automation.

## Study sequence and teaching

### T22.01 — Repository organization

Separate public headers, private source, tests, examples, tools and target backends by their consumption role. A minimal supported build should not accidentally depend on the developer’s source tree or optional examples. Layout is useful when it makes boundaries obvious, not when it adds empty directories.

Investigation: Organize an earlier component and rebuild its smallest supported configuration from a clean checkout.

Misconception to resolve: A neat directory tree alone does not establish a usable library boundary.

Observable evidence: Clean-build instructions, public/private inventory and target-backend separation. Evidence is developed in {ref}`PR-T22-01`.

### T22.02 — Naming and readability

Names can encode units, roles and ownership, while small explicit control flow reduces hidden state. Complexity metrics highlight review candidates rather than dictate automatic rewrites. Prefer a name that explains a domain constraint over a short ambiguous name that needs repeated comments.

Investigation: Review one interface and one failure-heavy function, rename unclear units/ownership and simplify only with preserved contracts.

Misconception to resolve: A lower branch count is not automatically clearer or safer code.

Observable evidence: Before/after review examples and behavior-preserving regression evidence. Evidence is developed in {ref}`PR-T22-01`.

### T22.03 — Documentation

Doxygen comments document preconditions, postconditions and resource/lifetime rules; usage examples test the public story. Rationale comments explain nonobvious invariants. Generated API references show interface details, while architecture narratives explain why boundaries and policies exist.

Investigation: Document an API, compile its usage example and write a short architecture note.

Misconception to resolve: Generated documentation does not enforce a contract or replace design rationale.

Observable evidence: Rendered references, executable examples and a consumer-readable ownership/failure narrative. Evidence is developed in {ref}`PR-T22-01`.

### T22.04 — Requirements and traceability

Stable requirement and test IDs connect behavior to evidence. Trace through API contracts, implementation decisions and tests, detecting requirements with no test and tests with no stated purpose. Coverage of IDs is a navigation aid; test quality still needs independent review.

Investigation: Build a bidirectional traceability table and deliberately insert one orphan requirement and one orphan test.

Misconception to resolve: A complete spreadsheet can still point to weak tests that cannot expose a defect.

Observable evidence: Orphan detection and an example test strengthened to challenge its requirement. Evidence is developed in {ref}`PR-T22-02`.

### T22.05 — Library packaging

Packaging installs public headers and artifacts with consumable build targets or explicit commands. Static/shared choices affect dependency closure, symbol visibility and runtime lookup. Test consumption outside both source and build trees, including a clean installation prefix.

Investigation: Package the small library and compile an independent consumer against installed artifacts only.

Misconception to resolve: A successful in-tree example does not test the package interface.

Observable evidence: Install manifest, exported-target/command evidence and clean-prefix consumer execution. Evidence is developed in {ref}`PR-T22-02`.

### T22.06 — Compatibility and FFI

FFI crosses calling convention, layout, string/buffer and ownership boundaries. Define length units, encoding, allocator/release pairing and version-skew behavior. A foreign runtime cannot safely guess private structure layout or release memory with a different allocator.

Investigation: Expose a minimal C ABI and call it from a small independent Python ctypes consumer with explicit signatures.

Misconception to resolve: A function name being visible does not make arbitrary foreign signatures compatible.

Observable evidence: Layout/calling-contract evidence, buffer ownership tests and version-skew rejection. Evidence is developed in {ref}`PR-T22-03`.

### T22.07 — Dependency and licensing records

A dependency inventory pins direct/transitive sources, versions and applicable licenses. Source reuse carries obligations distinct from an independent educational implementation informed by concepts. Record uncertainty and actual license text identity; popularity or repository labels do not decide compatibility.

Investigation: Produce a dependency/provenance ledger and separate reused code from original mechanisms and external test oracles.

Misconception to resolve: A permissive-looking top-level license does not necessarily cover every bundled component.

Observable evidence: Pinned inventory, license notices and unresolved-obligation records tied to actual artifacts. Evidence is developed in {ref}`PR-T22-03`.

### T22.08 — Code review and source reading

Review follows invariants, ownership, failure and generated code, using call/data flow to navigate unfamiliar source. Form a hypothesis before modifying a legacy path and test it against evidence. Review findings should name a contract and reproducer rather than only style preference.

Investigation: Read one selected unfamiliar implementation, map its key flow and review your component with an invariant/failure checklist.

Misconception to resolve: Reading functions in file order is not always the fastest route to understanding behavior.

Observable evidence: Call/data-flow notes, a hypothesis/reproducer and actionable findings with dispositions. Evidence is developed in {ref}`PR-T22-04`.

### T22.09 — Refactoring and regression analysis

Characterization tests preserve current behavior before a structural change, while intentionally changed contracts need new expectations. Bisection narrows a regression to a change; minimized inputs reveal its mechanism. Refactoring is successful when improved structure and preserved behavior are both demonstrated.

Investigation: Refactor one failure path after characterization, insert a regression and locate/minimize it through version history.

Misconception to resolve: Passing only new tests cannot demonstrate old consumers retained their behavior.

Observable evidence: Before/after consumer checks, bisection evidence and a retained minimized regression. Evidence is developed in {ref}`PR-T22-04`.

### T22.10 — Release engineering

A release includes versioned binaries, matching symbols, build/configuration provenance, changes and known limits. Reproducibility can mean identical bytes under controlled inputs or explainable differences under declared toolchains; state the claim. Clean installation and rollback/replacement tests establish deployment behavior.

Investigation: Create two small releases, install each into isolated prefixes and test replacement plus migration.

Misconception to resolve: An archive filename and successful local build are not a release evidence chain.

Observable evidence: Artifact hashes, matching debug identifiers, clean-consumer runs and rollback/migration results. Evidence is developed in {ref}`PR-T22-04`.

## Mastery gate and feedback

Consume the installed library from an independent project and foreign-language harness, then review/refactor/release it without losing contracts. Detect traceability gaps and explain all dependency/license provenance. The release dossier must make a known limitation visible rather than quietly burying it in source.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

After a delay, rebuild from a clean clone with pinned inputs, replace one dependency or package mode and repeat the independent-consumer and migration tests.

## Environment and limits

Use the recorded hosted laboratory in {ref}`guide-laboratory` and the per-project boundary in {ref}`guide-profiles`. C17 is the baseline; edition/extension experiments are isolated and capability checked. Supplied fixture oracles validate mathematical or declared synthetic expectations. They do not execute the learner’s C, prove all language behavior or certify target hardware. Record actual commands, versions, observations and unresolved limits separately.
