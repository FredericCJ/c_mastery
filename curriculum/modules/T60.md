# T60: A C-subset compiler with original x86-64 and Thumb backends

## Purpose and outcomes

Implement a complete small compiler pipeline rather than delegate its lexer, parser, intermediate representation or backend to a compiler framework. The executable core compiles expressions used in unsigned cm_expr(unsigned x){return EXPR;} with decimal constants0..65535, x, parentheses, addition and multiplication. The expression notation assigns unsigned32 type to every literal; its corresponding ISO C source explicitly suffixes each literal with u. Unsuffixed ISO C expressions can have different promotions or signed-overflow behavior and are not claimed equivalent. This intentionally bounded subset has complete declared behavior; full C declarations, pointers, control-flow and function calls remain required transfer extensions, not claimed coverage.

## Entry check and remediation

Predict integer promotions and unsigned modulo arithmetic, parse precedence by hand, and derive a calling convention stack diagram. Diagnose a parser accepting an invalid trailing token before writing the compiler.

## Study sequence and teaching

### T60.01 — Bounded lexer with exact progress

Lexing must distinguish an invalid token from end of input and preserve diagnostic position. Decimal accumulation can overflow before the parser sees a value. The restricted language deliberately rejects spellings outside its grammar.

Derive the pre-multiply bound and exact consumed extent, including an unterminated span. Explain why end-of-input is a successful token distinct from rejection.

Misconception and counterexample: Repair overflow accepted through unchecked decimal accumulation and a scanner that consumes a bad byte before reporting its location.

Investigation: Implement cc_token over a nonterminated byte span. Skip ASCII space/newline/tab; recognize decimal0..65535(kind1), x(2), ((3), )(4), +(5), *(6), and end(0). Return1 on token/end,0 on invalid or overflow. On failure preserve offset/kind/value. On success set value0 except constants. Do not call strtol or a lexer library.

Evidence: Add hexadecimal constants and comments; distinguish preprocessing tokens from semantic tokens and preserve exact diagnostic spans without accepting partial malformed literals.

### T60.02 — Precedence parser and bounded syntax construction

Precedence determines the tree, not execution order of arbitrary C side effects. The subset has pure expressions, so its tree can be lowered directly to a stack intermediate representation while retaining an independent tree derivation.

Prove each parser level consumes its grammar production or rejects, and derive linear token work with bounded recursion. Explain why no partially constructed intermediate representation is publishable.

Misconception and counterexample: A parser accepts the valid prefix2 of2? and silently drops the error. Another implements2+3*x as(2+3)*x. Separate tokenization, grouping and lowering defects.

Investigation: Implement cc_parse from the declared expression grammar, generating postfix `CONST`/`ARG`/`ADD`/`MUL` followed by `RET`. Multiplication binds tighter than addition; parentheses override. Limit nesting to16 and intermediate representation capacity to caller storage. On failure used remains unchanged; partially written intermediate representation scratch is unspecified and must never be executed. Reject every unconsumed nonspace byte.

Evidence: Add subtraction and left associativity, then introduce a side-effecting call and state which source sequencing must be preserved rather than inferred from precedence.

### T60.03 — Subset type and arithmetic semantics

A small compiler must state a precise language rather than accidentally accept a poorly implemented large one. This subset uses a32-bit unsigned value type; wraparound is deliberate. Host int width must not silently change the evaluator semantics.

Derive modulo behavior independently of host signed overflow; identify absent signed conversions, floating-point rules and pointer semantics rather than pretending they are covered.

Misconception and counterexample: A backend replaces multiplication by addition or performs signed overflow in its evaluator. Passing small positive constants is insufficient evidence.

Investigation: Implement cc_binary(op,a,b,out) for op3 addition and4 multiplication modulo2^32, using uint64_t intermediates and explicit conversion. Reject other opcodes without changing output. Identify the host assumptions required by uint32_t/uint64_t and compare with the C unsigned-return wrapper.

Evidence: Add a signed32 type with explicit overflow diagnostics, usual arithmetic conversions and casts; construct a case where the unsigned and signed programs must differ.

### T60.04 — Typed intermediate representation and interpreter

An intermediate representation makes ownership, stack effects and failure behavior inspectable between parsing and machine code. It is not just an opcode list: a consumer needs bounded storage, valid operands and a terminal result convention.

Associate every opcode with input/output type and stack effect; prove validated execution cannot underflow/overflow its bounded stack and returns the expression denotation.

Misconception and counterexample: A nominal interpreter reports success without publishing the computed result, while another executes malformed intermediate representation before checking its stack effects.

Investigation: Implement cc_run over verified CCIns with a local64-entry uint32_t stack and one x argument. `CONST` and `ARG` push; `ADD`/`MUL` consume two and push one; `RET` must be last with exactly one value. Reject malformed streams and preserve output. Use cc_binary for semantic arithmetic, not native signed expressions.

Evidence: Add basic blocks and conditional branches; derive join-state type/stack compatibility and bound or explicitly budget loops before extending execution.

### T60.05 — Intermediate representation verification and resource bounds

A compiler verifier checks properties the backend otherwise assumes. Rejecting malformed intermediate representation is not optional merely because the current parser behaves correctly. Resource bounds belong to the contract and must be measured before emission.

Derive prefix-height and terminal-height conditions and peak stack bytes separately for the two backends. Explain the verifier assumptions that remain outside its scope.

Misconception and counterexample: The faulty verifier accepts executable instructions after `RET`. That can conceal malformed data and causes consumers to disagree about the authoritative program extent.

Investigation: Implement cc_validate for1..128 instructions, at most64 live stack values, constants<=65535, opcodes1..5, no underflow, and exactly one final `RET` with height1. Return peak depth only on success. Reject any operation after `RET` and any missing `RET`.

Evidence: Serialize intermediate representation to a bytecode file; add version, checked count arithmetic and canonical endianness, then fuzz parser and verifier independently.

### T60.06 — Original x86-64 code emission

A correct stack intermediate representation can be lowered to a simple leaf function without a register allocator. Every push must have a matching pop, and32-bit arithmetic must zero-extend the return value as required by the chosen interface.

Map each intermediate representation stack transition to emitted instructions, prove balanced machine stack and identify all clobbered registers. The textual anchor is weaker than assembling and executing the result.

Misconception and counterexample: The mutant lowers multiply as addition. A different faulty emitter uses64-bit multiply without the required unsigned32 truncation. Differential execution must expose the semantic mismatch.

Investigation: Implement cc_x86 emitting NUL-terminated GNU assembly for cm_expr(unsigned x) from valid intermediate representation using edi input, eax result, rcx temporary and64-bit push/pop storage. Use bounded staging so too-small output capacity leaves caller bytes unchanged. No LLVM, compiler library or template compiler may replace emission.

Evidence: Add an actual function call: preserve argument x across it, restore16-byte call alignment and compare caller-saved/callee-saved decisions under nested expressions.

### T60.07 — Original Thumb code emission

Thumb integer calls use r0 for the first argument and result. Reusing r0 for constants destroys the argument unless it has another live location. Return addresses and stack alignment are ABI state, not intermediate representation values.

Prove the private operand stack remains word-aligned and returns to its public8-byte boundary. Identify the Thumb-state return and why r3 would not survive a newly added call.

Misconception and counterexample: The backend omits argument preservation, so expressions that load x after a constant compute from the constant instead. A constant-only test cannot detect this.

Investigation: Implement cc_thumb emitting Thumb-2 GNU assembly using r3 to retain x, r0/r1 temporaries, word pushes/pops and bx lr. Constants fit movw. No nested calls or FP operations are supported. Stage output transactionally and preserve the exact same unsigned32 semantics as x86.

Evidence: Retarget Thumb-1 without movw or the same instruction set assumptions; synthesize constants, inspect helper dependencies and execute on the corresponding emulator CPU.

### T60.08 — Differential compiler validation and translation limits

Agreement between two implementations is evidence only when they do not share the same fault and the source has defined semantics. Random source generation must track grammar, type and resource constraints; arbitrary C text is a poor differential oracle.

Separate front-end correctness, intermediate representation semantics, backend correctness and target environment. Define the supported source subset before interpreting an oracle disagreement.

Misconception and counterexample: An integrated path perturbs an otherwise correct result; a shared parser-based expected value would reproduce some parser faults and miss them. Use independently generated trees.

Investigation: Implement cc_compile_eval(source,n,x,out) composing parser, verifier and interpreter with bounded128-instruction storage. Preserve output on any failure. Generate valid expression trees independently, render source and mathematical denotation, then compare interpreter and both emitted targets. Minimize a mismatch while retaining its semantic predicate.

Evidence: Add variables, conditionals, loops and function calls in separate increments with revised grammar, intermediate representation verifier and both backends; retain counterexamples at each boundary and state any still-unimplemented C construct.

## Environment and limits

Compiler implementation C17 hosted with bounded caller storage. Generated x86-64 SysV and Thumb AAPCS32 integer leaf functions have no runtime dependencies; assembler/linker are tools, not compiler-mechanism libraries. Execute emitted x86-64 code against an independently compiled C oracle, execute Thumb output in a dedicated emulator, and complete changed-condition extensions. Public intermediate representation anchors do not certify a general C compiler. New hours are descriptive additions; accepted historical hours and receipts are immutable and do not limit study depth.
