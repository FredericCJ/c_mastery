# T03: The object model, pointers, and memory correctness

## Purpose and outcomes

Build a model of objects before optimizing addresses. Every memory operation needs a live object, suitable bounds, alignment and permitted access type. The projects separate portable reasoning from implementation observations and make ownership transitions explicit, including relocation and failure.

## Entry check and remediation

Read a pointer-to-array declaration and a const-qualified view from T02. If a pointer proof relies only on an address looking plausible, draw the containing object and its lifetime first. Remediate with a three-element array, an escaped local and a successful/failed resize timeline.

## Component progression

**One owner, several borrowed views.** Draw each live object and admitted extent before taking an address. Track views through mutation, resize, return and release; distinguish address reuse from lifetime continuation.

Before implementation, predict this discriminating case: **A successful resize returning the same numerical address must still invalidate old aliases under its contract.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T03.01 — Storage duration and lifetime

Lifetime belongs to an object, not the variable holding its address. Automatic storage ends with its defining block; allocated storage ends at release or a successful relocation; static and thread storage have different boundaries. A pointer can remain in scope after its referent has ceased to exist.

Investigation: Draw owner/view timelines for an escaped local, a thread-local object and an allocated buffer; replace the escaped local with caller storage.

Misconception to resolve: Returning a pointer does not extend the lifetime of the local object it names.

Observable evidence: Timelines naming creation, legal uses and invalidation, plus a repaired interface with a stated owner. Evidence is developed in {ref}`PR-T03-01`.

### T03.02 — Object and value representations

An object representation includes value bits and possibly padding. Equal member values need not produce identical structure bytes. Character access can inspect bytes, but it does not make all bit patterns valid typed values. Edition-sensitive representation claims need the selected standard and target, not a screenshot of one machine.

Investigation: Inspect a structure through unsigned char, compare its members separately and mark which bytes the layout leaves unspecified.

Misconception to resolve: memcmp equality is not general semantic equality for structures or floating values.

Observable evidence: A field-wise equality check, byte observations labeled implementation-specific and a list of conclusions the bytes cannot support. Evidence is developed in {ref}`PR-T03-01`.

### T03.03 — Alignment

Alignment is a placement constraint of a type. Array spacing preserves element alignment when each element has the required size/alignment relationship. Casting a byte address changes its type expression, not its placement. Storage interfaces must state capacity and alignment independently.

Investigation: Compute alignment padding for synthetic addresses and implement a caller-storage interface that rejects insufficiently aligned storage using a target-documented check.

Misconception to resolve: A large enough byte buffer is not necessarily suitably aligned for every type.

Observable evidence: Checked padding arithmetic, alignment requirements from the compiler and negative placement cases without invalid dereferences. Evidence is developed in {ref}`PR-T03-01`.

### T03.04 — Arrays and subobjects

A two-dimensional array contains row-array subobjects. Physical adjacency does not authorize arbitrary pointer arithmetic through every neighboring subobject. A pointer to a row and a pointer to a pointer describe different representations; the latter requires actual pointer objects.

Investigation: Traverse a matrix using row pointers and bounded indices, then explain why flattening through a guessed int ** is invalid.

Misconception to resolve: Contiguous bytes do not erase the nested object boundaries used in pointer reasoning.

Observable evidence: A nested-object diagram and separate row/column bounds arguments, checked against the interface type. Evidence is developed in {ref}`PR-T03-02`.

### T03.05 — Pointer arithmetic

Pointer addition and subtraction are justified within one array object, with one-past permitted for formation and comparison but not dereference. Subtraction also needs a result representable in ptrdiff_t. Relational comparison of unrelated pointers does not become portable because their numeric addresses are ordered.

Investigation: Implement a range cursor and prove each index before forming a pointer; classify same-array subtraction and unrelated-address comparisons.

Misconception to resolve: One-past is a sentinel position, not an extra element.

Observable evidence: A formation/access table and a proof that each subtraction names the same array and has a representable result. Evidence is developed in {ref}`PR-T03-02`.

### T03.06 — Null and special pointer values

A null pointer is a distinguished pointer value; its byte representation need not be all zero. void * supports specified object-pointer conversions, while function pointers form a separate category. Integer round trips have implementation-defined and optional-type boundaries and do not independently establish a live object.

Investigation: Compare null initialization, object/void round trips and an optional uintptr_t experiment; isolate any platform function-pointer conversion as an extension.

Misconception to resolve: An integer containing an address is not a portable capability to access arbitrary storage.

Observable evidence: A conversion ledger labeled ISO, implementation-defined or extension, without dereferencing reconstructed invalid pointers. Evidence is developed in {ref}`PR-T03-02`.

### T03.07 — Allocated storage and effective type

Allocated storage has no declared type, so the selected rules for typed writes, copying and accesses matter. A raw-storage container needs more than element byte size: alignment, construction, access and destruction protocols must agree. Copying a valid representation into appropriate storage differs from casting arbitrary bytes to an unrelated type.

Investigation: Specify one typed raw-storage slot and compare initialization by a typed write and copying from a live typed object.

Misconception to resolve: malloc provides storage; it does not make every cast-based access compatible with the object model.

Observable evidence: An access-type timeline and a container contract naming type, alignment, initialization and release. Evidence is developed in {ref}`PR-T03-03`.

### T03.08 — Aliasing and type punning

Aliasing rules restrict accesses through incompatible lvalue types. Inspecting representations through character types and copying with memcpy have different contracts from dereferencing a cast pointer. Union member inspection has edition and representation caveats; it is not a universal decoder for external bytes.

Investigation: Compare a byte-copy representation experiment with a cast-based pun and an explicitly labeled compiler extension; keep invalid cases out of execution tests.

Misconception to resolve: Disabling an optimization can hide a defect without making the source portable.

Observable evidence: A permitted-access table, portable byte-copy alternative and build observations distinguished from language guarantees. Evidence is developed in {ref}`PR-T03-03`.

### T03.09 — restrict contracts

restrict is a promise about associations and accesses during an execution of a block, not a promise that all pointer values are globally different. If an object is modified through one restricted association, conflicting accesses must respect the rule. Establish those obligations before comparing optimized loops.

Investigation: Write copy/transform contracts for disjoint and overlapping ranges, and choose a non-restrict entry point when overlap is permitted.

Misconception to resolve: Different starting addresses can still name overlapping ranges, and restrict is not a runtime overlap check.

Observable evidence: Range diagrams, valid/invalid association examples and optimized-code comparisons only for the valid contract. Evidence is developed in {ref}`PR-T03-03`.

### T03.10 — Provenance and address identity

Numeric address identity and valid object access are distinct. Base-standard lifetime/bounds rules already prohibit many reconstructions; provenance proposals and implementation models add their own framing and remain separate authorities. An allocator or container must document any address-integer technique and its target assumptions.

Investigation: Create a claim ledger for same-address reuse after release, integer round trips and a container-recovery idiom; distinguish established rules from proposed models.

Misconception to resolve: An allocator reusing the same address does not restore a stale pointer’s former lifetime.

Observable evidence: A labeled authority table and a handle-based alternative that avoids relying on stale address identity. Evidence is developed in {ref}`PR-T03-03`.

### T03.11 — Indeterminate state

Missing initialization is a value-state defect, while padding can be unspecified even in an otherwise initialized aggregate. Reading an uninitialized scalar or pointer cannot be justified by a benign observed bit pattern. Diagnostics and dynamic tools detect selected paths; they do not replace the actual access rules.

Investigation: Audit a record with scalar, pointer and padding state; initialize required members and use member-wise checks instead of padding comparisons.

Misconception to resolve: Zeroing bytes and declaring every member initialized are different claims for general types.

Observable evidence: An initialization checklist, minimized defect and a checker limitation tied to the selected example. Evidence is developed in {ref}`PR-T03-04`.

### T03.12 — Flexible and variable-sized objects

A flexible member’s payload follows its fixed prefix, so allocation must check prefix plus count times element size before acquisition. sizeof omits the variable payload and layout may include padding. VLA bounds must be valid at evaluation; availability and size-expression details depend on edition/implementation.

Investigation: Implement checked flexible-payload sizing and compare it with caller pointer/length storage; make one bounded VLA experiment with a documented fallback.

Misconception to resolve: A flexible array is not a pointer member, and a negative VLA bound is not an allocation-failure mechanism.

Observable evidence: Overflow tests, layout evidence, a positive-bound policy and a representation comparison. Evidence is developed in {ref}`PR-T03-04`.

### T03.13 — Invalidation and relocation

Successful realloc invalidates the old allocation and its derived pointers, even if an address appears unchanged. Failure leaves the original allocation owned by the caller. A container mutation therefore needs explicit view/iterator invalidation rules; stable handles can decouple identity from location.

Investigation: Implement resize through a temporary owner, inject failure and compare pointer views with slot/generation handles across relocation.

Misconception to resolve: Assigning realloc directly to the sole owner can lose the allocation on failure.

Observable evidence: Success/failure lifetime diagrams, leak-free failure tests and a documented invalidation table. Evidence is developed in {ref}`PR-T03-04`.

### T03.14 — Memory correctness case studies

A repair should expose the violated obligation: lifetime, bounds, overlap, release count or representation. offsetof describes member position but does not legitimize recovering any arbitrary enclosing object; container-recovery idioms require the actual containing type/object and suitable qualifiers. One successful run cannot cover all undefined executions.

Investigation: Repair one use-after-free, double release, overlapping copy and escaped view; audit a container-recovery idiom without treating it as generic pointer magic.

Misconception to resolve: A sanitizer-free run is evidence about that run, not proof of all pointer accesses.

Observable evidence: Minimal reproducers, obligation-based repairs, retained regressions and an assumptions list for recovered containers. Evidence is developed in {ref}`PR-T03-05`.

## Mastery gate and feedback

Given an unfamiliar memory operation, identify the live object, subobject, permitted access type, alignment and invalidation event before executing it. Demonstrate independent failure injection for resize and explain why an apparently equal address does not rescue a stale view. All memory-critical rubric dimensions must pass.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

Rebuild a buffer using stable handles and smaller capacities after a delay. Compare what changes in the public lifetime contract and which object-model proofs remain the same.
