# T02: Declarations, types, expressions, and translation units

## Purpose and outcomes

Read C interfaces as precise types and definitions rather than suggestive syntax. The module connects declarators, scopes, conversions and sequencing to separate compilation. By its end, a header can be reviewed without seeing its implementation, and a diagnostic can be interpreted without confusing accepted source with valid execution.

## Entry check and remediation

From T01, predict a pointer parameter call and rebuild two sources. If declarators are hard to read, isolate one identifier and apply parentheses before outward pointer/array/function operators. Revisit finite representations before mixed signed arithmetic. These are targeted exercises, not a return to every entry project.

## Study sequence and teaching

### T02.01 — Declaration grammar

A declarator describes how its identifier participates in expressions: parentheses bind before postfix arrays/functions, and pointers are read outward. In int (*p)[4], dereferencing p produces an array of four int; in int *p[4], indexing p produces an int pointer. A typedef introduces an alias, not an object or a new incompatible type.

Investigation: Make a catalog of pointer-to-array, array-of-pointers and function-pointer declarations; annotate declarations versus definitions and rewrite one nested declaration using two typedefs.

Misconception to resolve: Reading every declaration simply right-to-left loses the grouping established by parentheses.

Observable evidence: Expression-based explanations, compilable examples and intermediate typedefs that preserve the original type. Evidence is developed in {ref}`PR-T02-01`.

### T02.02 — Type categories

Types constrain what operations are meaningful. An incomplete structure may be named through a pointer before its layout is available, but its size cannot yet be used. Arrays and structures are aggregates; pointers and arithmetic types are scalar. Compatibility is a language relationship across declarations, not equality of a display string.

Investigation: Build a matrix of complete/incomplete, object/function, scalar/aggregate examples and compare two declarations of the same external function.

Misconception to resolve: Two typedef names for int do not prevent meters from being passed where seconds were intended.

Observable evidence: A compatibility table and a wrapper-struct experiment that demonstrates stronger semantic separation. Evidence is developed in {ref}`PR-T02-01`.

### T02.03 — Scope and identifier namespaces

Visibility and namespace are separate axes. A tag and an ordinary identifier may share spelling, while two members in different structures live in their own member namespaces. A label has function scope; a parameter name in a prototype does not introduce a lasting file-scope object. Shadowing can change meaning without changing the text of a use.

Investigation: Trace an identifier through nested blocks, a prototype, a structure tag/member and a label; repair a collision by naming the role.

Misconception to resolve: A name visible in one namespace does not automatically collide with the same spelling in every other namespace.

Observable evidence: An annotated scope map and negative examples for actual collisions, distinguished from legal but confusing shadowing. Evidence is developed in {ref}`PR-T02-01`.

### T02.04 — Linkage and storage classes

Linkage joins declarations of the same entity across scopes or translation units; storage duration describes object lifetime. File-scope static normally gives internal linkage, while a block static object has no linkage but persistent storage. extern may declare an existing definition rather than allocate a fresh object. Thread storage adds a per-thread instance, not automatic synchronization.

Investigation: Inspect symbols from two objects and deliberately mismatch a public declaration; record extern, static, register and thread-storage examples under their selected edition.

Misconception to resolve: Static does not always mean a private file symbol, and external linkage does not guarantee compatible declarations.

Observable evidence: A declaration/linkage/storage-duration table, symbol evidence and a repaired cross-unit mismatch. Evidence is developed in {ref}`PR-T02-01`.

### T02.05 — Functions and calls

A complete prototype fixes parameter types for conversion and checking. An array parameter is adjusted to a pointer; sizeof that parameter measures the pointer type, not caller capacity. Function pointers preserve call signatures: a cast may suppress a diagnostic while leaving a call through an incompatible type undefined.

Investigation: Pass a row pointer to a matrix function and a context-bearing callback to a dispatcher; state signatures before writing bodies.

Misconception to resolve: A function-pointer cast is not an adapter for a different calling contract.

Observable evidence: Header compilation, compatible callback calls and a rejected cast-based adaptation with a real wrapper alternative. Evidence is developed in {ref}`PR-T02-01`.

### T02.06 — Variadic interfaces

A variadic callee has no automatic count or type information for unnamed arguments. Default promotions turn float into double and small integer types into promoted integer types. va_arg must request the matching promoted type. A copied va_list supports a second traversal only when made with va_copy and ended separately.

Investigation: Design a tagged/count convention for a statistics formatter, perform two passes using va_copy, and audit every call-site argument after promotion.

Misconception to resolve: A format string documents a protocol; it does not make a mismatched variadic type safe.

Observable evidence: A promotion ledger, empty-list case, two-pass output and explicit va_start/va_end ownership for each list. Evidence is developed in {ref}`PR-T02-02`.

### T02.07 — Expressions and conversions

Precedence and associativity build the expression tree; conversions choose the operand/result types; sequencing supplies order only where the rules say so. In a mixed comparison, a negative signed value may become a large unsigned value. An explicit cast records a conversion but cannot make an out-of-range input valid.

Investigation: Draw the tree and type each node for arithmetic, conditional and assignment examples; add a range-checked conversion boundary.

Misconception to resolve: Parentheses choose grouping, not a left-to-right execution schedule.

Observable evidence: A typed expression tree and a table showing both accepted conversions and rejected out-of-range values. Evidence is developed in {ref}`PR-T02-02`.

### T02.08 — Sequencing and side effects

Sequenced-before is an ordering relation. Unsequenced conflicting modifications, or a modification and unrelated value read of the same scalar, can make an expression undefined; indeterminately sequenced evaluations occur in one order or the other without interleaving. Function argument order remains unspecified in the C17 baseline, so separate effects from argument construction.

Investigation: List side effects for a nested-call example and replace a conflicting increment/read expression with explicit temporary values.

Misconception to resolve: An unspecified order is not automatically undefined; the conflict and the missing sequencing relation must both be established.

Observable evidence: A sequencing graph, classification under the selected edition and a repair whose result no longer depends on argument order. Evidence is developed in {ref}`PR-T02-02`.

### T02.09 — Initialization

Initialization creates an initial value under initialization rules; later assignment is a different operation. Static-duration objects receive implicit initialization. A partially initialized aggregate initializes omitted members as required, but this does not promise all padding bytes have a particular representation. A block-scope compound literal has an enclosing-block lifetime, not the next-statement lifetime.

Investigation: Compare automatic/static aggregates, designated initializers, assignment and a returned compound-literal pointer; identify the escaping-lifetime defect.

Misconception to resolve: Zero values do not imply an all-zero representation for every type, and a compound literal is not automatically heap storage.

Observable evidence: A member-value table and a lifetime diagram with a corrected owner for any escaped data. Evidence is developed in {ref}`PR-T02-03`.

### T02.10 — Qualifiers and interfaces

const int * permits changing the pointer while restricting mutation through it; int *const fixes that pointer object. Qualifying one pointer level does not justify unsafe conversions at another level. volatile describes accesses for implementation-defined purposes; restrict states an aliasing obligation for certain accesses. Neither is a lock.

Investigation: Design a read-only view and a mutable destination API, test qualifier-loss diagnostics, and document volatile/restrict claims separately.

Misconception to resolve: Const access does not make an object globally immutable, and volatile does not establish interthread synchronization.

Observable evidence: Const-correct signatures, negative qualifier tests and a contract that names each qualifier’s actual obligation. Evidence is developed in {ref}`PR-T02-03`.

### T02.11 — Inline and multi-file definitions

A header must have a deliberate definition strategy. static inline gives each translation unit its own internally linked definition; an external definition belongs in an implementation source. ISO inline and historical GNU inline conventions differ, so acceptance and emitted symbols depend on dialect and configuration.

Investigation: Build two consumers of a self-contained header, compare a static-inline helper with one external function, and inspect symbols in strict and declared GNU modes.

Misconception to resolve: Inline is not a command to eliminate calls, and a header function body need not provide the required external definition.

Observable evidence: Header-alone compilation, successful two-consumer linking and a dialect-tagged symbol table. Evidence is developed in {ref}`PR-T02-04`.

### T02.12 — Constraints and diagnostics

Syntax describes permitted token structure; constraints add translation-time requirements. A conforming implementation must issue a diagnostic for a constraint violation, yet may continue translation. Many undefined executions require no diagnostic. Negative tests therefore record expected rejection or diagnostic categories without overfitting compiler wording.

Investigation: Create one syntax error, one incompatible declaration and one runtime precondition violation; keep the last out of the runnable success suite.

Misconception to resolve: Warnings-as-errors improve local policy but do not convert successful compilation into a conformance proof.

Observable evidence: A three-category diagnostic ledger with the authority, actual messages and limitations of each test. Evidence is developed in {ref}`PR-T02-04`.

## Mastery gate and feedback

Review an unseen public header, predict adjusted parameter types and symbol ownership, and repair one incompatible callback without a cast. Defend a mixed-arithmetic conversion and a sequencing classification. The mastery dossier includes negative compilations, not just successful examples.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

After a delay, add an independent third consumer and replace one typedef alias with a wrapper type. Explain the interface changes and which diagnostics become stronger.
