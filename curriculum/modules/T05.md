# T05: Standards evolution, dialects, and portability

## Purpose and outcomes

Treat an edition or dialect as a versioned contract. Learn how C changed, how legacy code can be migrated, and how implementation capability is measured without claiming whole-edition conformance. The elective survey keeps proposals and extensions visible while preserving the portable baseline.

## Entry check and remediation

Use T02 declaration and diagnostic reasoning. Read {ref}`guide-standards` before experiments. If draft and publication identities are confused, write a short authority table before proceeding. C23 projects need support probes, not an assumption that a mode flag implements every library facility.

## Study sequence and teaching

### T05.01 — Standards and authority

Published editions, drafts, corrigenda and proposals answer different questions. A normative shall imposes a requirement in its applicable document; a note or rationale explains rather than automatically extending it. N3096 is a pre-publication C23 draft, while later working drafts can include changes beyond the published edition.

Investigation: Build an authority ledger for three claims, recording document identity, wording category, edition and implementation evidence.

Misconception to resolve: A recent committee PDF is not necessarily the published edition named by a compiler flag.

Observable evidence: Traceable claims with separate normative, explanatory and measured columns. Evidence is developed in {ref}`PR-T05-01`.

### T05.02 — C89 and C90 baseline

Legacy C89/C90 code often reflects earlier declaration placement, prototype habits and historical implicit declarations. Port the intended defined behavior, not accidental effects of an old compiler. Replace old-style definitions and incompatible callback casts with complete prototypes and real adapters.

Investigation: Modernize a small historical callback/declarator example and build both a declared legacy configuration and the portable baseline.

Misconception to resolve: Compiling an old example today does not prove its old assumptions remain valid.

Observable evidence: A before/after semantic ledger, explicit prototype changes and regression cases for intended behavior. Evidence is developed in {ref}`PR-T05-01`.

### T05.03 — C95 and internationalization

C95 internationalization facilities address wide characters, multibyte conversion and alternative tokens within implementation locales. They do not specify a portable UTF-8 interchange format or grapheme processing. Historical compatibility and modern Unicode requirements therefore need different contracts.

Investigation: Locate the amendment-era facility names through the standards guide and compare a locale-dependent wide-character conversion with a strict UTF-8 byte grammar.

Misconception to resolve: wchar_t is not universally a Unicode code point or a fixed-width interchange unit.

Observable evidence: A facility/context table and an explicit boundary between locale state and protocol bytes. Evidence is developed in {ref}`PR-T05-01`.

### T05.04 — C99 language and library changes

C99 brought familiar mechanisms such as mixed declarations, designated initialization, compound literals, restrict and variadic macros. VLA and inline details need edition/implementation context; integer and formatting facilities also have header/library obligations. A migration suite should isolate each change.

Investigation: Port a tiny C90-style record initializer and formatter to C99, adding cases for lifetime, integer formatting and macro invocation.

Misconception to resolve: New syntax availability does not remove object-lifetime or call-type obligations.

Observable evidence: Separate compile/link/run evidence for each feature and regressions that preserve the old intended behavior. Evidence is developed in {ref}`PR-T05-02`.

### T05.05 — C11 changes

C11 added atomics, thread facilities, alignment, generic selection and static assertions, while some facilities depend on implementation support. Parsing an atomic declaration, linking a helper and executing a thread are distinct capabilities. Concurrency semantics are developed in the systems route, not inferred from one accepted snippet.

Investigation: Probe alignment, _Generic and _Static_assert; inventory thread/atomic support and any runtime dependency without claiming a race proof.

Misconception to resolve: A compiler feature and a complete runtime library are separate layers.

Observable evidence: A capability matrix with language acceptance, headers, linking, runtime and declared limits. Evidence is developed in {ref}`PR-T05-02`.

### T05.06 — C17 and corrections

C17 follows the C11 line with corrections rather than a large new feature set. DR400 documents conflicting zero-size realloc practices and a C17-labeled resolution: the zero-size ownership outcome needs implementation documentation, while nonzero failure preserves the old allocation. The record also makes zero-size use obsolescent. Avoid this ambiguity in the component by defining empty-buffer release separately; C23 rules are a distinct edition question.

Investigation: Compare DR400’s original wording, final proposed corrigendum and C17 status, then revise a resize contract to require nonzero requests.

Misconception to resolve: Renaming C11 syntax as a C17 innovation obscures the reason for the corrective edition; a null zero-size result is not a portable nonzero-failure ownership rule.

Observable evidence: A precise correction analysis, ownership decision table and a limit on what the committee record establishes. Evidence is developed in {ref}`PR-T05-03`.

### T05.07 — C23 declaration and expression facilities

C23 adds facilities including nullptr, typeof forms, object type inference, object constexpr and bit-precise integers. Similar names in C++ do not import C++ semantics. Some familiar spellings also change their authority: in C17, bool comes from <stdbool.h>, alignas from <stdalign.h> and static_assert from <assert.h>, as macros for _Bool, _Alignas and _Static_assert. C23 makes bool, alignas and static_assert language keywords and retains the underscored alternate spellings. Test their language/header boundaries separately. Bit-precise widths, enum changes and constant-expression rules need explicit probes and ABI constraints.

Investigation: Create isolated positive/negative probes for each selected facility, including old/new keyword spellings, a width boundary and a misuse of object constexpr as if it were a constexpr function.

Misconception to resolve: A successful nominal snippet is not whole-C23 conformance and a header-defined macro in C17 is not evidence of a C23 keyword.

Observable evidence: Per-facility source, configuration, header/spelling distinction, expected constraints and actual compile/link/run results. Evidence is developed in {ref}`PR-T05-04`.

### T05.08 — C23 preprocessing and library facilities

C23 preprocessing and library changes cross several layers: __VA_OPT__ changes token construction, #embed introduces input dependencies, attributes have support semantics, and checked/bit-operation headers require the chosen implementation. Expanded freestanding provisions do not mean every target ships a complete hosted libc.

Investigation: Probe empty variadics, an embedded byte file and checked/bit operations; list build inputs and distinguish header existence from successful calls.

Misconception to resolve: A C23 dialect flag does not certify #embed, every attribute or the entire runtime.

Observable evidence: A feature/dependency matrix and repeatable unsupported-feature responses. Evidence is developed in {ref}`PR-T05-04`.

### T05.09 — Feature detection and migration

Edition macros are useful gates but cannot substitute for documented capability tests on partial implementations. Keep portability boundaries narrow: a baseline mechanism, a separately selected enhancement and a regression suite shared by both. Strict and extension dialects expose different assumptions.

Investigation: Build baseline and feature configurations in GCC and Clang when available, recording unavailable compilers rather than fabricating results.

Misconception to resolve: A compiler version number alone does not identify the selected target’s headers or ABI.

Observable evidence: Versioned capability tests, fallback behavior and a migration comparison with explicit extension use. Evidence is developed in {ref}`PR-T05-04`.

### T05.10 — Beyond-base-standard mechanisms

Technical reports, provenance specifications and cleanup proposals can illuminate future design, but their status is part of the claim. Extensions need a replacement strategy and versioned implementation evidence. The elective survey is bounded reading and experiment design, not an assertion that unadopted mechanisms are C23.

Investigation: Select one non-base mechanism, identify its exact authority/status, and describe a portable alternative before any extension experiment.

Misconception to resolve: A widely implemented extension is not automatically an adopted ISO facility.

Observable evidence: An authority/status record, isolated experiment or documented non-execution and a replacement plan. Evidence is developed in {ref}`PR-T05-05`.

This is an elective topic with a separate project gate.

## Mastery gate and feedback

Defend a feature claim by edition, document status and actual implementation layer. Port one legacy construct without a signature cast, and show baseline/feature configurations with honest unavailable entries. Core mastery excludes the elective implementation survey, which has its own evidence gate.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

Re-run the capability matrix after a toolchain upgrade. Revise only claims invalidated by evidence; keep published-edition identities and proposal statuses distinct.

## Environment and limits

Use the recorded hosted laboratory in {ref}`guide-laboratory` and the per-project boundary in {ref}`guide-profiles`. C17 is the baseline; edition/extension experiments are isolated and capability checked. Supplied fixture oracles validate mathematical or declared synthetic expectations. They do not execute the learner’s C, prove all language behavior or certify target hardware. Record actual commands, versions, observations and unresolved limits separately.
