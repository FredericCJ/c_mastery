# T66: Ownership, lifetime and cleanup protocols

## Purpose and outcomes

Build and explain the representations and state transitions below, preserving the imported artifact contracts. The complete exercises are core work; descriptive hours do not cap depth. Distinguish ISO semantics, implementation diagnostics, runtime checks and programmer discipline.

## Entry check and remediation

Derive ownership through a failed acquisition and a retained borrow using the prerequisite artifacts. If a cancellation request is mistaken for completion, revisit io.async before admitting a storage reuse argument.

## Environment and limits

Use profile A: hosted ISO C17 on Linux x86-64, with exact-width integers and C17 atomics. The [ownership laboratory contract](../../labs/ownership/CONTRACTS.md) defines the live-object, callback and aliasing preconditions. GCC and Clang debug, release, ASan/UBSan and separate TSan profiles are declared in labs/ownership/family.json; pthreads provide the concurrent test backend. CMake, Python and diagnostic runtimes are host verification tools. Implement ownership and allocation policy from the declared primitives, preserving the imported V4Allocator ABI; a library ownership implementation cannot replace this work.

The instrumented allocator has eight actual int32_t[16] backing arrays; an owner acquires at most three blocks and borrowing has four guard slots. Exhaustion, partial construction, serial retirement and release-once accounting are part of the contract. Dynamic borrowing and the non-atomic reference-count path require external serialization; the atomic count path still requires an already owned strong or weak reference, valid publication and separate payload synchronization. Cancellation requests do not permit storage reuse before quiescence. Ordinary C copying can duplicate an owning representation, raw aliases can bypass guards, and strong cycles remain retained.

This hosted evidence does not certify a strict freestanding image, lock-free lowering, all interleavings or physical targets. Audit emitted helpers and link dependencies before transferring to another runtime. Security experiments remain the original local two-tenant array with synthetic values; a cross-tenant write demonstrates only its stated integrity failure. Author campaigns do not establish learner mastery or delayed transfer, and exact published C17 wording remains an access gap.

## Study sequence and teaching

### T66.01 — Owning handles and the partial-initialization frontier

Derive the construction frontier invariant and distinguish acquired storage, initialized object state and published ownership; compare explicit C cleanup with automatic language destruction.

Lengths[1,2,3] with failure on take2 produce `NOMEM`, one release, zero live blocks and unchanged empty output. Failure on take1 releases nothing. Three successful takes publish count3; two destroy calls together perform exactly three releases. A zero middle count causes no allocator invocation.

Construction: Implement transactional three-resource construction and idempotent destruction using the accepted typed allocator callback ABI, proving which prefix is owned at each failure point. The full assessed work is {ref}`X-T66-001`.

Misconception: Releasing uninitialized members is not equivalent to cleaning a valid empty owner.

Evidence: Inject failure on each acquisition, reject zero and overflowing lengths before any callback, instrument release order and exactly-once counts, and test repeated destruction. Kill the omitted-rollback mutant. Extend the anchor with a callback trace that proves reverse order, not just equal release totals.

### T66.02 — Scoped cleanup, conditional undo and publication by swap

Explain when a cleanup stack is a resource protocol, when an undo log is a semantic rollback protocol, and why neither automatically reverses already published external effects.

Register digits1 `ALWAYS`,2 `ON_SUCCESS`,3 `ON_ERROR`. Failure produces trace31; success produces21; a second finish appends nothing. Publishing three staged blocks over three old blocks leaves exactly three live blocks and consumes the staged owner.

Construction: Implement conditional LIFO cleanup and publication-by-swap with explicit callback effects, stack capacity, transferred ownership and nonlocal-exit restrictions. The full assessed work is {ref}`X-T66-002`.

Misconception: A callback that can longjmp breaks the exactly-once argument unless another boundary owns the remaining stack.

Evidence: Enumerate all success/failure policy combinations through depth4 against an independent reversed-list filter, test capacity8/9 and callback reentrancy rejection, inject failure before every registration, and trace publication before old cleanup. Kill a mutant that executes every conditional cleanup.

### T66.03 — Move protocols, source poisoning and the limits of must-use diagnostics

A consuming operation transfers or ends the caller's ownership and leaves the source unusable for another consumption. Check the emptied source and the destination's release obligation separately; ordinary C structure assignment can still create an unauthorized duplicate of the same owning representation.

Separate ownership transfer, physical byte copying, source poisoning and diagnostic enforcement; explain why ISO C17 cannot prevent all implicit copies of this public struct.

After moving three blocks, destination.count=3 and source.count=0. Consuming the source returns `DEAD`; consuming the destination releases three blocks once; a second consume returns `DEAD`. A direct C assignment copying the original owner is a counterexample to an alleged static move-only guarantee.

Construction: Implement checked move/consume operations and an isolated diagnostic probe that intentionally ignores OW_MUST_USE, with extension-enabled and portable builds reported separately. The full assessed work is {ref}`X-T66-003`.

Misconception: A warning attribute is neither an ISO C17 guarantee nor proof that a result was used correctly.

Evidence: Test self-move, occupied destination, empty source, repeated consumption and allocator release counts. Reject the source-not-poisoned mutant. Compile a copied owner without consuming both copies: use it as a static counterexample, not an unbounded double-free experiment. Record whether GCC/Clang actually emit the ignored-result diagnostic.

### T66.04 — Runtime borrow tracking, range splitting and finite token identities

Derive reader/writer interval exclusion separately from pointer lifetime, then explain finite identity exhaustion and why a runtime token does not prevent illicit raw aliases.

A writer[0,8) blocks a reader[3,4). Splitting it at3 creates[0,3) and[3,8), invalidates the parent token and admits no gap or overlap. A writer[8,8) may coexist because it touches no element. A released token cannot release a later loan in the same slot.

Construction: Implement bounded acquire/release and transactional writer splitting with arithmetic-safe extent checks, generation retirement and an explicit guard ownership rule. The full assessed work is {ref}`X-T66-004`.

Misconception: A generation counter is finite; wraparound needs a lifetime bound or retirement policy.

Evidence: Use an independent finite-set intersection oracle for all small extents/ranges/read-write combinations, then test SIZE_MAX bounds and UINT32_MAX serial retirement. Exhaust the slot table before split and compare complete pre/post books and output canaries. Kill the conflict-check omission mutant; explain that reduced exhaustive checks do not prove arbitrary C lifetimes.

### T66.05 — Interior-mutability cells and guard escape boundaries

Interior mutability here means mutation through a shared interface mediated by an exclusive live guard. The guard protocol, not a const-qualified pointer or descriptive type name, enforces admitted access; its non-atomic bookkeeping still requires external serialization.

Explain how dynamic borrow guards permit controlled mutation through a shared interface without making const a global immutability or thread-safety guarantee.

Cell value9, old-output sentinel71 and one reader: replace(4) returns `BUSY`, leaves value9 and sentinel71. Read succeeds with9; write through that reader returns `INVALID`. After release, reading with the old token returns `STALE` and replace publishes4 while returning old9.

Construction: Implement guarded read/write and transactional replacement, composing the range guard protocol without bypassing its identity or exclusivity checks. The full assessed work is {ref}`X-T66-005`.

Misconception: Atomic storage of the payload does not make a non-atomic guard table safe.

Evidence: Test shared readers, exclusive writer, stale/released token, zero-length and partial-range tokens, failed replacement output canaries and every allowed guard-release order. Reject replacement that ignores an active guard. Analyze an escaped raw-pointer API as a contract counterexample rather than treating a clean sanitizer run as proof.

### T66.06 — Strong and weak ownership with atomic and non-atomic counts

The implicit weak reference retains the control block while any strong reference exists. The last strong release destroys the value and then drops that implicit retention; an explicit weak reference may keep the control block alive afterward, but cannot resurrect the destroyed value.

Prove the distinct value/control lifetimes, no-resurrection property and count-overflow behavior; distinguish reference-count synchronization from pointee synchronization and cycle collection.

Downgrade, retain, drop, drop yields strong0,weak1, one value destruction and no control reclamation. Upgrade now fails `DEAD`. Dropping the remaining weak reclaims the control once. Four threads each retain/drop5000 times while holding their own strong reference; after all owned strong references end, destruction occurs once, and a retained weak keeps the control available for a failed upgrade.

Construction: Implement strong/weak ownership twice, first under exclusion and then with C17 atomics, documenting initialization publication, owned-reference preconditions, callback effects and each memory-order edge. The full assessed work is {ref}`X-T66-006`.

Misconception: Making the count atomic does not make arbitrary payload mutations race-free.

Evidence: Trace every strong/weak boundary with an independent counter model, test maximum-count refusal, and reject omission of the implicit weak release. Run the actual four-thread anchor, separate TSan if available, GCC/Clang optimized and ASan/UBSan builds, inspect atomic lowering and report lock-free status. A quiet ThreadSanitizer run does not prove the memory-order argument or reclaim safety for fabricated references.

### T66.07 — Copy-on-write values with transactional detach

Copy-on-write detach first acquires and copies private backing, then changes the selected owner. Inject failure before publication and account for the staged buffer: both logical values must remain unchanged, while a unique owner needs no detach allocation.

Explain logical value independence, shared representation and detach cost; distinguish copy-on-write from a deep copy guarantee or automatically synchronized shared mutation.

Two references to[1,2,3], write index1=9, fail-at2: `NOMEM` and both logical values remain[1,2,3]. Retry succeeds with old[1,2,3], new[1,9,3], one reference each and two buffers. Dropping both releases both buffers. A unique write must leave allocator attempts unchanged.

Construction: Implement reference sharing, failure-preserving detach, unique mutation and last-owner release with explicit control-block and mutable-borrow lifetimes. The full assessed work is {ref}`X-T66-007`.

Misconception: A shared buffer plus reference count is not enough if clients can write its elements directly.

Evidence: Compare every owner value to independently copied Python lists across clone/write/drop traces, inject allocation failure at each detach, test index bounds and reference overflow, and count allocations/copies for unique versus shared mutation. Reject a mutant that writes shared backing in place. Check that a borrowed mutable alias cannot legally survive cloning.

### T66.08 — Thread affinity, address pinning and asynchronous quiescence

Separate address-sensitive validity, thread affinity, guard permission and asynchronous reclamation; explain why checked assertions are weaker than a language pinning guarantee.

Bind addressA/thread7, submit, cancel, attempt rebindB: `BUSY` and addressA remains retained. Complete then rebindB succeeds. Thread8 fails, and an address comparison using a separately live B reports `STALE`. Completion before submission or repeated completion is rejected.

Construction: Implement the address/thread/pending state machine and an explicit io.async adapter, identifying the actual event that permits storage reuse and the lifetime of every retained address. The full assessed work is {ref}`X-T66-008`.

Misconception: A caller-supplied thread number is a model input, not an authentication mechanism.

Evidence: Enumerate submit/cancel/complete/rebind traces with output-state canaries, include duplicate events and wrong-thread calls, and reject rebinding after cancellation while pending. Use only pointers to actual live test objects. Inspect a copied self-referential record to explain why its old internal address is wrong without dereferencing a dangling pointer.

### T66.09 — Adversarial allocation through the existing typed callback ABI

Allocation failure injection selects a particular acquisition attempt so every construction prefix can be tested for complete rollback. Allocation poisoning writes a diagnostic pattern during the instrumented backing store's lifetime transitions; recognizing that pattern can expose selected misuse, but does not authorize access through an expired borrow or protect against arbitrary aliases.

Distinguish allocator policy, backing storage, object initialization, protocol invalidation, poison diagnostics and actual memory-safety enforcement; explain instrumentation overflow and observer effects.

Take16 succeeds; fail-at2 makes take1 return null. Live1,peak1,attempts2. Release poisons all16 requested elements, gives live0/releases1; a second release only records an invalid-release event. Starting attempts at SIZE_MAX refuses allocation and leaves it at SIZE_MAX.

Construction: Implement fail-at-N, counting and poisoning as the accepted containers.array allocator callback adapter, preserving typed storage legality and explicit finite-capacity behavior. The full assessed work is {ref}`X-T66-009`.

Misconception: Poisoning catches selected mistakes; it cannot stop a client reading a still-addressable stale alias.

Evidence: Sweep every allocation failure point of frontier and COW workloads, fill all eight slots, test sizes0/16/17 and counter extrema, and verify requested-prefix poison plus release accounting. Compare the imported header byte for byte with the accepted ABI and reject the no-poison mutant. Integrate with the learner dynamic array and T65 error paths, measuring actual calls rather than inferring zero allocation from source spelling.

### T66.10 — A checked façade around a trusted core: bounded tenant-isolation failure

Derive the integer-wrap admission defect, attacker-controlled transition and exact violated authority property; distinguish a checked trusted-core boundary from whole-process memory safety.

With 32-bit unsigned, offset=UINT_MAX-3,count8,value7 passes the flawed wrapped check and changes tenant1 indices12..15 from99 to7. The repaired API returns `INVALID` and leaves both tenants unchanged. This is a bounded integrity-property violation in original teaching code, not an out-of-bounds C access.

Construction: Implement the subtraction-based boundary check, unchanged-on-failure behavior and an internal validated range record, preserving the simple core while documenting every remaining caller and same-process assumption. The full assessed work is {ref}`X-T66-010`.

Misconception: A private type name does not stop hostile code with arbitrary writes in the same address space.

Evidence: Run the local cross-tenant demonstration with synthetic canaries, compare flawed/repaired outcomes, enumerate all ordinary tenant/offset/count combinations around8 and test UINT_MAX wrap cases. Reject the flawed-check mutant by a normal semantic assertion. Explain why ASan may remain quiet: every actual array access is in bounds. Test mitigation regression without claiming arbitrary code execution or privilege escalation.
