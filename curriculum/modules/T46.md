# T46: A bounded language runtime from representation to execution

## Purpose and outcomes

Build a small compiler and virtual machine to make representation, machine state, verification, recursion and lifetime policies observable in original C. The same VM core executes on Linux, an emulated Cortex-M4 and the own-kernel route. The compiler remains hosted. Twelve milestones add 98 implementation/verification hours; reading, assessment and consolidation bring this family to 124 hours. Existing parsers, allocation reasoning and tests retain their original credit. This is a runtime specialization with deliberate limits, not a production language implementation.

## Entry check and remediation

Explain a typed value versus object bytes; trace a checked addition and a bounded stack; draw an owning/borrowed edge and an iterative graph traversal. Repair exactly the failed T03/T04/T14/T16/T18 gate. Hosted language work can proceed before firmware or kernel integration; PR-T46-11 requires the relevant startup/build foundations and keeps unavailable target evidence pending.

## Study sequence and teaching

### T46.01 — Values and a portable bytecode image

The first deliverable is a portable program image and value contract. Write the magic, function descriptors and code bytes individually; a C structure dump would inherit host padding and byte order. Decode a negative int32 via its mathematical unsigned representation before converting a representable result. Implement `cvm_encode` and `cvm_decode` for the bounded container first: check count, region lengths, contiguous descriptors and arity/local bounds, then publish the complete output. These raw codec functions deliberately do not accept instructions for execution. An unknown opcode can round-trip as bytes; the next checkpoint rejects it through the instruction verifier. Keep every output byte and reported length unchanged on failure. Value tags belong to the educational language: Boolean true is not an integer accepted by addition. Object references carry a slot and generation rather than exposing a native address.

Investigate: Hand-encode the bytes for a program returning 42, round-trip them without running the VM, then encode the INT32_MIN immediate as 00 00 00 80. Predict every truncation verdict. Keep a canary program as the destination and prove rejection does not publish a partially decoded image. Develop the artifact in {ref}`PR-T46-01`.

### T46.02 — Structural and stack-height verification

First scan each function interval to discover instruction boundaries and validate operand widths. Then validate all branch targets, including unreachable instructions. A bounded worklist propagates the operand-stack height from each function entry; every incoming edge at a join must agree. A return requires exactly one value relative to its frame. Direct-call arity is checked against the descriptor. Infinite loops with a balanced stack can verify: verification establishes this representation discipline, not termination. Locals initialization and tags remain runtime checks. Add `cvm_load` and `cvm_save` as verified wrappers around the earlier raw codec; publish only after `cvm_verify` succeeds. This milestone has no dispatch or compiler dependency.

Investigate: Break one valid image at a time: truncate an immediate, branch into an immediate, change a call arity, add a mismatched join or allow fallthrough beyond the function. Retain the first rejecting phase. Derive the finite worklist bound from code bytes rather than relying on unbounded recursion. Develop the artifact in {ref}`PR-T46-02`.

### T46.03 — Checked dispatch and operand stack

A dispatch iteration consumes exactly one unit of guest fuel and updates explicit machine state. Addition, subtraction and multiplication use a representable int64 intermediate; division rejects zero and INT32_MIN divided by -1 before the C operation. Integer division truncates toward zero. The operand stack is a caller-owned array with a checked push; verified per-function heights do not bound the sum of live caller temporaries and a callee. Results are written only on a successful return. A failed run can leave diagnostic VM state and must be reinitialized before independent replay.

Investigate: Trace two integer constants and ADD by hand. Compare nominal, extreme, wrong-tag and divide-by-zero cases. Keep a nearby valid boundary beside every rejection. Explain why changing overflow to wrapping would change the language rather than repair this implementation. Develop the artifact in {ref}`PR-T46-03`.

### T46.04 — Explicit call frames and recursion

A function is a descriptor; an invocation is a live frame. Arguments move from the caller operand stack into initialized callee locals. The callee has its own instruction position and saves the operand-stack base to restore on return. Repeated calls to the same function therefore have distinct local values and return histories. The VM loop itself never recursively invokes cvm_run. The sixteen-frame bound produces FRAME_LIMIT before constructing a seventeenth frame; this is a VM resource condition, not a claim about exhausting the C stack.

Investigate: Compile or hand-encode sum(5) and draw its six nested sum calls plus entry frame. Compare a finite result with unbounded self-calls stopped at the frame limit. Reject the same function invoked with the wrong number of arguments before running any instruction. Develop the artifact in {ref}`PR-T46-04`.

### T46.05 — A bounded hosted expression compiler

The hosted compiler uses a deliberately small prefix grammar to keep representation and semantic work visible. It collects top-level function signatures before compiling bodies, so direct forward calls have known arity. Within a function, lexical let bindings map names to bounded slots; the initializer sees the outer environment and the body sees the new binding. Shadowing is allowed, but a self-reference without an outer binding is rejected. Compiler recursion is limited to 64 expression levels and source spans to 4096 bytes. Neither the syntax nor checked numeric semantics claims C or Lox compatibility.

Investigate: Begin with literals and binary expressions, then introduce one lexical binding and shadow it. Predict (+ (let x 40 x) x) inside outer x=2. Preserve an existing program on unknown-name, extra-token, excessive-depth and out-of-range-literal failures. Test emitted bytecode separately from parser acceptance. Develop the artifact in {ref}`PR-T46-05`.

### T46.06 — Conditionals, mutation and bounded loops

Every expression leaves one value. An if consumes a Boolean condition and leaves exactly the chosen arm value; its two joins must agree. set updates an existing local and leaves the assigned value. do evaluates and discards its first expression before returning its second. while repeatedly checks a Boolean condition, discards each body value and returns nil when false. Emitted branch offsets are absolute offsets into the code region. These policies make stack equations simple enough to prove. A source loop is not trusted to terminate merely because it was compiled.

Investigate: Lower a local counter from zero to five and annotate each branch target and stack height. Change the condition to true and retain the fuel-stop evidence. Try an integer condition, unknown assignment target and branch into an immediate. Explain why equal output on one path cannot validate both arms. Develop the artifact in {ref}`PR-T46-06`.

### T46.07 — Arena phase and object handles

Start with sixteen fixed pair slots and arena mode. Each successful allocation owns a new generation; the seventeenth allocation fails even if previous objects are unreachable. A pair holds two tagged values, enabling a small object graph without a string subsystem or external allocation. A reference is valid only when its slot is occupied and its generation matches. Generation values never wrap: an exhausted-generation slot is retired. Reset destroys the entire VM lifetime; callers must discard all prior references, because generation checks do not provide identity across separate VM initializations.

Investigate: Allocate all sixteen pairs and retain the exact failure of the seventeenth request. Read both fields of a valid handle, then distinguish wrong-tag and stale-generation errors. Draw which handles a caller must release or re-root before enabling collection. Develop the artifact in {ref}`PR-T46-07`.

### T46.08 — Nonmoving mark-sweep and temporary roots

The root set consists of live operand-stack values, initialized locals in live frames and an explicit host/temporary-root stack. Marking visits each object at most once, so cycles do not require recursive C calls. Sweep begins only after complete marking and a reserved sweep budget; a budget failure cannot free an object that marking did not finish examining. The critical allocation experiment fills the heap, keeps a child only in a C temporary, then constructs its parent. cvm_pair must temporarily root both operands before collection. A returned object held outside the VM must be pushed as a root before a subsequent allocation can collect it.

Investigate: Compare rooted and unrooted cycles; retain slot/generation traces. Fill the heap with garbage and allocate a parent around a temporary child. Kill the supplied missing-root mutant with this case. Force GC budget exhaustion and prove that failed collection did not sweep existing objects. The collector is nonmoving and stop-the-world, not a real-time collector. Develop the artifact in {ref}`PR-T46-08`.

### T46.09 — Guest, collection and host budgets

Guest fuel counts dispatched instructions, GC budget counts root/edge inspections and the fixed sweep pass, and host budget counts callback invocations. The ledgers are independent: an infinite loop consumes fuel while leaving host and GC budgets unchanged if it performs neither activity. These units are educational accounting, not CPU cycles or wall-clock deadlines. Verification and compilation have their own finite size bounds. The embedding adapter must bound blocking work separately and cannot reenter the same VM from a callback. Resource refusal is a supported result and does not demonstrate application correctness.

Investigate: Measure all three counters before and after a finite run, infinite loop, collection and callback. Exhaust one budget at a time. Present a callback that could block as a counterexample to claiming a time guarantee from fuel. Keep the actual host deadline policy in the adapter contract. Develop the artifact in {ref}`PR-T46-09`.

### T46.10 — Embedding and bounded store services

The embedding boundary accepts a numeric service ID and int32 argument, returning an int32 or error. It is intentionally narrower than a native FFI. The store adapter owns a pre-opened store and supports two fixed services: commit vm-result and read it. It encodes the integer as four explicit little-endian bytes. A failed commit may be indeterminate; the VM reports HOST_ERROR and the caller must recover the store rather than blindly replay a write. The host budget is charged before invocation. Store correctness belongs to its own tested contract and is not inferred from a successful VM response.

Investigate: First use the deterministic echo callback and test denied budget, absent service and adapter failure. Then run the separate store integration with an accepted store implementation. Record which layer owns transaction recovery and what HOST_ERROR can and cannot establish about durable bytes. Develop the artifact in {ref}`PR-T46-10`.

### T46.11 — One VM core across Linux, Thumb and a kernel

Only the C VM core crosses the target boundary. The hosted compiler produces bytecode offline; the freestanding target loads and verifies that same representation. The supplied Thumb route uses QEMU MPS2 AN386 Cortex-M4 with explicit vectors, reset initialization, memory placement and semihosted reporting. It does not model the STM32F439 board or validate physical bus timing. The own-kernel route links the same core with the kernel user ABI and its audited support helpers. Object compatibility and a target compile are useful gates, but actual target execution is a separate observation.

Investigate: Run the portable image on Linux, then the Thumb script and the own-kernel integration. Record source/image hashes and actual exit/transcript. Inspect undefined helpers and the link map. A missing emulator or board keeps its corresponding evidence pending rather than replacing it with a synthetic successful result. Develop the artifact in {ref}`PR-T46-11`.

### T46.12 — Runtime defense, mutation and delayed transfer

Freeze a program, bytecode image, build identity and result before defending the design. Explain one accepted program and one rejected program at every boundary: source, format, verifier, VM types/resources and host services. Visible tests and assessor mutations are guided regression evidence; they are not a blind diagnosis assessment. A separate reviewer can supply an unrevealed malformed image or root-lifetime defect. In solo study, state what you already know. Revisit after at least a week with smaller capacities or a new bounded host service and regenerate only the affected evidence.

Investigate: Submit a source-to-result diagram and one minimized counterexample per boundary. Compare GCC and Clang, debug and optimized builds, then appropriate sanitizer evidence. Retain all pending physical/kernel claims explicitly. A green tiny example does not close every topic objective or prove isolation against hostile native code. Develop the artifact in {ref}`PR-T46-12`.

Use six delayed hours for two changed-condition defenses. ## Environment and limits

CVM1 has eight functions, 1024 code bytes, 64 operand slots, sixteen frames, eight locals per frame, sixteen pair objects and eight explicit roots. The compiler accepts at most 4096 source bytes and 64 nested expression levels. No required closures, JIT, moving/generational collector, native FFI, floating point, arbitrary object mutation or production sandbox is claimed. Native callback correctness and bounded I/O remain embedding obligations. The compiler uses hosted string operations; the core requires no libc calls in source, while actual compiler helpers are audited per target.
