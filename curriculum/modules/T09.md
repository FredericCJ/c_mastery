## Purpose and outcomes

Read a binary as a set of linking/loading promises. Trace symbols, relocations, dynamic/TLS metadata and layout into a declared dependency and memory budget before converting or deploying an image. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce.

## Entry check and remediation

Distinguish an object from an executable and identify a symbol reference in disassembly. If code addresses and file offsets are confused, redo the T08 address trace and the T07 explicit link. Use {ref}`guide-entry` for diagnostic evidence and {ref}`guide-roadmap` for route choices. Domain numbers are coverage IDs, not an instruction to study them numerically.

## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T09.01 — ELF structure

ELF sections organize link-time information; program headers organize loading. A zero-fill segment can require RAM without storing those zero bytes in the file.

Investigate: Decode a synthetic header table and then compare a relocatable object, executable and shared object. A common mistake is: The section table alone specifies the runtime mappings. Evidence: The report separately totals file bytes, load-image bytes and memory bytes. Develop that evidence in [PR-T09-01](../projects/PR-T09-01.md).
### T09.02 — Symbols and binding

Binding determines which definitions can satisfy references. Local names stay within an object; weak definitions have lower precedence; undefined references need resolution. Common symbols depend on compiler conventions.

Investigate: Link two objects and an archive with controlled duplicate and weak symbols. A common mistake is: Identical C names always denote one link-time entity. Evidence: A symbol-resolution ledger explains every chosen definition and every diagnosed conflict. Develop that evidence in [PR-T09-01](../projects/PR-T09-01.md).
### T09.03 — Static archives

An archive is searched for members needed by unresolved references at the relevant point in the link. Its existence on the command line does not force every member into the result.

Investigate: Reverse archive order, then use a justified grouping experiment and inspect the resulting map. A common mistake is: Static libraries are linked wholesale by default. Evidence: The extracted-member set agrees with a hand-traced unresolved-symbol set. Develop that evidence in [PR-T09-01](../projects/PR-T09-01.md).
### T09.04 — Relocations

Relocation records identify unfinished address computations. For a simplified PC-relative field, the linker applies S+A−P; the result must fit the relocation width.

Worked relocation: for S=4096, A=-4 and P=4112, S+A-P=-20. That fits signed eight bits (-128 through 127) and is represented by low byte 0xEC. With S=4352 the displacement is 236: low byte 0xEC still appears, but the relocation must reject it because 236 exceeds the signed range. Byte matching alone would accept the wrong result.

Investigate: Calculate a positive, negative and overflowing relocation, then locate one real relocation and its final bytes. A common mistake is: A relocation contains only an absolute address. Evidence: Hand arithmetic, width checks and the binary report agree; overflow is rejected rather than truncated silently. Develop that evidence in [PR-T09-02](../projects/PR-T09-02.md).
### T09.05 — Position-independent code

PIC forms addresses without assuming one fixed load address. PIE applies position independence to an executable; static and dynamic loading remain separate dimensions.

Investigate: Build the same address-taking example as non-PIE, PIE and a shared object and identify its address-formation mechanisms. A common mistake is: PIC and dynamic linking mean the same thing. Evidence: Relocations and disassembly explain which addresses remain load-dependent. Develop that evidence in [PR-T09-02](../projects/PR-T09-02.md).
### T09.06 — Dynamic linking

The interpreter loads dependencies and resolves symbols using an implementation-defined policy documented for the chosen loader. GOT/PLT mechanisms can defer some bindings, but not every environment uses lazy binding.

Investigate: Compare eager and lazy modes for a trusted tiny executable and trace one interposed symbol. A common mistake is: The first library with a familiar filename is necessarily the selected dependency. Evidence: A dependency-search explanation matches the recorded loader paths and binding observations. Develop that evidence in [PR-T09-03](../projects/PR-T09-03.md).
### T09.07 — TLS and initialization metadata

TLS and initializer arrays are metadata that require runtime code. Merely placing a pointer in an init section does not call it; each thread requires an appropriate TLS instance.

Investigate: Locate TLS and initializer sections, then trace the code that processes one initializer. A common mistake is: Linker metadata performs initialization by itself. Evidence: The report identifies producer metadata, runtime consumer and lifetime of each instance. Develop that evidence in [PR-T09-03](../projects/PR-T09-03.md).
### T09.08 — Linker-script fundamentals

A linker script maps input sections into output addresses and can distinguish load address from execution address. A RAM-resident initialized object may have bytes stored in a flash load image.

Investigate: Describe a text/data/zero-fill layout with region capacities and exported boundaries, and calculate the copy interval. A common mistake is: Every object has one address meaningful at every stage. Evidence: A region ledger distinguishes VMA, LMA, file offset and initialization responsibility. Develop that evidence in [PR-T09-04](../projects/PR-T09-04.md).
### T09.09 — Retention and garbage collection

Garbage collection follows linker reachability, which can miss tables consumed indirectly. KEEP preserves selected sections but archive extraction remains a separate decision.

Investigate: Create a registration table and observe its disappearance, then justify the smallest retention rule. A common mistake is: KEEP automatically pulls every archive member into the image. Evidence: The map shows the expected retained table and excludes a deliberately unused function. Develop that evidence in [PR-T09-04](../projects/PR-T09-04.md).
### T09.10 — Memory and image budgets

Image budgets count different resources: text/constant bytes, stored initial data, RAM data and zero-fill. Alignment holes and metadata may dominate a tiny example.

Investigate: Calculate budgets from a declared map and add linker assertions for one region limit. A common mistake is: Small file size proves low runtime RAM use. Evidence: A failing over-budget case is caught at link time and each byte category is attributed. Develop that evidence in [PR-T09-04](../projects/PR-T09-04.md).
### T09.11 — ABI evolution

Source compatibility allows recompilation; binary compatibility must preserve the machine-visible interface. Visibility and symbol versioning constrain what clients can depend on.

Investigate: Change a public structure or function contract in a toy library and classify old-client outcomes. A common mistake is: An unchanged function name guarantees old binaries work. Evidence: A compatibility matrix distinguishes source rebuild success, binary linkage and semantic agreement. Develop that evidence in [PR-T09-03](../projects/PR-T09-03.md).
### T09.12 — Binary transformations

Converting ELF to a raw image discards structure and often debug information. Address correlation, build IDs and checksum placement must be preserved in separate artifacts or declared transforms.

Investigate: Inspect a synthetic sparse image and define raw/HEX outputs plus a retained debug companion. A common mistake is: Stripping is a harmless final cleanup with no traceability effect. Evidence: An address-to-source and checksum ledger explains every post-link transformation. Develop that evidence in [PR-T09-05](../projects/PR-T09-05.md).
