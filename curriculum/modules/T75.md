# T75: Flow control and resilient services

## Purpose and outcomes

Construct time, admission, load and effect-identity mechanisms in C17, then compose them with the accepted local service artifacts. Cancelled waiting, completed work and rolled-back effects are distinct facts. The parent deadline, outstanding ownership and resource budget must remain visible across every layer.

## Entry check and remediation

Reconstruct io.deadline, io.async, conc.channel and generation-handle contracts. Explain a late completion after timeout, a full-channel retry, and a duplicate effect after lost acknowledgement. Remediate checked arithmetic in X-T04-001, lifetime in X-T03-005 and modular versus nonwrapping time in X-T30-002.

## Study sequence and teaching

### T75.01 — Cancellation trees and budgets across clock domains

The remaining budget is the inherited allowance minus elapsed work and explicitly modeled propagation costs, not a fresh full timeout at every hop. A cancellation acknowledgement must establish the borrower's terminal release event before scope storage is reclaimed; the atomic cancellation flag supplies only the request.

A request deadline bounds the shared request budget across nested operations; a timeout limits one local wait. Neither proves that remote work stopped. C has no automatic context-lifetime or deadline-propagation rule; both need explicit ownership and clock assumptions.

Implement RZScope init/cancel/check/remaining over immutable parent links, atomic cancellation flags and injected uint64 ticks. Limit depth to8, choose the earliest inherited deadline, and reject unrepresentable standalone addition. Then implement a request-budget envelope for two simulated hosts with unrelated clock origins: it carries remaining duration, never a raw local absolute deadline. Deduct local elapsed work and state the transport-delay assumption. Add a completion acknowledgement owned by each asynchronous borrower, retaining scope storage until all acknowledgements arrive.

Parent created at10 with budget10 expires20. A child at13 asking100 still expires20; at19 remaining is1 and at20 it is expired. Cancelling the parent makes the child `CANCELLED`. No borrowed storage becomes reclaimable solely because cancellation was requested.

Required evidence: {ref}`X-T75-001` assesses each objective separately. Exhaust now0–16/budget0–16 across parent/child creation and every cancellation/finish permutation for two borrowers. Use mathematical min and arbitrary-precision addition as an oracle. Test UINT64_MAX edges and chain depth8/9. Compare Go Context documented cancellation and deadline behavior with the C runtime checks and caller lifetime discipline; never infer acknowledgement from an atomic flag.

### T75.02 — Five overload policies and bounded pending producers

In the required readiness adapter, define flow credit as permission to occupy a bounded amount of receiver capacity and state exactly when that credit returns. The four-slot queue alone does not supply this protocol or bound producer-held offers; credit return also does not acknowledge an application effect.

A fixed queue does not bound memory if arbitrary producers wait while retaining payloads. Overload policy changes the service contract and cannot be compared using throughput alone.

Implement RZQueue/RZOffer with four copied unsigned messages and `BLOCK`, `REJECT`, `DROP`, `OVERWRITE` and `DEGRADE` policies exactly as CONTRACTS.md specifies. A blocked offer is a retained operation to retry, not a hidden sleeping thread. Degrade coalesces newest by max and reports reduced semantics. Implement rz_forward using your actual T73 nonblocking channel send and remove the head only on acceptance. Then add a bounded two-producer readiness adapter that registers before checking readiness, acknowledges cancellation and never creates an unbounded waiting-producer list.

Queue[1,2,3,4] plus DROP9 remains[1,2,3,4]; OVERWRITE9 becomes[2,3,4,9]; DEGRADE10 changes newest to10 and reports `DEGRADED`. `BLOCK` retains pending ownership. Expiry before a later retry terminates that offer without enqueuing it. A full imported channel leaves the local head in place.

Required evidence: {ref}`X-T75-002` assesses each objective separately. Enumerate all policies at count0,1,3,4 with pending/closed/cancelled/expired states. Compare exact sequences with an independent list model. Drive a real MsgHub capacity1 to `FULL` and assert head preservation, then drain and retry. In the original malicious schedule, generate a burst beyond admission capacity and observe only bounded logical message loss/coalescing; no external traffic or host settings are involved.

### T75.03 — Hashed timer-wheel collisions, cancellation and expiry work

A timer-wheel bucket contains candidates sharing a modular index, so due times1 and5 can collide without expiring together. In the required two-level extension, a timer cascade moves a coarse timer into a finer level while preserving its absolute due time and cancellation identity; moving it is not callback execution.

The important wheel tradeoff is not merely replacing a comparison with modulo. Collisions, cancellation frequency, finite identity and concentrated expiries determine correctness and latency.

Implement the four-bucket/four-slot wheel with delay1..16, absolute due ticks, intrusive index links and owner/generation identities. Tick advances one unit and returns every due slot as a bitmask; cancellation unlinks immediately. Extend to a two-level wheel that cascades coarse timers into fine buckets, preserving exact expiry and cancellation identity. Reopen the PR-T50-05 sealed scheduler decision and add this as a third measured alternative to its existing structures under the same timer contract.

At now0 a delay5 timer maps to bucket1 but must not fire at tick1; it fires exactly at5. Cancelling generation1 then reusing that slot at generation2 makes the old ID `STALE`. Simultaneous due timers all appear in the returned mask, without invoking callbacks during linkage traversal.

Required evidence: {ref}`X-T75-003` assesses each objective separately. Use an independent sorted map of absolute due times, not another wheel. Exhaust pairs of due1..16 and every cancellation point; verify back-links after each step. Add a delayed-clock jump that crosses three revolutions and either process all missed ticks or specify a bounded late-fire policy. Record the selected scheduler decision before measurement; historical paper VAX numbers are source observations only.

### T75.04 — Overflow-safe token buckets and competing rate contracts

Burst credit is the stored token allowance available for an immediate admission burst. Lazy refill replenishes it only up to capacity, and spending it does not reserve an active-operation permit; a separate concurrency bound is needed when admitted requests can remain outstanding.

Multiplication can wrap before a clamp notices it, and repeatedly rounding refill can silently suppress credit. A rate limit also does not stop an unlimited number of slow admitted calls from remaining active.

Implement RZBucket with integral capacity/rate1..16 and costs1..capacity. Refill lazily under monotonic uint64 ticks, saturating before a potentially overflowing multiplication. A rejected spend retains elapsed-time refill but spends no tokens. Extend to fractional fixed-point replenishment without rounding away long-term credit, then compose a second peak bucket with rollback of admission when either bucket denies.

Capacity4/rate1 starts with4. Spending4 at0 succeeds; another1 at0 is `FULL`. At1 one token is available and exactly-cost admission succeeds. Advancing to UINT64_MAX fills only to4 without arithmetic overflow. Backward time is `INVALID` without mutation.

Required evidence: {ref}`X-T75-004` assesses each objective separately. For capacity/rate1..16 and elapsed0..19, compare every single-step refill/spend with integer arithmetic; add UINT64_MAX gaps. Generate length0–6 cost/time sequences with same-time bursts, backward time and impossible costs. Preserve fractional remainder in the extension and verify splitting an idle interval does not change credit. Do not execute tc or modify host network policy.

### T75.05 — Jittered retry schedules with a shared deadline and attempt budget

The retry budget bounds extra attempts even when the draw is zero, while retry jitter spreads their start times under the stated draw distribution. Neither changes the operation's effect semantics: the shared deadline, repeat-safety contract and per-dispatch resource charge still apply.

Backoff can amplify overload while making average latency look better. Randomizing when an unsafe operation repeats does not make its effects idempotent.

Implement RZRetry schedule with bounded attempts, capped exponential windows and injected full-jitter draws. Reject unsafe-to-repeat operations and starts at or beyond the inherited deadline. Implement a deterministic PRNG adapter with unbiased bounded selection using rejection sampling; keep its seed record and entropy limitations explicit. Connect scheduled attempts to the accepted communications.tcp_fault loss/duplicate/late-ack model, charging every dispatch to a common retry limiter at one chosen layer.

Base2/cap8 produces draw windows[0,2],[0,4],[0,8]. At now9 with deadline10, draw1 rejects and preserves attempt count. A non-idempotent request rejects before scheduling. Three admitted retries exhaust a maximum3 budget even if all draws were zero.

Required evidence: {ref}`X-T75-005` assesses each objective separately. Use arbitrary-precision min(cap,base*2^k) and a finite draw enumeration oracle. For unbiased selection, enumerate a small synthetic random source and count accepted residues exactly; do not equate one histogram with proof of randomness. Trace original attempt plus retries, limiter charges, pending completions and cancellation. Security demonstration remains synthetic retry amplification in the teaching model, with bounded requests and no external endpoint.

### T75.06 — Health breakers, bulkheads and stale completions

Health decisions summarize observations, while a bulkhead bounds admitted resource ownership. Conflating them allows an otherwise healthy slow backend to exhaust callers or an old completion to erase newer failure evidence.

Implement RZGate with separate closed/open/half-open health state and active-permit limit1..2. Two consecutive backend failures open for4 ticks; a single half-open probe decides recovery. Each permit carries owner, slot and nonwrapping generation; completion also uses its saved admission epoch so an old success cannot heal a new open period. Add a sliding-window failure-rate policy and a two-tenant bulkhead variant with explicitly reserved capacity, retaining neutral client-error outcomes.

With limit1, a second simultaneous admission returns `BUSY` even while `CLOSED`. Two classified failures open. An older outstanding success releases capacity but leaves the newer `OPEN` state unchanged. At cooldown equality one probe may enter, a second is `BUSY`, and successful probe closes. Repeated completion is `STALE`.

Required evidence: {ref}`X-T75-006` assesses each objective separately. Enumerate admit/fail/succeed/neutral sequences through each finite generation. Test old admission before two failures, then a late success after `OPEN`. Check capacity and exactly-once release after every event. Use an original synthetic overload trace to demonstrate the missing-limit mutant permits excess work; the stale-epoch mutant reopens traffic after a declared trip. Observe counters/status only, not external service load.

### T75.07 — Hedged responses and ownership of losing work

A hedged request deliberately allows overlapping attempts under one deadline. Its first acceptable result can be available before operation quiescence: every started loser still needs a terminal completion before its response storage and permits can be reclaimed.

Returning a fast answer does not reclaim the slow attempt. Treating cancellation as completion creates lifetime defects, while treating any response as a winner can return a quick error instead of a valid result.

Implement RZHedge for original attempt0 and one delayed attempt1. Choose the first acceptable response before the shared deadline, request cancellation of outstanding attempts, and track their actual terminal completions separately. Expose result availability independently from quiescence. Add a completion arbiter with two concurrent workers in the dedicated local harness, each retaining its own response storage, and integrate deduplicated effects when both attempts reach the receiver.

A rejected response7 at1 does not win. Start the hedge at2; acceptable8 at3 wins. If original0 remains outstanding, result8 is available but quiescent is false and cancel_requested includes0. Its later response7 cannot replace8; only its completion makes the operation reclaimable.

Required evidence: {ref}`X-T75-007` assesses each objective separately. Enumerate started/completed masks, both acceptable bits, completion orders and deadline equality. Assert first acceptable value stability and that quiescence means every started attempt terminated. Count active permits until loser acknowledgement. The public model is serialized; concurrent correctness requires the submitted arbiter and its synchronization proof, not merely passing this model.

### T75.08 — Idempotent effects, finite deduplication and storage fencing

The deduplication window is the finite interval during which a request identity retains its original parameters and result. Once that record expires, the same identity may apply again; persistence across restart and indefinitely preventing duplicate effects need additional contracts beyond this volatile lookup table.

Deduplication needs an identity contract and retention limit. A timed-out lease or a unique randomly generated identifier does not establish that an old writer is fenced off after a newer owner acts.

Implement RZReceiver for a checked synthetic integer total, four retained requests, two authenticated-model client IDs and finite retention1..16 ticks. A request has client,id,fence,delta. Replays within retention return the original result; changed parameters conflict; stale fencing tokens reject at the protected receiver. Publish effect and dedup record together. Add an append-only local teaching journal with explicit process-termination points around record/effect publication, then replay recovery without claiming the in-memory anchor is durable.

Client0/id1/fence2/delta3 at0 applies total3. Its replay at1 returns3 without another effect; delta4 with that ID conflicts. Client1 at fence1 is stale. With retention4, the same id at4 is no longer retained and may apply again, producing6. This bounded window is not indefinite exactly-once execution.

Required evidence: {ref}`X-T75-008` assesses each objective separately. Enumerate client0..1, id1..3, delta-1..1, same/different payload, fence1..3 and every expiry boundary. Use a map of original requests/results plus a scalar high-water fence as the oracle. Attacker capability is replay/reorder or changing admitted request fields in this isolated original receiver; success is a synthetic counter change forbidden by the stated fence policy, or acceptance of conflicting intent. Repair and verify both rejection and unchanged effect. No real credentials, storage service or deployment is targeted.

### T75.09 — Resilient telemetry admission, committed effects and draining

A committed notification outbox retains the delivery obligation alongside the effect. The public anchor reserves a volatile pending slot before its synthetic commit; the required durable extension must instead define the persistence boundary and recover that obligation after process termination. Channel acceptance alone proves neither consumer delivery nor durable recording.

Locally correct components can compose into lost committed notifications, duplicated effects, retry storms or premature cleanup. A service acceptance result needs a defined commit point and recovery policy, not a collection of successful unit tests.

Implement RZService by composing the accepted deadline, limiter, breaker, receiver, pending queue and actual T73 MsgHub. Reserve notification capacity before committing a new synthetic effect; flush only consumes a pending ID when channel send accepts it. Then build the full local telemetry service through the existing IPC/reactor/TCP-fault artifacts, using the wheel for retries and deadlines, limiter for all original/retry/hedge work, breaker permits until terminal completion, and deduplication for repeated requests. Keep the executable anchor and this required integration as distinct evidence obligations.

A new delta2 request applies once and queues its ID. Flush to channel0 allows msg_select to observe that exact ID. Filling the four pending slots rejects the next request before changing receiver.total. A full/cancelled imported channel retains pending notifications. Cancellation after an admitted effect cannot make its already-reserved notification disappear.

Required evidence: {ref}`X-T75-009` assesses each objective separately. For the public anchor, fill/drain the real MsgHub, close/cancel it and compare pending IDs with receiver records.
