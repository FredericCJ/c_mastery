## Purpose and outcomes

Make allocation follow object lifetimes and bounded backing storage. Implement local policies rather than delegating to malloc, and preserve ownership under exhaustion, migration and rollback. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce. The published workload includes 10 h of explicitly elective project work; a core-only route subtracts those project hours, without removing core awareness.

Repeat T18 API/ownership, T03 effective type/lifetime and T04 checked arithmetic before implementing policy if any boundary is unclear. ## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T16.01 — Allocator contracts

An allocator acquires storage; it does not initialize application objects. Allocate, release and resize need contracts for alignment, zero size, exhaustion and who owns the old object after failure.

Storage legality is part of acceptance. Under the selected C17 baseline, an aligned declared unsigned-char array is still a declared character array; alignment alone does not license arbitrary T* lvalue access. The portable byte arena uses byte APIs and explicit copying into/out of actual typed objects. A typed pool uses a real array of the selected T. A hosted harness may separately supply genuine allocated storage through a backing callback, while the studied allocator/container policy stays local. Firmware casts or mapping-backed typed objects need an explicit, inspected implementation contract and are reported under that contract, not as a blanket ISO C guarantee. Check effective type, alignment, bounds and lifetime independently.

Investigate: Write an allocator callback interface and a transition table before choosing a policy. A common mistake is: An allocator return automatically contains a valid initialized object. Evidence: Zero-size and exhaustion cases have one documented result and ownership remains unambiguous. Develop that evidence in [PR-T16-01](../projects/PR-T16-01.md).
### T16.02 — Layout and checked arithmetic

Alignment adds padding before payload placement. For power-of-two a, padding can be computed as (a−offset%a)%a, then bounds checked before addition. Metadata and minimum fragment sizes consume capacity too.

Investigate: Calculate layouts for several requests near the end of a fixed region using checked size arithmetic. A common mistake is: Rounding an already overflowing sum repairs overflow. Evidence: Payload, padding, headers and remaining capacity reconcile exactly; unsupported alignment fails before mutation. Develop that evidence in [PR-T16-01](../projects/PR-T16-01.md).
### T16.03 — Bump and arena allocation

A bump arena advances a cursor through caller-owned storage and reclaims a whole lifetime region at reset. Reset invalidates every borrowed object in that region, even if its bytes are unchanged.

Worked arena accounting: with cursor 3, size 5 and alignment 8, padding is 5, so the allocation begins at offset 8 and ends at 13. A later ten-byte request aligned to 4 would end at 26 and must fail in a 24-byte region, preserving cursor 13. A one-byte alignment-1 request can then succeed at 13. Count padding as charged storage, and check additions before forming any pointer.

Investigate: Implement an aligned arena with high-water tracking and generation-marked debug handles. A common mistake is: An arena reset preserves live pointers because memory was not freed to the OS. Evidence: Allocation traces never overlap, satisfy alignment and identify all invalidated handles after reset. Develop that evidence in [PR-T16-01](../projects/PR-T16-01.md).
### T16.04 — Checkpoints and temporary regions

A mark records a rollback boundary, not an independent allocation owner. Nested temporary regions must close in order, and an escaped borrow can outlive the storage it names.

Investigate: Implement nested marks with generation/order checks and a deliberate escaped-reference test. A common mistake is: Rollback is safe whenever the cursor can be restored numerically. Evidence: Out-of-order rollback is rejected and a lifetime diagram distinguishes surviving and invalidated objects. Develop that evidence in [PR-T16-02](../projects/PR-T16-02.md).
### T16.05 — Stack allocation

A stack allocator reclaims the most recent block using explicit metadata. That storage policy does not run application cleanup, and it is unrelated to the compiler stack merely because both are LIFO.

Investigate: Implement release with a top-block token and separate cleanup callbacks. A common mistake is: Reclaiming bytes disposes of resources held by the object. Evidence: Non-top releases fail without state change and exactly-once cleanup evidence is separate from byte accounting. Develop that evidence in [PR-T16-02](../projects/PR-T16-02.md).
### T16.06 — Fixed-block pools

A fixed pool divides storage into aligned slots and tracks free membership. Generation handles detect reuse only while the generation scheme remains meaningful; raw stale pointers bypass that protection.

Investigate: Implement a pool bitmap plus index/generation handles and exhaustion/double-release tests. A common mistake is: A reused slot address has the same object identity. Evidence: The ownership model rejects stale handles and reports a generation-wrap policy. Develop that evidence in [PR-T16-03](../projects/PR-T16-03.md).
### T16.07 — Variable-size free lists

A free-list policy chooses among holes. Splitting must leave either a usable remainder or absorb the tail; searching faster and fragmenting less are different goals.

Investigate: Implement first-fit with a declared minimum remainder and adversarial request traces. A common mistake is: Total free bytes guarantees one request can be served. Evidence: Largest-free-block and search-step evidence explain failures despite adequate total free space. Develop that evidence in [PR-T16-04](../projects/PR-T16-04.md).
### T16.08 — Boundary tags and coalescing

Boundary metadata lets an allocator locate adjacent blocks for coalescing. Updating tags and list membership must be one coherent mutation so traversal never sees overlapping free extents.

Investigate: Add boundary tags and left/right/both-neighbor merge cases, checking the heap after every step. A common mistake is: Merging adjacent bytes alone completes free-list repair. Evidence: Ordered block extents, boundary tags and free-list membership agree after all merge orders. Develop that evidence in [PR-T16-04](../projects/PR-T16-04.md).
### T16.09 — Segregated classes and slabs

Size classes reduce search and group similar objects but round requests upward. A slab with one live slot still retains its backing storage, and reuse requires reinitialization of object state.

Investigate: Implement two fixed size classes and calculate internal waste and partial-slab occupancy. A common mistake is: Freed cached objects are already initialized for their next owner. Evidence: Per-class capacity, retained bytes and reinitialization tests distinguish cache storage from live payload. Develop that evidence in [PR-T16-05](../projects/PR-T16-05.md).
### T16.10 — Buddy and real-time-oriented allocation

Buddy splitting constrains sizes to powers of two; a buddy is found by toggling the relevant address bit only within the correctly aligned region. Algorithmic bounds do not cover interrupt interference or cache misses. This topic is elective; its implementation project is optional.

Investigate: Implement a small elective buddy allocator or analyze pinned TLSF source after additional inspection. A common mistake is: Constant-time indexing proves a complete hard real-time latency bound. Evidence: Split/merge traces and a separate hardware-assumption list limit any timing claim. Develop that evidence in [PR-T16-06](../projects/PR-T16-06.md).
### T16.11 — Resize and migration

Resize can retain location or migrate contents. On failure the original ownership remains; after a successful move aliases and iterators to the old block become invalid. Shrink must respect metadata/minimum fragment rules.

Investigate: Implement move-resize with injected allocation failure, then add one justified in-place policy. A common mistake is: A failed resize frees the old object. Evidence: Snapshot contents and identity are preserved on failure; successful migration copies only the retained payload. Develop that evidence in [PR-T16-07](../projects/PR-T16-07.md).
### T16.12 — Backing storage and concurrency

Backing storage and synchronization are independent layers. A mapping supplies bytes to an allocator; a shared allocator lock protects metadata, not every application object stored inside.

Investigate: Adapt an arena to static storage and a declared Linux mapping backend, and compare per-thread ownership with a locked shared policy. A common mistake is: A thread-safe allocator makes allocated objects thread-safe. Evidence: Backend effects and metadata locking are separated from application publication/lifetime arguments. Develop that evidence in [PR-T16-08](../projects/PR-T16-08.md).
### T16.13 — Lifetime architecture

Regions should follow real use intervals: per-message, per-frame and persistent objects need different reclamation points. Forcing independently released objects into one arena can retain large amounts of dead storage.

Investigate: Draw object use intervals for a parser/request pipeline and choose region boundaries. A common mistake is: One arena per program is always the simplest efficient lifetime design. Evidence: Peak-live and retained-byte calculations justify the selected regions and the exceptions. Develop that evidence in [PR-T16-08](../projects/PR-T16-08.md).
### T16.14 — Allocator verification

Allocator verification models live extents independently of policy and checks overlap, alignment and ownership after each action. Instrumentation changes latency and sometimes layout, so measurement costs must be disclosed.

Investigate: Generate allocate/free/resize traces with failures and compare against an abstract live-allocation model. A common mistake is: Passing a few throughput runs establishes allocator correctness. Evidence: Minimized corruption traces and separate peak/fragmentation/latency reports support bounded conclusions. Develop that evidence in [PR-T16-09](../projects/PR-T16-09.md).
