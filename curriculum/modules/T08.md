## Purpose and outcomes

Connect C semantics to one declared machine/ABI without importing platform observations into portable C. Read instructions and encoded bytes, uphold call boundaries and test assembly against an adversarial harness. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce.

## Entry check and remediation

Explain a pointer/length array loop and signed versus unsigned comparison in C, then identify load/store/call instructions in one short disassembly. Remediate pointer arithmetic in T03, integer semantics in T04 and driver staging in T07 before writing assembly. Use {ref}`guide-entry` for diagnostic evidence and {ref}`guide-roadmap` for route choices. Domain numbers are coverage IDs, not an instruction to study them numerically.

## Component progression

**A hostile caller around an assembly kernel.** Name argument/result locations, preserved registers, stack alignment and permitted accesses. Test adversarial surrounding register values and inspect actual instruction bytes.

Before implementation, predict this discriminating case: **A routine returning the right answer while corrupting a callee-saved register.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T08.01 — Instruction-set fundamentals

Disassembly exposes an instruction-set computation: loads and stores use effective addresses, branches test a selected condition, and calls transfer control according to a convention. Cache latency is a different layer.

Investigate: Trace an indexed structure access instruction by instruction and calculate its effective addresses. A common mistake is: One measured cycle count is an ISA guarantee. Evidence: A register/memory trace predicts the result and states which timing claims remain microarchitecture-specific. Develop that evidence in [PR-T08-01](../projects/PR-T08-01.md).

### T08.02 — Registers and flags

Caller-saved registers may be destroyed by a call; callee-saved registers must be restored. Arithmetic flags describe a particular instruction result, including signed versus unsigned comparisons.

Investigate: Track a signed and unsigned branch over the same bit pattern, and poison preserved registers before a call. A common mistake is: A register that happened to survive one call is preserved by contract. Evidence: A mechanical harness detects a missing restore and an annotated trace distinguishes the comparison conditions. Develop that evidence in [PR-T08-01](../projects/PR-T08-01.md).

### T08.03 — Call boundaries

An ABI classifies arguments before assigning registers or stack storage. A large return value can introduce a hidden storage pointer; that shifts apparent parameter positions.

Investigate: Compare scalar, small-aggregate and large-aggregate call sites on the declared x86-64 target. A common mistake is: C source parameter order completely describes the machine call. Evidence: Call-site and callee annotations agree on registers, spill slots, result storage and alignment. Develop that evidence in [PR-T08-02](../projects/PR-T08-02.md).

### T08.04 — Stack frames

A frame contains more than source locals: saved state, spilled temporaries, padding and sometimes outgoing arguments. Optimization can remove the frame pointer or replace a tail call with a jump.

Investigate: Compare recursive and iterative routines under two optimizations and account for every observed stack adjustment. A common mistake is: Source-level local sizes equal total frame size. Evidence: A stack diagram distinguishes observed frames from a conservative bound and names any red-zone assumption. Develop that evidence in [PR-T08-02](../projects/PR-T08-02.md).

### T08.05 — Data layout and ABI compatibility

LP64 and ILP32 differ in integer and pointer widths; padding separates member offsets from payload sizes. Binary compatibility is a promise about layout and calling conventions, not only matching declarations.

Investigate: Generate a layout manifest and compare a packed or differently configured object against it. A common mistake is: Equal sizeof values prove compatible layout. Evidence: Offsets, alignment, widths and symbol-level interface checks identify the intentionally incompatible pair. Develop that evidence in [PR-T08-02](../projects/PR-T08-02.md).

### T08.06 — Floating-point ABI

Floating-point instructions and floating-point parameter passing are separate decisions. On Arm, soft, softfp and hard-float choices can differ even when arithmetic instructions are available.

Investigate: Inspect target attributes for one compatible and one incompatible floating-point library pairing; diagram who preserves FP registers. A common mistake is: A hardware FPU makes every library ABI compatible. Evidence: The audit rejects mismatched call conventions and keeps x86-64 observations separate from Arm examples. Develop that evidence in [PR-T08-03](../projects/PR-T08-03.md).

### T08.07 — Standalone assembly

Standalone assembly owns the full call boundary: exported symbol, section placement, preserved registers and stack alignment. Unwind annotations describe recovery state; they do not execute the restore.

Investigate: Write a short callable integer routine and an intentionally broken preserved-register variant. A common mistake is: Returning the correct value is enough to satisfy the ABI. Evidence: Repeated calls with register sentinels and a debugger/unwind inspection expose the broken variant. Develop that evidence in [PR-T08-03](../projects/PR-T08-03.md).

### T08.08 — Inline assembly

Inline assembly describes both an instruction and a contract with the optimizer. Tied operands share storage; early-clobber prevents overlap with inputs; a memory clobber constrains compiler motion rather than ordering a CPU.

Investigate: Compare a correct operand specification with one missing a clobber at multiple optimization levels. A common mistake is: volatile asm or a memory clobber automatically acts as a hardware fence. Evidence: A constraints explanation and generated-code comparison identify the compiler and hardware obligations separately. Develop that evidence in [PR-T08-04](../projects/PR-T08-04.md).

### T08.09 — Exceptions and privileged execution

A trap crosses an architectural exception boundary, with privilege and saved-state rules unlike a normal call. Kernel entry does not follow the portable C abstract machine.

Investigate: Classify ordinary calls, syscalls, interrupts and privileged instructions in a table; inspect a documented trap boundary. A common mistake is: Every instruction visible in disassembly is legal in userspace. Evidence: The table states privilege, return mechanism and saved-state owner without attempting privileged operations on the host. Develop that evidence in [PR-T08-04](../projects/PR-T08-04.md).

### T08.10 — Compiler-to-machine reasoning

The compiler may transform a defined computation while preserving observable behavior. Source, intermediate representation and final instructions answer different questions; undefined behavior removes the premise of the comparison.

Worked encoding anchor: in the declared 64-bit mode with no prefixes and default 32-bit operand size, B8 78 56 34 12 selects the MOV-immediate form for EAX. Its immediate is 0x12345678 because the least significant byte comes first; the encoding is five bytes. This one form is not a general x86 decoder, and changing operand size or prefixes changes the investigation.

Investigate: Compare a defined strength-reduction example with a separately diagnosed overflow-invalid variant. A common mistake is: An unexpected instruction sequence proves an optimizer bug. Evidence: A minimized case first states its language preconditions, then explains one eliminated branch, inline call or spill. Develop that evidence in [PR-T08-01](../projects/PR-T08-01.md).
