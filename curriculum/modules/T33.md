## Purpose and outcomes

State properties precisely and connect them to concrete C semantics, bounded environments and reported verifier obligations. A proof artifact must make its assumptions and skipped/unproved goals visible.

## Entry check and remediation

Derive a prefix-sum invariant, trace one bounded pointer extent and distinguish mathematical versus unsigned/signed C arithmetic. Repair T03/T04/T14 reasoning selectively. Review T32 independent-oracle and reproducibility work before installing the selected CBMC/Frama-C/solver environment.

## Study sequence and teaching

### T33.01 — Specifications and invariants

A specification relates concrete state to mathematical meaning. For a bounded prefix sum, require a valid extent, define the accepted integer range and state which bytes may change. Safety, functional result and eventual termination are separate properties. Write pre/postconditions and an abstraction mapping for the fixture before choosing a verifier. The misconception is that a precise English return-value sentence also specifies lifetime, ownership and side effects.

Apply this mechanism in [PR-T33-01](../projects/PR-T33-01.md).

### T33.02 — Loop reasoning

A useful loop invariant carries what is already processed and what remains valid. For summing n elements, i<=n and accumulator=sum of elements before i support the exit result; an overflow bound must also be preserved. Prove initialization, one iteration and exit, then give n-i as the termination variant. Testing all small n is not an inductive proof for arbitrary n. Evidence is a proof outline plus a broken-invariant counterexample.

Apply this mechanism in [PR-T33-01](../projects/PR-T33-01.md).

### T33.03 — Arithmetic and memory models

Mathematical integers do not wrap, while unsigned C arithmetic is modular and signed overflow is not a valid arithmetic step. Pointer validity also needs extent, lifetime and aliasing assumptions. Compare the fixture's unbounded result with an explicitly eight-bit modular result, then write the stronger precondition needed for equality. Evidence includes the promoted intermediate type and every memory bound; silently replacing C expressions with ideal arithmetic proves a different program.

Apply this mechanism in [PR-T33-02](../projects/PR-T33-02.md).

### T33.04 — Contracts and annotations

Annotations belong to the API: requires describe caller obligations, ensures describe results and assigns describe the frame. ACSL's logical integers need explicit connections to machine values. Annotate a caller-storage prefix-sum or maximum routine and test that its documented failure behavior matches the contract. An omitted frame condition can leave a functional proof compatible with unwanted writes. Evidence includes a side-effect counterexample and repaired frame.

Apply this mechanism in [PR-T33-02](../projects/PR-T33-02.md).

### T33.05 — Bounded model checking

A bounded model checker explores a finite encoding of input, loops and environment. Build a CBMC harness with nondeterministic n/data under the public contract, assert the result/bounds, and require unwinding assertions. The loop guard may need one more unwinding evaluation than body iterations. A too-small bound can hide a reachable defect. Preserve successful obligations, failed counterexamples, tool defaults and an intentionally insufficient-bound run.

Apply this mechanism in [PR-T33-03](../projects/PR-T33-03.md).

### T33.06 — Deductive verification

Deductive proof generates obligations under contracts and models. With WP, inspect initialization/preservation/postcondition and runtime-error goals separately, including selected arithmetic and memory models. Start with a small integer routine whose range fits; do not use the Real model to claim C floating-point correctness. Evidence lists proved, assumed, unproved and unsupported obligations. 'No reported failures' is inadequate if goals were skipped or a precondition excluded every call.

Apply this mechanism in [PR-T33-04](../projects/PR-T33-04.md).

### T33.07 — Abstract interpretation

Abstract interpretation computes an over-approximation of reachable values. An interval containing zero can warn about division even if a richer relation would rule zero out. Inspect an Eva alarm, justify an invariant or partition, and rerun without suppressing actual behavior. Evidence separates a real defect from an imprecision alarm and records soundness/context assumptions. Sequential Eva does not directly establish asynchronous interrupt correctness.

Apply this mechanism in [PR-T33-05](../projects/PR-T33-05.md).

### T33.08 — Environment models

An environment model determines what the proof can see. If an adapter always returns full success, the harness cannot prove cleanup after partial progress, invalid counts or allocation failure. Make nondeterministic outcomes range over the real documented contract, with explicit exclusion of unsupported asynchronous hardware. Evidence includes one counterexample admitted only after repairing an overly helpful stub. More assumptions can make a proof easier while making its claim weaker.

Apply this mechanism in [PR-T33-03](../projects/PR-T33-03.md).

### T33.09 — Concurrency reasoning

**Elective extension.** The elective finite queue model can test abstract linearization and FIFO histories under a declared sequentially consistent event model. Enumerate interleavings while preserving each participant's order and identify publication/removal points. This is not proof that a C acquire/release implementation realizes the abstract history, nor that an interrupt/compiler extension has ISO-thread semantics. Evidence includes accepted/rejected histories and a separate memory-order argument with its unsupported cases disclosed.

Apply this mechanism in [PR-T33-06](../projects/PR-T33-06.md).

### T33.10 — Evidence composition

Compose evidence by property: a proof may establish bounds under preconditions, instrumentation may find exercised lifetime defects, tests may establish vectors, and a scope may measure a physical pulse. Maintain a claim/assumption/artifact table with trusted compiler, runtime, solver and hardware entries. Do not add coverage percentages to proof percentages. The final argument states which properties are unproved and which counterexamples would invalidate the environment model.

Apply this mechanism in [PR-T33-05](../projects/PR-T33-05.md).

**Shared scope limit — An Axiomatic Basis for Computer Programming:** A small illustrative language and historical formalism, not modern C semantics. Signed overflow, aliasing, memory safety and termination need current C/tool evidence. Remaining paper pages were not visually inspected.

**Shared scope limit — CBMC training: What is loop unwinding?:** Training examples do not select a release or prove a hardware environment. Pin tool version, check defaults and report assumptions, reachability and every unwinding result. The old CPROVER manual routes returned navigation only.

**Shared scope limit — ANSI/ISO C Specification Language:** Logical arithmetic has no machine overflow by default. Language expressiveness does not imply every clause is supported by each plug-in; WP limitations must accompany assignments.

**Shared scope limit — WP Plug-in Manual:** Proof is conditional on contracts, runtime-error obligations and models. Tutorial reports skipped unaligned-pointer/function-pointer guards. The Real Model explicitly does not establish C/IEEE floating-point correctness. Selected passages only; no solver execution.

**Shared scope limit — The Eva plug-in:** False alarms can result from approximation. Soundness is relative to the specified context and supported semantics. Current manual states asynchronous interrupts are not directly modeled; do not claim full firmware proof from sequential analysis.
