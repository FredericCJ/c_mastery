## Purpose and outcomes

Establish ownership of a bare-metal image from reset through entry. Every copied byte, stack assumption and runtime dependency should be observable in the image and in a bounded startup trace.

## Entry check and remediation

Trace load/run addresses, identify a linker symbol versus a C object, and explain why calling C needs an ABI-valid stack. If any answer is weak, repair the corresponding T08/T09/T11 leaf before flashing. Draw the selected board/core/device documentation boundary and check the fixture's hexadecimal regions by hand.

Use {ref}`guide-entry` for the diagnostic policy and {ref}`guide-roadmap` for route order. Only the stated prelude leaves must precede a dependent project.

## Component progression

**Reset-to-main as an inspected memory transform.** Name reset state, vector ownership, stack region and load/run addresses. Verify copy, zero and retained ranges before trusting global values.

Before implementation, predict this discriminating case: **A valid link map paired with an incorrect startup zero range.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T27.01 — Hardware evidence and target selection

The MCU, package, board revision and emulator are four identities. An F439ZI board record must distinguish RM0090, DS9484, UM1974, ES0206 and the Arm core guide. Build an evidence ledger with memory banks and observed boot configuration, then compare it to the synthetic target fixture. Assuming every Cortex-M4 board has STM32 registers is the central trap. Your evidence must mark each claim as document-derived, image-derived, emulator-observed or physical-board-observed.

Apply this mechanism in [PR-T27-01](../projects/PR-T27-01.md).

### T27.02 — Reset and boot ownership

Reset begins under hardware/ROM ownership before application startup. Boot selection changes the aliased vector source; a debugger may establish state a cold power cycle never supplies. Draw the Flash/system-memory/SRAM decision and annotate who owns clocks, interrupts and reset-cause capture at handoff. Treat watchdog, software and power resets as separate trials. Evidence is an observed PC/vector-source trace plus a reset-state ledger; 'it runs after loading in the debugger' does not establish standalone boot.

Apply this mechanism in [PR-T27-01](../projects/PR-T27-01.md).

### T27.03 — Vector table

The first vector word supplies the initial stack and subsequent words select exception handlers under the architecture's encoding rules. Retaining the section in the linked image matters as much as defining the array. Construct a vector section, inspect its bytes/symbols and reject a reset address outside executable Flash. A linker symbol's presence does not prove placement. For bootloader offsets, state alignment/VTOR rules from the chosen implementation and preserve a before/after relocation inspection.

Apply this mechanism in [PR-T27-02](../projects/PR-T27-02.md).

### T27.04 — Stack initialization

The stack descends within a reserved region and must satisfy AAPCS alignment before compiled C is called. A public call boundary requires eight-byte alignment even if ordinary stack operations preserve four. Budget call depth plus nested exception frames and any FPU extension; a canary reports tested usage, not all possible paths. Select an initial stack from the fixture, demonstrate alignment checks, and explain how overflow enters a bounded failure path rather than assuming unused RAM is safe.

Apply this mechanism in [PR-T27-02](../projects/PR-T27-02.md).

### T27.05 — Initialized and zeroed data

An initialized object has load bytes in Flash and execution storage in RAM; zero-initialized objects need clearing, while explicitly retained regions need a different policy. Implement startup copying/clearing from linker ranges, including a second RAM bank, and use distinct sentinels to expose overlap. Clearing 'all RAM' destroys retained evidence. Compare the exact expected memory transformation with debugger reads before main and prove each loop's bounds without relying on libc being initialized.

Apply this mechanism in [PR-T27-03](../projects/PR-T27-03.md).

### T27.06 — Early machine setup

Early setup must establish only the prerequisites actually used by startup and the application. Configure the F439 clock path with readiness checks and bounded failure, respecting disabled-PLL configuration and applicable peripheral-clock errata. Do not call floating-point code before selecting and documenting the core/FPU ABI/state policy. Test a never-ready clock in the logical adapter. Evidence includes the ordered access trace and an actual target clock observation when a frequency claim is made.

Apply this mechanism in [PR-T27-04](../projects/PR-T27-04.md).

### T27.07 — Runtime hooks and entry

A reset handler is a runtime policy: it decides whether initialization arrays run, which hooks exist and what happens if application entry returns. Calling main does not automatically provide libc, allocation or constructors. Implement a named entry contract with a deterministic halt/recovery return policy and one supported initialization-hook sequence. Evidence is a symbol/dependency audit and an ordered hook trace, including an unsupported-hook rejection rather than a silent skipped initializer.

Apply this mechanism in [PR-T27-03](../projects/PR-T27-03.md).

### T27.08 — Independent startup implementation

First annotate a vendor startup file against its linker symbols and core assumptions, then replace selected copying/vector/entry pieces with your own minimal implementation. Keep the comparison narrowly scoped so a known board image remains available during diagnosis. Source similarity is not equivalence; inspect final symbols, load/run addresses and disassembly. Your independent implementation must reach the same sentinel state from an actual reset while preserving documented differences.

Apply this mechanism in [PR-T27-04](../projects/PR-T27-04.md).

### T27.09 — Retained state and boot handoff

Retained bytes need a validity protocol because reset does not imply they describe the current image. Use a magic, version, length and checksum for accidental corruption, then reject invalid or incompatible records before consuming payload. A boot handoff also owns vector base, stack, pending interrupts and clocks. Test stale versions and interrupted record writes in the fixture. Checksums establish consistency under this model, not cryptographic authenticity or freshness against an attacker.

Apply this mechanism in [PR-T27-05](../projects/PR-T27-05.md).

### T27.10 — Bring-up verification

Bring-up observations should get simpler as startup gets earlier: debugger memory, one register marker, then minimal GPIO/UART output after prerequisites exist. Deliberately break one vector, one copy range and one clock-ready condition; classify the failure before editing code. Repeat without debugger initialization and power-cycle the physical board. An emulator trace can establish its own machine behavior, but cannot establish Nucleo pin levels or cold-start electrical behavior.

Apply this mechanism in [PR-T27-05](../projects/PR-T27-05.md).

Read the bounded selections before the corresponding project, then annotate one contract or assumption you will test. The assigned reading table is generated from the exact inspected locators. Spend the remaining reading budget on original teaching, worked traces and target documentation comparisons, not whole uninspected chapters.

**STM32F405/415, STM32F407/417, STM32F427/437 and STM32F429/439 advanced Arm-based 32-bit MCUs — 2.4 Boot configuration (1 h):** Trace reset vector source.

**Procedure Call Standard for the Arm Architecture — 6.2.1.2 Stack constraints at a public interface (1 h):** Establish the C call boundary.

**CMSIS-Core (Cortex-M): Startup File startup_<device>.c — Startup File startup_<device>.c (1 h):** Compare generic startup structure.

**STM32 Nucleo-144 boards (MB1137) — Introduction (1 h):** Identify board applicability.

**Shared scope limit — STM32F405/415, STM32F407/417, STM32F427/437 and STM32F429/439 advanced Arm-based 32-bit MCUs:** Inspected Rev21; newer Rev22 delta uninspected. F439 RCC is chapter6, not earlier-family chapter7. Additional authoring inspection supports bounded 7-bit I2C transmit/single-byte receive and full-duplex SPI sequencing; optimized I2C multibyte/NACK timing and full error chapters remain outside scope. ADC sampling/trigger/single conversion are inspected, but analog electrical accuracy and Stop/Standby recipes are not. Physical timings, package pins and device electrical conditions need DS/board evidence and measurement.

**Shared scope limit — Procedure Call Standard for the Arm Architecture:** Select the actual ABI variant and floating-point options used by the toolchain; this document does not choose a board memory map or linker layout.

**Shared scope limit — CMSIS-Core (Cortex-M): Startup File startup_<device>.c:** Generic template contains adaptation TODOs and Armv8-M stack-limit/sealing operations; it must not be copied verbatim to Cortex-M4. Device startup and linker/runtime initialization must be inspected for the selected compiler.

**Shared scope limit — STM32 Nucleo-144 boards (MB1137):** Inspected Rev 8, not current Rev 11. Board revision, actual solder bridges and clock population must be recorded on physical hardware; described defaults are not a measurement of the learner's board.

## Mastery gate and feedback

Start the minimal image from reset, identify vector/stack/copy/hook evidence and explain a deliberately broken range. Physical-board completion includes standalone power-cycle success; emulator completion is a separately labeled stage. Failure in early entry requires shrinking to a marker before adding drivers.

For every linked objective, retain a separately labeled explanation, implementation/analysis artifact and check. Use {ref}`guide-assessment` for the rubric; one passing fixture does not establish all three objectives of a topic.

## Consolidation and transfer

A week later, relocate a small data section to another verified RAM bank and change the retained-record version. Predict the map and startup changes, then demonstrate rejection of old state. Review how a bootloader would change reset ownership.
