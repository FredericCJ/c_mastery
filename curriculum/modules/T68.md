# T68: Metaprogramming, reflection and law-driven generation

## Purpose and outcomes

Build and explain the representations and state transitions below, preserving the imported artifact contracts. The complete exercises are core work; descriptive hours do not cap depth. Distinguish ISO semantics, implementation diagnostics, runtime checks and programmer discipline.

## Entry check and remediation

Derive ownership through a failed acquisition and a retained borrow using the prerequisite artifacts. State the backing lifetime, aliasing and failure contract before composing the prerequisite artifacts.

## Environment and limits

Use profile A: hosted Linux x86-64 and ISO C17 with extensions disabled and -Wall -Wextra -Wpedantic -Werror. Follow the [metaprogramming laboratory contract](../../labs/metaprog/CONTRACTS.md), including live, disjoint input/output objects and serialized operations. GCC and Clang debug, release and ASan/UBSan are the declared profiles. Preprocessor output and positive/negative translation units assess generation and constraints; Python, CMake and temporary generated-file compilation are host verification facilities, not substitutes for the C mechanisms.

The template rings each hold four elements, the C17 nonempty variadic demonstration accepts one to four arguments, the token expander admits at most 32 tokens, and the build graph has at most eight nodes. The property runner enumerates bounded pairs through 255 and finds a local minimum under its stated shrinking moves. Every bound has an explicit rejection or exhaustion rule. Generated signatures and _Generic distinguish declared categories, while runtime extents, callback purity, ownership and algebraic laws require separate checks or discipline. The formatter treats percent sequences as literal data and may not delegate conversion to printf-family routines.

The explicit token-context model is not a complete C or Rust macro parser, and its hygiene argument is confined to that representation. FNV-1a equality/cache keys are not cryptographic integrity or authenticated-cache guarantees. No final C23 or C++26 feature guarantee follows from an inspected proposal or census entry; the implementation baseline remains C17 and exact final-edition text gaps stay recorded. Experiments use original local programs and synthetic inputs. Hosted diagnostics and finite law tests do not establish strict freestanding closure, arbitrary compile-time evaluation, absolute mastery or the required delayed transfer.

## Study sequence and teaching

### T68.01 — Template-header monomorphization and associated types

Explain how repeated template-header inclusion generates distinct typed functions, how associated element/ring types must agree, and why token substitution has no trait-implementation proof or automatic instantiation isolation.

Push0..3, pop0, push4, then pop1..4. Both scalar and pair instances preserve every semantic field. Full/empty operations leave their designated output/control state unchanged.

Construction: Derive head<count/capacity invariants, occupied logical slots and output ownership. Compare generated specialization with Rust generic/associated-type obligations and show a mismatched ring/element instantiation diagnosed by C. Explain why a template include guard would silently suppress the second instantiation and why internal macro names can collide. The full assessed work is {ref}`X-T68-001`.

Misconception: A generic-looking macro can accidentally generate only one instance if it uses a normal include guard.

Evidence: Run metaprog.mono and inspect preprocessed two-instance source. Kill incorrect-tail-index and stationary-head mutants. Compile and link two translation units using declarations to detect accidental multiple definitions; record generated symbol count and text size separately from handwritten equivalents under the same capacity/failure contract.

### T68.02 — Constraint probes and constant storage parameters

Separate a required C constraint diagnostic, a chosen -Werror rejection, and a runtime range guard; show which properties constant-size generic storage can check before execution.

count4,width8,limit32 yields32;limit31fails. SIZE_MAX*2 fails before overflow; count0 or width0 is outside this storage contract.

Construction: Derive count<=SIZE_MAX/width before multiplication and the independent budget bound. Explain why C17 _Static_assert requires an integer constant expression, VLA support differs from fixed arrays, and syntactically valid macros do not impose an abstract trait. Compare the inspected Rust const-generic type/use restrictions without claiming arbitrary compile-time evaluation equivalence. The full assessed work is {ref}`X-T68-002`.

Misconception: Record the exact diagnostic class rather than treating any compiler error as success.

Evidence: Run metaprog.constraints and compile the negative constraint probes expecting a named diagnostic, not a link failure. Kill multiplication-overflow omission and storage-budget omission independently. Test size_t-width changes analytically and inspect whether published C23 wording is available before attributing a C2x compiler behavior to the standard.

### T68.03 — Policy composition with explicit failure semantics

Explain how a policy changes the operation contract and therefore the permitted performance comparison; distinguish compile-time specialization from runtime policy dispatch.

Inputs[7,5],limit10: rejecting policyfails unchanged; saturating policyreturns10. Empty inputreturns0 under eitherpolicy.

Construction: Prove value<=limit before subtracting limit-value, and define how a single input greater thanlimit is handled. Inputs/outputs are disjoint. State no allocation, single-threaded execution and failure publication at the end. Compare a policy parameter with Rust const parameters/trait-associated behavior only at the documented boundary. The full assessed work is {ref}`X-T68-003`.

Misconception: Equivalent result values are insufficient when one policy promises failure and another promises success.

Evidence: Run metaprog.policies and inject every prefix crossing the limit. Kill accidental-saturation-for-rejection and wrong-empty-identity mutants. Inspect specialized and dynamic assembly and benchmark only comparisons preserving the same overflow and empty-input contracts.

### T68.04 — Portable C17 variadic machinery and single evaluation

Derive a bounded1..4argument dispatch macro without __VA_OPT__ or GNU comma deletion, and distinguish single evaluation from the unspecified order of function arguments.

seed7 andarity0..4 produce sums0,7,15,24,34 with evaluation counts0,1,2,3,4. Arity5fails preserving bothoutputs. No argument-order claim is made.

Construction: Show token substitution, rescan, selector position and parentheses for each admitted arity. Explain why an empty token argument differs from omitted variadic arguments in C17, and why this lab deliberately has a distinct zero-argument entry. Compare N3033 proposal semantics without presenting a proposal as the inspected final C23 standard. The full assessed work is {ref}`X-T68-004`.

Misconception: Single evaluation does not promise left-to-right evaluation.

Evidence: Run metaprog.variadic, inspect -E output, and compile strict C17 probes. Kill duplicate-evaluation and incorrect-zero-identity mutants. Add arguments with commas protected by parentheses and demonstrate an unsafe unparenthesized form in a diagnostic-only target; retain a separate C2x __VA_OPT__ observation.

### T68.05 — Generic customization with cv-preserving receivers

Explain why selecting a function designator with _Generic and calling it afterward preserves typed receiver checking, while invalid unselected expressions can still require diagnostics.

Mutable7 and const9 produce316 with2evaluations and unchanged pointees. Selecting the mutable policy for the const receiver produces the wrong semantic marker even if a cast lets it compile.

Construction: Distinguish top-level pointer qualifiers from pointed-to const and state the compatible-type association restrictions. The controlling expression is not evaluated; only the selected call argument is evaluated. Explain why the generic selection should choose valid function names rather than embed branch-specific invalid field operations. The full assessed work is {ref}`X-T68-005`.

Misconception: The controlling expression being unevaluated does not make arbitrary unselected expressions syntactically or semantically valid.

Evidence: Run metaprog.generic and compile unsupported-type/const-write diagnostic probes. Kill const-receiver-policy substitution and extra controlling-expression evaluation mutants. Check GCC and Clang with C17, and record implementation differences involving top-level qualifiers as observations requiring precise source interpretation.

### T68.06 — Single-source field reflection and explicit wire operations

Derive declarations, field names, offsets and wire operations from one authoritative field list without confusing implementation layout reflection with a portable serialization format.

Record{code0x1234,value0x89abcdef} encodes12 34 89 AB CD EF. The field schema table has two records; native offsets are offsetof(MPRecord,code/value), independent of wire positions0/2.

Construction: Explain stringification/token substitution and why the field list is a local schema, not arbitrary introspection of undeclared C types. Distinguish native field offset, native sizeof, wire width and schema identity. Compare the declared generated interface with language macro/derive facilities; no C++26 reflection claim is inferred without inspected final specification. The full assessed work is {ref}`X-T68-006`.

Misconception: A single registry prevents some duplication but does not prove every handwritten consumer was regenerated.

Evidence: Run metaprog.reflection and regenerate a changed schema in a temporary workspace. Kill endian reversal and missing-field-descriptor mutants. Compile under altered packing/alignment only as an implementation-specific comparison and retain canonical wire bytes unchanged.

### T68.07 — Derived equality, hashing and shrinking law counterexamples

Explain the equality-implies-equal-hash law, why cached/nonsemantic fields must be excluded consistently, and what deterministic generation plus shrinking establishes and leaves unproved.

Keys(1,2,cache0) and(1,2,cache9) compareequal and hash equally; (1,3,0) differs. Propertyx+y<5 over0..8 yields a failing pair ofsum5. Reflexivity finds no failure in the bounded domain.

Construction: Prove reflexivity/symmetry/transitivity obligations separately from hashing and collisions. Specify FNV parameters and unsigned64 wrap; this is not a cryptographic integrity claim. The shrinking order finds a local minimum under decrement moves, not necessarily a globally simplest witness for arbitrary nonmonotone predicates. Callback/context must remain live, deterministic and side-effect controlled. The full assessed work is {ref}`X-T68-007`.

Misconception: A smaller input that violates the callback preconditions is not a valid counterexample to its stated law, even if it triggers a diagnostic or abnormal termination.

Evidence: Run metaprog.laws, independently recompute canonical hashes and enumerate bounded law triples. Kill equality-ignores-y and hash-includes-cache mutants. Inject a deliberately wrong equality/hash callback through the learner testing.faults adapter and retain a minimized witness; explain why equal hashes do not imply equal keys.

### T68.08 — Typed formatting and transactional bounded sinks

Distinguish compile-time argument-category checking from compile-time parsing of an arbitrary format string, and prove bounded sink failure does not publish partial output.

Appenduint32zero yieldsbyte30; appendliteral%n yieldspercent/n, with no conversion interpretation. Appending4294967295 to a sink with9freebytes fails unchanged; with10freebytes writes exactly10digits.

Construction: Derive the10digit bound for UINT32_MAX and reverse temporary digits only after capacity admission. For text, prove scan stops on insufficient capacity without publishing a prefix. Compare C++ basic_format_string constant-evaluation compatibility with this narrower C factory: it enforces argument categories, not arbitrary formatting grammar or backing lifetime. The full assessed work is {ref}`X-T68-008`.

Misconception: Typed arguments alone cannot validate an arbitrary runtime format string.

Evidence: Run metaprog.formatting, compile an unsupported MP_ARG category probe, and test every capacity0..11. Kill failure-used-count modification and zero-as-empty-output mutants. Compare against an independent decimal-string oracle and a guard-filled output suffix; distinguish valid text termination preconditions from bound checking.

### T68.09 — A bounded hygienic token expander written in C

Explain variable capture using symbol identity plus syntax context, and distinguish preserving call-site argument context from assigning a fresh context to introduced bindings.

Pattern[introduced7,arg0,introduced7],argument(symbol7,context5),next12 producescontexts12,5,12 andnext13. ExhaustedUINT_MAX, insufficient output capacity or bad argument index leaves state unchanged.

Construction: Define identifier equality as(symbol,context), track binding/reference identities through an expansion, and show how call-site symbol7/context5 remains distinct from introducedsymbol7/context12. Explain nested expansion context retention and finite namespace exhaustion. Compare the inspected Rust mixed-site hygiene rules precisely; the model uses an explicit stronger uniform context scheme for introduced names. The full assessed work is {ref}`X-T68-009`.

Misconception: Freshness ends when a finite context counter wraps; reject before publishing.

Evidence: Run metaprog.hygiene and compare against an independent token/context transformer. Kill retagged-call-site-argument and wrapping-context mutants. Build a tiny environment resolver to demonstrate harmless capture: the flawed output resolves the argument to the introduced synthetic binding instead of its caller binding. Retain corrected and flawed token traces.

### T68.10 — Declarative build graphs and deterministic table generation

Derive build ordering separately from action invalidation, identify hidden inputs, and explain why a content key is only as complete and collision-resistant as its declared input model.

Two nodes0->1 executeorder[0,1]. Changingnode0configuration changes bothkeys. A cycle0<->1 fails with previous outputs unchanged. Generated source retains all64bits of eachkey and is reproducible byte-for-byte.

Construction: Prove Kahn-style readiness and termination, show how dependency content propagates into consumers, and distinguish source identity from timestamp ordering. Compare Ninja explicit/implicit/order-only dependency semantics and command-line rebuild tracking. The educational FNV key is not collision-resistant; require full input equality or a suitable cryptographic digest before any untrusted shared cache use. The full assessed work is {ref}`X-T68-010`.

Misconception: A fast noncryptographic hash cannot authenticate build inputs.

Evidence: Run metaprog.buildgraph and independent Python topological/hash reconstruction. Kill omitted-configuration and omitted-dependency-key mutants. Compile/run the generated C table consumer, permute input storage without changing logical IDs, and inject a missing implicit dependency to demonstrate stale generated metadata.
