## Purpose and outcomes

Build representations yourself, with ownership and failure semantics established before mutations. The T18 ownership/API work is a hard prerequisite: capacity, iterator invalidation and cleanup are part of each container contract. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce. The published workload includes 10 h of explicitly elective project work; a core-only route subtracts those project hours, without removing core awareness.

## Entry check and remediation

Produce a T18 ownership table covering creator, borrower, mutator and destroyer; prove one checked size multiplication. Remediate T04 arithmetic and T03 object lifetimes before any container allocation. T18 API and ownership work is required first, including failure effects and borrow invalidation. ## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T14.01 — Representation contracts

A container represents logical contents with storage and metadata. Its valid states, borrow lifetimes and mutation permissions belong to the interface before algorithms are chosen.

Storage legality is part of acceptance. Under the selected C17 baseline, an aligned declared unsigned-char array is still a declared character array; alignment alone does not license arbitrary T* lvalue access. The portable byte arena uses byte APIs and explicit copying into/out of actual typed objects. A typed pool uses a real array of the selected T. A hosted harness may separately supply genuine allocated storage through a backing callback, while the studied allocator/container policy stays local. Firmware casts or mapping-backed typed objects need an explicit, inspected implementation contract and are reported under that contract, not as a blanket ISO C guarantee. Check effective type, alignment, bounds and lifetime independently.

Investigate: Write empty/full/destroyed state transitions and an ownership table before implementing any mutation. A common mistake is: A non-null pointer always denotes a valid live container. Evidence: Invariant checks distinguish valid empty storage, exhaustion and destroyed handles. Develop that evidence in [PR-T14-01](../projects/PR-T14-01.md).
### T14.02 — Fixed arrays and views

A slice borrows a range; it does not own or extend its storage lifetime. Insertion must account for capacity and overlapping movement, while a strided view changes address calculations.

Investigate: Implement bounded insertion/erase and a strided view over caller storage. A common mistake is: A view remains valid after its owner reallocates. Evidence: Boundary and overlap vectors plus an invalidation table justify every access. Develop that evidence in [PR-T14-01](../projects/PR-T14-01.md).
### T14.03 — Dynamic arrays

Dynamic growth trades spare capacity for fewer relocations. Doubling gives an amortized argument, not a promise about one append; reserve failure must retain the old allocation and contents.

Investigate: Implement reserve/append/insertion with an allocator callback that fails at each acquisition point. A common mistake is: Amortized constant append means every append is constant time. Evidence: A growth-cost ledger and failure snapshots preserve ownership and expose invalidated borrows. Develop that evidence in [PR-T14-02](../projects/PR-T14-02.md).
### T14.04 — Linked structures

List edges encode ownership and reachability. A sentinel simplifies endpoint cases, while an intrusive node belongs to its containing object and cannot be freed as an independent wrapper.

Investigate: Implement singly and doubly linked variants and verify both directions after every removal. A common mistake is: Unlinking a node automatically destroys its payload. Evidence: Head/tail and bidirectional link checks cover first, last, singleton and repeated removal cases. Develop that evidence in [PR-T14-03](../projects/PR-T14-03.md).
### T14.05 — Stacks, queues, and deques

Stack, queue and deque behavior specifies which logical end is accessed, independently of array or linked representation. Overflow and batch insertion need atomicity or a documented partial-success policy.

Investigate: Implement bounded stack/deque operations and compare a linked queue under the same logical trace. A common mistake is: Queue semantics determine its allocation strategy. Evidence: Reference contents and operation counts agree while exhaustion leaves the declared state unchanged. Develop that evidence in [PR-T14-03](../projects/PR-T14-03.md).
### T14.06 — Ring buffers

A ring uses modular positions but needs a convention to distinguish full from empty. With capacity C and a count, occupied slots can wrap into two spans without moving data.

Investigate: Implement split-span bulk push/pop using caller storage. A common mistake is: Equal head and tail always means empty. Evidence: Wrap vectors reconstruct logical FIFO order and prove available/free counts at every transition. Develop that evidence in [PR-T14-01](../projects/PR-T14-01.md).
### T14.07 — Hash tables

Chaining stores collision groups explicitly; open addressing probes through them. A tombstone preserves reachability after deletion, while an empty slot can terminate a failed search.

Investigate: Implement one chained and one linear-probing table with deliberate colliding immutable keys. A common mistake is: Deleting a probed key can turn its slot directly into empty. Evidence: Collision/tombstone traces and failure-injected rehashes preserve every remaining key. Develop that evidence in [PR-T14-04](../projects/PR-T14-04.md).
### T14.08 — Heaps and priority queues

A heap stores a partial order rather than a fully sorted sequence. Children at 2i+1 and 2i+2 require checked bounds before arithmetic; equal priorities need a declared tie policy.

Investigate: Implement bottom-up build, insertion and extraction with an explicit update-key exclusion or handle scheme. A common mistake is: A heap array is globally sorted. Evidence: Parent-child invariants and extraction order match a multiset oracle, including ties. Develop that evidence in [PR-T14-05](../projects/PR-T14-05.md).
### T14.09 — Search trees

An ordered tree separates ordering from parent/child ownership. Two-child deletion replaces or moves a successor, so iterator and payload lifetimes cannot be inferred from key equality.

Investigate: Implement search, insertion, all deletion shapes and explicit-stack traversal. A common mistake is: Deleting a key always frees the exact node originally returned by search. Evidence: Sorted traversal, reachability and parent-link checks agree after each mutation. Develop that evidence in [PR-T14-05](../projects/PR-T14-05.md).
### T14.10 — Balanced trees

AVL balance limits the difference between child heights. Rotations preserve in-order contents but update local links/heights; deletion may require repairing several ancestors.

Worked AVL repair: choose height(empty)=0 and height(leaf)=1, and balance=height(left)-height(right). Inserting 30,20,10 first makes root 30 left-heavy with balance +2. Rotate right at 30: root becomes 20 with leaf children 10 and 30; their heights are 1 and the root height is 2. Duplicate 20 is rejected with the entire structure unchanged. Deleting leaf 30 leaves root 20, left child 10, height 2 and balance +1; ancestor checks still run. More demanding deletion orders can decrease heights through several ancestors, so this anchor does not justify insertion-style early stopping.

Investigate: Implement a complete AVL family with LL, RR, LR, RL and cascading deletion tests. A common mistake is: Insertion rotations alone complete a balanced-tree implementation. Evidence: Every node has correct stored height and balance at most one after exhaustive small-key permutations. Develop that evidence in [PR-T14-06](../projects/PR-T14-06.md).
### T14.11 — Tries and prefix indexes

A byte trie consumes key units along edges and marks terminal keys separately from prefixes. Empty and embedded-zero keys need explicit length semantics; compression changes memory layout without changing lookup meaning.

Investigate: Implement a length-delimited trie, then compare its node cost with a sketched radix representation. A common mistake is: An internal node automatically denotes a stored key. Evidence: Prefix enumeration and exact membership distinguish empty key, prefix-only path and full key. Develop that evidence in [PR-T14-07](../projects/PR-T14-07.md).
### T14.12 — Bitsets and sparse sets

Dense bitsets pay for the universe; sparse sets pay for present members plus an index. Generation-based clearing avoids immediate writes but introduces wraparound and stale-generation obligations.

Investigate: Implement bounded bitset algebra and a sparse set with insertion/deletion/iteration. A common mistake is: Fast clear can ignore generation wraparound forever. Evidence: Set-algebra oracles, storage totals and clearing-cost measurements include an explicit wrap/reset policy. Develop that evidence in [PR-T14-07](../projects/PR-T14-07.md).
### T14.13 — Disjoint sets and graphs

Union-find represents equivalence classes using roots; path compression rewrites paths but preserves partitions. Graph storage is a different abstraction: adjacency lists, matrices and compressed rows answer different access patterns.

Investigate: Implement union-by-size with compression and convert a fixed graph among three representations. A common mistake is: A union-find parent edge is an original graph edge. Evidence: Partition checks and normalized edge sets agree after unions and representation conversion. Develop that evidence in [PR-T14-08](../projects/PR-T14-08.md).
### T14.14 — Advanced structures

An advanced structure earns its complexity through a workload and a precise promise. Skip-list randomness or probabilistic filters do not create deterministic worst-case guarantees by themselves. This topic is elective; its implementation project is optional.

Investigate: Choose a skip list, B-tree or membership filter and retain a simple exact model. A common mistake is: A probabilistic membership hit proves the key is present. Evidence: The elective report separates false-positive/ordering guarantees, resource costs and implementation evidence. Develop that evidence in [PR-T14-09](../projects/PR-T14-09.md).
### T14.15 — Container verification

A mutation test must compare logical contents and representation invariants, especially after failure. A benchmark answers workload costs, while asymptotic reasoning explains scaling.

Investigate: Generate short operation sequences and check invariants after every operation and allocator failure. A common mistake is: A final correct result excuses transient ownership corruption. Evidence: Minimized traces preserve the earliest broken invariant and benchmark setup discloses distributions and instrumentation. Develop that evidence in [PR-T14-02](../projects/PR-T14-02.md).
