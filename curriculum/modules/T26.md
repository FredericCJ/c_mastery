## Purpose and outcomes

Reach core awareness of concurrent histories, progress, identity, reclamation and kernel boundaries. Optional implementations have separate gates; awareness diagrams never certify a safe reclamation algorithm or loaded kernel module. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce. The published workload includes 24 h of explicitly elective project work; a core-only route subtracts those project hours, without removing core awareness.

## Entry check and remediation

Construct a release/acquire publication graph and distinguish atomicity from a compound invariant. Remediate T25 memory-order/CAS work and T14 ring invariants; awareness starts only when these are explicit. Use {ref}`guide-entry` for diagnostic evidence and {ref}`guide-roadmap` for route choices. Domain numbers are coverage IDs, not an instruction to study them numerically.

## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T26.01 — Concurrent-object specifications

A concurrent object is specified by permitted operation histories. Linearizability asks whether completed operations can be placed at single points consistent with real-time order; a valid memory execution alone does not supply that abstract history.

Investigate: Classify small queue histories and nominate a linearization point for each successful operation. A common mistake is: Memory-model consistency implies FIFO linearizability. Evidence: A sequential-history witness or contradiction is supplied for each declared fixture. Develop that evidence in [PR-T26-01](../projects/PR-T26-01.md).
### T26.02 — Progress guarantees

Progress claims have different quantifiers: some participant makes progress, this participant completes, or an isolated participant completes. Allocation, atomics and scheduling can weaken the claim outside the core algorithm.

Investigate: Compare blocking/obstruction-free/lock-free/wait-free claims against declared stalled-participant traces. A common mistake is: Lock-free means every operation has a fixed completion bound. Evidence: The claim names participants, steps and external assumptions instead of reporting only aggregate throughput. Develop that evidence in [PR-T26-01](../projects/PR-T26-01.md).
### T26.03 — SPSC structures

An SPSC queue partitions responsibility: producer publishes occupied slots and consumer releases them for reuse. Counter wrap and slot lifetime require an explicit arithmetic model, not informal head/tail intuition.

Investigate: Analyze a bounded SPSC publication/reuse graph; optionally implement it after the core awareness gate. A common mistake is: Single producer/consumer removes all ordering requirements. Evidence: The slot state trace and wrap proof identify both publication and reclamation edges. Develop that evidence in [PR-T26-01](../projects/PR-T26-01.md), [PR-T26-04](../projects/PR-T26-04.md).
### T26.04 — MPSC and MPMC structures

Multiple producers add reservation states distinct from publication. A producer that reserves then stalls can affect consumers and other producers differently depending on the algorithm.

Investigate: Study the inspected Michael–Scott algorithm or a fully declared slot protocol and trace contention/cancellation. A common mistake is: Adding CAS to an SPSC head creates a complete MPMC design. Evidence: Every slot/node has a named owner and the trace separates reservation, publication and completion assumptions. Develop that evidence in [PR-T26-01](../projects/PR-T26-01.md), [PR-T26-05](../projects/PR-T26-05.md).
### T26.05 — ABA and identity

ABA occurs when a value changes away and back while its object identity or lifetime changes. A tag can distinguish reuse only until wrap or unavailable atomic width defeats its assumptions.

Investigate: Construct a stale compare-exchange with object reuse and analyze generation/tag alternatives. A common mistake is: Equal pointer bits prove the same live object remained there. Evidence: The trace explicitly names object identities, reuse and tag-wrap limits. Develop that evidence in [PR-T26-02](../projects/PR-T26-02.md), [PR-T26-05](../projects/PR-T26-05.md).
### T26.06 — Hazard pointers

Hazard protection announces a candidate pointer, then validates that the source still names the same live object before dereferencing. Retirement differs from reclamation; a scan must establish the scheme’s protection obligations.

Investigate: Perform an awareness-level protection/validation/retire timeline and account for stalled/departing participants. A common mistake is: Publishing a pointer once is enough to make arbitrary reclamation safe. Evidence: The timeline identifies each protected interval and retained node; implementation requires an independently inspected complete protocol. Develop that evidence in [PR-T26-02](../projects/PR-T26-02.md), [PR-T26-05](../projects/PR-T26-05.md).
### T26.07 — Epoch and quiescence schemes

Epoch schemes delay reuse until participants that could hold old references pass a required quiescent boundary. A stalled active participant can retain old objects indefinitely unless failure policy changes the assumptions.

Investigate: Model retirement epochs and participant progress with an explicit active/inactive table. A common mistake is: Elapsed wall-clock time alone completes a grace period. Evidence: A reclamation eligibility table and retained-memory calculation include a stalled participant. Develop that evidence in [PR-T26-02](../projects/PR-T26-02.md), [PR-T26-05](../projects/PR-T26-05.md).
### T26.08 — RCU concepts

RCU separates publishing a new version, readers using a version and reclaiming an old version after the appropriate grace period. Userspace libraries and the Linux kernel expose different contexts and APIs.

Investigate: Analyze a read/copy/publish/grace/reclaim sequence and classify model-specific obligations. A common mistake is: Completing a publication store immediately permits freeing the old object. Evidence: An object-lifetime diagram names the grace-period owner and refuses to infer one environment’s API rules from another. Develop that evidence in [PR-T26-02](../projects/PR-T26-02.md), [PR-T26-05](../projects/PR-T26-05.md).
### T26.09 — Kernel programming boundaries

Kernel code runs under version-specific build and execution contracts. User pointers need checked access mechanisms, allocation flags encode context constraints, and some contexts cannot sleep.

Investigate: Create an awareness dossier for an isolated version-matched kernel test environment and classify candidate calls by context. A common mistake is: A userspace pointer or allocator contract can be reused directly in a kernel callback. Evidence: The dossier names isolation, API/version sources and prohibited operations before any optional implementation. Develop that evidence in [PR-T26-03](../projects/PR-T26-03.md).
### T26.10 — Kernel memory and lifetime models

The kernel memory model uses its own marked accesses and ordering primitives. Module removal must also wait for callbacks/work that retain code or objects; ordering alone does not extend lifetime.

Worked kernel lifetime graph: external producer -> module_text; queued/running work -> module_text and device_object. With one queued and one running instance in the declared model, smp_mb preserves all these lifetime edges. An unload attempt therefore fails the model gate. Stop and wait for every producer first, then let cancel_work_sync return under its no-racing-enqueue and permitted-context preconditions. Only then are pending/running work zero; release the object and consider code removal eligible within this narrow graph. That eligibility is not a real-module verdict: any IRQ, timer, RCU, delayed work or other registration adds a distinct obligation outside this fixture.

Investigate: Contrast a portable C ordering graph with the inspected LKMM relations and model callback unload states. A common mistake is: A memory barrier proves a callback cannot run after unloading its code. Evidence: Separate ordering and lifetime ledgers identify the drain/grace obligations; kernel experiments remain optional and isolated. Develop that evidence in [PR-T26-03](../projects/PR-T26-03.md).

## Mastery gate and feedback

Explain one positive path and one failure/counterexample for every subtopic without reading your implementation. Submit each project’s leaf-objective checklist with a distinct evidence item; shared runs may support several items only when the relation is explained. Re-run the saved independent fixture verifier, then reproduce at least one artifact from a clean environment. Passing those checks is evidence within their scope, not full-domain certification.

If an invariant, lifetime or environment claim cannot be defended, return to its project’s smallest trace and remediate the named entry knowledge. If a tool result disagrees with reasoning, minimize before changing expected results. A module passes when all core projects and awareness duties are accepted; elective implementation gaps remain visible. Use {ref}`guide-assessment` and {ref}`guide-audit` for review records.
