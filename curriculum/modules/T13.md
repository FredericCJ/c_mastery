## Purpose and outcomes

Treat resource effects as observable contracts. Measure with stated coverage, characterize cold/warm and contended paths, and choose restricted replacements only after defining what is actually required. The intended result is a mechanism you can explain, a bounded artifact you can inspect and an evidence trail someone else can reproduce.

## Entry check and remediation

Given a callback, name possible allocation/blocking/state effects even when its return value is deterministic. If output correctness is the only criterion, redo a T12 interface contract and the profile guide. Use {ref}`guide-entry` for diagnostic evidence and {ref}`guide-roadmap` for route choices. Domain numbers are coverage IDs, not an instruction to study them numerically.

## Study sequence and teaching

Work through the mechanism notes in order within each project, alternating hand prediction with observation. Preserve the first counterexample rather than only a final green test. Full implementations belong to the projects; these notes explain what they must establish.

### T13.01 — Effects contract

An effects contract includes allocation, stack, synchronization, OS work, persistent state and blocking, including callback effects. Correct return values alone do not characterize suitability.

Investigate: Draw a reachable call graph and annotate effects and unknown nodes before measuring. A common mistake is: A pure-looking API name implies no environmental effects. Evidence: A component and a transitive ledger distinguish proven restrictions, observed paths and unresolved callees. Develop that evidence in [PR-T13-01](../projects/PR-T13-01.md).
### T13.02 — Heap allocation census

An allocation interceptor sees only the interfaces it hooks. A library can use an internal allocator, a pool or mapping path outside that hook; reuse can hide storage activity on later calls.

Investigate: Compare source inspection, wrapper interception and a process-level observation on fresh and warm executions. A common mistake is: No observed malloc call proves no storage acquisition. Evidence: The report states interception coverage and includes a deliberate bypass path. Develop that evidence in [PR-T13-01](../projects/PR-T13-01.md).
### T13.03 — Stack consumption

Stack use depends on call depth, alignment, spills and dynamic storage, not merely local declarations. Whole-system bounds must add nested contexts that measurements may never trigger.

Investigate: Combine a static synthetic call graph with compiler frame estimates and an observed high-water experiment. A common mistake is: The largest single frame is the whole-program maximum. Evidence: A conservative path/nesting bound is separated from measured high water and unknown callback frames. Develop that evidence in [PR-T13-02](../projects/PR-T13-02.md).
### T13.04 — Locking and contention

Lock acquisition is not the same observation as contention. Stream, allocator and once initialization locks can be hidden behind simple APIs, and reentrant entry adds a different failure mode.

Investigate: Compare uncontended, contended and reentrant scenarios in a small annotated call graph. A common mistake is: An uncontended benchmark proves a routine never blocks. Evidence: Each scenario records synchronization assumptions and distinguishes lock presence from measured waiting. Develop that evidence in [PR-T13-02](../projects/PR-T13-02.md).
### T13.05 — Lazy initialization

First-call paths can initialize state or acquire resources that steady-state timing misses. A reset must genuinely restore the relevant process/library state.

Investigate: Measure the first and repeated calls in independently launched processes, recording configuration and inputs. A common mistake is: Repeating a function in one process reproduces its first-call cost. Evidence: The sample grouping distinguishes process startup, lazy initialization and subsequent calls. Develop that evidence in [PR-T13-02](../projects/PR-T13-02.md).
### T13.06 — System interaction

Syscalls expose kernel interaction, but user-space work and already-reserved storage may occur without a syscall. Conversely, an OS mapping acquires address space without necessarily making every page resident.

Investigate: Attribute a controlled operation to user computation, syscalls and storage ledgers separately. A common mistake is: Absence of syscalls proves absence of allocation or blocking. Evidence: A trace interpretation states what the observation excludes and what it cannot see. Develop that evidence in [PR-T13-01](../projects/PR-T13-01.md).
### T13.07 — Global and thread-local state

errno is thread-local state in the relevant implementation; locale, streams and caches may have broader sharing. Independent instances need state separation or explicit reset rules.

Investigate: Build a state ownership table for a small parser/formatter adapter and compare concurrent instance use. A common mistake is: Thread-local errno makes the entire API reentrant. Evidence: A two-instance test and state diagram identify every persistent value and its reset/lifetime owner. Develop that evidence in [PR-T13-03](../projects/PR-T13-03.md).
### T13.08 — Execution-context suitability

Thread safety, reentrancy and signal safety answer different questions. Fixed storage does not bound execution time, and an ISR cannot safely inherit arbitrary userspace blocking assumptions.

Investigate: Classify a fixed-buffer operation, a mutex-protected operation and a signal-handler callback. A common mistake is: Allocation-free means safe in every execution context. Evidence: A context suitability matrix separates memory bounds, time bounds, interruption and allowed services. Develop that evidence in [PR-T13-03](../projects/PR-T13-03.md).
### T13.09 — Implementation comparison

Implementation observations belong to a version and configuration. The inspected glibc 2.41 qsort path selects stack or acquired temporary storage and has an allocation-failure heapsort fallback; inspected musl 1.2.5 uses a different smoothsort path. A common signature does not imply common effects.

Worked source branch: the inspected glibc 2.41 source reserves a 1024-byte temporary stack buffer. Sorting 64 four-byte elements needs 256 temporary bytes and selects it; 300 four-byte elements need 1200 and reach the acquisition branch, which falls back to heapsort if acquisition fails. For ten 64-byte elements and eight-byte pointers, indirect storage is 2*10*8+64=224 bytes. These are source-selected temporary requirements, not total-stack bounds; helper and comparator frames/effects remain separate. The restricted local replacement accepts at most sixteen ints, so its workload and API exclusions are explicit.

Investigate: Audit the two pinned qsort source paths, annotate comparator/transitive-helper unknowns and separate source branches from runtime measurements. A common mistake is: One libc result is a portable C guarantee, or qsort necessarily implements quicksort. Evidence: The conclusion labels API guarantees, inspected temporary-buffer/fallback paths and separately measured behavior; equivalent-key order is not presumed stable. Develop that evidence in [PR-T13-04](../projects/PR-T13-04.md).
### T13.10 — Replacement decisions

Replacement begins with a restricted requirement, not a general claim to improve a mature routine. An at-most-sixteen-int sorter can reject unsupported capacity visibly and use an explicit local insertion invariant without supplying general qsort semantics.

Investigate: Implement that narrow insertion-sort replacement with actual caller-owned int storage and no external sorting/byte calls; compare sortedness and multiplicities using a hosted oracle. A common mistake is: A shorter implementation is necessarily safer or faster. Evidence: Empty, duplicate, endpoint, exact-capacity and over-capacity cases plus dependency/effect audit support a bounded decision; a rejected input remains unchanged. Develop that evidence in [PR-T13-04](../projects/PR-T13-04.md).
