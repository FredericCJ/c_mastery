## Purpose and outcomes

Optimize one verified kernel by forming cost hypotheses, inspecting generated code and measuring representative work. Preserve exact/approximate semantic contracts while changing layout, vectorization and build strategy.

## Entry check and remediation

Pass T17's independent-reference/error checks and T32's reproducible test habit. Draw nonoverlapping array extents and a publication/race argument using the selected T25 leaves; the full pthread route is unnecessary for the scalar/SIMD kernel. Repair only ratio/units, stride arithmetic or sampling/distribution vocabulary before measurements.

Use {ref}`guide-entry` for the diagnostic policy and {ref}`guide-roadmap` for route order. Only the stated prelude leaves must precede a dependent project.

## Component progression

**Optimization after a fixed correctness gate.** Measure the workload before transforming layout, branches, alias information or vector code. Compare generated code and consumed results under matched builds.

Before implementation, predict this discriminating case: **An apparently faster kernel whose observable work was optimized away or whose input contract changed.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T34.01 — Optimization specification

Optimization starts with a contract: representative sizes/data, allowed numeric error, latency/throughput targets and memory/energy limits. Reuse the scalar correctness oracle before changing code. A faster result on one favorable input can fail the deployed workload or its error allowance. Define pass/fail gates independently of timing and include both tiny and large cases. Evidence is a workload ledger whose correctness gates cannot be relaxed to rescue a speed claim.

Apply this mechanism in [PR-T34-01](../projects/PR-T34-01.md).

### T34.02 — Cost models

Work, instruction count and memory traffic are different cost models. A vector add has about one arithmetic operation per element but reads two arrays and writes one; define the measured boundary before calculating bytes or intensity. Use a simple roofline-style ceiling to form a bottleneck hypothesis, then revise it using actual evidence. A theoretical ceiling is not a measured rate or a Cortex-M WCET bound. Preserve the model and its counterexample.

Apply this mechanism in [PR-T34-01](../projects/PR-T34-01.md).

### T34.03 — Memory hierarchy

Stride and working set determine which memory hierarchy is stressed. A blocked traversal can reuse a tile, while a transposed or hot/cold layout changes touched bytes without changing the algorithmic result. Implement variants of the T17 matrix/data kernel and calculate a declared synthetic cache-line footprint. Real TLB/cache observations require actual host counters and sizes. Alignment alone does not guarantee a gain; evidence includes semantic equality and generated access patterns.

Apply this mechanism in [PR-T34-02](../projects/PR-T34-02.md).

### T34.04 — Control and instruction effects

Branches, dependencies and code size trade against one another. A branchless selection may execute extra work or extend a dependence chain, while an unrolled loop may increase instruction-cache pressure and spills. Compare branchy and branchless bounded clamp/count kernels under predictable and mixed inputs. 'Fewer branches' is not an acceptance criterion. Evidence links measured distributions to disassembly, including spills/code bytes and a workload where the anticipated gain disappears.

Apply this mechanism in [PR-T34-02](../projects/PR-T34-02.md).

### T34.05 — Compiler optimization evidence

Compiler reports are explanations to check against final code. Compile the scalar loop at fixed settings, retain vectorization diagnostics, inspect intermediate/final instructions and identify one justified missed optimization. If aliasing prevents transformation, inspect the interface before adding restrict. A report that says vectorized does not establish correctness or actual speed. Evidence preserves flags, object identity, report text and the corresponding machine-code loop.

Apply this mechanism in [PR-T34-03](../projects/PR-T34-03.md).

### T34.06 — Auto-vectorization

Auto-vectorization can change iteration order, reduction grouping and alias assumptions. Permit restrict only for demonstrably nonoverlapping extents; a forbidden overlap must be rejected by the API or excluded explicitly, not accidentally benchmarked. Use unsigned elementwise arithmetic for the initial kernel to avoid floating-reduction ambiguity, then revisit a sum under its numeric tolerance. Evidence includes alias/tail cases, scalar comparison and a valid contract supporting each hint.

Apply this mechanism in [PR-T34-03](../projects/PR-T34-03.md).

### T34.07 — Explicit SIMD

Explicit SIMD works on lanes with an extent contract. The core x86 teaching kernel uses SSE2 four-lane uint32 addition modulo 2^32, unaligned full-vector loads/stores, and a scalar tail. For nine elements, process two groups of four and one tail; an unaligned load still needs sixteen valid bytes. Implement a scalar fallback and forbid partial overlap. Evidence includes wrap values, lengths 0–9, offset alignments and final instructions on a verified supported host.

Apply this mechanism in [PR-T34-04](../projects/PR-T34-04.md).

### T34.08 — ISA dispatch

Dispatch must not execute specialized instructions while checking whether they are supported. Put the baseline selector and SSE2 implementation in separate translation units with recorded flags; use the documented positive/zero feature result and a force-scalar test option. On the selected x86-64 Linux environment also record applicable OS/ABI support. AVX dispatch is an unassigned extension requiring OS-state checks. Evidence is selector tests, baseline disassembly and a specialized path that is unreachable under the unsupported-feature fixture.

Apply this mechanism in [PR-T34-04](../projects/PR-T34-04.md).

### T34.09 — Benchmark construction

A benchmark must retain its result, exclude unrelated setup and state how warmup/cache state/affinity/clock changes are handled. Record repeated samples and report median plus spread; preserve raw samples rather than a single rounded speedup. The supplied times are synthetic oracle data, not measurements. Implement a harness with a consumed checksum and paired baseline/variant runs. Evidence includes empty-loop overhead and one source of uncertainty the setup cannot eliminate.

Apply this mechanism in [PR-T34-05](../projects/PR-T34-05.md).

### T34.10 — Profiling and counters

Sampling and counters estimate where cost occurs under their own limits. Correlate hot addresses with matching code; record counter availability, multiplexing scale and permission failures. A scaled event count is not exact when workloads change during multiplexing. Use sampling plus one supported counter when available, otherwise report the missing evidence and rely on a narrower timing claim. Evidence includes raw enabled/running times, scaling arithmetic and a revised bottleneck hypothesis.

Apply this mechanism in [PR-T34-05](../projects/PR-T34-05.md).

### T34.11 — Whole-program optimization

LTO and PGO alter whole-program decisions and introduce build/profile assumptions. Compare plain, LTO and representative-profile builds, inspect code/dependencies and retest the correctness gate. A training workload biased toward one branch may regress a different input distribution. Evidence includes build cost, executable size, profile identity/mismatch diagnostics and a held-out workload. A flag alone does not prove the linker performed the intended transformation.

Apply this mechanism in [PR-T34-06](../projects/PR-T34-06.md).

### T34.12 — Embedded optimization

Embedded optimization trades latency, Flash, RAM/stack and energy; the fastest version can be unacceptable in another budget. Deploy two semantically equivalent variants only after the target startup/dependency audit, measure actual execution and optionally current with recorded equipment, and keep error limits fixed. Emulator cycle counts do not establish F439 physical energy or WCET. Evidence distinguishes measured speed/size/stack from inferred models and retains regression thresholds with configuration.

Apply this mechanism in [PR-T34-06](../projects/PR-T34-06.md).

## Reading guidance

Read the bounded selections before the corresponding project, then annotate one contract or assumption you will test. The assigned reading table is generated from the exact inspected locators. Spend the remaining reading budget on original teaching, worked traces and target documentation comparisons, not whole uninspected chapters.

**Roofline: An Insightful Visual Performance Model for Multicore Architectures — Roofline Model (1 h):** State the memory/compute boundary.

**Using the GNU Compiler Collection: Options That Control Optimization — -O2 (1 h):** Compare fixed optimization settings.

**Using the GNU Compiler Collection: Options That Control Optimization — -fstrict-aliasing (1 h):** Audit optimization preconditions.

**Clang SSE2 intrinsic header, selected definitions — _mm_add_epi32 (1 h):** Select modulo lane semantics.

**Clang SSE2 intrinsic header, selected definitions — _mm_loadu_si128 (1 h):** Respect full-vector extent.

**GCC x86 built-in CPU detection contract — __builtin_cpu_supports (1 h):** Build positive/zero feature dispatch.

**Using the GNU Compiler Collection: Options That Control Optimization — -flto (1 h):** Inspect whole-program compile/link behavior.

**GCC program instrumentation options, selected verification and hardening contracts — -fprofile-generate (1 h):** Collect a representative training profile.

**Using the GNU Compiler Collection: Options That Control Optimization — -fprofile-use (1 h):** Reject mismatched profiles.

**Shared scope limit — Roofline: An Insightful Visual Performance Model for Multicore Architectures:** Original examples are multicore floating-point kernels with DRAM traffic. It is a reasoning model, not a universal prediction or proof of Cortex-M4 latency, WCET or energy. State the measured memory boundary and ceilings.

**Shared scope limit — Using the GNU Compiler Collection: Options That Control Optimization:** The reference version is deliberately fixed; installed compiler identity and target-dependent behavior require separate evidence. Enabling fast-math changes admissible numeric semantics and needs a documented error/exception contract.

**Shared scope limit — Clang SSE2 intrinsic header, selected definitions:** These functions specify four-lane modulo integer addition and full 16-byte unaligned access; unaligned access still requires the complete valid extent. Intrinsic header/source version is fixed, installed compiler is not verified. No other intrinsic or ISA dispatch mechanism was inspected.

**Shared scope limit — GCC x86 built-in CPU detection contract:** Does not verify installed GCC internals or OS support for arbitrary AVX state. Teaching core specialization uses SSE2 on an identified supported x86 host; AVX/ifunc expansion requires additional OS-state and loader research.

**Shared scope limit — GCC program instrumentation options, selected verification and hardening contracts:** Selected options only, not every instrumentation feature. Flag availability and effective dependencies vary with installed compiler/target. GNU/Linux hardening aggregate is not a bare-metal recipe; instrumentation changes resource/timing behavior.

Present a correct scalar/auto/SIMD kernel, safe dispatch, generated-code explanation and reproducible benchmark/counter evidence. Show a held-out workload and a rejected faster-but-invalid budget variant. Embedded physical completion needs an actual target comparison; observed maxima remain measured values.

For every linked objective, retain a separately labeled explanation, implementation/analysis artifact and check. Use {ref}`guide-assessment` for the rubric; one passing fixture does not establish all three objectives of a topic.
