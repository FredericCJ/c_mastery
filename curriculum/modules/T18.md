# T18: Contracts, ownership, and API design

## Purpose and outcomes

Design interfaces as contracts over values, resources, lifetimes and execution contexts. This module should precede serious container design: ownership vocabulary and failure guarantees prevent representation convenience from silently dictating caller obligations.

## Entry check and remediation

Use T03 lifetime diagrams and T12 bounded-buffer/error reasoning. Given a pointer parameter, name owner, capacity and invalidation before writing code. If the interface promises “safe” without a specific failure/alias contract, narrow it until the promise can be tested.

## Component progression

**An API whose failures preserve a state.** Write success and failure postconditions, ownership transfer points and callback effects. Compile a second consumer that attempts every documented boundary.

Before implementation, predict this discriminating case: **A capacity error leaving a caller unable to determine which object it owns.** Carry its evidence into the projects below. Reuse one accepted component revision; new projects charge their new mechanism or experiment, not a second implementation of the old one.

Follow the [project route](../guides/project-route.md) for ordering. Domain numbers are reference categories. The [laboratory](../guides/laboratory.md) and [shared contract cards](../guides/component-contracts.md) separate automatic execution from reasoning, transfer and physical observations.

## Study sequence and teaching

### T18.01 — Domain and representation contracts

Representable states are broader than permitted domain states. An integer may encode milliseconds, a sentinel or an invalid negative duration; a structure can be initialized yet violate its invariant. Specify units, ranges and sentinel meanings at the boundary, including deliberate target-width assumptions.

Investigation: Write a bounded byte-view and timeout domain contract, then list representable but forbidden states.

Misconception to resolve: A C type alone rarely expresses the entire domain contract.

Observable evidence: Value partitions, unit-aware names and explicit acceptance/rejection tests. Evidence is developed in {ref}`PR-T18-01`.

### T18.02 — Function contracts

A function contract separates caller preconditions from promised postconditions and preserved invariants. Capacity, overlap, mutation and failure effects need independent clauses. For append, success changes length/content; failure can promise unchanged state only if validation or staging precedes mutation.

Investigation: Define append pre/postconditions and prove the capacity check before writing.

Misconception to resolve: A return code does not by itself say whether partial mutation occurred.

Observable evidence: A contract table and state snapshots proving the declared success/failure guarantee. Evidence is developed in {ref}`PR-T18-01`.

### T18.03 — Ownership vocabulary

Ownership names who must release a resource, borrowing names temporary use without release authority, transfer changes the release obligation, and weak access does not keep the owner alive. Apply the same vocabulary to memory, descriptors, locks and device sessions. Copying an address does not copy ownership.

Investigation: Create creation/release/transfer ledgers for a buffer and a non-memory resource, contrasting shared and weak access.

Misconception to resolve: Every pointer holder is not an independent owner entitled to release it.

Observable evidence: Resource ledgers with exactly one release obligation or an explicit shared-count protocol. Evidence is developed in {ref}`PR-T18-02`.

### T18.04 — Lifetime relationships

Views depend on owner lifetimes and may additionally depend on mutation epochs. Callbacks depend on the lifetime of their context and registration. SQLite’s result pointers illustrate invalidation by conversion, stepping, reset and finalization, so “borrowed until close” may still be too weak a description.

Investigation: Design an owner/view/callback timeline and replace one fragile direct pointer with a generation handle.

Misconception to resolve: An owner still being alive does not guarantee a view survives every owner mutation.

Observable evidence: An invalidation table and stale-view tests tied to exact operations. Evidence is developed in {ref}`PR-T18-02`.

### T18.05 — Object lifecycle

An object lifecycle defines legal operations in uninitialized, active, failed, stopped and destroyed states. Partial initialization acquires only a prefix of resources; shutdown should release exactly that prefix. Repeated stop/destroy behavior must be specified rather than guessed from a null field.

Investigation: Implement a lifecycle machine with injected init failure and a deliberate repeated-shutdown policy.

Misconception to resolve: A failed initialization is not automatically equivalent to a fully constructed object.

Observable evidence: State/operation table, failure-point tests and release counts. Evidence is developed in {ref}`PR-T18-03`.

### T18.06 — Opaque and exposed representations

Opaque pointers hide layout but often require allocation or a factory; exposed structs enable embedding and direct layout dependence. Caller-owned opaque storage needs an actual size/alignment contract, not guessed byte arrays. Choose by ABI, allocation policy, debugging and embedding needs.

Investigation: Compare all three representations for one object and implement a version with explicit caller-storage requirements.

Misconception to resolve: Opaque does not mean allocation-free, and hidden layout does not remove ABI obligations.

Observable evidence: Representation alternatives, size/alignment evidence and an independently compiled consumer. Evidence is developed in {ref}`PR-T18-03`.

### T18.07 — Errors and result types

Status returns, tagged results and output parameters trade clarity, size and compatibility. A sentinel can collide with a valid result; separate status from payload when that ambiguity exists. Define whether outputs are initialized, unchanged or partially valid on each failure.

Investigation: Design a lookup that permits zero as a valid value and a parse operation with explicit output-state rules.

Misconception to resolve: A null or zero result is not necessarily an error without a contract.

Observable evidence: Result tables, sentinel-collision cases and output-state checks. Evidence is developed in {ref}`PR-T18-01`.

### T18.08 — Execution-context contracts

Execution-context properties belong to a boundary and its reachable callees: allocation, blocking, reentrancy, thread access and ISR suitability are different claims. State whether callbacks are synchronous or asynchronous, what they may retain, and when cancellation completes ownership transfer.

Investigation: Write context contracts for a synchronous transform and deferred completion adapter.

Misconception to resolve: A function containing no allocation spelling is not automatically bounded or ISR-safe.

Observable evidence: Call/effect ledger, callback lifetime/retention rules and cancellation traces. Evidence is developed in {ref}`PR-T18-04`.

### T18.09 — Contract enforcement

Compile-time checks reject configuration/type violations; runtime validation handles untrusted/environmental inputs; assertions express internal obligations under a chosen fault policy. Disabled assertions must not remove required validation or side effects. Tests expose counterexamples within their scope.

Investigation: Build enabled/disabled assertion configurations and compare externally invalid input behavior.

Misconception to resolve: An assertion is not a reliable user-input error path when it can disappear.

Observable evidence: Checks classified by purpose and identical required validation across build modes. Evidence is developed in {ref}`PR-T18-01`.

### T18.10 — API evolution

Evolution can change source, ABI, ownership or behavior independently. A new layout or a transferred result changes caller obligations even if a function name survives. Version a boundary, deprecate deliberately and test a consumer outside the implementation tree.

Investigation: Add a versioned operation while keeping an old consumer usable, with a migration note for changed constraints.

Misconception to resolve: A library version number does not itself ensure compatibility.

Observable evidence: Independent-consumer builds, compatibility matrix and an ownership-aware migration example. Evidence is developed in {ref}`PR-T18-04`.

## Mastery gate and feedback

Defend an API against hostile-but-valid caller cases, invalid input and resource failure. Show lifetime/invalidation and output-state guarantees explicitly. An independent consumer must compile and reproduce the documented behavior without inspecting private source.

For independent study, make predictions before execution, compare an independent oracle, inspect one counterexample and defend the result aloud or in a short recorded review. Link each original objective to a specific artifact; use {ref}`guide-assessment` to score it. A failed gate requires a minimized cause, a corrected model and a fresh regression, not repeated nominal runs.

## Consolidation and transfer

After a delay, change the allocator, storage representation or callback timing. Revise the contract first, then test the migration against the earlier consumer.
