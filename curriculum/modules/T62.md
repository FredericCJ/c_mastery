# T62: Advanced Linux I/O and completion ownership

## Purpose and outcomes

Build event and completion-driven I/O with explicit partial progress, identity, buffer lifetime and durable-result semantics. Use real local pipes/files for host investigations and deterministic schedules for hard-to-reproduce boundaries.

## Entry check and remediation

Repair a short-write loop, distinguish EINTR/EAGAIN/EOF, and show ownership of a buffer across io.async cancellation. Do not start completion-driven code until a delayed callback cannot reach released storage.

## Study sequence and teaching

### T62.01 — Vectored partial progress

A short write can stop inside an iovec element. Retrying the original vector duplicates already accepted bytes; advancing by elements instead of bytes skips data. Validation must also reject a backend reporting more progress than remained.

Prove accepted progress plus remaining extent equals the original stream length, including zero spans and overflow. Distinguish kernel acceptance from remote delivery or persistence.

Misconception and counterexample: The faulty cursor resets the within-element offset after a short write, duplicating the first byte of the next span on retry.

Investigation: Implement li_advance(lengths,count,position,bytes) for a valid vector cursor. Compute remaining extent with checked size_t arithmetic, reject excess progress transactionally, then advance across zero-length elements and normalize the terminal position to{count,0}. This is caller-side accounting, not a writev replacement.

Evidence: Add EINTR, EAGAIN and an error after a nonzero prefix; define whether the API returns progress plus deferred error or an immediate terminal error and test consumers.

### T62.02 — Edge readiness and fair draining

Edge-triggered notification reports a readiness transition, not one unit of work. If a consumer processes only one item and sleeps again, remaining data can wait indefinitely. Fairness requires remembering ready work when a per-dispatch budget expires.

Distinguish kernel notification, locally remembered readiness and actual EAGAIN. Derive a fairness budget that does not lose readiness or spin forever after EOF.

Misconception and counterexample: The mutant clears readiness at budget exhaustion while unread data remains. The pipe receives no new edge, exposing a liveness failure while the process continues running.

Investigation: Implement li_ready_after(result,budget_exhausted) for a synthetic read result: positive progress retains readiness, -2 means EAGAIN and clears readiness,0 EOF clears readiness,-1 terminal error clears readiness. Return1 while progress remains, even when a dispatch budget was exhausted. Exercise the actual anonymous-pipe EPOLLET adapter and compare drain-to-EAGAIN with a local ready queue.

Evidence: Add two continuously active peers and timerfd deadlines; prove bounded dispatch work and measure fairness under equivalent correctness contracts.

### T62.03 — Shared submission ring arithmetic

Shared rings combine modular counters with a bounded live distance. Masking an index hides overflow of occupancy if the producer ignores the consumer position. Ordering the payload and tail publication is a separate obligation.

Derive the bounded-distance interpretation under counter wrap. Separate single-producer ownership, ring-slot lifetime and payload-before-tail publication.

Misconception and counterexample: A producer masks tail and overwrites a still-owned full slot. Adding a barrier cannot repair missing capacity admission.

Investigation: Implement li_slot(head,tail,capacity,out) for uint32_t monotonic counters: capacity is a power of two in1..2^30, unsigned tail-head must be<capacity, and output is tail&(capacity-1). Reject invalid/full states unchanged. Then map the arithmetic to raw io_uring offsets and acquire/release operations after feature probing.

Evidence: Add multiple producers or change queue depth away from a power of two; redesign reservation and indexing rather than reusing the single-owner mask proof.

### T62.04 — Generation-tagged completion ownership

File descriptors and request slots can be reused while old completions are still queued. An identity must distinguish the current operation from a prior occupant. Completion publication and payload release need a single terminal owner.

Prove each target completion is consumed once and cannot authorize release of another generation. State finite-generation exhaustion policy and metadata versus payload lifetime.

Misconception and counterexample: The mutant ignores generation and lets a stale completion finish a new request. Demonstrate harmless wrong-result publication using two synthetic requests, not another process’s data.

Investigation: Implement li_event on LIRequest with state0 idle,1 submitted,2 cancel-requested,3 completed,4 released. Events0 submit,1 request cancel,2 target completion(result),3 release. Require matching generation for every event. Completion is allowed from1/2 once; release only from3 once. Failed transitions preserve the object.

Evidence: Add multishot operations where nonterminal completions retain ownership; derive terminal recognition and buffer recycling from the actual opcode flags.

### T62.05 — Cancellation acknowledgement versus target completion

Cancel and target have distinct completion records. In the inspected io_uring contract, successful cancellation has posted the target completion queue entry by submission return; EALREADY may leave a later target completion. Application consumption and ownership remain separate from kernel posting. The cancel result tells what happened to the cancellation request; releasing the target buffer still depends on the target’s terminal contract.

Name separate ownership of cancel request, target request and payload. Explain how success, not-found and already-completing cancellation results change scheduling but do not substitute for a target terminal event.

Misconception and counterexample: The faulty adapter frees the target buffer when its cancel request completes, then processes a late target completion queue entry. A sanitizer finding identifies a lifetime violation, not kernel exploitability.

Investigation: Implement li_releasable(cancel_ack,target_terminal) accepting only boolean inputs and returning target_terminal. Build a schedule harness with two completion queue entries that permutes cancellation completion, target completion and close; inspect actual io_uring cancellation result codes on the original temporary-file/pipe operations.

Evidence: Add a timeout linked to a multishot request; enumerate which completion queue entries are terminal and determine whether the backend supports the requested cancellation semantics.

### T62.06 — Deadlines, timer events and wraparound

Progress can refresh an idle deadline without extending an overall operation deadline. Timer notification may be delayed or coalesced, so the state machine compares current monotonic time with its recorded start instead of counting callbacks.

State the half-range observation assumption and prove equality is expiration. Distinguish wall-clock corrections, monotonic elapsed time and deadline policy.

Misconception and counterexample: The faulty start+duration comparison wraps the deadline and expires an operation prematurely. Resetting the total deadline after each byte also permits indefinite slow progress.

Investigation: Implement li_expired(start,now,duration,out) for a wrapping32-bit tick model with duration1..2^31-1 and elapsed distance known below2^31. Set out when unsigned now-start>=duration. Reject invalid duration without changing out. Use timerfd in the Linux adapter and keep real monotonic timestamps separate from modeled ticks.

Evidence: Combine idle and total deadlines with eventfd shutdown and signalfd notifications; measure cancellation latency without claiming observed maxima are universal bounds.

### T62.07 — Durable replacement and power-loss cuts

A completed write, a file synchronization and a directory-entry synchronization establish different facts. Replacing a pathname can be atomic to observers without being durable after power loss.

Specify observable atomicity, persistence, filesystem assumptions and failure recovery. Account for open file descriptors to the replaced old inode and permissions on the new object.

Misconception and counterexample: A program reports durable success after rename but before directory synchronization. Its normal readback passes while power loss can invalidate the stated guarantee.

Investigation: Implement li_durable(write_done,file_synced,renamed,directory_synced) requiring all flags exactly1. Then write a local temporary-file replacement adapter: write fully, fsync the new file, rename within its temporary directory, fsync that directory, and report exactly which stage failed. Use a synthetic power-loss-cut ledger; do not claim real power-loss durability from a normal process exit.

Evidence: Change filesystem, mount options and cross-directory replacement; derive which ordering/atomicity arguments and power-loss experiments must be repeated.

### T62.08 — Zero-copy claims and retained buffers

Avoiding one userspace copy does not remove all data movement or lifetime obligations. A page can remain referenced by a kernel operation after local submission; mutation or release before quiescence changes the data being transmitted.

Distinguish copy avoidance, kernel retention, DMA mapping and application borrowing. Derive memory-pressure/backpressure costs and what the selected syscall actually promises.

Misconception and counterexample: The mutant releases after terminal I/O while an application borrower still uses the buffer. Kernel completion does not revoke independent application ownership.

Investigation: Implement li_buffer_release(submitted,terminal,borrowers) returning true only when submitted/terminal are booleans, every submitted operation is terminal, and borrowers0. Use it to compare read/write, sendfile/splice and a mapped-buffer path over synthetic local files; measure bytes copied, syscalls, CPU time and retained memory under the same output contract.

Evidence: Introduce direct I/O alignment constraints and unsupported-filesystem errors; preserve a semantically equivalent fallback and measure overhead without silently changing durability.
